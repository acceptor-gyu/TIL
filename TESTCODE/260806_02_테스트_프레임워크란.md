# 테스트 프레임워크란

## 개요
테스트 프레임워크(Test Framework)의 개념과 역할, 그리고 테스트 러너/어설션/목킹 등 구성 요소가 어떻게 유기적으로 동작하는지 학습합니다.

## 상세 내용

### 1. 테스트 프레임워크란 무엇인가

**정의**
테스트 프레임워크는 테스트 코드를 "작성 → 탐색 → 실행 → 결과 검증 → 리포팅"까지 일관된 방식으로 처리할 수 있도록 표준화된 API와 실행 엔진을 제공하는 도구 모음이다. JUnit, TestNG, pytest, Jest 등이 대표적이다.

**프레임워크 vs 라이브러리**
- 라이브러리(Library): 개발자가 필요한 시점에 함수/클래스를 호출한다. 즉 제어 흐름의 주도권이 개발자 코드에 있다.
- 프레임워크(Framework): 프레임워크가 실행 흐름을 주도하고, 개발자가 작성한 코드(테스트 메서드)를 프레임워크가 특정 시점에 호출한다. 이를 IoC(Inversion of Control, 제어의 역전)라고 부른다.
- 테스트 프레임워크는 `@Test`가 붙은 메서드를 개발자가 직접 호출하지 않는다. 테스트 러너가 클래스를 스캔하고, 생명주기에 맞춰 메서드를 호출해준다는 점에서 전형적인 프레임워크 구조를 갖는다.

**왜 필요한가**
- 반복되는 검증 로직(assert, 실행, 리포트 생성)을 자동화해 사람의 실수를 줄인다.
- 실패한 테스트를 즉시 파악할 수 있어 회귀(regression)를 조기에 방지한다.
- CI/CD 파이프라인과 연동해 빌드-테스트-배포 사이클을 자동화한다.

### 2. 핵심 구성 요소

**테스트 러너(Test Runner)**
- 테스트 클래스/메서드를 탐색(discovery)하고 실행 순서를 결정한 뒤 실행 결과를 수집·리포팅하는 엔진.
- JUnit 5에서는 `TestEngine` 인터페이스가 이 역할을 하며, IDE나 빌드 도구는 `Launcher API`를 통해 엔진을 호출한다.

**어설션(Assertion)**
- 실제 값과 기대 값을 비교해 테스트 성공/실패를 판정하는 도구.
- JUnit 5 기본 제공: `org.junit.jupiter.api.Assertions` (`assertEquals`, `assertThrows`, `assertAll` 등)
- 서드파티 라이브러리: AssertJ(`assertThat(...).isEqualTo(...)` 유창한 체이닝 API), Hamcrest(matcher 기반)
- `assertAll()`을 사용하면 여러 검증을 묶어서 실행하고, 하나가 실패해도 나머지 검증까지 모두 수행한 뒤 한 번에 실패 목록을 보여준다(soft assertion과 유사한 효과).

**픽스처(Fixture)와 생명주기**
- 픽스처: 테스트 실행 전후에 필요한 고정된 환경/데이터(DB 초기화, 목 객체 생성 등).
- JUnit 5 생명주기 어노테이션
  - `@BeforeAll` / `@AfterAll`: 클래스 전체에서 1회 실행 (기본적으로 static 메서드 필요, `@TestInstance(PER_CLASS)`면 인스턴스 메서드도 가능)
  - `@BeforeEach` / `@AfterEach`: 각 테스트 메서드 실행 전/후마다 실행
- 기본 테스트 인스턴스 전략은 `PER_METHOD`(테스트마다 새 인스턴스 생성)이며, `@TestInstance(Lifecycle.PER_CLASS)`로 변경하면 클래스당 인스턴스를 하나만 재사용한다.

**목킹(Mocking)**
- 협력 객체(의존성)를 실제 구현 대신 가짜 객체로 대체해 테스트 대상을 격리하는 기법.
- Mockito 대표 개념
  - Dummy: 그냥 채워 넣는 용도, 동작 검증 없음
  - Stub: 미리 정해진 값을 반환하도록 설정된 객체 (`when(...).thenReturn(...)`)
  - Mock: 호출 여부/횟수/인자를 검증할 수 있는 객체 (`verify(mock).method()`)
  - Spy: 실제 객체를 감싸서 일부만 스텁 처리, 나머지는 실제 로직 실행
- JUnit 5와 연동 시 `@ExtendWith(MockitoExtension.class)`를 사용하면 `@Mock`, `@InjectMocks` 어노테이션이 자동으로 초기화된다.

**파라미터화 테스트(Parameterized Test)**
- 동일한 테스트 로직을 여러 입력값에 대해 반복 실행하는 기법.
- `@ParameterizedTest` + `@ValueSource`, `@CsvSource`, `@MethodSource`, `@EnumSource` 등을 조합해 사용.
- 중복 코드를 줄이고 경계값/예외 케이스를 표 형태로 명확하게 표현할 수 있다.

### 3. 대표 프레임워크 비교

| 생태계 | 프레임워크 | 특징 |
|---|---|---|
| JVM | JUnit 5 (Jupiter) | 사실상 표준, 확장 모델 기반의 유연한 아키텍처 |
| JVM | TestNG | `@DataProvider`, 유연한 그룹/의존성 테스트 지원 |
| JVM | Spock (Groovy) | given-when-then 스타일의 BDD, 강력한 Mocking 내장 |
| JVM | Kotest (Kotlin) | Kotlin DSL 기반, 다양한 테스트 스타일(StringSpec 등) 제공 |
| Python | pytest | fixture 기반 DI, 플러그인 생태계가 강력 |
| JS/TS | Jest | 테스트 러너 + 어설션 + 목킹이 올인원으로 통합 |
| Go | testing 패키지 | 표준 라이브러리 자체에 내장, 최소주의 |

**xUnit 계열의 공통 설계 철학**
- Kent Beck과 Erich Gamma가 만든 SUnit(Smalltalk)에서 유래한 xUnit 패밀리(JUnit, NUnit, PyUnit 등)는 다음 요소를 공통으로 갖는다.
  - Test Case: 검증 단위
  - Test Fixture: 준비/정리 로직
  - Test Suite: 테스트 케이스 묶음
  - Test Runner: 실행 및 결과 보고
- "테스트 격리"와 "일관된 생명주기"라는 철학을 공유하며, 이 구조 덕분에 여러 언어에서 비슷한 학습 곡선으로 테스트를 작성할 수 있다.

### 4. JUnit 5 아키텍처

**3계층 구조**
- **JUnit Platform**: JVM에서 테스트 프레임워크를 실행하기 위한 기반. `TestEngine` API를 정의하고, `Launcher`를 통해 IDE/빌드 도구가 테스트를 실행할 수 있게 한다.
- **JUnit Jupiter**: JUnit 5의 새로운 프로그래밍 모델(`@Test`, `@BeforeEach` 등)과 확장 모델을 제공하며, Jupiter 기반 테스트를 실행하는 `TestEngine` 구현체를 포함한다.
- **JUnit Vintage**: 기존 JUnit 3/4로 작성된 테스트를 JUnit Platform 위에서 실행할 수 있게 해주는 `TestEngine`. 마이그레이션 기간 동안의 하위 호환을 위한 것으로, 현재는 deprecated 상태이며 신규 프로젝트에는 권장되지 않는다.
- 각 서브 프로젝트는 공개된 API로 통신하기 때문에, 여러 `TestEngine`을 동시에 등록해 Jupiter 테스트와 레거시 JUnit 4 테스트를 같은 빌드에서 함께 실행할 수 있다.

**확장 모델(Extension Model)과 @ExtendWith**
- JUnit 4의 `Runner`, `@Rule` 같은 여러 확장 메커니즘을 JUnit 5는 단일 `Extension` API로 통합했다.
- `@ExtendWith(...)`는 반복 가능(repeatable) 어노테이션으로, 테스트 클래스/인터페이스/메서드/필드/파라미터 어디에도 붙일 수 있다.
- 대표적인 확장 포인트 인터페이스
  - `BeforeEachCallback` / `AfterEachCallback`
  - `BeforeAllCallback` / `AfterAllCallback`
  - `ParameterResolver` (테스트 메서드 파라미터 자동 주입, 예: `@Mock` 필드 초기화)
  - `TestInstancePostProcessor`
- 여러 확장이 등록되면 선언 순서대로(또는 `@Order` 지정 시 그 순서대로) 실행되며, `@ExtendWith(MockitoExtension.class)`처럼 서드파티 라이브러리도 이 확장 포인트를 구현해 JUnit과 통합된다.
- 인터페이스에 `@ExtendWith`, `@Tag`를 선언하면 이를 구현하는 테스트 클래스가 자동으로 상속받는다.

**어노테이션 기반 실행 흐름**
1. `TestEngine`이 테스트 클래스를 탐색(discovery)
2. 클래스 인스턴스 생성 (`TestInstance.Lifecycle` 전략에 따라)
3. 등록된 확장(`Extension`)의 콜백 실행 (`BeforeAllCallback` → `@BeforeAll` → `BeforeEachCallback` → `@BeforeEach` → `@Test` → `AfterEachCallback`/`@AfterEach` → `AfterAllCallback`/`@AfterAll`)
4. 결과를 `Launcher`가 수집해 리포팅

### 5. 테스트 실행 파이프라인

**빌드 도구 연동**
- Gradle: `test { useJUnitPlatform() }` 설정으로 JUnit Platform을 사용하도록 지정
- Maven: Surefire 플러그인이 JUnit Platform Launcher를 통해 테스트를 실행 (`maven-surefire-plugin` 최신 버전은 별도 설정 없이 JUnit 5를 인식)

**테스트 격리와 실행 순서**
- 기본적으로 테스트 메서드 간 상태 공유를 피하기 위해 `PER_METHOD` 인스턴스 전략을 사용한다.
- 테스트 실행 순서는 기본적으로 결정적이지 않으며(재현성 있는 순서를 보장하지 않음), 순서가 필요하면 `@TestMethodOrder`(`MethodOrderer.OrderAnnotation`, `MethodOrderer.MethodName` 등)를 명시적으로 사용해야 한다. 순서에 의존하는 테스트는 그 자체로 안티패턴에 가깝다는 점도 함께 인지해야 한다.
- `@Tag`를 이용해 테스트를 분류(예: `unit`, `integration`, `slow`)하고, Gradle/Maven 설정에서 특정 태그만 선택적으로 실행할 수 있다.

**리포트와 커버리지 연계**
- Surefire/Gradle test 태스크는 XML/HTML 리포트를 생성하며 CI에서 이를 파싱해 실패 여부를 판단한다.
- JaCoCo(Java Code Coverage)와 연동하면 라인/브랜치 커버리지를 함께 측정할 수 있고, 커버리지 임계값 미달 시 빌드를 실패시키는 게이트를 걸 수 있다.

## 핵심 정리
- 테스트 프레임워크는 러너 + 어설션 + 픽스처 + 목킹의 조합으로 테스트를 표준화한다.
- JUnit 5는 Platform/Jupiter/Vintage 3계층으로 분리되어 확장성과 하위 호환(레거시 JUnit 4 테스트 실행)을 동시에 확보한다.
- 프레임워크는 실행 흐름의 주도권(IoC)을 가진다는 점에서 단순 어설션 라이브러리(AssertJ, Hamcrest)와 구분된다.
- `@ExtendWith`로 대표되는 Extension Model은 JUnit 4의 여러 확장 메커니즘(Runner, Rule)을 하나의 API로 통합한 JUnit 5의 핵심 개선점이다.

## 기술적 한계와 보완 전략
- 프레임워크만으로 좋은 테스트가 보장되지 않음 → 테스트 설계 원칙(FIRST: Fast, Independent, Repeatable, Self-validating, Timely / AAA: Arrange-Act-Assert) 병행 적용.
- 과도한 목킹으로 인한 취약한 테스트(구현 세부사항에 결합되어 리팩터링 시 쉽게 깨짐) → 통합 테스트, 슬라이스 테스트(`@WebMvcTest`, `@DataJpaTest` 등)로 보완해 실제 협력 관계를 일부 검증.
- 느린 테스트 스위트 → 병렬 실행(`junit.jupiter.execution.parallel.enabled=true`), `@Tag`를 이용한 테스트 분류(빠른 유닛 테스트만 우선 실행), Testcontainers 재사용 전략(싱글톤 컨테이너 패턴) 등으로 피드백 루프 단축.
- 순서 의존적/공유 상태에 의존하는 테스트는 병렬 실행이나 리팩터링 시 깨지기 쉬우므로, 테스트 간 완전한 독립성을 설계 단계에서 강제하는 것이 중요하다.

## 키워드
- **테스트 프레임워크(Test Framework)**: 테스트 작성·실행·검증·리포팅을 표준화된 방식으로 처리할 수 있게 해주는 도구 모음. 실행 흐름의 주도권을 프레임워크가 갖는다(IoC).
- **JUnit 5**: Platform, Jupiter, Vintage 세 개의 서브 프로젝트로 구성된 JVM 테스트 프레임워크. 사실상 자바 진영의 표준.
- **Test Runner**: 테스트를 탐색하고 생명주기에 맞춰 실행한 뒤 결과를 수집·보고하는 실행 엔진. JUnit 5에서는 `TestEngine`이 이 역할을 담당.
- **Assertion**: 실제 값과 기대 값을 비교해 성공/실패를 판정하는 도구. `Assertions`, AssertJ, Hamcrest 등이 있다.
- **Fixture**: 테스트 실행 전후에 필요한 고정된 준비/정리 환경. `@BeforeEach`/`@AfterEach` 등으로 관리한다.
- **Mocking**: 협력 객체를 가짜 객체로 대체해 테스트 대상을 격리하는 기법. Stub/Mock/Spy로 세분화된다.
- **xUnit**: SUnit에서 유래한 테스트 프레임워크 패밀리의 총칭(JUnit, NUnit, PyUnit 등). Test Case/Fixture/Suite/Runner라는 공통 구조를 공유한다.
- **Test Lifecycle**: 테스트 인스턴스 생성부터 소멸까지의 실행 흐름과 이를 제어하는 어노테이션 체계(`@BeforeAll`, `@BeforeEach`, `TestInstance.Lifecycle` 등).
- **AssertJ**: `assertThat(...)` 형태의 유창한(fluent) 체이닝 API를 제공하는 어설션 라이브러리. 가독성이 높은 검증 코드를 작성할 수 있다.
- **파라미터화 테스트(Parameterized Test)**: 동일한 테스트 로직을 여러 입력값에 대해 반복 실행하는 기법. `@ParameterizedTest`와 다양한 `@...Source` 어노테이션으로 구현한다.
- **Extension Model**: JUnit 5에서 `@ExtendWith`를 통해 테스트 실행 각 단계에 개입할 수 있게 해주는 확장 메커니즘. JUnit 4의 Runner/Rule을 대체 및 통합했다.
