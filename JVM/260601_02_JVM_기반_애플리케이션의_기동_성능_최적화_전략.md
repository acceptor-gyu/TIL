# JVM 기반 애플리케이션의 기동 성능 최적화 전략

## 개요

JVM 기반 애플리케이션의 기동(startup) 성능은 오토스케일링과 서버리스 환경이 보편화되면서 점점 중요해지고 있다. 인스턴스가 요청을 받기 전까지 걸리는 시간(Cold Start)은 직접적인 비용과 사용자 경험 저하로 이어진다. 이 문서에서는 JVM의 기동 과정을 단계별로 분석하고, 각 단계를 단축하기 위한 전략들을 정리한다.

## 상세 내용

### 1. JVM 기동 성능이 중요한 이유

**Cold Start와 오토스케일링**

오토스케일링 환경에서는 트래픽 급증 시 새 인스턴스를 빠르게 띄워야 한다. JVM은 기동 시 클래스 로딩, JIT 컴파일 워밍업, 빈 초기화 등의 비용을 모두 치른 뒤에야 정상 처리가 가능하다. Spring Boot 기반 서비스는 통상 기동에 5~12초가 소요되며, 이 구간 동안 인입된 요청은 처리 지연 또는 실패를 겪는다.

서버리스 환경(AWS Lambda, Google Cloud Run 등)은 요청이 없을 때 인스턴스를 0으로 줄이기 때문에 Cold Start가 지속적으로 발생한다. JVM 언어 기반 함수는 Node.js나 Python 런타임 대비 Cold Start가 수배 이상 느려 실질적인 사용이 어렵다.

**핵심 지표**

| 지표 | 설명 |
|------|------|
| **TTFR (Time-To-First-Request)** | 프로세스 시작부터 첫 요청을 처리할 수 있는 상태까지 걸린 시간 |
| **TTPP (Time-To-Peak-Performance)** | JIT 컴파일이 충분히 진행되어 최대 처리 성능에 도달하기까지 걸린 시간 |

TTFR은 Readiness Probe가 통과되는 시점을 의미하며, TTPP는 그보다 훨씬 나중에 도달한다. 두 지표를 분리해서 인식하는 것이 최적화 전략 선택에 중요하다.

### 2. JVM 기동 과정의 단계별 비용

JVM 기동은 크게 세 가지 비용으로 구성된다.

**① 클래스 로딩 (Class Loading)**

JVM은 클래스를 처음 사용할 때 `.class` 파일을 읽어 파싱하고 검증(Verification)한 뒤 링킹(Linking)을 수행한다. Spring Boot 애플리케이션은 수천~수만 개의 클래스를 로딩하며 이 과정이 기동 시간의 상당 부분을 차지한다.

```
클래스 로딩 단계:
Loading → Verification → Preparation → Resolution → Initialization
```

**② JIT 컴파일과 워밍업**

JVM의 HotSpot 컴파일러는 처음에는 인터프리터 모드로 코드를 실행하다가, 호출 횟수가 임계치를 넘으면 단계적으로 컴파일을 수행한다.

```
Tier 0: 인터프리터 (느리지만 즉시 실행)
Tier 1: C1 컴파일러 (빠른 컴파일, 낮은 최적화)
Tier 2: C1 + 프로파일링 (프로파일 수집)
Tier 3: C1 + 전체 프로파일링
Tier 4: C2 컴파일러 (느린 컴파일, 높은 최적화 → Peak Performance)
```

Tier3 진입 임계치는 기본 2,000회, Tier4는 15,000회이다. 피크 성능에 도달하려면 핵심 경로가 수만 번 실행되어야 하므로 기동 직후 구간에서는 성능이 낮다.

**③ 힙 초기화와 GC 워밍업**

JVM 기동 시 힙 메모리를 예약하고 GC 스레드를 초기화한다. 초기에는 GC 튜닝 데이터가 없어 Full GC가 발생하기 쉽고, 이 역시 초기 응답 지연의 원인이 된다.

### 3. 클래스 로딩 최적화

**CDS (Class Data Sharing)**

CDS는 JVM이 표준 라이브러리 클래스들의 파싱·검증·링킹 결과를 공유 아카이브(`.jsa` 파일)에 저장해 두고, 다음 기동 시 이를 메모리 맵으로 직접 적재하는 기술이다. JDK 12부터 기본 CDS 아카이브가 JDK 배포본에 포함되어 별도 설정 없이 동작한다.

```bash
# 기본 CDS 아카이브 확인
java -Xshare:on -version

# CDS 비활성화 비교
java -Xshare:off -jar app.jar
```

**AppCDS (Application Class Data Sharing)**

JDK 10(JEP 310)에서 도입되었으며, 애플리케이션 클래스패스의 클래스까지 아카이브에 포함할 수 있다.

```bash
# 1단계: 클래스 목록 추출
java -XX:DumpLoadedClassList=classes.lst -jar app.jar

# 2단계: 아카이브 생성
java -Xshare:dump -XX:SharedClassListFile=classes.lst \
     -XX:SharedArchiveFile=app-cds.jsa \
     --class-path app.jar

# 3단계: 아카이브 적용
java -Xshare:on -XX:SharedArchiveFile=app-cds.jsa -jar app.jar
```

**Dynamic CDS Archive (JDK 13, JEP 350)**

JDK 13부터는 애플리케이션 종료 시 자동으로 아카이브를 생성하는 Dynamic CDS가 추가되었다. JDK 19부터는 `-XX:+AutoCreateSharedArchive` 플래그로 더욱 간단하게 사용할 수 있다.

```bash
# JDK 19+: 자동 아카이브 생성·갱신
java -XX:+AutoCreateSharedArchive -XX:SharedArchiveFile=app-cds.jsa -jar app.jar
```

**JEP 483 (Project Leyden, JDK 24)**

JEP 483은 CDS를 확장해 클래스를 이미 링크된 상태로 저장하는 AOT 캐시를 도입한다. Spring PetClinic 기준 약 41% 기동 시간 단축 효과가 측정되었다.

### 4. JIT 워밍업 최적화

**Tiered Compilation 튜닝**

워밍업 시간을 줄이는 가장 간단한 방법은 C2 컴파일을 비활성화하고 C1만 사용하는 것이다. Tier 4 최적화가 없어 피크 성능은 낮지만 TTFR은 크게 단축된다. 피크 성능이 크게 중요하지 않은 서버리스 함수나 짧게 실행되는 작업에 적합하다.

```bash
# C1만 사용 (서버리스/짧은 실행 시간에 적합)
-XX:TieredStopAtLevel=1

# 임계치 낮춰 빠르게 C2로 승격 (워밍업 단축)
-XX:Tier3InvocationThreshold=1000
-XX:Tier4InvocationThreshold=5000
```

**ReadyNow / PGO 기반 사전 컴파일**

Azul Zing(ReadyNow) 같은 상용 JVM은 이전 실행의 컴파일 프로파일을 저장해 다음 기동 시 즉시 최적화된 코드를 사용한다. OpenJDK에서도 JDK 25의 JEP(Ahead-of-Time Method Profiling)를 통해 메서드 호출 횟수, 브랜치 빈도, 인라이닝 후보 등의 프로파일을 재사용하는 기능이 추가되고 있다.

**CRaC (Coordinated Restore at Checkpoint)**

CRaC는 JVM이 완전히 워밍업된 상태의 프로세스 스냅샷을 찍고(Checkpoint), 이후 기동 시 스냅샷에서 복원(Restore)하는 방식이다. 복원 후 TTFR은 수십 밀리초 수준까지 단축된다.

```
전통적 기동: 클래스 로딩 → JIT 워밍업 → 서비스 가능
CRaC:        스냅샷 복원(40ms) → 서비스 가능 (JIT 이미 완료된 상태)
```

Spring Boot 3.2+에서 CRaC를 공식 지원한다. 단, 현재 Linux 환경에서만 동작하며 외부 리소스(소켓, 파일 핸들, DB 커넥션 등)의 복원 처리가 필요하다.

```java
// Spring Boot CRaC 지원 예시
@SpringBootApplication
public class Application implements ApplicationRunner {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
// application.properties
spring.checkpoint.restore=on-refresh
```

### 5. AOT 컴파일과 네이티브 이미지

**GraalVM Native Image**

GraalVM Native Image는 Java 애플리케이션을 빌드 타임에 네이티브 바이너리로 컴파일한다. JVM 없이 실행되므로 클래스 로딩·JIT 워밍업 비용이 전혀 없다.

| 항목 | JVM (Spring Boot) | Native Image |
|------|-------------------|--------------|
| 기동 시간 | 5~12초 | 40~120ms |
| 메모리 사용 | 높음 | 낮음 |
| 피크 처리량 | 높음 (JIT 최적화) | 10~25% 낮음 |
| 빌드 시간 | 수십 초 | 5~20분 |

**Native Image의 제약 사항**

빌드 타임 정적 분석(Reachability Analysis)으로 리플렉션, 동적 클래스 로딩, JNI 사용 시 명시적 설정이 필요하다.

```json
// reflect-config.json (리플렉션 대상 명시)
[
  {
    "name": "com.example.MyClass",
    "allDeclaredMethods": true,
    "allDeclaredFields": true
  }
]
```

Profile-Guided Optimization(PGO)을 적용하면 JIT 대비 처리량 격차를 30~50% 회복할 수 있다.

**Project Leyden**

Project Leyden은 GraalVM처럼 JVM을 버리지 않으면서도 Native Image에 준하는 기동 성능을 표준 OpenJDK에서 달성하는 것을 목표로 한다.

- **JDK 24 (JEP 483)**: AOT 클래스 캐시. 클래스를 링크된 상태로 저장.
- **JDK 24 (JEP 514)**: 트레이닝 실행과 캐시 빌드를 단일 명령으로 통합.
- **JDK 25**: Ahead-of-Time Method Profiling으로 JIT 워밍업 가속.

```bash
# JDK 24+: AOT 캐시 생성 및 사용
java -XX:AOTCacheOutput=app.aot -jar app.jar  # 트레이닝 실행
java -XX:AOTCache=app.aot -jar app.jar        # 캐시 적용 실행
```

### 6. 프레임워크/애플리케이션 레벨 최적화

**Spring Boot 지연 초기화 (Lazy Initialization)**

기본적으로 Spring은 기동 시 모든 빈을 생성한다. 지연 초기화를 활성화하면 빈이 처음 사용될 때 생성되므로 기동 시간을 50% 이상 단축할 수 있다. 단, 첫 요청 응답 시간이 증가하는 트레이드오프가 있다.

```yaml
# application.yaml
spring:
  main:
    lazy-initialization: true
```

**Spring Boot AOT Processing**

Spring Boot 3.0부터 AOT 처리를 지원한다. 빌드 타임에 ApplicationContext를 분석해 런타임에 필요한 설정·메타데이터를 미리 생성하여, 기동 시 리플렉션과 동적 분석 비용을 줄인다.

```bash
# Maven AOT 빌드
./mvnw spring-boot:process-aot
./mvnw spring-boot:build-image  # Native Image 포함 빌드
```

**컴포넌트 스캔 범위 최소화**

넓은 패키지를 스캔할수록 클래스 로딩과 빈 탐색 비용이 늘어난다.

```java
// 안 좋은 예: 최상위 패키지 전체 스캔
@SpringBootApplication  // com.example 전체 스캔

// 좋은 예: 필요한 패키지만 명시
@SpringBootApplication(scanBasePackages = {"com.example.core", "com.example.api"})
```

불필요한 자동 설정을 제외하는 것도 효과적이다.

```java
@SpringBootApplication(exclude = {
    DataSourceAutoConfiguration.class,
    SecurityAutoConfiguration.class
})
```

### 7. 컨테이너/배포 환경 튜닝

**JVM 메모리 플래그와 컨테이너 정합**

컨테이너 환경에서는 JVM이 호스트 메모리 전체를 인식해 힙을 과도하게 설정하는 문제가 발생한다. `-XX:+UseContainerSupport` (JDK 10 이후 기본 활성)와 함께 비율 기반 설정을 사용한다.

```bash
# 컨테이너 메모리의 75%를 최대 힙으로 설정
-XX:MaxRAMPercentage=75.0
-XX:InitialRAMPercentage=50.0
-XX:+UseContainerSupport

# CPU 집약적인 기동 가속을 위해 컴파일 스레드 수 조정
-XX:CICompilerCount=2
```

**Kubernetes Readiness / Liveness / Startup Probe 전략**

Spring Boot Actuator 2.3+는 `/actuator/health/liveness`와 `/actuator/health/readiness` 엔드포인트를 기본 제공한다. Kubernetes 환경에서 Spring Boot를 감지하면 자동으로 등록된다.

```yaml
# Kubernetes 배포 예시
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 10

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 5

# startupProbe: 느리게 뜨는 JVM 앱 보호
startupProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  failureThreshold: 20   # 최대 20회 재시도
  periodSeconds: 5       # 5초 간격 → 최대 100초 대기
```

- **livenessProbe**: JVM과 Spring Context가 살아있는지 확인. 실패 시 컨테이너 재시작.
- **readinessProbe**: 외부 의존성(DB, 캐시 등)까지 준비된 상태 확인. 실패 시 로드밸런서에서 제외.
- **startupProbe**: 기동 중에만 동작하며, 성공 전까지 liveness/readiness 체크를 억제. 느리게 뜨는 JVM 앱에 필수.

## 핵심 정리

기동 성능은 **클래스 로딩 + JIT 워밍업 + 초기화 비용**의 합으로 결정된다. 각 비용을 어떤 전략으로 줄이느냐에 따라 트레이드오프가 다르다.

| 전략 | 클래스 로딩 | JIT 워밍업 | 피크 성능 | 운영 복잡도 |
|------|:-----------:|:----------:|:---------:|:-----------:|
| CDS / AppCDS | 단축 | 영향 없음 | 동일 | 낮음 |
| Tiered Stop At 1 | 영향 없음 | 단축 | 낮아짐 | 낮음 |
| CRaC | 우회 | 우회 | 동일 | 높음 (Linux 전용, 리소스 복원 필요) |
| GraalVM Native Image | 우회 | 우회 | 10~25% 낮음 | 높음 (리플렉션 설정, 긴 빌드) |
| Project Leyden AOT | 단축 | 단축 | 동일 | 낮음 (표준 OpenJDK) |
| Spring Lazy Init | 영향 없음 | 영향 없음 | 동일 | 낮음 (첫 요청 지연) |

## 기술적 한계와 보완 전략

**Native Image의 동적 기능 제약**

GraalVM Native Image는 빌드 타임 정적 분석에 기반하므로 리플렉션, 동적 프록시, 동적 클래스 로딩이 기본적으로 제한된다. Spring AOP, Hibernate, Jackson 등 프레임워크의 많은 기능이 리플렉션에 의존하므로 `reflect-config.json`, `proxy-config.json` 등의 힌트 파일이 필요하다. GraalVM Tracing Agent를 통해 자동 생성할 수 있다.

```bash
# Tracing Agent로 힌트 파일 자동 생성
java -agentlib:native-image-agent=config-output-dir=META-INF/native-image \
     -jar app.jar
```

**CRaC의 외부 리소스 복원 문제**

Checkpoint 시 열려있는 소켓, DB 커넥션, 파일 핸들 등은 복원 후 무효화된다. `Resource` 인터페이스를 구현해 Checkpoint 직전에 자원을 닫고, Restore 후 재연결하는 핸들러를 등록해야 한다.

```java
public class MyResource implements Resource {
    @Override
    public void beforeCheckpoint(Context<? extends Resource> context) {
        // 소켓/커넥션 닫기
    }

    @Override
    public void afterRestore(Context<? extends Resource> context) {
        // 소켓/커넥션 재연결
    }
}
```

보안 측면에서도 Checkpoint 스냅샷에 민감한 정보(비밀번호, 토큰 등)가 포함될 수 있어 스냅샷 저장소 접근 제어가 필요하다.

**AppCDS 아카이브 관리**

AppCDS 아카이브는 JDK 버전, 클래스패스, JVM 옵션에 의존하므로 배포 환경이 바뀌면 아카이브를 재생성해야 한다. CI/CD 파이프라인에서 이미지 빌드 시 아카이브를 함께 생성하는 것이 권장된다.

## 키워드

- **Cold Start**: 서버리스·오토스케일링 환경에서 새 인스턴스가 기동되어 요청을 처리할 수 있는 상태까지 걸리는 시간. JVM 기반 앱은 클래스 로딩과 JIT 워밍업으로 인해 타 런타임 대비 Cold Start가 길다.

- **Class Data Sharing (CDS / AppCDS)**: JVM이 클래스 파싱·검증·링킹 결과를 공유 아카이브에 저장해 다음 기동 시 재사용하는 기술. CDS는 JDK 표준 라이브러리, AppCDS는 애플리케이션 클래스까지 포함한다. JDK 12 이후 기본 CDS 아카이브가 기본 제공된다.

- **Tiered Compilation**: JVM HotSpot이 인터프리터 → C1(클라이언트 컴파일러) → C2(서버 컴파일러) 순으로 단계적으로 최적화를 수행하는 방식. 초기에는 빠른 기동을 위해 인터프리터나 C1을 사용하고, 충분한 프로파일이 쌓이면 C2로 승격해 피크 성능을 달성한다.

- **JIT Warmup**: JVM이 피크 성능에 도달하기까지 필요한 워밍업 구간. 핵심 코드 경로가 임계 횟수(기본 Tier4: 15,000회) 이상 실행되어야 C2 컴파일이 완료된다. 기동 직후에는 처리량이 피크 대비 크게 낮을 수 있다.

- **CRaC (Coordinated Restore at Checkpoint)**: 완전히 워밍업된 JVM 프로세스의 스냅샷을 찍고 이후 기동 시 복원하는 OpenJDK 프로젝트. TTFR을 수십 ms 수준으로 단축할 수 있다. 현재 Linux 전용이며 외부 리소스(소켓, DB 커넥션 등)의 재연결 핸들링이 필요하다.

- **GraalVM Native Image**: Java 애플리케이션을 빌드 타임에 네이티브 바이너리로 AOT 컴파일하는 기술. 기동 시간 40~120ms, 낮은 메모리 사용이 장점이나 동적 기능 제약과 긴 빌드 시간이 단점이다. PGO를 적용하면 JIT 대비 처리량 격차를 줄일 수 있다.

- **AOT Compilation**: Ahead-of-Time 컴파일. 실행 전 미리 컴파일을 수행해 런타임 컴파일 비용을 제거한다. GraalVM Native Image, Spring Boot AOT Processing, Project Leyden AOT Cache 등이 이에 해당한다.

- **Project Leyden**: 표준 OpenJDK에 AOT 기능을 통합하는 프로젝트. JDK 24의 JEP 483(AOT 클래스 캐시), JEP 514(트레이닝 실행 단순화), JDK 25의 AOT Method Profiling 등을 통해 Native Image 없이 기동 성능을 대폭 향상한다.

- **Spring Boot AOT**: Spring Boot 3.0+에서 지원하는 빌드 타임 AOT 처리. 런타임에 수행하던 ApplicationContext 분석, 빈 탐색, 리플렉션 기반 설정을 빌드 타임으로 이동해 기동 비용을 줄인다. GraalVM Native Image 빌드의 전제 조건이기도 하다.

- **Time-To-First-Request (TTFR)**: JVM 프로세스 시작부터 첫 번째 요청을 실제로 처리할 수 있는 상태가 되기까지 걸린 시간. Kubernetes Readiness Probe가 통과하는 시점과 동일하다. 기동 성능 최적화의 주요 목표 지표.
