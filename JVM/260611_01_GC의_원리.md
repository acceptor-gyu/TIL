# GC의 원리

## 개요

GC가 어떤 원리로 살아있는 객체와 죽은 객체를 구분하고 메모리를 회수하는지 그 내부 동작 메커니즘을 정리한다. 단순히 "자동으로 메모리를 해제한다"를 넘어, 어떤 알고리즘과 자료구조를 기반으로 GC가 동작하는지를 다룬다.

## 상세 내용

### 가비지 판별의 두 가지 접근

#### 참조 카운팅(Reference Counting)

객체마다 참조 횟수를 관리하고, 카운트가 0이 되는 순간 즉시 회수하는 방식이다.

- 구현이 단순하고 회수 시점이 예측 가능하다
- **순환 참조(Circular Reference) 문제**: A → B → A처럼 서로를 참조하면 카운트가 0이 되지 않아 회수 불가
- Python의 CPython 구현체가 이 방식을 기본으로 사용하지만, JVM은 채택하지 않는다

#### 도달 가능성 분석(Reachability Analysis)

JVM이 실제로 사용하는 방식이다. GC Root라는 출발점으로부터 참조 그래프를 DFS(깊이 우선 탐색)로 순회하면서 도달 가능한 모든 객체를 마킹하고, 마킹되지 않은 객체를 가비지로 판별한다.

- 순환 참조가 있어도, GC Root에서 도달하지 못하면 가비지로 처리
- STW(Stop-The-World) 동안 Heap의 스냅샷을 고정하고 분석하는 것이 기본 전제다

### GC Root와 객체 그래프 탐색

**GC Root**는 "반드시 살아있어야 하는 참조 출발점"이다. JVM이 GC Root로 인정하는 것들은 다음과 같다.

| GC Root 종류 | 설명 |
|---|---|
| 스택 프레임의 로컬 변수 | 현재 실행 중인 메서드의 지역 변수와 파라미터 |
| static 변수 | 클래스에 속한 정적 필드 (메서드 영역에 저장) |
| JNI 참조 | Native 코드에서 Java 객체를 참조하는 경우 |
| 활성 스레드 | 현재 실행 중인 모든 스레드 객체 |
| 클래스 로더 | 로드된 클래스 자체 |
| 모니터(synchronized 락) | 현재 락을 보유 중인 객체 |

GC Root에서 참조를 따라 탐색하면서 도달 가능한 모든 객체는 "Live Object"로 마킹된다. 마킹이 끝난 후 마킹되지 않은 객체는 가비지로 회수된다.

### 핵심 GC 알고리즘

#### Mark-Sweep

가장 기본적인 2단계 알고리즘이다.

1. **Mark 단계**: GC Root에서 시작해 도달 가능한 모든 객체에 마킹 비트를 설정
2. **Sweep 단계**: Heap 전체를 순회하며 마킹되지 않은 객체의 메모리를 회수

- 장점: 구현이 단순하고 살아있는 객체를 이동시키지 않는다
- 단점: **단편화(Fragmentation)** 발생 - 해제된 메모리가 불연속적으로 흩어져 큰 객체를 할당하기 어려워진다

#### Mark-Compact

Mark-Sweep의 단편화 문제를 해결하기 위해 Compaction 단계를 추가한다.

1. **Mark 단계**: 도달 가능한 객체 마킹
2. **Compact 단계**: 살아있는 객체를 Heap의 한쪽 끝으로 연속적으로 이동

- 장점: 단편화가 없고, 새 객체 할당이 포인터 하나만 이동하면 되어 빠르다(Bump Pointer Allocation)
- 단점: 객체를 이동시키므로 이동 비용과 참조를 갱신하는 비용이 발생한다

#### Copying(복사)

Heap을 두 개의 동일한 반(Semi-Space)으로 나누고, 한쪽만 사용하다가 GC 시 살아있는 객체만 다른 반으로 복사한다.

1. **From-Space**: 현재 사용 중인 영역
2. **To-Space**: 비어있는 영역

GC가 발생하면 From의 Live Object를 To로 복사하고, From 전체를 비운다. 그 후 From과 To 역할을 교체한다.

- 장점: 복사 후 단편화 없음, 할당이 매우 빠르다
- 단점: Heap의 절반만 실제로 사용 가능하여 공간 효율이 50%에 불과하다
- **JVM의 Young Generation(Survivor 영역)이 이 방식을 사용**한다

### 약한 세대 가설(Weak Generational Hypothesis)

> "대부분의 객체는 금방 죽는다(Most objects die young)"

프로그램을 실제로 관찰한 경험적 사실로, JVM Heap을 세대별로 분리하는 근거가 된다.

- 임시 변수, 루프 내 생성 객체, 요청 처리 중 생성된 DTO 등 대부분은 매우 짧은 생애를 가진다
- 반면 오래 살아남은 객체(캐시, 싱글톤, 커넥션 풀 등)는 계속 살아있을 가능성이 높다

이 가설 덕분에 **Young Generation에서만 자주 GC(Minor GC)를 수행하고, Old Generation은 드물게 GC(Major/Full GC)를 수행하는 전략**이 효율적이다. Young Generation은 전체 Heap의 1/3 정도로 작기 때문에, GC 빈도가 높아도 빠르게 처리된다.

### Heap 구조와 객체의 이동

```
[ Young Generation (1/3) ]    [ Old Generation (2/3) ]
 ┌─────────┬──────┬──────┐    ┌─────────────────────┐
 │  Eden   │  S0  │  S1  │    │    Tenured Space     │
 └─────────┴──────┴──────┘    └─────────────────────┘
```

#### Eden → Survivor (Minor GC 시)

1. 새 객체는 모두 Eden에 할당된다
2. Eden이 꽉 차면 Minor GC가 발생한다
3. Eden의 Live Object는 현재 비어있는 Survivor(예: S0)로 복사된다
4. 이미 S1에 있던 Live Object도 S0으로 복사된다 (age +1)
5. Eden과 S1은 완전히 비워진다

#### Survivor → Old Generation (Promotion)

- Survivor에서 살아남을 때마다 객체의 **age(나이) 카운터**가 1씩 증가한다
- age가 일정 임계값(기본값: **15**)에 도달하면 Old Generation으로 **승격(Promotion)**된다
- `-XX:MaxTenuringThreshold` 옵션으로 임계값을 조정할 수 있다
- Eden이나 Survivor에 담기 너무 큰 객체(Large Object)는 바로 Old Generation에 할당된다

#### Card Table과 Remembered Set (세대 간 참조 추적)

Old Generation의 객체가 Young Generation의 객체를 참조할 수 있다. Minor GC 시 Young 영역만 스캔하면 이 참조를 놓치게 되므로, 이를 추적하는 자료구조가 필요하다.

**Card Table**
- Heap 메모리를 512바이트 단위의 "카드(Card)"로 분할한다
- Old → Young 참조가 있는 카드를 "dirty"로 표시한다
- Minor GC 시 dirty 카드만 추가로 스캔하여 세대 간 참조를 찾는다
- 전체 Old Generation을 스캔하는 비용을 피할 수 있다

**Remembered Set (RSet)**
- G1 GC에서 사용하는 방식으로, 각 Region이 자신을 참조하는 다른 Region의 카드 정보를 직접 보관한다
- RSet 덕분에 특정 Region만 독립적으로 수집(Evacuation)할 수 있다

### Stop-The-World와 GC의 비용

#### STW가 발생하는 이유

GC가 참조 그래프를 탐색하는 도중 애플리케이션 스레드가 객체를 생성하거나 참조를 변경하면 일관성 있는 Heap 스냅샷을 얻을 수 없다. 따라서 GC는 탐색 전에 모든 애플리케이션 스레드를 일시 중단시킨다. 이것이 STW다.

STW 동안 사용자 요청은 처리되지 않으므로, STW 시간 = 지연 시간(Latency) 증가다.

#### Safepoint

JVM은 스레드를 아무 시점에나 멈출 수 없다. 스레드가 안전하게 멈출 수 있는 특정 지점을 **Safepoint**라고 한다.

- 메서드 호출, 루프 backedge, 예외 처리 직전 등 코드의 특정 위치에 삽입된다
- JVM이 STW를 요청하면, 각 스레드는 다음 Safepoint에 도달했을 때 스스로 일시 정지한다
- 이 협력적(Collaborative) 방식 덕분에 스레드는 항상 일관된 상태에서 멈출 수 있다
- `Time to safepoint`: STW 요청 후 모든 스레드가 Safepoint에 도달할 때까지 걸리는 시간도 GC 오버헤드에 포함된다

#### 처리량(Throughput) vs 지연 시간(Latency) 트레이드오프

| 목표 | 전략 | 대표 GC |
|---|---|---|
| 최대 처리량 | STW를 길게 허용하되 GC 빈도를 줄인다 | Parallel GC |
| 최소 지연 시간 | 짧고 잦은 STW, 대부분의 작업을 Concurrent하게 | G1, ZGC, Shenandoah |
| 균형 | 처리량과 지연 시간 모두 적절히 | G1 GC (Java 9+ 기본값) |

## 핵심 정리

- GC는 참조 카운팅이 아닌 도달 가능성 분석으로 가비지를 판별한다
- 기본 알고리즘은 Mark-Sweep / Mark-Compact / Copying으로 나뉘며 각각 단편화와 비용 측면의 트레이드오프가 있다
- 약한 세대 가설을 기반으로 Heap을 세대별로 나눠 GC 효율을 극대화한다
- Card Table은 Old → Young 참조를 추적하여 Minor GC 시 Old 전체 스캔 비용을 피한다
- Safepoint는 STW를 안전하게 시작하기 위한 협력적 메커니즘이다
- 모든 GC는 본질적으로 STW 비용을 수반하며, 이를 최소화하는 것이 현대 GC의 목표다

## 기술적 한계와 보완 전략

전통적인 GC(Serial, Parallel)는 GC 작업 전체를 STW 구간 안에서 수행한다. Heap이 클수록 STW 시간이 길어지고 애플리케이션 지연이 커진다.

| 한계 | 보완 전략 |
|---|---|
| STW로 인한 지연 | Concurrent Marking: GC가 마킹 작업을 애플리케이션과 병렬로 수행 |
| 세대 간 참조 추적 오버헤드 | Card Table / Remembered Set으로 스캔 범위 최소화 |
| 대용량 Heap에서의 스캔 비용 | G1의 Region 분할, ZGC의 Colored Pointer로 전체 Heap 스캔 회피 |

**현대 GC의 접근: 삼색 마킹(Tri-Color Marking)**

Concurrent GC(G1, ZGC, Shenandoah)가 애플리케이션 실행 중에 마킹을 수행하기 위해 사용하는 알고리즘이다.

- **흰색(White)**: 아직 방문하지 않은 객체 (잠재적 가비지)
- **회색(Gray)**: 방문했지만 자식 참조를 아직 처리하지 않은 객체
- **검은색(Black)**: 방문 완료 + 자식 참조 모두 처리된 Live Object

GC는 GC Root를 회색으로 칠하며 시작한다. 회색 객체의 자식을 모두 처리하면 검은색이 된다. 마킹이 끝나면 흰색 객체만 가비지다. 이 방식은 애플리케이션이 실행 중에 객체 참조를 변경해도 마킹 일관성을 유지하는 Write Barrier와 함께 사용된다.

**ZGC의 목표**: Heap 크기와 무관하게 STW를 1ms 이하로 유지한다. 마킹, 재배치, 참조 처리 등 대부분의 작업을 Concurrent하게 수행하고 STW는 스레드 스택 스캔 등 최소한의 작업에만 사용한다.

## 키워드

- **Reachability Analysis (도달 가능성 분석)**: GC Root에서 참조 그래프를 탐색하여 도달 불가능한 객체를 가비지로 판별하는 방식. JVM의 기본 가비지 식별 전략
- **GC Root**: 도달 가능성 분석의 출발점. 스택 로컬 변수, static 변수, JNI 참조, 활성 스레드 등이 해당된다
- **Mark-Sweep**: 도달 가능한 객체를 마킹하고, 마킹되지 않은 객체의 메모리를 회수하는 가장 기본적인 GC 알고리즘. 단편화 문제가 있다
- **Mark-Compact**: Mark-Sweep에 Compaction을 추가한 방식. 살아있는 객체를 한쪽으로 모아 단편화를 해소하지만 이동 비용이 발생한다
- **Copying GC**: Heap을 두 반으로 나눠 한쪽에서 다른 쪽으로 Live Object만 복사하는 방식. 단편화 없이 빠른 할당이 가능하나 공간 효율이 50%다. Young Generation의 Survivor 영역이 이 방식을 사용한다
- **Weak Generational Hypothesis (약한 세대 가설)**: "대부분의 객체는 금방 죽는다"는 경험적 전제. Young/Old 영역 분리와 세대별 GC 전략의 이론적 근거다
- **Stop-The-World**: GC가 Heap의 일관된 스냅샷을 확보하기 위해 모든 애플리케이션 스레드를 일시 중단하는 현상. 지연 시간에 직접적인 영향을 미친다
- **Safepoint**: 스레드가 STW 요청에 응답하여 안전하게 일시 정지할 수 있는 코드 내 특정 지점. JVM의 STW는 협력적 Safepoint 메커니즘을 기반으로 동작한다
- **Card Table / Remembered Set**: 세대 간 참조(Old → Young)를 추적하기 위한 자료구조. Card Table은 Heap을 512바이트 카드로 분할해 dirty 표시하고, G1의 Remembered Set은 Region 단위로 이 정보를 관리한다
- **Promotion (객체 승격)**: Young Generation의 Survivor 영역에서 age 임계값(기본 15)에 도달한 객체가 Old Generation으로 이동하는 과정
