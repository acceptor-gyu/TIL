# JVM은 도대체 어떻게 구동될까?

## 개요
자바 프로그램이 .java 소스에서 실제로 실행되기까지, JVM 내부에서 어떤 단계를 거쳐 구동되는지 학습한 내용. 단순히 "바이트코드를 실행한다"는 수준을 넘어 클래스 로딩, 런타임 메모리 구조, 실행 엔진, GC까지 전체 흐름을 연결해서 이해하는 것이 목표다.

## 상세 내용

### 1. 컴파일과 실행의 큰 그림

```
.java  →  javac  →  .class (바이트코드)  →  JVM 실행  →  네이티브 코드
```

- **WORA (Write Once, Run Anywhere)**: 소스코드를 플랫폼 독립적인 바이트코드로 컴파일하고, 각 플랫폼의 JVM이 그것을 해석·실행하기 때문에 가능하다.
- `.class` 파일은 JVM 명세(JVM Specification)에 정의된 포맷의 이진 파일이며, 운영체제나 CPU 아키텍처와 무관하다.
- `java` 명령 실행 시 가장 먼저 `JNI_CreateJavaVM()` 함수가 호출되어 JVM 인스턴스가 생성된다.

### 2. 클래스 로딩 (Class Loader Subsystem)

클래스 로딩은 **로딩 → 링킹 → 초기화** 세 단계로 이루어지며, 이 단계들은 순차적이 아닌 겹치면서 진행된다.

#### 로딩 (Loading)
- `.class` 파일을 찾아 JVM 메모리(Method Area)에 적재한다.
- JVM은 필요한 클래스를 **동적으로** 로드한다. 즉, 참조되는 시점에 로드된다.

#### 링킹 (Linking)
세 가지 하위 단계로 구성된다.

| 단계 | 설명 |
|------|------|
| Verification (검증) | 바이트코드가 JVM 명세에 부합하는지 확인. CDS 아카이브에 이미 검증된 클래스는 건너뜀 |
| Preparation (준비) | static 필드를 위한 메모리 할당, 기본값으로 초기화 |
| Resolution (해석) | 상수 풀의 심볼릭 참조(Symbolic Reference)를 직접 참조(Direct Reference)로 교체 |

#### 초기화 (Initialization)
- static 초기화 블록 실행 및 static 필드 초기화가 텍스트 순서대로 진행된다.
- 클래스 초기화 이전에 부모 클래스(superclass)가 먼저 초기화되어야 한다.

#### 클래스 로더 종류

```
Bootstrap ClassLoader        ← JDK 핵심 클래스 (java.lang.*)
        ↑ 부모
Platform ClassLoader         ← Java SE 플랫폼 API (Java 9+ Extension 대체)
        ↑ 부모
Application ClassLoader      ← 애플리케이션 클래스패스
        ↑ 부모
Custom ClassLoader           ← 직접 구현한 로더 (WAS, OSGi 등)
```

#### 부모 위임 모델 (Parent Delegation Model)
- 클래스 로드 요청이 오면 **자신이 먼저 로드하지 않고** 부모 로더에게 위임한다.
- 부모가 실패한 경우에만 자신이 직접 로드를 시도한다.
- **핵심 보안 이점**: `java.lang.String` 같은 핵심 클래스를 악의적으로 교체하는 것을 방지한다.
- 자식 로더는 부모 로더가 로드한 클래스를 볼 수 있지만, 부모 로더는 자식 로더의 클래스를 볼 수 없다.

```
클래스 요청
    ↓
Application ClassLoader → Platform ClassLoader → Bootstrap ClassLoader
                                                        ↓ (찾으면 반환, 없으면)
                                         ← Platform ClassLoader (찾으면 반환, 없으면)
        ← Application ClassLoader (직접 로드 시도)
```

### 3. 런타임 데이터 영역 (Runtime Data Area)

JVM의 메모리 영역은 **스레드 공유 영역**과 **스레드별 영역**으로 구분된다.

#### 스레드 공유 영역

| 영역 | 설명 |
|------|------|
| **Heap** | 객체 인스턴스와 배열이 할당되는 영역. GC의 주 관리 대상 |
| **Metaspace** | 클래스 메타데이터 저장 (Java 8부터 PermGen을 대체). 네이티브 메모리에서 관리되어 자동으로 크기가 조절됨 |

**Heap 세부 구조 (Generational GC 기준):**
```
Heap
├── Young Generation
│   ├── Eden Space     ← 새 객체 최초 할당
│   ├── Survivor 0     ← Minor GC 후 생존 객체 이동
│   └── Survivor 1
└── Old Generation     ← 오래 살아남은 객체 승격(Promotion)
```

#### 스레드별 영역 (각 스레드마다 독립적으로 생성)

| 영역 | 설명 |
|------|------|
| **JVM Stack** | 메서드 호출마다 스택 프레임(Stack Frame) 생성. 지역 변수, 피연산자 스택, 현재 메서드의 상수 풀 참조 보관 |
| **PC Register** | 현재 실행 중인 JVM 명령어의 주소를 저장. 네이티브 메서드 실행 시에는 undefined |
| **Native Method Stack** | JNI를 통해 호출되는 네이티브(C/C++) 메서드용 스택 |

> **스택 프레임(Stack Frame)**: 메서드 1개 호출 = 스택 프레임 1개 push. 메서드 종료 시 pop.

### 4. 실행 엔진 (Execution Engine)

실행 엔진은 클래스 로더가 메모리에 올린 바이트코드를 실제로 실행한다.

#### 인터프리터 vs JIT 컴파일러

| 구분 | 인터프리터 | JIT 컴파일러 |
|------|-----------|-------------|
| 방식 | 바이트코드를 한 줄씩 해석·실행 | 바이트코드를 네이티브 코드로 컴파일 후 실행 |
| 기동 속도 | 빠름 | 느림 (컴파일 오버헤드) |
| 런타임 성능 | 느림 | 빠름 (컴파일된 코드 재사용) |
| 사용 시점 | 초기 실행, 콜드 코드 | 자주 실행되는 "핫 코드" |

#### HotSpot 탐지
- JVM은 메서드 호출 횟수와 루프 반복 횟수를 추적한다.
- 이 카운터가 특정 임계값(CompileThreshold)을 초과하면 해당 코드를 **핫스팟(HotSpot)**으로 간주하고 JIT 컴파일을 트리거한다.

#### Tiered Compilation (계층형 컴파일)
Java 8부터 기본 활성화된 5단계 최적화 시스템이다.

| 레벨 | 실행 주체 | 설명 |
|------|----------|------|
| Level 0 | 인터프리터 | 기본 실행, 프로파일링 없음 |
| Level 1 | C1 컴파일러 | 빠른 컴파일, 프로파일링 없음 (단순 메서드) |
| Level 2 | C1 컴파일러 | 기본 프로파일링 수집 시작 |
| Level 3 | C1 컴파일러 | 상세한 동적 프로파일 수집 |
| Level 4 | C2 컴파일러 | 프로파일 기반 고도 최적화 (최종 목표) |

- **C1 컴파일러**: 빠른 컴파일 속도가 목표. 기동 성능에 유리.
- **C2 컴파일러**: 높은 최적화 수준이 목표. 메서드 인라이닝, 탈출 분석(Escape Analysis), 루프 펼치기(Loop Unrolling) 등 공격적인 최적화 적용.
- C2는 런타임 조건 변화에 대응하기 위해 **가정 검증 술어(predicate)**를 삽입하고, 가정이 깨지면 역최적화(Deoptimization)하여 인터프리터로 복귀한다.

#### Native Method Interface (JNI)
- 자바 코드에서 C/C++ 등 네이티브 코드를 호출하는 인터페이스.
- `System.currentTimeMillis()` 같은 메서드가 내부적으로 JNI를 사용한다.

### 5. 가비지 컬렉션 개요

GC는 Heap에서 더 이상 참조되지 않는 객체를 찾아 메모리를 회수하는 프로세스다.

#### GC가 구동에 미치는 영향
- **STW (Stop-The-World)**: GC 실행 중에는 모든 애플리케이션 스레드가 멈춘다. GC 종류에 따라 STW 시간이 크게 다르다.
- **Young Generation GC (Minor GC)**: Eden이 꽉 찰 때 발생. 비교적 빠르고 STW 시간이 짧다.
- **Old Generation GC (Major/Full GC)**: Old 영역이 꽉 찰 때 발생. STW 시간이 길어 서비스 레이턴시에 직접 영향을 준다.

#### 주요 GC 알고리즘 간단 비교

| GC | 특징 | 기본 적용 버전 |
|----|------|--------------|
| Serial GC | 단일 스레드, 소규모 애플리케이션용 | - |
| Parallel GC | 멀티스레드, 처리량 우선 | Java 8 이하 서버 기본 |
| G1 GC | 예측 가능한 STW 시간, Region 기반 | Java 9+ 기본 |
| ZGC | 초저지연, STW < 1ms 목표 | Java 15 Production Ready |
| Shenandoah GC | 동시 압축, 낮은 레이턴시 | OpenJDK 제공 |

> **Java 21에서는 Generational ZGC**가 도입되어 ZGC의 처리량이 크게 향상되었다.

### 6. JVM 기동 시퀀스 정리

`java MyApp` 실행부터 `main()` 메서드가 호출되기까지의 전체 흐름이다.

```
1. OS: java 프로세스 생성
        ↓
2. JVM Launcher: 인자 파싱, JVM 옵션 분리, JAVA_HOME/CLASSPATH 확인
        ↓
3. JNI_CreateJavaVM(): JVM 인스턴스 초기화
   - 시스템 리소스 감지 (CPU, 메모리)
   - GC 알고리즘 선택
   - Heap, Metaspace 초기화
   - 핵심 스레드 생성 (main, GC, JIT compiler, signal dispatcher 등)
        ↓
4. Bootstrap ClassLoader: 핵심 클래스 로드
   (java.lang.Object, String, Class, Thread 등 ~450개)
        ↓
5. 애플리케이션 메인 클래스 로딩 & 링킹 & 초기화
   - static 필드 초기화
   - static 블록 실행
        ↓
6. main(String[] args) 메서드 호출 → 애플리케이션 실행 시작
```

> Inside.java 측정 기준: HelloWorld 실행 시 M4 MacBook에서 **약 62ms** 내 완료.

#### 워밍업 (Warm-up)과 기동 성능
- JVM은 처음에 인터프리터로 실행하다가, 핫스팟을 발견하면 점차 C1 → C2로 전환한다.
- **콜드 스타트(Cold Start)**: JIT 컴파일이 아직 이루어지지 않은 초기 실행 상태. 레이턴시가 높다.
- **워밍업 완료**: C2가 핵심 메서드를 최적화 컴파일한 이후. 안정적인 고성능 상태.
- 서버리스(Lambda 등) 환경에서는 콜드 스타트가 치명적이므로 `-XX:TieredStopAtLevel=1`으로 C2를 비활성화하는 전략을 쓰기도 한다.

**워밍업 단축 기법 요약:**
- **CDS (Class Data Sharing)**: 클래스 메타데이터를 공유 아카이브로 저장해 재사용
- **AOT (Ahead-of-Time) 컴파일**: JEP 483 (JDK 24)으로 AOT 클래스 로딩·링킹 지원
- **JEP 515 (AOT Method Profiling)**: 이전 실행의 프로파일을 JVM 재시작 시 즉시 활용해 JIT 최적화 시간 단축 (OpenJDK 최신 논의 중)
- **CRaC (Coordinated Restore at Checkpoint)**: 워밍업된 JVM 상태를 스냅샷으로 저장·복원

## 핵심 정리
- JVM 기동은 **클래스 로딩 → 링킹 → 초기화 → 실행**의 연속이며, 각 단계는 필요할 때(on-demand) 수행된다.
- **부모 위임 모델**은 클래스 로더의 신뢰성과 보안을 보장하는 핵심 설계다. 클래스 식별은 "클래스 이름 + 그것을 로드한 클래스 로더"의 조합으로 이루어진다.
- **Tiered Compilation**은 C1의 빠른 기동과 C2의 고성능 최적화를 결합한 실용적인 전략이다. 대부분의 핫 코드는 Level 3(C1 전체 프로파일링) → Level 4(C2 최적화)로 전환된다.
- **STW GC**는 애플리케이션 레이턴시의 숨겨진 적이다. G1/ZGC 선택과 힙 크기 튜닝이 실서비스 품질에 직결된다.
- JVM 워밍업은 초기 레이턴시 스파이크의 근본 원인이며, CDS·AOT·CRaC 등 현대적인 기법으로 단축할 수 있다.

## 기술적 한계와 보완 전략

| 한계 | 설명 | 보완 전략 |
|------|------|----------|
| 콜드 스타트 레이턴시 | JIT 컴파일 전 인터프리터 실행으로 초기 응답이 느림 | CRaC, AOT, CDS 활용 |
| Full GC STW | Old 영역 수집 시 수백 ms ~ 수초 멈춤 발생 가능 | ZGC/Shenandoah 전환, 힙 크기 조정 |
| 메모리 오버헤드 | JVM 자체(JIT 스레드, GC 스레드 등)가 상당한 메모리 차지 | GraalVM Native Image로 메모리 대폭 절감 |
| 클래스 로딩 병목 | 대규모 Spring Boot 앱은 기동 시 수천 개 클래스 로딩 | Spring AOT, GraalVM, Layered JAR |

## 키워드

- **클래스 로더 (Class Loader)**: `.class` 파일을 찾아 JVM 메모리에 적재하는 컴포넌트. Bootstrap, Platform, Application 세 가지 기본 로더가 계층 구조를 이룬다.
- **부모 위임 모델 (Parent Delegation Model)**: 클래스 로드 요청을 부모 로더에게 먼저 위임하고, 부모가 실패한 경우에만 자신이 로드하는 방식. 핵심 클래스의 무결성과 보안을 보장한다.
- **런타임 데이터 영역 (Runtime Data Area)**: JVM이 프로그램 실행 중 사용하는 메모리 영역. Heap, Metaspace(스레드 공유), JVM Stack, PC Register, Native Method Stack(스레드별)으로 구성된다.
- **바이트코드 (Bytecode)**: `javac`가 `.java`를 컴파일하여 생성하는 플랫폼 독립적인 중간 코드. JVM 명세에 정의된 명령어 집합으로 구성된다.
- **실행 엔진 (Execution Engine)**: 바이트코드를 실제로 실행하는 JVM 컴포넌트. 인터프리터, JIT 컴파일러, GC로 구성된다.
- **JIT 컴파일러**: 런타임에 바이트코드를 네이티브 코드로 컴파일하는 컴파일러. 자주 실행되는 핫스팟 코드를 대상으로 한다.
- **HotSpot**: Oracle/OpenJDK의 JVM 구현체 이름이자, JIT가 자주 실행되는 코드("핫한 지점")를 탐지하는 메커니즘. 메서드 호출 횟수와 루프 반복 횟수로 판단한다.
- **Tiered Compilation**: 인터프리터(Level 0)부터 C1(Level 1~3), C2(Level 4)까지 5단계로 점진적 최적화를 수행하는 방식. Java 8부터 기본 활성화.
- **Metaspace**: Java 8부터 PermGen을 대체한 클래스 메타데이터 저장 영역. 네이티브 메모리에서 동적으로 크기가 조절된다.
- **가비지 컬렉션 (GC)**: Heap에서 더 이상 참조되지 않는 객체를 자동으로 회수하는 메모리 관리 메커니즘. Minor GC(Young), Major GC(Old), Full GC로 구분된다.
