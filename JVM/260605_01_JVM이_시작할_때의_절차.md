# JVM이 시작할 때의 절차

## 개요
JVM이 `java` 명령으로 실행된 순간부터 사용자 코드의 `main` 메서드가 호출되기까지, 내부적으로 어떤 단계를 거쳐 부트스트랩되는지를 정리한다. JVM 시작 절차는 크게 런처 실행 → JNI를 통한 JVM 생성 → 런타임 초기화 → 클래스 로딩 및 링킹 → `main` 실행 순으로 이어진다.

## 상세 내용

### 1. java 런처(Launcher) 실행

`java` 실행 파일은 단순한 바이너리가 아니라 JVM 인스턴스를 띄우기 위한 네이티브 런처다. 실행 시점에 다음 순서로 처리한다.

**환경 변수 처리**

런처가 가장 먼저 읽는 환경 변수는 `JAVA_TOOL_OPTIONS`과 `JDK_JAVA_OPTIONS`이다. 두 변수는 역할이 다르다.

| 변수 | 처리 시점 | 특징 |
|---|---|---|
| `JAVA_TOOL_OPTIONS` | `JNI_CreateJavaVM` 호출 시점 (VM 내부) | 런처 전용 옵션(`-client`, `-server` 등) 사용 불가 |
| `JDK_JAVA_OPTIONS` | 런처가 명령행 파싱 직전 | 명령행 앞에 prepend, `@파일` 참조 가능, `-jar` 등 불허 |

```bash
# 예시: 컨테이너 환경에서 힙 설정을 외부 주입할 때 자주 사용
export JAVA_TOOL_OPTIONS="-Xmx512m -XX:+UseG1GC"
java -jar app.jar
```

**인자 분류**

런처는 전달받은 인자를 네 가지로 분류한다.
- VM 옵션: `-Xmx`, `-XX:+...` 등 JVM에 직접 전달
- 시스템 프로퍼티: `-Dkey=value` 형태, `System.getProperty()`로 접근 가능
- 클래스패스 / 모듈패스: `-cp`, `--module-path` 등
- 애플리케이션 인자: 메인 클래스 또는 JAR 이름 이후의 나머지

**libjvm.so(dylib/dll) 로딩**

런처는 실행 환경에 따라 Client VM 또는 Server VM을 선택한 뒤, 해당 구현체를 담은 공유 라이브러리(`libjvm.so`, macOS에서는 `libjvm.dylib`)를 동적 로드한다. 이 라이브러리 안에 `JNI_CreateJavaVM` 심볼이 존재해야 하며, 라이브러리가 이 심볼을 내보내지 않으면 런처가 즉시 오류로 종료한다.

### 2. JNI를 통한 JVM 인스턴스 생성

런처는 `libjvm.so`에서 `JNI_CreateJavaVM` 함수 포인터를 획득한 뒤 호출한다. 이 함수 하나가 JVM 전체를 메모리에 올린다.

**JavaVMInitArgs 구성**

```c
JavaVMInitArgs vm_args;
JavaVMOption options[3];
options[0].optionString = "-Djava.class.path=.";
options[1].optionString = "-Xmx256m";
vm_args.version  = JNI_VERSION_21;
vm_args.nOptions = 2;
vm_args.options  = options;
vm_args.ignoreUnrecognized = JNI_FALSE;

JavaVM *jvm;
JNIEnv *env;
JNI_CreateJavaVM(&jvm, (void **)&env, &vm_args);
```

함수가 반환하면 두 핸들을 얻는다.
- `JavaVM *jvm`: VM 자체에 대한 핸들. `AttachCurrentThread` / `DestroyJavaVM` 등을 이 핸들로 호출한다.
- `JNIEnv *env`: 현재 스레드(메인 스레드)에서 자바 코드를 호출하기 위한 환경. 스레드마다 독립적으로 존재한다.

메인 스레드는 이 과정에서 JVM에 attach되어 이후 자바 코드를 실행할 수 있는 상태가 된다.

---

### 3. VM 런타임 초기화

`JNI_CreateJavaVM` 내부에서 다음 서브시스템들이 순서대로 초기화된다.

**메모리 서브시스템**

GC 알고리즘 선택이 가장 먼저 이루어진다. JDK 23 기준 기본 GC는 G1이다. GC 선택이 확정되면 힙 영역을 OS에서 예약(reserve)한다. 이 시점에서는 물리 메모리 커밋이 아닌 가상 주소 공간 예약만 발생하며, 실제 커밋은 사용량에 따라 점진적으로 이루어진다.

메타스페이스도 이 단계에서 초기화된다. 메타스페이스는 클래스 메타데이터(클래스 구조, 메서드 테이블, 상수 풀 등)를 저장하는 네이티브 힙 영역이다.

**CDS 아카이브 매핑 결정**

CDS(Class Data Sharing) 아카이브가 존재하면 이 시점에 메모리에 매핑한다. 기본 아카이브 위치는 `$JAVA_HOME/lib/server/classes.jsa`이며, JDK 12부터 `-Xshare:auto`가 기본값이다. 아카이브가 있으면 부트스트랩 클래스 로딩 시 검증·파싱 과정을 생략하고 read-only 메모리 매핑으로 대체해 약 33%의 시작 시간 단축 효과를 낸다.

**스레드 및 동기화 서브시스템**

JVM 내부 스레드 스케줄러, 모니터 잠금, 세이프포인트 메커니즘 등이 초기화된다.

**Template Interpreter 준비**

HotSpot VM의 Template Interpreter는 바이트코드 명령어별로 네이티브 코드 조각(template)을 미리 생성해 두는 방식으로 동작한다. JIT 컴파일 전에는 이 인터프리터가 바이트코드를 실행한다. JIT 컴파일러 스레드(C1/C2 컴파일러)도 이 단계에서 초기화된다.

### 4. 부트스트랩 클래스 로딩

VM 런타임이 준비되면 자바 세계를 부팅한다. 클래스로더 계층부터 구성한다.

**클래스로더 계층 구성**

```
Bootstrap ClassLoader   (네이티브, 기계어)
       │
Platform ClassLoader    (구 Extension ClassLoader, java.lang.ClassLoader 서브클래스)
       │
Application ClassLoader (System ClassLoader, 사용자 클래스패스 담당)
```

Bootstrap ClassLoader는 JVM이 직접 구현한 네이티브 코드로, `java.base` 모듈의 핵심 클래스를 로드할 책임을 진다.

**핵심 클래스 선로딩(Pre-loading)**

JVM이 동작하려면 자바 코드를 실행하기도 전에 몇 가지 클래스가 먼저 존재해야 한다.

- `java.lang.Object`: 모든 클래스의 수퍼클래스
- `java.lang.Class`: 클래스 자체를 표현하는 클래스
- `java.lang.String`: 문자열 상수 표현에 필요
- `java.lang.Thread`: 메인 스레드 객체
- `java.lang.System`: 표준 입출력, 시스템 프로퍼티

간단한 Hello World 프로그램 실행에도 약 450개 이상의 클래스가 이 단계에서 로드된다.

**System.initPhase1 / initPhase2 / initPhase3**

핵심 클래스가 로드된 후 세 단계 초기화가 순서대로 실행된다.

| Phase | 주요 역할 |
|---|---|
| `initPhase1` | VM 기본 프로퍼티 초기화, `sun.boot.library.path` 등 내부 경로 설정 |
| `initPhase2` | 모듈 시스템(JPMS) 부트스트랩, `ModuleBootstrap.boot()` 호출 |
| `initPhase3` | 시스템 클래스로더 설치, 표준 입출력(`System.in/out/err`) 초기화 |

Phase3가 완료되면 `System.setOut()`, `System.setIn()` 등이 정상 동작하는 완전한 자바 런타임이 갖춰진다.

### 5. 클래스 로딩과 링킹 단계

JVM 명세는 클래스 사용 전에 반드시 Loading → Linking → Initialization 순서를 거치도록 규정한다.

**Loading (로딩)**

클래스파일의 이진 표현(bytecode)을 찾아 메모리(메타스페이스)에 올린다. CDS 아카이브가 있는 경우 파일 시스템 접근 없이 매핑된 메모리에서 직접 읽는다.

**Linking (링킹)**

세 단계로 구성된다.

1. **Verification (검증)**: 클래스 구조가 JVM 명세를 준수하는지 확인한다. 타입 안전성, 제어 흐름 유효성 등을 검사한다. CDS 아카이브에서 로드된 클래스는 이미 검증된 상태이므로 이 단계를 생략한다.

2. **Preparation (준비)**: static 필드를 기본값으로 초기화한다. 정수형은 `0`, 참조형은 `null` 등으로 설정된다. 아직 개발자가 지정한 초기값은 반영되지 않는다.

3. **Resolution (해결)**: Constant Pool의 심볼릭 참조(예: 메서드 이름 + 디스크립터 문자열)를 실제 메모리 주소나 메서드 테이블 오프셋으로 교체한다. 이 단계는 **lazy**하게 수행된다. 즉, `invokespecial`, `invokevirtual`, `getstatic` 등의 바이트코드가 처음 실행될 때 해당 참조만 해결된다.

**Initialization (초기화)**

클래스의 `<clinit>` 메서드를 실행한다. static 블록과 static 필드 초기화 코드가 여기에 해당한다.

```java
class Config {
    // 이 두 라인이 <clinit>으로 컴파일됨
    static final int TIMEOUT = Integer.parseInt(System.getenv("TIMEOUT"));
    static {
        System.out.println("Config loaded");
    }
}
```

`<clinit>`은 클래스의 **최초 능동적 사용(first active use)** 시점에 딱 한 번 실행된다. 능동적 사용은 다음 경우에 해당한다.
- `new` 로 인스턴스 생성
- static 필드 읽기 / 쓰기 (`ConstantValue`로 컴파일되는 `static final` 상수 제외)
- static 메서드 호출
- 서브클래스 초기화 시 수퍼클래스 초기화

JVM은 `<clinit>` 실행을 스레드 안전하게 보호하며, 동시에 여러 스레드가 동일 클래스를 초기화하려 해도 단 한 번만 실행된다.

### 6. main 메서드 탐색과 실행

**메인 클래스 로드 및 시그니처 검증**

런처가 지정한 메인 클래스를 Application ClassLoader가 로드하고, JVM은 다음 시그니처를 가진 메서드를 찾는다.

```java
public static void main(String[] args)
```

이 시그니처가 없으면 `NoSuchMethodException`과 함께 종료된다. JDK 21부터 `void`가 아닌 반환형을 허용하는 방향으로 논의 중이다.

**애플리케이션 인자 전달**

런처가 파싱한 애플리케이션 인자들이 `String[]` 배열로 변환되어 `main(args)`에 전달된다.

**종료 절차**

`main` 메서드가 정상 반환되거나 `System.exit(code)`가 호출되면 JVM 종료 시퀀스가 시작된다.

1. **Shutdown Hook 실행**: `Runtime.getRuntime().addShutdownHook(thread)`로 등록된 스레드들이 병렬로 실행된다. 실행 순서는 보장되지 않는다.
2. **Finalizer 실행**: `System.runFinalizersOnExit(true)`(사용 지양)가 활성화된 경우, 미실행 finalizer들을 실행한다.
3. **JVM 종료**: 모든 Hook과 Finalizer가 완료되면 JVM 프로세스가 종료된다.

주의사항: `SIGKILL` (`kill -9`) 또는 OS 강제 종료 시 Shutdown Hook은 실행되지 않는다.

### 한 눈에 보기

```
java 런처 실행(환경변수·인자 파싱, libjvm 로딩) → JNI_CreateJavaVM(JVM 인스턴스 생성)
  → VM 런타임 초기화(GC·힙·메타스페이스·CDS·인터프리터) → 부트스트랩 클래스 로딩(코어 클래스 + System.initPhase1~3)
  → 클래스 로딩·링킹(Load → Verify → Prepare → Resolve → <clinit>) → main 탐색·실행 → 종료(Shutdown Hook → JVM halt)
```

> 한 줄 요약: **런처가 네이티브로 JVM을 띄우고 → JVM이 코어 클래스를 부팅한 뒤 → 그 위에서 `main`을 실행**한다.

## 핵심 정리

- JVM 시작은 "런처가 네이티브로 JVM을 띄우고, JVM이 자바 코어 클래스를 부팅한 뒤, 그 위에서 main을 실행"하는 다층 구조다.
- `JAVA_TOOL_OPTIONS`는 JVM 내부(`JNI_CreateJavaVM`)에서 처리되고, `JDK_JAVA_OPTIONS`는 런처 수준에서 처리되어 명령행 앞에 prepend된다.
- `System.initPhaseN`은 모듈 시스템과 핵심 런타임을 단계적으로 켜는 핵심 진입점이다.
- 클래스는 필요 시점에 lazy하게 로딩/초기화되며, `<clinit>`은 최초 능동 사용 시 단 한 번 실행된다.
- CDS는 부트스트랩 클래스 로딩 비용을 줄여 시작 시간을 단축하는 대표 기법이다.

## 기술적 한계와 보완 전략

- 클래스 로딩/링킹/JIT warm-up으로 인한 초기 기동 지연 → CDS/AppCDS, AOT(JEP 483 / Project Leyden), CRaC로 보완
- 다수 클래스 초기화로 인한 startup latency → lazy initialization 활용 및 의존성 정리
- 컨테이너 환경에서의 자원 인식 문제 → `UseContainerSupport`, 적절한 힙/CPU 옵션 설정
- Shutdown Hook 미실행 위험 → 신호 기반 강제 종료보다 graceful shutdown 설계 우선

## 키워드

### java launcher
`java` 실행 파일을 가리키며, JVM 공유 라이브러리(`libjvm.so`)를 동적 로드하고 `JNI_CreateJavaVM`을 호출해 JVM 인스턴스를 생성하는 네이티브 부트스트랩 프로그램이다. VM 옵션 파싱, 클래스패스 결정, 환경 변수 처리를 담당한다.

### JNI_CreateJavaVM
JNI Invocation API의 핵심 함수. 이 함수 한 번의 호출로 JVM 인스턴스 전체(힙, GC, 인터프리터, JIT, 메타스페이스 등)가 초기화된다. 반환값으로 `JavaVM *`과 `JNIEnv *` 핸들을 제공하며, `JAVA_TOOL_OPTIONS` 환경 변수도 이 함수 내부에서 처리된다.

### Bootstrap ClassLoader
JVM이 네이티브 코드로 직접 구현한 최상위 클래스로더. `java.base` 모듈의 핵심 클래스(`Object`, `String`, `Class`, `Thread` 등)를 로드한다. 자바 코드로 접근하면 `null`을 반환하는 특수한 클래스로더다.

### System.initPhase
`java.lang.System`의 패키지-프라이빗 static 메서드로, JVM이 VM 네이티브 코드에서 직접 호출한다. Phase1은 VM 기본 프로퍼티, Phase2는 모듈 시스템(JPMS) 부트스트랩, Phase3는 시스템 클래스로더 및 표준 입출력 초기화를 담당한다.

### Class Linking
Loading 이후 클래스가 실행 가능한 상태로 전환되는 과정. Verification(구조 검증) → Preparation(static 필드 기본값 설정) → Resolution(심볼릭 참조 해결)의 세 단계로 구성된다. Resolution은 lazy하게 수행된다.

### clinit
클래스 초기화 메서드(`<clinit>`)의 JVM 내부 표현. static 블록과 static 필드 초기화 코드가 컴파일러에 의해 단일 `<clinit>` 메서드로 합성된다. 클래스의 최초 능동적 사용 시점에 JVM이 단 한 번 호출하며, 멀티스레드 환경에서도 안전하게 단 한 번만 실행됨이 보장된다.

### Class Data Sharing (CDS)
사전에 핵심 클래스의 로딩·검증·레이아웃 계산 결과를 `.jsa` 아카이브 파일에 저장해 두고, JVM 시작 시 이를 read-only 메모리에 매핑해 재사용하는 최적화 기법. JDK 12부터 `-Xshare:auto`가 기본값이며 약 33%의 시작 시간 단축 효과를 낸다. AppCDS는 이를 애플리케이션 클래스까지 확장해 최대 50%까지 개선 가능하다.

### Template Interpreter
HotSpot VM이 JIT 컴파일 이전에 바이트코드를 실행하기 위해 사용하는 인터프리터. 각 바이트코드 명령어에 대응하는 네이티브 코드 조각(template)을 JVM 시작 시점에 미리 생성해 둔다. 순수 switch-dispatch 인터프리터보다 빠르며, JIT 컴파일 대상이 결정되기 전까지의 실행을 담당한다.

### Lazy Initialization
클래스 초기화(`<clinit>` 실행)를 해당 클래스가 실제로 사용되는 시점까지 미루는 전략. JVM 명세가 보장하는 기본 동작이다. 사용되지 않는 클래스는 초기화되지 않으므로 불필요한 자원 낭비와 시작 지연을 방지한다. Resolution 단계도 같은 방식으로 lazy하게 동작한다.

### main 메서드
`public static void main(String[] args)` 시그니처를 가진 자바 애플리케이션의 진입점. JVM은 런처가 지정한 클래스에서 이 시그니처를 탐색하며, 없으면 `NoSuchMethodException`으로 종료한다. main이 반환되거나 `System.exit()`가 호출되면 Shutdown Hook → Finalizer → JVM 종료의 순서로 정리 절차가 진행된다.
