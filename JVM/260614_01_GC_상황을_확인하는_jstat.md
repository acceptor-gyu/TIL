# GC 상황을 확인하는 jstat

## 개요
JVM의 GC 동작과 힙 메모리 사용 현황을 실시간으로 모니터링할 수 있는 표준 도구인 `jstat`(JVM Statistics Monitoring Tool)에 대해 정리한다.

## 상세 내용

### jstat이란
- JDK에 기본 포함된 JVM 통계 모니터링 CLI 도구
- 별도 에이전트 없이 실행 중인 JVM의 클래스 로딩, 컴파일, GC, 힙 영역별 사용량을 조회한다
- HotSpot JVM에 대해 설계된 실험적 도구(experimental tool)로, 출력 포맷이 버전마다 달라질 수 있다
- 원격 JVM 모니터링 시에는 대상 호스트에서 `jstatd` 데몬이 실행되어 있어야 한다

### 기본 사용법

```bash
jstat [outputOptions] [-t] [-h lines] <vmid> [interval[s|ms] [count]]
```

| 파라미터 | 설명 |
|---------|------|
| `vmid` | 모니터링할 JVM의 로컬 PID (또는 원격 JVM 식별자) |
| `interval` | 출력 주기. 숫자만 쓰면 ms, `s` 접미어 사용 시 초 단위 |
| `count` | 출력 횟수. 생략 시 무한 반복 |
| `-t` | 첫 번째 컬럼에 JVM 시작 이후 경과 시간(초) 추가 |
| `-h n` | n개의 샘플마다 헤더를 반복 출력 |

**예시: 1초 간격으로 10회 gcutil 출력**
```bash
jstat -gcutil 12345 1000 10
```

**예시: 타임스탬프 포함, 헤더 3줄마다 반복**
```bash
jstat -t -gcutil -h3 12345 1000
```

**예시: 원격 JVM 모니터링**
```bash
jstat -gcutil 40496@remote.domain 1000
```

### 주요 옵션

| 옵션 | 설명 |
|------|------|
| `-gc` | 각 힙 영역(Eden, Survivor, Old, Metaspace)의 절대 용량/사용량(kB) |
| `-gcutil` | 각 영역 사용률(%)과 GC 횟수/소요 시간 |
| `-gccause` | `-gcutil`과 동일하나 마지막/현재 GC 발생 원인 컬럼 추가 |
| `-gcnew` | Young generation(Eden + Survivor) 영역 상세 통계 |
| `-gcold` | Old generation 및 Metaspace 상세 통계 |
| `-gcnewcapacity` | Young 영역 용량 변화 추이 |
| `-gcoldcapacity` | Old 영역 용량 변화 추이 |
| `-gcmetacapacity` | Metaspace 용량 변화 추이 |
| `-class` | 클래스 로딩/언로딩 통계 |
| `-compiler` | JIT 컴파일 통계 |
| `-printcompilation` | 최근 JIT 컴파일된 메서드 목록 |

### 출력 컬럼 해석

#### -gc 옵션 주요 컬럼

| 컬럼 | 의미 |
|------|------|
| S0C / S1C | Survivor Space 0 / 1 현재 용량 (kB) |
| S0U / S1U | Survivor Space 0 / 1 현재 사용량 (kB) |
| EC / EU | Eden Space 용량 / 사용량 (kB) |
| OC / OU | Old Space 용량 / 사용량 (kB) |
| MC / MU | Metaspace 용량 / 사용량 (kB) |
| CCSC / CCSU | Compressed Class Space 용량 / 사용량 (kB) |
| YGC / YGCT | Young GC 횟수 / 총 소요 시간 (초) |
| FGC / FGCT | Full GC 횟수 / 총 소요 시간 (초) |
| GCT | 전체 GC 총 소요 시간 (초) |

#### -gcutil 옵션 주요 컬럼

| 컬럼 | 의미 |
|------|------|
| S0 / S1 | Survivor Space 0 / 1 사용률 (%) |
| E | Eden Space 사용률 (%) |
| O | Old Space 사용률 (%) |
| M | Metaspace 사용률 (%) |
| CCS | Compressed Class Space 사용률 (%) |
| YGC / YGCT | Young GC 횟수 / 총 소요 시간 (초) |
| FGC / FGCT | Full GC 횟수 / 총 소요 시간 (초) |
| GCT | 전체 GC 총 소요 시간 (초) |

#### -gccause 추가 컬럼

| 컬럼 | 의미 |
|------|------|
| LGCC | 마지막 GC의 발생 원인 (Last GC Cause) |
| GCC | 현재 진행 중인 GC의 원인 (Current GC Cause) |

대표적인 LGCC/GCC 값 예시:
- `Allocation Failure`: Eden 영역이 꽉 차서 새 객체 할당 실패
- `G1 Humongous Allocation`: G1GC에서 대형 객체(region 크기의 50% 초과) 할당
- `System.gc()`: 명시적 GC 호출
- `Metadata GC Threshold`: Metaspace 임계치 초과
- `No GC`: 현재 GC 없음

#### -gcnew 추가 컬럼

| 컬럼 | 의미 |
|------|------|
| TT | Tenuring Threshold. 객체가 Old 영역으로 승격되기까지 살아남아야 하는 Young GC 횟수 |
| MTT | Maximum Tenuring Threshold |
| DSS | Desired Survivor Size. JVM이 목표로 하는 Survivor 영역 사용량 (kB) |

### 활용 시나리오

#### Full GC 빈도 및 STW 시간 추적
```bash
jstat -gcutil -h5 <pid> 1000
```
- FGC 값이 빠르게 증가하거나 FGCT 누적 시간이 크다면 Full GC로 인한 STW(Stop-The-World)가 성능에 영향을 주고 있는 것이다
- GCT 대비 FGCT 비율이 높으면 Full GC가 전체 GC 시간을 지배하고 있다는 신호

#### 메모리 누수(Old 영역 지속 증가) 진단
```bash
jstat -gcutil <pid> 5000
```
- Young GC가 반복되어도 O(Old 사용률)이 꾸준히 상승한다면 메모리 누수를 의심한다
- 해제되지 않는 객체가 Old 영역을 점유하므로 결국 Full GC → OOM으로 이어진다

#### GC 원인 확인
```bash
jstat -gccause <pid> 1000
```
- LGCC에서 `Allocation Failure`가 반복되면 Eden/Heap 크기 조정 검토
- `Metadata GC Threshold`가 반복되면 `-XX:MetaspaceSize` / `-XX:MaxMetaspaceSize` 튜닝 필요

#### GC 튜닝 전후 비교
- GC 옵션 변경 전 YGC, YGCT, FGC, FGCT를 일정 시간 동안 수집한 뒤
- 옵션 변경 후 동일 조건에서 재수집하여 횟수와 소요 시간 감소 여부를 비교한다

### 실행 예시 출력 해석

```
$ jstat -gcutil 12345 1000 5

  S0     S1     E      O      M     CCS    YGC     YGCT    FGC    FGCT     GCT
  0.00  85.32  72.41  66.80  95.52  89.14      7    0.300     0    0.000    0.300
  0.00  85.32  91.23  66.80  95.52  89.14      7    0.300     0    0.000    0.300
  0.00   0.00   3.11  68.10  95.52  89.14      8    0.342     0    0.000    0.342
```

- 두 번째에서 세 번째 행 사이에 E(Eden)가 91% → 3%로 떨어지고 YGC가 7→8로 증가: Young GC 발생
- O(Old)가 66.80% → 68.10%로 소폭 상승: Young GC 이후 승격된 객체가 Old에 추가됨
- FGC = 0이므로 Full GC는 아직 발생하지 않은 상태

## 핵심 정리
- `jstat`은 실행 중인 JVM의 GC와 힙 상태를 주기적으로 관찰하는 경량 도구이다.
- `-gcutil`로 영역별 사용률을, `-gccause`로 GC 원인을 빠르게 파악할 수 있다.
- FGC(Full GC) 횟수와 FGCT가 급증하면 성능 문제를 의심해야 한다.
- Old 영역 사용률(O)이 GC 후에도 지속적으로 우상향하면 메모리 누수의 강력한 신호다.

## 기술적 한계와 보완 전략
- 스냅샷 기반 폴링이라 폴링 주기 사이의 순간적 변화는 놓칠 수 있다 → GC 로그(`-Xlog:gc*`)나 JFR(Java Flight Recorder)과 병행 활용
- 원인 분석보다는 현상 관찰에 적합하다 → 힙 덤프(`jmap -dump`), 프로파일러(VisualVM, async-profiler)로 보완
- 출력 포맷이 JDK 버전 간에 변경될 수 있어 자동화 스크립트 파싱 용도로는 적합하지 않다

## 키워드

### jstat
JDK에 내장된 JVM 통계 모니터링 CLI 도구. 실행 중인 JVM 프로세스의 GC, 힙 영역별 사용량, 클래스 로딩, JIT 컴파일 통계를 주기적으로 폴링하여 출력한다.

### GC 모니터링
GC 발생 횟수, 소요 시간, 힙 영역별 사용률 변화를 지속적으로 관찰하는 행위. 성능 이상 탐지, 튜닝 효과 검증, 메모리 누수 진단의 첫 단계다.

### JVM Statistics
JVM이 수집하는 내부 성능 지표의 총칭. jstat은 이를 외부에서 조회하는 인터페이스를 제공한다. 클래스 로딩 횟수, GC 이벤트, JIT 컴파일 통계 등을 포함한다.

### gcutil
jstat의 옵션 중 하나. 각 힙 영역(Eden, Survivor, Old, Metaspace)의 사용률을 퍼센트(%)로 표시하며 GC 횟수와 소요 시간도 함께 보여준다. 절대 용량보다 비율 위주로 빠르게 상태를 파악할 때 유용하다.

### gccause
jstat의 옵션 중 하나. `-gcutil`의 모든 정보에 더해 LGCC(마지막 GC 원인)와 GCC(현재 GC 원인)를 추가로 표시한다. GC가 왜 발생했는지 빠르게 파악하는 데 유용하다.

### Full GC
Old 영역 전체를 대상으로 수행하는 GC. Young GC(Minor GC)에 비해 수행 시간이 길고 STW(Stop-The-World) 시간도 크다. jstat에서는 FGC(횟수), FGCT(소요 시간)로 확인한다.

### Young GC
Eden 영역이 꽉 찼을 때 Young generation(Eden + Survivor)을 대상으로 수행하는 GC. Minor GC라고도 부른다. jstat에서는 YGC(횟수), YGCT(소요 시간)으로 확인한다.

### 힙 영역
JVM의 객체 저장 공간. Young generation(Eden + Survivor 0/1)과 Old generation, 그리고 클래스 메타데이터를 저장하는 Metaspace로 구성된다. jstat은 각 영역의 용량과 사용량을 별도 컬럼으로 제공한다.

### STW (Stop-The-World)
GC 수행 중 모든 애플리케이션 스레드가 일시 정지되는 현상. Full GC에서 STW 시간이 길어지면 응답 지연이나 타임아웃으로 이어질 수 있다.

### 메모리 누수 진단
애플리케이션이 더 이상 사용하지 않는 객체를 참조로 인해 GC가 회수하지 못하는 상태를 탐지하는 과정. jstat에서 Young GC 이후에도 Old 영역 사용률이 꾸준히 오르면 누수를 의심한다.
