# 5가지 GC 방식

## 개요
HotSpot JVM이 제공하는 대표적인 5가지 Garbage Collector(Serial, Parallel, CMS, G1, ZGC)의 내부 동작 방식, 수집 단계, 적합한 환경을 비교한다. 앞선 TIL에서 GC 알고리즘(Mark-Sweep, Copying 등)의 이론적 차이를 다뤘다면, 이번에는 각 컬렉터가 실제로 어떤 단계를 거쳐 수집을 수행하는지에 집중한다.

## 상세 내용

### 1. Serial GC

**활성화 플래그**: `-XX:+UseSerialGC`

#### 구조

```
Heap
├── Young Generation
│   ├── Eden
│   ├── Survivor0 (From)
│   └── Survivor1 (To)
└── Old Generation
```

#### 동작 방식

**Minor GC (Young 영역)**
1. Eden이 꽉 차면 GC 발생, **단일 스레드**로 STW
2. Eden + Survivor(From)의 살아있는 객체를 Survivor(To)로 **복사(Copying)**
3. Age 임계값(`-XX:MaxTenuringThreshold`, 기본 15)을 초과한 객체는 Old 영역으로 **승격(Promotion)**
4. Eden과 Survivor(From)은 통째로 비움, From/To 역할 교환

**Major GC (Old 영역)**
1. Old 영역이 꽉 차면 단일 스레드로 STW
2. GC Root에서 도달 가능한 객체 표시(Mark)
3. 표시되지 않은 객체 해제(Sweep)
4. 살아있는 객체를 연속된 공간으로 압축(Compact) → 단편화 없음

#### 특징 요약

| 항목 | 내용 |
|------|------|
| GC 스레드 수 | 1개 (단일) |
| Young 알고리즘 | Copying |
| Old 알고리즘 | Mark-Sweep-Compact |
| STW | GC 전 단계 |
| 적합 환경 | CLI 도구, 단일 CPU, 힙 < 100MB |

---

### 2. Parallel GC (Throughput Collector)

**활성화 플래그**: `-XX:+UseParallelGC` (Java 8 기본값)

#### Serial GC와의 차이

Serial GC와 **알고리즘은 동일**하지만, GC 스레드를 여러 개 사용한다는 점이 핵심 차이다.

```
Serial GC:   [GC Thread 1] ─────────────── Eden 전체 처리
Parallel GC: [GC Thread 1] ─── Eden 1/4
             [GC Thread 2] ─── Eden 2/4
             [GC Thread 3] ─── Eden 3/4
             [GC Thread 4] ─── Eden 4/4
             (병렬 처리로 STW 시간 단축)
```

#### GC 스레드 수 결정 공식

```
CPU 수 <= 8:  GC 스레드 = CPU 수
CPU 수 >  8:  GC 스레드 = 3 + (CPU 수 * 5 / 8)
```

수동 지정: `-XX:ParallelGCThreads=N`

#### Throughput 목표 설정

Parallel GC는 다음 두 목표 파라미터로 자동 조정된다.

- `-XX:MaxGCPauseMillis=<ms>`: 최대 Pause 목표 (힙 크기 자동 축소로 달성 시도)
- `-XX:GCTimeRatio=<N>`: GC 시간 비율 목표, 전체 실행 시간 중 `1/(1+N)` 이하 유지 (기본값 99 → GC 1% 이하)

#### 특징 요약

| 항목 | 내용 |
|------|------|
| GC 스레드 수 | 멀티 (CPU 수 기반) |
| Young 알고리즘 | Parallel Copying |
| Old 알고리즘 | Parallel Mark-Sweep-Compact |
| STW | GC 전 단계 (단, 병렬로 빠름) |
| 적합 환경 | 배치 처리, ETL, 처리량 우선 서버 |

---

### 3. CMS GC (Concurrent Mark-Sweep)

**활성화 플래그**: `-XX:+UseConcMarkSweepGC`
**상태**: Java 9 deprecated, Java 14에서 완전 제거 (JEP 363)

#### 설계 목표

Old 영역 GC를 애플리케이션과 **동시(Concurrent)** 수행하여 STW 시간을 최소화한다. Young 영역은 Serial/Parallel과 동일하게 Copying 방식으로 처리한다.

#### Old 영역 수집 단계 (6단계)

```
1. Initial Mark       [STW]  ← 짧음
   └── GC Root에서 직접 참조되는 객체만 표시 (depth 1)

2. Concurrent Mark    [동시]  ← 오래 걸림
   └── Initial Mark에서 찾은 객체를 시작으로 전체 힙 탐색

3. Concurrent Preclean [동시]
   └── Concurrent Mark 중 변경된 참조를 미리 처리

4. Remark             [STW]  ← 짧음
   └── Concurrent Mark 중 변경된 객체를 재확인

5. Concurrent Sweep   [동시]  ← 오래 걸림
   └── 표시되지 않은 객체 해제 (이동/압축 없음)

6. Concurrent Reset   [동시]
   └── 다음 CMS 수집을 위한 내부 데이터 구조 초기화
```

STW는 1단계(Initial Mark)와 4단계(Remark)에서만 발생하므로 Pause 시간이 짧다.

#### 치명적 단점: 단편화와 Concurrent Mode Failure

CMS는 **Compact 단계가 없다**. Sweep 이후 해제된 공간이 파편화되고, 결국 큰 객체를 위한 연속 공간이 부족해진다.

두 가지 실패 시나리오:
1. **Promotion Failure**: Young 영역에서 승격할 공간이 Old에 없을 때 → Full GC(단일 스레드 STW) 발생
2. **Concurrent Mode Failure**: Concurrent Sweep이 완료되기 전에 Old가 꽉 찰 때 → Full GC 발생

이 두 실패는 매우 긴 STW를 유발하며, CMS의 저지연 장점을 완전히 무너뜨린다.

#### Deprecated 배경

- 단편화 문제 근본 해결 불가
- G1 GC가 저지연과 Compaction을 모두 제공하며 실질적인 후계자가 됨
- Shenandoah, ZGC의 등장으로 더 이상 유지 가치가 없다고 판단

### 4. G1 GC (Garbage First)

**활성화 플래그**: `-XX:+UseG1GC` (Java 9+ 기본값)

#### Region 기반 힙 구조

G1 GC는 기존의 연속적인 Young/Old 분리 대신 힙을 **1MB~32MB 크기의 동일한 Region**으로 분할한다.

```
힙 크기에 따른 Region 크기 결정:
  목표: 전체 Region 수가 약 2048개
  예)  4GB 힙 → Region 크기 2MB
      32GB 힙 → Region 크기 16MB
수동 지정: -XX:G1HeapRegionSize=N
```

각 Region은 동적으로 역할이 부여된다.

```
┌───┬───┬───┬───┬───┬───┬───┬───┐
│ E │ S │ O │ E │ H │ H │ O │ S │  E: Eden
├───┼───┼───┼───┼───┼───┼───┼───┤  S: Survivor
│ O │ E │ E │ O │ O │ E │ S │ O │  O: Old
└───┴───┴───┴───┴───┴───┴───┴───┘  H: Humongous
```

Region의 역할은 GC 사이클마다 재배정된다. 이 유연성이 Pause 예측을 가능하게 한다.

#### 수집 단계

**Young-only Collection (Minor GC)**
- Eden Region이 꽉 차면 발생
- Eden + Survivor Region에서 살아있는 객체를 새 Survivor/Old Region으로 이동
- STW이지만 멀티 스레드로 빠르게 처리

**Concurrent Marking Cycle**
```
1. Initial Mark      [STW, Minor GC와 편승]
   └── GC Root 직접 참조 표시

2. Root Region Scan  [동시]
   └── Survivor Region에서 Old 참조 스캔

3. Concurrent Mark   [동시]
   └── 전체 힙 도달 가능 객체 표시

4. Remark            [STW]
   └── SATB(Snapshot-At-The-Beginning) 버퍼 처리, 빈 Region 회수

5. Cleanup           [STW + 동시]
   └── 완전히 비어있는 Region 즉시 회수, 다음 Mixed GC를 위한 후보 목록 작성
```

**Mixed GC**
- Concurrent Marking 완료 후 실행
- Young Region + **가비지 비율이 높은 Old Region** 함께 수집
- `MaxGCPauseMillis` 목표에 맞게 몇 개의 Old Region을 수집할지 예측 모델로 결정
- 여러 번 반복 실행되며 Old Region을 점진적으로 비움

#### Humongous Object 처리

Region 크기의 **절반 이상**인 객체는 Humongous Object로 분류된다.

```
Region 크기 2MB → 1MB 이상 객체가 Humongous
```

- Old Generation의 연속된 Region에 직접 할당됨
- Young GC 대상이 아님 → 오래 살아남는 경향
- Concurrent Marking Cleanup 단계 또는 Full GC에서만 회수
- 배열 타입(`int[]`, `byte[]` 등) Humongous 객체는 예외적으로 Minor GC에서도 회수 시도

#### Pause 예측 모델

G1은 내부적으로 **각 Region의 GC 소요 시간을 통계로 추적**하여 `MaxGCPauseMillis` 목표에 맞는 Collection Set(수집할 Region 목록)을 동적으로 결정한다.

```
-XX:MaxGCPauseMillis=200  (기본값 200ms)
```

이 값이 너무 작으면 Old Region 수집을 줄여 목표를 맞추려 하지만, 그 결과 Old 영역이 쌓여 Full GC로 이어질 수 있다.

#### 특징 요약

| 항목 | 내용 |
|------|------|
| 힙 구조 | Region 기반 (1~32MB) |
| Young 알고리즘 | Parallel Copying |
| Old 알고리즘 | Concurrent Mark + Incremental Compaction |
| STW | Initial Mark, Remark, Cleanup 일부 |
| 적합 환경 | 대부분의 서버 애플리케이션, 힙 4GB~수십 GB |

### 5. ZGC / Shenandoah (저지연 차세대 GC)

#### ZGC

**활성화 플래그**: `-XX:+UseZGC`
**상태**: Java 15 production-ready, JDK 21부터 Generational ZGC 도입, JDK 23부터 Generational이 기본

##### Colored Pointer (컬러 포인터)

ZGC의 핵심 기술은 **64비트 포인터의 상위 비트에 GC 메타데이터를 인코딩**하는 것이다.

```
64비트 포인터 레이아웃:
┌─────────┬────┬────┬──────┬────────────────────────────────────────┐
│ 사용 안함 │ M0 │ M1 │ Remap│           실제 객체 주소 (42비트)         │
└─────────┴────┴────┴──────┴────────────────────────────────────────┘
  18비트    1비트 1비트  1비트
```

- **Marked0/Marked1**: 현재 GC 사이클에서 표시 여부
- **Remapped**: 객체가 새 위치로 이동 완료되었는지 여부
- **Finalizable**: finalize() 호출이 필요한 객체

이 방식은 별도의 Mark 비트맵이나 메타데이터 테이블이 불필요하여 **메모리 효율**이 높다.

##### Load Barrier (로드 배리어)

애플리케이션 스레드가 힙에서 **참조를 읽을 때마다** JIT가 삽입한 작은 코드가 실행된다.

```java
// 애플리케이션 코드 (원본)
Object obj = someField;

// JIT 컴파일 후 (ZGC Load Barrier 삽입)
Object obj = someField;
if (obj.Remapped == 0) {  // 이동이 완료되지 않은 경우
    obj = forwardingTable[obj];  // 새 주소로 리다이렉트
    someField = obj;             // 참조 업데이트
}
```

이 배리어가 있기 때문에 ZGC는 **애플리케이션 실행 중에도 객체를 이동**시킬 수 있다. 배리어가 자동으로 최신 주소를 반환해주기 때문이다.

##### ZGC STW 단계

ZGC에서 STW는 극히 짧은 3개 단계에서만 발생한다.

```
1. Pause Mark Start    [STW, sub-ms]
   └── GC Root에서 직접 참조 표시 시작

2. Concurrent Mark     [동시]
   └── 전체 힙 도달 가능 객체 표시

3. Pause Mark End      [STW, sub-ms]
   └── 잔여 SATB 버퍼 처리

4. Concurrent Prepare for Relocation  [동시]
   └── 이동할 Region 선정, Forwarding Table 구성

5. Pause Relocate Start  [STW, sub-ms]
   └── GC Root 참조 업데이트 시작

6. Concurrent Relocate  [동시]
   └── 객체 실제 이동, Load Barrier가 앱 스레드의 참조 업데이트 처리
```

STW는 총 3번이며, 각각 힙 크기와 무관하게 sub-millisecond를 목표로 한다.

##### Generational ZGC (JDK 21+)

기존 ZGC는 Young/Old 세대 구분이 없어 CPU 오버헤드가 컸다. JDK 21에서 도입된 Generational ZGC는 Young/Old를 분리하여 단명 객체를 더 자주, 더 저렴하게 수집한다.

```
활성화: -XX:+UseZGC -XX:+ZGenerational  (JDK 21~22)
JDK 23부터는 -XX:+UseZGC만으로 Generational이 기본
```

#### Shenandoah GC

**활성화 플래그**: `-XX:+UseShenandoahGC`
**개발**: Red Hat, OpenJDK 포함 배포

ZGC와 동일하게 Concurrent Compaction을 지원하지만, 내부 구현이 다르다.

| 항목 | ZGC | Shenandoah |
|------|-----|------------|
| 동시 이동 방식 | Colored Pointer + Load Barrier | Brooks Pointer (forwarding pointer) |
| 메타데이터 위치 | 포인터 비트 | 객체 헤더 앞 8바이트 |
| 메모리 오버헤드 | 컬러 포인터 테이블 | 객체당 8바이트 추가 |
| 포함 배포 | OpenJDK | OpenJDK |

**Brooks Pointer**: 모든 객체의 헤더 앞에 forwarding pointer를 추가한다. 객체가 이동 중이면 Brooks Pointer가 새 주소를 가리켜, 어느 스레드가 접근하더라도 올바른 위치를 참조할 수 있다.

### GC 선택 기준 비교

#### Throughput vs Latency Trade-off

```
높은 Throughput ←─────────────────────────→ 낮은 Latency
Serial  →  Parallel  →  G1  →  Shenandoah / ZGC
(단순)     (병렬)      (균형)     (저지연 특화)
```

Throughput과 Latency는 반비례 관계다. 동시 GC 작업은 애플리케이션 CPU를 빼앗아 전체 처리량을 낮추고, STW를 줄이는 대신 CPU 오버헤드를 높인다.

#### 힙 크기와 코어 수에 따른 권장 GC

| 힙 크기 | 코어 수 | 권장 GC |
|--------|---------|---------|
| < 256MB | 1~2 | Serial GC |
| < 4GB | 4+ | Parallel GC (처리량 우선) 또는 G1 |
| 4GB ~ 32GB | 4+ | G1 GC (균형) |
| 32GB+ | 8+ | ZGC (JDK 21+ Generational) 또는 Shenandoah |
| TB급 | 많을수록 좋음 | ZGC |

#### 버전별 기본 GC 변천사

| Java 버전 | 기본 GC | 주요 변경 |
|-----------|---------|---------|
| Java 8 | Parallel GC | CMS가 주요 저지연 옵션 |
| Java 9 | G1 GC | CMS deprecated |
| Java 11 | G1 GC | ZGC 실험적 추가 (JEP 333) |
| Java 14 | G1 GC | CMS 완전 제거 (JEP 363) |
| Java 15 | G1 GC | ZGC production-ready (JEP 377) |
| Java 21 | G1 GC | Generational ZGC 도입 (JEP 439) |
| Java 23 | G1 GC | Generational ZGC가 기본 ZGC 모드 |

## 핵심 정리

- **핵심 포인트 1**: CMS는 Concurrent Mark-Sweep으로 STW를 Initial Mark와 Remark 두 단계로만 줄였지만, Compact 단계 부재로 인한 단편화가 치명적 약점이었다. G1은 Region을 점진적으로 이동·압축하여 이 문제를 해결했다.
- **핵심 포인트 2**: G1의 핵심 혁신은 Region 기반 힙 구조와 Pause 예측 모델이다. 수집할 Region을 `MaxGCPauseMillis` 목표에 맞게 동적으로 선정함으로써 처음으로 예측 가능한 Pause를 제공했다.
- **핵심 포인트 3**: ZGC는 Colored Pointer와 Load Barrier를 통해 객체 이동 자체를 동시 수행하여 힙 크기와 무관한 sub-millisecond Pause를 달성한다. 단, 이를 위한 CPU/메모리 오버헤드가 존재하므로 처리량 우선 환경에서는 Parallel GC가 여전히 유효하다.

## 기술적 한계와 보완 전략

- **ZGC/Shenandoah의 CPU 오버헤드**: 동시 GC 작업이 애플리케이션 스레드와 CPU를 경쟁하므로, 동시 처리량이 중요한 환경에서는 오히려 전체 성능이 저하될 수 있다. 배치 처리 환경에서는 Parallel GC 유지를 검토해야 한다.
- **ZGC의 힙 여유 공간 요구**: Concurrent Compaction 진행 중에도 새로운 객체 할당이 계속되므로, 힙 여유 공간(Headroom)이 부족하면 Allocation Stall이 발생한다. ZGC 사용 시 힙을 넉넉하게 설정해야 한다.
- **G1 Humongous Object 주의**: Region 크기 절반 이상의 객체가 잦으면 Old Region이 빠르게 차고 Full GC로 이어진다. Humongous 객체 할당 패턴을 GC 로그에서 모니터링하고, `-XX:G1HeapRegionSize`를 늘려 Humongous 분류 임계값을 높이는 것을 고려한다.
- **어떤 GC도 STW를 완전히 제거하지 못한다**: ZGC조차 Initial Mark, Relocate Start 등에서 매우 짧지만 STW가 발생한다. 절대적인 무중단이 필요한 환경은 없다는 점을 인지하고 SLA를 현실적으로 설정해야 한다.

## 키워드

- **Serial GC**: 단일 스레드로 Young(Copying) + Old(Mark-Sweep-Compact)를 순차 처리하는 가장 단순한 컬렉터. 소형 힙과 단일 CPU 환경에 적합하며, Footprint(메모리 오버헤드)가 가장 작다.
- **Parallel GC**: Serial GC와 동일한 알고리즘을 멀티 스레드로 병렬화한 컬렉터. Java 8의 기본 GC이며, 처리량(Throughput)을 극대화한다. STW 자체는 발생하지만 병렬 처리로 시간을 단축한다.
- **CMS (Concurrent Mark-Sweep)**: Old 영역 GC를 Initial Mark(STW) → Concurrent Mark → Remark(STW) → Concurrent Sweep의 4단계로 나눠 대부분을 동시 실행하는 컬렉터. Compact 부재로 인한 단편화가 치명적 결함이며 Java 14에서 제거됐다.
- **G1 GC (Garbage First)**: 힙을 1~32MB Region으로 분할하고, 가비지 비율이 높은 Region을 우선 수집(Garbage First)하여 `MaxGCPauseMillis` 목표를 달성하는 컬렉터. Mixed GC로 점진적 Old Region 수집이 가능하다. Java 9+ 기본값.
- **ZGC**: 64비트 포인터 상위 비트에 GC 메타데이터를 인코딩하는 Colored Pointer와 참조 읽기마다 실행되는 Load Barrier를 통해 객체 이동을 완전 동시 처리하는 컬렉터. 힙 크기와 무관하게 sub-millisecond Pause를 목표로 한다.
- **Shenandoah GC**: 모든 객체 헤더 앞에 8바이트 Brooks Pointer(forwarding pointer)를 추가하여 동시 압축(Concurrent Compaction)을 구현한 컬렉터. Red Hat이 개발하며 ZGC와 유사한 저지연을 제공한다.
- **Stop-The-World (STW)**: GC 수행 중 모든 애플리케이션 스레드를 Safepoint에서 강제 정지시키는 상태. 모든 GC 컬렉터에서 최소 일부 단계에서 발생하며, 저지연 GC의 설계 핵심 과제다.
- **Throughput vs Latency**: GC 선택의 핵심 트레이드오프. Throughput은 전체 실행 시간 중 GC에 소비되지 않는 비율, Latency는 개별 Pause의 최대/평균 시간이다. Concurrent GC는 STW를 줄이지만 동시 작업으로 CPU를 소비해 처리량이 낮아진다.
- **Region 기반 힙**: G1/ZGC처럼 힙 전체를 연속 영역이 아닌 고정 크기 Region으로 분할하는 구조. GC 대상을 일부 Region으로 한정하여 전체 힙 스캔 없이 부분 수집이 가능하고, Pause 시간 예측과 제어가 용이해진다.
- **Colored Pointer / Load Barrier**: ZGC의 핵심 기술. Colored Pointer는 포인터 비트에 GC 상태를 인코딩하고, Load Barrier는 참조 읽기 시 포인터 상태를 확인하여 필요 시 최신 주소로 업데이트한다. 이 조합으로 동시 객체 이동이 가능해진다.
