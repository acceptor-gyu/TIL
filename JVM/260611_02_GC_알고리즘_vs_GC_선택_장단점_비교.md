# GC 알고리즘 vs GC 선택: 장단점 비교

## 개요
GC "알고리즘"(Mark-Sweep, Mark-Compact, Copying 등)과 실제 "GC 구현체/컬렉터"(Serial, Parallel, CMS, G1, ZGC, Shenandoah)를 구분하고, 각각의 장단점을 비교하여 워크로드에 맞는 선택 기준을 정리한다.

## 상세 내용

### 1. GC 알고리즘 vs GC 컬렉터 개념 구분

많은 개발자들이 "G1 GC 알고리즘을 쓴다"고 말하지만 이는 엄밀히 표현하면 부정확하다.

| 구분 | 정의 | 예시 |
|------|------|------|
| **GC 알고리즘** | 객체를 회수하는 방법론(이론) | Mark-Sweep, Copying, Mark-Compact |
| **GC 컬렉터** | 알고리즘을 Young/Old 영역에 조합한 실제 구현체 | Serial, Parallel, G1, ZGC |

컬렉터는 내부적으로 여러 알고리즘을 혼합하여 사용한다. 예를 들어 Serial GC는 Young 영역에 Copying 알고리즘, Old 영역에 Mark-Compact 알고리즘을 사용한다.

**둘을 혼동하면 안 되는 이유**: 알고리즘 수준의 이해 없이 컬렉터를 선택하면 튜닝 방향을 잡을 수 없다. 예를 들어 "단편화가 발생했다"는 문제는 Mark-Sweep 알고리즘의 한계임을 알아야 해결책을 찾을 수 있다.

### 2. 기본 GC 알고리즘 비교

#### Reference Counting의 한계
객체가 참조될 때마다 카운트를 증가시키고, 0이 되면 즉시 회수하는 방식이다.

- **장점**: STW 없이 실시간으로 메모리 회수 가능
- **치명적 단점**: 순환 참조(Circular Reference) 해결 불가
  - `A → B → A` 처럼 서로 참조하면 카운트가 영구적으로 0이 되지 않아 메모리 누수 발생
- JVM은 이 이유로 Reference Counting을 기본 전략으로 사용하지 않는다

#### Mark-Sweep

```
[Mark 단계]  GC Root에서 도달 가능한 모든 객체에 표시
[Sweep 단계] 표시되지 않은 객체의 메모리를 해제
```

- **장점**: 살아있는 객체를 이동시키지 않으므로 참조 포인터 업데이트 불필요
- **단점**: 메모리 단편화(Fragmentation) 발생 → 큰 객체 할당 실패 가능

#### Mark-Compact

```
[Mark 단계]  도달 가능한 객체 표시
[Compact 단계] 살아있는 객체를 힙의 한쪽 끝으로 압축 이동
[포인터 업데이트] 이동된 객체를 가리키는 모든 참조 갱신
```

- **장점**: 단편화 없음, 새 객체 할당이 bump-the-pointer 방식으로 매우 빠름
- **단점**: Compact 단계에서 객체 이동과 포인터 업데이트 비용이 높음 → STW 시간 증가

#### Copying (Scavenge)

```
힙을 From-Space / To-Space로 절반씩 분할
살아있는 객체만 To-Space로 복사 → From-Space 전체를 한번에 해제
역할 전환: To-Space가 새 From-Space가 됨
```

- **장점**: 단편화 없음, 죽은 객체가 많을수록 빠름(Young 영역 특성에 최적)
- **단점**: 힙의 절반만 사용 가능(공간 낭비), 살아있는 객체가 많으면 복사 비용 급증

#### Generational(세대별) GC 가설

JVM GC 설계의 핵심 전제: **대부분의 객체는 짧게 살다가 죽는다(Weak Generational Hypothesis)**.

이를 기반으로 힙을 두 영역으로 분리한다.

| 영역 | 대상 | 적용 알고리즘 |
|------|------|--------------|
| **Young Generation** | 새로 생성된 객체 | Copying (빠른 Minor GC) |
| **Old Generation** | 오래 살아남은 객체 | Mark-Compact (Major GC) |

Young 영역에서 일정 횟수 이상 살아남은 객체는 Old 영역으로 **승격(Promotion)** 된다.

### 3. GC 컬렉터별 특징과 장단점

#### Serial GC (`-XX:+UseSerialGC`)

- **구조**: Young - Copying / Old - Mark-Compact, **단일 스레드**
- **STW**: GC 동안 애플리케이션 스레드 전부 정지
- **장점**: 오버헤드가 적고 단순함
- **단점**: 멀티코어 활용 불가, 힙이 커질수록 Pause 폭발적 증가
- **적합**: CLI 도구, 소형 임베디드, 단일 코어 환경

#### Parallel GC (`-XX:+UseParallelGC`, Java 8 기본값)

- **구조**: Serial GC와 동일 알고리즘이지만 **GC 스레드 다중화**
- **STW**: GC 동안 모두 정지하지만 GC 자체는 병렬 처리
- **장점**: 처리량(Throughput) 극대화
- **단점**: Pause 시간이 길고 예측 불가능
- **적합**: 배치 처리, ETL, Pause 시간보다 처리량이 중요한 워크로드

#### CMS (Concurrent Mark Sweep) - deprecated

- **구조**: Young - Copying / Old - **Concurrent Mark-Sweep**
- **STW**: Initial Mark + Remark 두 단계만 STW, 나머지는 애플리케이션과 동시 실행
- **장점**: Old GC에서의 Pause 시간 대폭 감소
- **단점**:
  - Compact 단계 없음 → **단편화** 발생 → Concurrent Mode Failure 시 Full GC 발생
  - 동시 마킹으로 인한 **CPU 오버헤드** 증가
  - Java 9에서 deprecated, Java 14에서 제거됨
- **교훈**: 저지연을 위해 Compact를 포기하면 결국 단편화로 무너진다

#### G1 GC (`-XX:+UseG1GC`, Java 9+ 기본값)

- **구조**: 힙을 **1MB~32MB 크기의 Region**으로 분할, 각 Region은 동적으로 Eden/Survivor/Old 역할 부여
- **핵심 개념**:
  - Young-only Collection: Eden과 Survivor Region만 수집
  - Mixed Collection: Young Region + 가비지 비율이 높은 Old Region 함께 수집
  - `MaxGCPauseMillis` 목표에 맞춰 Collection Set 크기를 예측 모델로 동적 조정
- **장점**: 예측 가능한 Pause 목표 설정, 대형 힙에서 안정적
- **단점**: Remembered Set 유지 비용, Region 단편화, 튜닝 파라미터 복잡
- **적합**: 대부분의 서버 애플리케이션, 4GB~수십 GB 힙

#### ZGC (`-XX:+UseZGC`, Java 15 production-ready)

- **핵심 기술**: **컬러 포인터(Colored Pointers)** - 64비트 포인터의 상위 비트에 메타데이터(Marked0/Marked1/Remapped/Finalizable)를 저장
- **동작**: 힙을 Z-Page 단위로 분할, Load Barrier를 통해 객체 이동을 애플리케이션과 **완전 동시** 진행
- **STW**: Initial Mark, Remap Root 등 극히 짧은 단계만 STW (sub-millisecond)
- **JDK 21+**: Generational ZGC 도입으로 Young/Old 분리 → CPU 효율 대폭 개선
- **장점**: 힙 크기에 무관하게 1ms 미만 Pause 목표
- **단점**: Load Barrier와 동시 재배치로 인한 **CPU/메모리 오버헤드** 상당함
- **적합**: 초저지연이 필요한 대규모 힙 환경 (수십~수백 GB), JDK 21+ 환경

#### Shenandoah GC (`-XX:+UseShenandoahGC`, Red Hat 개발)

- **핵심 기술**: **Brooks Pointer** - 모든 객체 헤더에 forwarding pointer 추가. 이동 중인 객체는 Brooks Pointer가 새 위치를 가리켜 동시 접근 지원
- **동작**: Concurrent Compaction - 압축(Compact)도 STW 없이 동시 진행
- **장점**: ZGC와 유사한 저지연, OpenJDK와 함께 배포
- **단점**: 객체당 추가 8바이트(Brooks Pointer) → 메모리 오버헤드, CPU 오버헤드 높음
- **적합**: ZGC와 유사한 초저지연 요구, Red Hat 기반 환경

### 4. 핵심 평가 지표

GC 선택은 항상 **세 가지 트레이드오프** 위에서 결정된다.

```
         Throughput(처리량)
              /\
             /  \
            /    \
           /      \
 Latency  /________\  Footprint
(지연시간)            (메모리 사용)
```

세 가지를 동시에 최적화하는 것은 불가능하다. 하나를 얻으면 다른 하나를 잃는다.

| 지표 | 설명 | 관련 GC |
|------|------|---------|
| **Throughput** | GC에 소비되지 않는 시간 비율 | Parallel GC |
| **Latency** | 개별 Pause의 최대/평균 시간 | ZGC, Shenandoah |
| **Footprint** | GC 자체가 소비하는 메모리 | Serial GC |

#### STW(Stop-The-World) 시간 비교 (참고 수치)

| GC 컬렉터 | 평균 Pause 시간 |
|-----------|--------------|
| Serial GC | ~80ms |
| Parallel GC | ~45ms |
| G1 GC | ~60ms (목표 설정 가능) |
| Shenandoah | ~1ms |
| ZGC / GenZGC | ~0.03ms |

> 주의: 위 수치는 힙 크기, 객체 수명 분포, 하드웨어에 따라 크게 달라진다. 반드시 실제 환경에서 측정하라.

#### 힙 크기 확장성

- **Serial/Parallel**: 힙 증가 시 Pause 시간 선형 증가 → 대형 힙 부적합
- **G1**: Region 기반으로 Pause 상한선 제어 가능 → 중~대형 힙 적합
- **ZGC/Shenandoah**: 힙 크기에 거의 무관한 Pause → 대형 힙에서 진정한 가치 발휘

### 5. GC 선택 기준 (워크로드별)

#### 워크로드 유형별

| 워크로드 | 특징 | 권장 GC |
|---------|------|---------|
| 배치/ETL | 처리량 최우선, Pause 허용 가능 | Parallel GC 또는 G1 |
| REST API 서버 | 응답시간 SLA 존재 (<50ms) | G1 (일반), ZGC (엄격한 SLA) |
| 실시간 금융/게임 | sub-ms 지연 요구 | ZGC (JDK 21+) 또는 Shenandoah |
| CLI/소형 도구 | 작은 힙, 단순성 중요 | Serial GC |

#### 힙 크기별

| 힙 크기 | 권장 GC |
|--------|---------|
| < 1GB | Serial 또는 Parallel |
| 1GB ~ 8GB | G1 GC (기본값) |
| 8GB ~ 수십 GB | G1 또는 ZGC (JDK 21+) |
| 수백 GB | ZGC (Generational ZGC 필수) |

#### 컨테이너/클라우드 환경 고려사항

- JVM은 컨테이너 메모리 한도를 인식하지 못하는 문제가 있었으나 JDK 10+부터 `-XX:+UseContainerSupport`(기본 활성화)로 cgroup 한도를 자동 감지
- 컨테이너 환경에서 ZGC/Shenandoah의 동시 스레드 수가 CPU 쿼터를 초과하지 않도록 주의
- `-XX:ActiveProcessorCount`로 프로세서 수를 명시적으로 지정하는 것이 안전

### 6. GC 선택 시 흔한 오해와 함정

#### "최신 GC가 항상 좋다"는 오해

ZGC가 Pause 시간이 극히 짧지만, 동시 GC 작업으로 인한 **CPU 오버헤드**가 크다. 처리량이 중요한 배치 작업에서 ZGC를 적용하면 오히려 전체 처리 시간이 늘어날 수 있다.

```
잘못된 판단: "ZGC가 최신이니까 무조건 좋겠지"
올바른 판단: "이 서비스의 SLA와 리소스 환경에서 어느 GC가 최적인가"
```

#### 튜닝 없이 컬렉터만 바꾸는 함정

GC를 교체하면서 힙 크기, GC 스레드 수, Region 크기 등을 재조정하지 않으면 오히려 성능이 저하된다.

- G1으로 전환 시 `MaxGCPauseMillis`, `G1HeapRegionSize` 검토 필수
- ZGC로 전환 시 힙 여유 공간(Heap Headroom) 충분히 확보 필요 (동시 GC 중 신규 할당 공간 필요)

## 핵심 정리

- **핵심 포인트 1**: GC 알고리즘은 "방법론"이고, GC 컬렉터는 그 알고리즘을 Young/Old 영역별로 조합한 "구현체"다. 컬렉터를 선택할 때는 내부 알고리즘의 장단점을 이해해야 한다.
- **핵심 포인트 2**: 모든 GC는 **처리량·지연시간·메모리**의 트레이드오프 위에서 선택된다. 세 가지를 동시에 달성하는 GC는 존재하지 않는다.
- **핵심 포인트 3**: 정답 컬렉터는 없다. 워크로드 특성(배치 vs 실시간), 힙 크기, SLA, 가용 CPU 리소스에 따라 최선의 선택이 달라진다. 반드시 실제 환경에서 측정하라.

---

## 기술적 한계와 보완 전략

- 저지연 GC(ZGC/Shenandoah)도 동시 작업으로 인한 CPU·메모리 오버헤드가 존재한다 → 힙 여유 공간(Headroom)을 충분히 확보하고 CPU 쿼터에 주의
- 어떤 GC도 STW를 완전히 제거하지는 못한다 (Initial Mark, Safepoint 등) → SLA에 맞는 Pause 목표를 설정하고 GC 로그와 JVM 메트릭을 지속적으로 모니터링
- GC 선택 후에는 JVM 플래그 튜닝, 힙 크기 조정, 애플리케이션 코드 최적화(객체 할당 패턴)를 함께 진행해야 최대 효과를 얻을 수 있다

## 키워드

- **Mark-Sweep**: GC Root에서 도달 가능한 객체를 표시(Mark)한 뒤 표시되지 않은 메모리를 해제(Sweep)하는 알고리즘. 단편화 발생이 단점.
- **Mark-Compact**: Mark-Sweep 이후 살아있는 객체를 힙의 한쪽으로 압축(Compact)하는 알고리즘. 단편화가 없지만 이동 비용이 크다.
- **Copying**: 힙을 From-Space/To-Space로 나눠 살아있는 객체만 복사하는 알고리즘. Young 영역에 주로 사용되며 단편화가 없다.
- **Generational GC**: 대부분의 객체는 금방 죽는다는 Weak Generational Hypothesis를 기반으로 Young/Old 영역을 분리하여 효율을 높이는 GC 설계 원칙.
- **G1 GC**: 힙을 1~32MB Region으로 분할하고 Pause 목표 시간(`MaxGCPauseMillis`)에 맞춰 Collection Set을 동적으로 결정하는 컬렉터. Java 9+ 기본값.
- **ZGC**: 컬러 포인터(64비트 주소 상위 비트에 GC 상태 메타데이터 저장)와 Load Barrier를 활용해 객체 재배치를 완전 동시 처리하는 컬렉터. JDK 21의 Generational ZGC로 CPU 효율 개선.
- **Shenandoah**: Brooks Pointer(객체 헤더에 forwarding pointer 추가)를 사용해 동시 압축(Concurrent Compaction)을 구현한 컬렉터. Red Hat이 개발.
- **Throughput vs Latency**: GC 선택의 핵심 트레이드오프. 처리량(전체 실행 시간 중 GC 비율)과 지연시간(개별 Pause 길이)은 반비례 관계다.
- **Stop-The-World (STW)**: GC가 수행되는 동안 모든 애플리케이션 스레드가 강제로 일시 정지되는 상태. Safepoint에서 발생하며, 저지연 GC의 핵심 과제다.
- **Heap Footprint**: GC 메커니즘 자체가 사용하는 메모리 오버헤드. ZGC/Shenandoah는 동시 처리를 위한 추가 메모리(컬러 포인터 테이블, Brooks Pointer 등)가 필요하다.
- **GC 튜닝**: GC 컬렉터를 선택한 후 힙 크기, GC 스레드 수, Region 크기, Pause 목표 등의 JVM 플래그를 워크로드에 맞게 조정하는 작업.
- **Region 기반 수집**: G1/ZGC처럼 힙을 고정 크기 Region으로 분할하여 GC 대상을 일부 Region으로 한정함으로써 전체 힙 GC를 피하고 Pause 시간을 제어하는 방식.
