# JVM 예외는 JVM에서 어떻게 처리될까

## 개요

Java 예외(Exception)가 발생했을 때 JVM 내부에서 어떤 절차로 처리되는지, 바이트코드 수준의 예외 테이블(Exception Table)과 핸들러 탐색 메커니즘을 중심으로 정리한다.

## 상세 내용

### 1. 예외 처리의 기본 구조

**Throwable 계층 구조**

```
Throwable
├── Error          (JVM 수준 치명적 오류 - OutOfMemoryError, StackOverflowError 등)
└── Exception
    ├── RuntimeException  (Unchecked - NullPointerException, IllegalArgumentException 등)
    └── 그 외 Exception   (Checked - IOException, SQLException 등)
```

- `Error`: JVM 자체 문제로 복구 불가능. 애플리케이션에서 처리하지 않는 것이 원칙.
- `Exception (Checked)`: 컴파일러가 `try-catch` 또는 `throws` 선언을 강제한다.
- `RuntimeException (Unchecked)`: 컴파일러 강제 없음. 주로 프로그래밍 오류를 나타낸다.

**`athrow` 바이트코드 명령**

`throw new SomeException()` 코드는 두 단계로 컴파일된다.

1. `new` + `invokespecial`: 예외 객체를 힙에 생성하고 생성자를 호출한다. 이 시점에 `fillInStackTrace()`가 실행되어 현재 콜 스택이 캡처된다.
2. `athrow`: 오퍼랜드 스택 최상단의 예외 객체 참조를 꺼내 예외 처리 메커니즘을 시작한다.

즉, 예외 객체 생성(스택 트레이스 캡처)과 `athrow`(예외 전파 시작)는 별개의 시점이다.

### 2. 예외 테이블(Exception Table)

**구조**

모든 예외 처리 로직이 있는 메서드는 컴파일 결과물(`.class`)의 `Code` 속성 안에 `Exception Table`을 포함한다. 이 테이블은 JVM이 런타임에 예외 핸들러를 탐색하는 데 사용하는 핵심 자료구조다.

| 필드 | 의미 |
|---|---|
| `start_pc` | 예외 처리 범위의 시작 바이트코드 오프셋 (try 블록 시작) |
| `end_pc` | 예외 처리 범위의 끝 바이트코드 오프셋 (exclusive, try 블록 끝) |
| `handler_pc` | 예외 발생 시 점프할 핸들러의 바이트코드 오프셋 (catch 블록 시작) |
| `catch_type` | 잡을 예외 타입 (상수 풀 인덱스). `0`이면 모든 예외(finally 핸들러) |

**`javap -v`로 예외 테이블 확인하기**

아래 Java 코드를 예시로 살펴보자.

```java
public void example() {
    try {
        int result = 10 / 0;
    } catch (ArithmeticException e) {
        System.out.println("caught: " + e.getMessage());
    } finally {
        System.out.println("finally");
    }
}
```

`javap -v` 출력에서 Exception Table은 대략 아래와 같이 나타난다.

```
Exception table:
   from    to  target type
       0     8    11   Class java/lang/ArithmeticException
       0     8    22   any
      11    22    22   any
```

- `0 ~ 8`: try 블록 범위
- `11`: ArithmeticException 핸들러 시작 (catch 블록)
- `22`: finally 핸들러 시작 (`type = any`)

**try-catch-finally가 바이트코드로 변환되는 방식**

Java 6 이전에는 `jsr` (jump to subroutine) / `ret` 명령으로 finally 블록을 서브루틴처럼 호출했다. Java 7부터는 `jsr`/`ret`가 폐기되고, 컴파일러가 finally 블록 코드를 catch 경로와 정상 종료 경로 각각에 **물리적으로 복제(inline duplicate)** 삽입하는 방식으로 변경되었다. 이로 인해 finally가 있는 메서드는 바이트코드 크기가 늘어날 수 있다.

### 3. 예외 핸들러 탐색 절차

**예외 발생 ~ 핸들러 탐색 흐름**

```
athrow 실행
    │
    ▼
현재 메서드의 Exception Table을 순서대로 탐색
    │
    ├─ [현재 PC가 start_pc ~ end_pc 범위 내]
    │       └─ catch_type이 발생 예외 타입과 일치(또는 슈퍼타입)?
    │               ├─ YES → handler_pc로 점프, 핸들러 실행 → 종료
    │               └─ NO  → 다음 Entry 탐색
    │
    └─ [매칭 핸들러 없음 → Stack Unwinding]
            │
            ▼
        현재 프레임 종료, 호출자 프레임으로 복귀
        호출자의 Exception Table에서 동일 과정 반복
            │
            └─ [최상위 프레임까지 없음]
                    │
                    ▼
                Thread.getUncaughtExceptionHandler() 호출
                기본 동작: 스택 트레이스 출력 후 스레드 종료
```

**Stack Unwinding 상세**

JVM은 예외 전파 시 콜 스택의 각 프레임을 되감으면서 아래를 수행한다.
- `finally` 핸들러(`catch_type = 0`)는 예외 타입과 무관하게 실행된다.
- `catch` 핸들러가 매칭되면 해당 프레임에서 실행을 재개하고 언와인딩을 중단한다.
- 언와인딩 중 `finally`가 새 예외를 던지면 원래 예외는 억제되거나 대체된다.

**UncaughtExceptionHandler**

최상위까지 핸들러가 없을 때 JVM은 아래 순서로 `UncaughtExceptionHandler`를 찾는다.

1. 해당 스레드에 설정된 핸들러 (`thread.setUncaughtExceptionHandler(...)`)
2. 스레드가 속한 `ThreadGroup`의 핸들러
3. `Thread.setDefaultUncaughtExceptionHandler(...)`로 설정된 전역 핸들러
4. 모두 없으면 기본 동작: `System.err`에 스택 트레이스 출력 후 스레드 종료

### 4. finally와 스택 추적(Stack Trace)

**finally 블록의 바이트코드 중복 삽입**

앞서 설명한 것처럼 Java 7 이후 컴파일러는 finally 코드를 다음 세 경로에 각각 복사한다.
- 정상 종료 경로 (try 블록 완료 후)
- 각 catch 블록 이후
- 예외 전파 경로 (Exception Table의 `any` 핸들러)

이는 코드 중복을 만들지만 `jsr`/`ret`의 복잡한 검증 문제를 제거하고 JIT 최적화를 단순화한다.

**try-with-resources와 suppressed exception**

Java 7에서 도입된 `try-with-resources`는 `AutoCloseable`의 `close()`를 암묵적 `finally`에서 호출한다. try 블록과 `close()` 양쪽에서 예외가 발생하면, `close()` 예외는 주 예외에 `addSuppressed()`로 첨부된다. `Throwable.getSuppressed()`로 억제된 예외 목록을 조회할 수 있다.

```java
try (Resource r = new Resource()) {
    // 예외 A 발생
} // close()에서 예외 B 발생 → B는 A에 addSuppressed됨
```

스택 트레이스에서 `Suppressed:` 접두사로 표시된다.

**`fillInStackTrace()`와 스택 트레이스 생성 비용**

`new Exception()`이 호출되는 순간 `Throwable` 생성자 내에서 `fillInStackTrace()`가 실행된다. 이 메서드는 현재 스레드의 콜 스택 전체를 순회하며 `StackTraceElement` 배열을 생성한다. 스택 깊이에 비례해 비용이 선형 증가한다.

Aleksey Shipilëv의 벤치마크 연구에 따르면 `-XX:-StackTraceInThrowable` JVM 옵션으로 스택 트레이스 생성을 비활성화하면 예외 생성 비용이 약 96% 감소한다.

### 5. JIT 컴파일과 예외 처리

**인터프리터 vs JIT 컴파일된 코드에서의 예외 처리 차이**

인터프리터 모드에서는 Exception Table을 매번 순차 탐색한다. JIT 컴파일 후에는 컴파일러가 예외가 드물다는 가정(speculation) 하에 예외 경로 코드를 메인 코드에서 분리하거나, null 체크 등을 암묵적 트랩으로 대체하여 정상 경로를 최적화한다.

**예외 경로의 비최적화(Deoptimization)**

JIT는 "이 경로에서는 예외가 발생하지 않을 것"이라는 가정으로 코드를 최적화한다. 런타임에 그 가정이 깨지면 JVM은 해당 메서드를 인터프리터로 되돌리는 **Deoptimization**을 수행한다. 예외가 반복적으로 발생하면 JVM이 가정을 철회하고 예외 경로를 메인 코드에 다시 포함시키는 재컴파일이 일어나 성능이 불안정해진다.

**Hot path에서 예외를 흐름 제어로 쓰면 안 되는 이유**

```java
// 안티패턴: 예외를 루프 종료 조건으로 사용
try {
    while (true) {
        process(iterator.next()); // NoSuchElementException으로 루프 탈출
    }
} catch (NoSuchElementException e) { }

// 올바른 방식
while (iterator.hasNext()) {
    process(iterator.next());
}
```

예외를 제어 흐름으로 사용하면:
1. 예외가 발생할 때마다 `fillInStackTrace()` 비용이 발생한다.
2. JIT의 happy path 최적화 가정을 깨뜨려 Deoptimization을 유발한다.
3. 코드의 의도를 흐려 가독성을 해친다.

## 핵심 정리

- 예외 처리는 메서드별 Exception Table을 통해 동작하며, JVM은 `athrow` 시점의 PC가 어느 범위(`start_pc` ~ `end_pc`)에 속하는지로 핸들러를 찾는다.
- 매칭 핸들러가 없으면 Stack Unwinding을 통해 호출자 프레임으로 전파되며, 최상위까지 없으면 `UncaughtExceptionHandler`가 처리하고 스레드가 종료된다.
- 스택 트레이스 생성(`fillInStackTrace`)은 스택 깊이에 비례한 선형 비용이 발생하므로, 예외를 일반적인 제어 흐름으로 사용하는 것은 성능과 JIT 최적화 모두를 저해하는 안티패턴이다.

## 기술적 한계와 보완 전략

**예외 객체 생성과 fillInStackTrace의 성능 비용 완화**

| 전략 | 방법 | 트레이드오프 |
|---|---|---|
| JVM 옵션으로 비활성화 | `-XX:-StackTraceInThrowable` | 전역 적용, 디버깅 불가 |
| 생성자 파라미터 활용 | `new Throwable(msg, cause, enableSuppression, false)` (Java 7+) | 특정 예외에만 적용 가능 |
| `fillInStackTrace()` 오버라이드 | `return this;` 반환 | 스택 정보 손실 |
| 예외 객체 캐싱/재사용 | static final 예외 인스턴스 사용 | 스택 트레이스가 생성 시점 고정 |

**예외 기반 제어 흐름의 대안**

- `Optional<T>`: 값의 부재를 표현 (null 대신)
- Result 타입 패턴: 성공/실패를 타입으로 모델링 (Vavr의 `Either`, `Try` 등)
- 사전 조건 검사: 예외 발생 가능 상황을 미리 `if`로 가드

## 키워드

**Exception Table**: JVM이 메서드별로 관리하는 예외 핸들러 매핑 테이블. `start_pc`, `end_pc`, `handler_pc`, `catch_type` 4개 필드로 구성되며 `.class` 파일의 `Code` 속성에 포함된다.

**athrow**: 예외를 던지는 JVM 바이트코드 명령어. 오퍼랜드 스택에서 `Throwable` 참조를 꺼내 Exception Table 탐색을 시작한다.

**Stack Unwinding**: 현재 프레임에서 예외 핸들러를 찾지 못했을 때 콜 스택의 이전 프레임으로 되돌아가며 핸들러를 탐색하는 과정. 경로상의 `finally` 블록은 모두 실행된다.

**Throwable**: Java 예외 계층의 최상위 클래스. `Error`와 `Exception`의 공통 부모이며, 스택 트레이스 저장(`stackTrace`), 원인 체이닝(`cause`), 억제 예외(`suppressedExceptions`) 목록을 필드로 보유한다.

**handler_pc / catch_type**: Exception Table의 두 핵심 필드. `handler_pc`는 핸들러 코드 시작 오프셋, `catch_type`은 잡을 예외의 상수 풀 인덱스이며 `0`이면 `finally` 핸들러를 의미한다.

**fillInStackTrace**: `Throwable` 생성 시 자동 호출되는 메서드로 현재 스레드의 콜 스택 전체를 `StackTraceElement[]`로 캡처한다. 스택 깊이에 비례한 비용이 발생하며 예외 생성 비용의 가장 큰 원인이다.

**try-with-resources**: Java 7에서 도입된 구문으로 `AutoCloseable` 리소스를 자동으로 `close()`한다. 본문과 `close()` 양쪽에서 예외 발생 시 `close()` 예외는 `addSuppressed()`로 주 예외에 첨부된다.

**UncaughtExceptionHandler**: 스레드 내에서 핸들러 없이 전파된 예외를 최종 처리하는 인터페이스. 스레드 단위, ThreadGroup 단위, 전역 단위로 설정 가능하다.

**Bytecode**: JVM이 실행하는 중간 표현 언어. `.java` → `.class` 컴파일 결과물이며 플랫폼 독립적이다. `javap -c` / `javap -v`로 역어셈블해 확인할 수 있다.

**Deoptimization**: JIT 컴파일러가 세운 최적화 가정이 런타임에 깨졌을 때 해당 메서드를 인터프리터 실행으로 되돌리는 과정. 예외를 제어 흐름으로 남용하면 Deoptimization이 반복되어 성능이 저하된다.
