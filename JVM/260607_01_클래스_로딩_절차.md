# 클래스 로딩 절차

## 개요
JVM이 `.class` 바이트코드를 메모리로 적재하여 실행 가능한 상태로 만드는 일련의 과정을 정리한다. 클래스 로딩은 단순히 파일을 읽는 것이 아니라 **로딩(Loading) → 링킹(Linking: 검증·준비·해석) → 초기화(Initialization)** 의 단계로 구성된 엄격한 생애주기를 따른다. 각 단계가 언제, 어떤 조건에서 트리거되는지 이해하는 것이 핵심이다.

## 상세 내용

### 1. 로딩(Loading)

`ClassLoader`가 클래스의 이진 표현(바이트코드)을 찾아 읽어들이는 단계다.

**클래스 로더 계층 구조 (Java 9+ 기준)**

```
Bootstrap ClassLoader
    ↓
Platform ClassLoader (구 Extension ClassLoader)
    ↓
Application(System) ClassLoader
    ↓
사용자 정의 ClassLoader
```

**로더의 두 가지 역할 구분**

- **시작 로더(Initiating Loader)**: 클래스 로딩을 최초로 요청한 로더
- **정의 로더(Defining Loader)**: `defineClass()`를 호출하여 실제로 클래스를 생성한 로더

JVM 명세 상 클래스는 `(클래스 이름 + 정의 로더)`의 조합으로 식별된다. 같은 이름이더라도 정의 로더가 다르면 서로 다른 타입으로 취급되며, 이를 **Runtime Package** 격리라고 한다.

**로딩 결과**

- 클래스 메타데이터가 Metaspace(메서드 영역)에 적재됨
- 힙(Heap)에 해당 클래스의 `java.lang.Class` 객체가 생성됨

---

### 2. 링킹(Linking)

로딩된 클래스를 JVM 런타임 환경에 통합하는 단계다. 세 단계로 구성된다.

#### 2-1. 검증(Verification)

바이트코드의 무결성, 보안, 타입 안전성을 검사한다. JVM 명세(§4.10)에 정의된 제약 조건을 위반하면 `VerifyError`가 발생한다.

검증 항목:
- `ClassFile` 구조의 정확성
- 클래스 버전 호환성 (`UnsupportedClassVersionError` 원인)
- 바이트코드 명령어 유효성
- 타입 규칙 준수 여부

#### 2-2. 준비(Preparation)

정적(static) 필드를 위한 메모리를 확보하고 **기본값(default value)** 을 할당한다. 개발자가 선언한 초기값이 아닌 타입별 기본값이다.

| 타입 | 기본값 |
|------|--------|
| `int`, `short`, `byte`, `char` | `0` |
| `long` | `0L` |
| `float` | `0.0f` |
| `double` | `0.0d` |
| `boolean` | `false` |
| 참조 타입 | `null` |

> 준비 단계는 기본값, 초기화 단계는 실제 선언된 값을 할당한다는 점이 핵심 차이다.

#### 2-3. 해석(Resolution)

상수 풀(Constant Pool)의 **심볼릭 레퍼런스(Symbolic Reference)** 를 실제 메모리 주소를 가리키는 **다이렉트 레퍼런스(Direct Reference)** 로 변환한다.

해석 대상:
- 클래스/인터페이스 심볼릭 참조
- 필드 참조
- 메서드 참조
- 메서드 타입 및 핸들

해석은 지연(lazy) 수행이 가능하다. 명세 상 초기화 이후에 수행되어도 허용된다. 이 지연 처리가 `ClassNotFoundException`과 `NoClassDefFoundError`의 혼동을 낳는다.

---

### 3. 초기화(Initialization)

`<clinit>()` 메서드(클래스 초기화 메서드)가 실행되며, 정적 변수에 **개발자가 선언한 실제 값**이 할당되고 `static` 블록이 실행된다.

#### 3-1. 초기화 트리거 조건 (Active Use)

JVM 명세는 다음 상황에서만 초기화를 보장한다:

```java
// 1. 인스턴스 생성
MyClass obj = new MyClass();

// 2. 정적 필드 읽기/쓰기 (getstatic, putstatic)
MyClass.STATIC_FIELD = 10;
int v = MyClass.STATIC_FIELD;

// 3. 정적 메서드 호출 (invokestatic)
MyClass.staticMethod();

// 4. 리플렉션을 통한 명시적 로딩
Class.forName("com.example.MyClass");

// 5. JVM 시작 시 main() 클래스
// 6. assert 문이 활성화된 클래스
```

#### 3-2. 초기화가 트리거되지 않는 경우 (Passive Use)

```java
// 배열 생성 - 원소 타입 초기화 안 됨
MyClass[] array = new MyClass[10];

// 클래스 리터럴 참조
Class<?> clazz = MyClass.class;

// 컴파일 타임 상수(static final) 참조
// - 이미 컴파일러가 상수를 인라인하여 원본 클래스 참조 불필요
int value = MyConstants.COMPILE_TIME_CONSTANT;
```

#### 3-3. 초기화 순서

부모 클래스의 `<clinit>()`가 자식보다 먼저 실행된다. JVM이 순환 참조를 방지한다.

```java
class A {
    static { System.out.println("A init"); }
}
class B extends A {
    static { System.out.println("B init"); }
}
// new B() 결과:
// A init
// B init
```

#### 3-4. 스레드 안전성

JVM은 `<clinit>()`이 단 한 번만 실행되도록 락으로 보호한다. 여러 스레드가 동시에 같은 클래스를 초기화하려 하면 JVM이 한 스레드만 실행하고 나머지는 대기시킨다.

---

### 4. 부모 위임 모델(Parent Delegation Model) 심화

#### 4-1. 동작 방식

```
ClassLoader.loadClass(name) 호출
    ↓
캐시(findLoadedClass) 확인
    ↓ (없으면)
부모 로더에 위임 (parent.loadClass)
    ↓ (부모가 실패하면)
자신의 findClass() 호출
```

#### 4-2. 위임 모델이 보장하는 것

- **코어 클래스 변조 방지**: `java.lang.String` 같은 클래스를 사용자가 덮어쓸 수 없음
- **네임스페이스 격리**: 동일한 클래스가 여러 로더에서 중복 로드되지 않음
- **일관성**: 모든 컴포넌트가 동일한 JDK 핵심 클래스를 사용

#### 4-3. 위임 모델의 한계와 역전(Inversion)

표준 위임 모델이 부적합한 상황이 존재한다:

| 상황 | 해결 방식 |
|------|-----------|
| **Tomcat 웹 컨테이너** | Child-First 전략: 웹 앱 클래스로더가 자신의 클래스패스를 먼저 검색, Jakarta EE API만 부모에 위임 |
| **OSGi 프레임워크** | 계층 구조 없는 피어(peer) 방식의 네트워크 아키텍처 |
| **Java 모듈 시스템(JPMS)** | 모듈 경계와 접근 제어를 통한 캡슐화 강화 |
| **사용자 정의 로더** | `loadClass()` 대신 `findClass()` 오버라이딩으로 표준 위임 유지 |

---

### 5. ClassNotFoundException vs NoClassDefFoundError

Resolution의 지연 처리와 관련하여 두 오류가 자주 혼동된다.

| 구분 | `ClassNotFoundException` | `NoClassDefFoundError` |
|------|--------------------------|------------------------|
| 타입 | Checked Exception | Unchecked Error |
| 발생 시점 | 런타임 명시적 로딩 시 | 링킹/초기화 단계 실패 |
| 주요 원인 | `Class.forName()` 등 호출 시 클래스패스에 없음 | 컴파일 시점엔 있었으나 런타임에 없거나, 초기화 중 에러 발생 |
| 관계 | 원인이 됨 | `Caused by: ClassNotFoundException`으로 표시되기도 함 |

`NoClassDefFoundError`가 발생하면 "Caused By:" 항목에서 근본 원인을 찾아야 한다.

### 6. 언로딩(Unloading)과 Metaspace OOM

#### 6-1. 클래스 언로딩 조건

JVM 명세는 클래스를 **정의한 클래스 로더가 GC 대상이 될 때**에만 클래스를 언로딩한다고 정의한다.

클래스 로더가 GC될 수 없는 조건:
- 로더가 생성한 어떤 클래스의 인스턴스가 살아있는 경우
- 로더 자체에 대한 살아있는 참조가 있는 경우
- 해당 클래스의 `Class` 객체가 살아있는 참조를 가진 경우

#### 6-2. Metaspace 누수 패턴

동적으로 클래스를 생성하는 프레임워크(Hibernate, Spring, JPA 등)는 Metaspace 누수에 취약하다.

```
동적 클래스 생성(Proxy, CGLIB, ASM 등)
    ↓
ClassLoader가 해당 클래스의 Metaspace 아레나 소유
    ↓
ClassLoader에 대한 참조 해제 실패 (스레드, 리스너, 캐시 등)
    ↓
Metaspace 아레나 해제 불가
    ↓
java.lang.OutOfMemoryError: Metaspace
```

Metaspace 정리는 Full GC 시에만 이루어지므로, 누수가 발생하면 빠르게 OOM으로 이어진다.

#### 6-3. 진단 및 대응

- JVM 옵션: `-XX:+HeapDumpOnOutOfMemoryError` 로 힙 덤프 수집
- 분석 도구: Eclipse MAT, VisualVM, YourKit
- 예방: 클래스 로더 참조를 명시적으로 해제하고, `WeakReference` 활용
- 임시 대응: `-XX:MaxMetaspaceSize=<size>` 로 크기 제한 조정

---

## 핵심 정리
- 클래스 로딩은 로딩 → 검증 → 준비 → 해석 → 초기화의 순서를 따른다
- 준비 단계는 기본값, 초기화 단계는 실제 값을 할당한다는 점이 핵심 차이다
- 부모 위임 모델로 코어 클래스의 안전성과 네임스페이스 격리를 보장한다
- 클래스 식별자는 `(클래스 이름 + 정의 클래스 로더)`의 조합이다
- `<clinit>()`는 JVM이 락으로 보호하여 멀티스레드 환경에서도 단 한 번만 실행된다
- 클래스 언로딩은 정의 로더가 GC될 때만 발생하며, Metaspace 누수의 근본 원인이 된다

## 기술적 한계와 보완 전략
- 위임 모델의 한계: 웹 컨테이너(Tomcat)나 모듈 시스템에서는 Child-First나 피어 방식으로 위임을 깨거나 역전시키는 커스텀 로더가 필요
- Resolution의 지연 처리로 인한 `NoClassDefFoundError` vs `ClassNotFoundException` 혼동 - "Caused By:" 항목을 반드시 확인
- Metaspace 누수: 동적 클래스 생성/로더 미해제 시 언로딩 실패 → Full GC 시에만 정리되므로 빠르게 OOM으로 이어질 수 있음

## 키워드

| 키워드 | 설명 |
|--------|------|
| **ClassLoader** | 클래스의 바이트코드를 찾아 JVM 런타임에 올리는 컴포넌트. Bootstrap/Platform/Application 계층으로 구성됨 |
| **Parent Delegation Model** | ClassLoader가 자신보다 부모에게 먼저 클래스 로딩을 위임하는 방식. 코어 클래스 변조를 방지하고 네임스페이스를 격리함 |
| **Linking** | 로딩된 클래스를 JVM 런타임에 통합하는 단계. Verification → Preparation → Resolution으로 구성됨 |
| **Verification** | 바이트코드의 구조적 정확성, 타입 안전성, 보안 규칙 준수 여부를 검사하는 링킹 1단계 |
| **Initialization** | `<clinit>()` 실행을 통해 정적 변수에 실제 값을 할당하고 static 블록을 수행하는 마지막 단계 |
| **clinit** | JVM이 자동 생성하는 클래스 초기화 메서드(`<clinit>()`). static 초기화 블록과 static 필드 초기화 코드를 포함하며, JVM 락으로 단 한 번만 실행을 보장함 |
| **Symbolic Reference** | 클래스 파일의 상수 풀에 이름 기반으로 저장된 참조. Resolution 단계에서 실제 메모리 주소인 Direct Reference로 변환됨 |
| **Metaspace** | Java 8부터 PermGen을 대체한 클래스 메타데이터 저장 영역. 네이티브 메모리에 할당되며, ClassLoader 단위로 아레나를 소유함 |
| **Class Unloading** | 정의 클래스 로더가 GC될 때 함께 해제되는 클래스 제거 과정. 동적 클래스 환경에서 로더 참조가 남아있으면 언로딩 불가로 Metaspace OOM 발생 |
| **Runtime Package** | (클래스 이름 + 정의 클래스 로더)의 조합으로 결정되는 클래스의 실제 식별자. 같은 이름이라도 로더가 다르면 다른 타입으로 취급됨 |
