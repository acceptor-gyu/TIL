# 강제로 GC 시키기

## 개요

Java 애플리케이션에서 `System.gc()`와 `Runtime.getRuntime().gc()`를 통해 GC를 명시적으로 요청하는 방법을 살펴본다. 이 호출이 실제로 의미하는 바가 "강제(force)"가 아닌 "요청(suggestion)"이라는 점, 운영 환경에서 권장되지 않는 이유, 그리고 의도하지 않게 명시적 GC가 발생하는 경로를 정리한다.

## 상세 내용

### System.gc()와 Runtime.gc()

#### 내부 호출 흐름

`System.gc()`는 독자적인 GC 구현체가 아니다. 내부적으로 `Runtime.getRuntime().gc()`에 위임하는 단순한 래퍼 메서드다.

```java
// java.lang.System
public static void gc() {
    Runtime.getRuntime().gc();
}
```

`Runtime.gc()`는 native 메서드로 선언되어 있고, HotSpot JVM의 경우 `jvm.cpp`의 `JVM_GC` 함수로 연결된다. 이 함수는 내부적으로 `Universe::heap()->collect(GCCause::_java_lang_system_gc)`를 호출하여 GC 원인(cause)을 `_java_lang_system_gc`로 표시하고 수집을 요청한다.

#### "요청"이지 "강제"가 아니다

JVM 명세는 `System.gc()`를 호출하더라도 **GC가 반드시 즉시 실행되어야 한다고 보장하지 않는다**. JVM은 이 요청을 무시하거나 지연시킬 수 있다.

JVM이 요청 처리 전 고려하는 요소들은 다음과 같다.

- 현재 힙 점유율과 여유 공간
- 최근 GC 이력 (과도한 GC 방지)
- 활성화된 GC 컬렉터의 종류
- JVM 옵션 (`-XX:+DisableExplicitGC` 등)

---

### GC 요청이 처리되는 방식

#### VMThread와 GC 트리거 메커니즘

HotSpot JVM에서 GC는 **VMThread**라는 전용 스레드가 실행한다. 애플리케이션 스레드가 `System.gc()`를 호출하면 GC 요청이 VMThread의 작업 큐(VM Operation Queue)에 추가된다. VMThread는 큐에서 작업을 꺼내 GC를 수행한다.

```
애플리케이션 스레드
  System.gc() 호출
        │
        ▼
  VM_GenCollectFull 오퍼레이션 생성
  (GCCause = _java_lang_system_gc)
        │
        ▼
  VMThread 작업 큐에 삽입
        │
        ▼
  VMThread가 Safepoint 설정 → 모든 앱 스레드 정지 (STW)
        │
        ▼
  Full GC 수행 (Young + Old 전체)
        │
        ▼
  Safepoint 해제 → 앱 스레드 재개
```

#### Full GC와 STW 비용

기본적으로 `System.gc()`를 호출하면 **Full GC**가 발생한다. Full GC는 Young 영역과 Old 영역을 모두 수집하므로, 힙 크기가 클수록 STW(Stop-The-World) 시간이 길어진다.

예를 들어 힙이 4GB인 서버에서 Full GC가 수 초간 발생하면, 그 시간 동안 모든 요청이 멈추는 것과 같다. 이것이 운영 환경에서 명시적 GC가 위험한 이유다.

---

### GC 관련 JVM 옵션

#### -XX:+DisableExplicitGC

`System.gc()` 호출을 완전히 무력화한다. 이 옵션이 활성화되면 코드에서 `System.gc()`를 호출해도 **아무 일도 일어나지 않는다**.

```bash
java -XX:+DisableExplicitGC -jar application.jar
```

운영 환경에서는 애플리케이션 코드나 서드파티 라이브러리의 `System.gc()` 호출을 차단하기 위해 이 옵션을 권장하는 경우가 많다.

단, 이 옵션은 **RMI DGC의 System.gc()는 막지 못한다**는 점이 중요하다. RMI 내부 GC는 별도 메커니즘으로 동작한다.

#### -XX:+ExplicitGCInvokesConcurrent

`System.gc()` 호출 시 Full GC 대신 **Concurrent GC 사이클을 시작**하도록 한다. STW를 최소화하면서도 GC 요청 자체는 처리된다.

```bash
java -XX:+UseG1GC -XX:+ExplicitGCInvokesConcurrent -jar application.jar
```

G1 GC에서 이 옵션을 사용하면 `System.gc()`가 Evacuation Pause를 시작하고 Concurrent Marking 사이클을 트리거하는 방식으로 처리된다. 요청 스레드는 Concurrent Marking이 완료될 때까지 블로킹된다.

#### GC별 System.gc() 동작 차이 비교

| GC | 기본 동작 | ExplicitGCInvokesConcurrent 적용 시 |
|----|-----------|-------------------------------------|
| Serial GC | 단일 스레드 Full GC + STW | 미지원 |
| Parallel GC | 멀티 스레드 Full GC + STW | 미지원 |
| G1 GC | Full GC + STW | Concurrent Marking 사이클 시작 (STW 최소화) |
| ZGC | ZGC 수집 사이클 | 이미 대부분 Concurrent이므로 효과 동일 |
| Shenandoah | Concurrent 수집 사이클 | 이미 Concurrent이므로 효과 동일 |

ZGC와 Shenandoah는 기본 설계 자체가 대부분 Concurrent이므로, `System.gc()`를 호출해도 Full STW GC가 발생하지 않는다. G1 GC에서는 `-XX:+ExplicitGCInvokesConcurrent`가 가장 큰 효과를 발휘한다.

### 명시적 GC가 발생하는 의외의 경로

#### DirectByteBuffer / Off-Heap 메모리와 Cleaner

NIO의 `DirectByteBuffer`는 힙 외부(Off-Heap)에 메모리를 할당한다. 이 메모리의 해제는 GC가 `DirectByteBuffer` 객체를 수집할 때 연결된 `Cleaner`가 `free()`를 호출하는 방식으로 이루어진다.

문제는 **힙 메모리는 여유롭지만 Off-Heap 메모리가 고갈**되는 상황이다. 힙 GC가 충분히 자주 발생하지 않으면 Cleaner가 호출되지 않아 `DirectByteBuffer`가 해제되지 않는다. 결국 JVM 내부에서 Out-of-Memory 상황을 피하기 위해 System.gc()를 호출한다.

```java
// JDK 내부 코드 (Bits.java) - 단순화
private static void reserveMemory(long size, ...) {
    // Off-Heap 할당 시도 실패 시
    System.gc();         // GC를 유도하여 Cleaner 실행을 기대
    Thread.sleep(100);   // GC 완료 대기
    // 재시도 ...
}
```

`-XX:+DisableExplicitGC`를 적용하면 이 내부 `System.gc()` 호출도 무력화되어 `DirectByteBuffer`를 많이 사용하는 애플리케이션에서 `OutOfMemoryError: Direct buffer memory`가 발생할 수 있다. 이 경우 대안으로 `-XX:+ExplicitGCInvokesConcurrent`를 사용하거나 `-XX:MaxDirectMemorySize`를 명시적으로 설정해야 한다.

#### RMI 분산 GC (DGC, Distributed Garbage Collection)

Java RMI는 분산 환경에서 원격 객체의 수명을 관리하기 위해 **분산 GC(DGC)**를 구현한다. DGC는 원격 참조를 유지하기 위해 주기적으로 로컬 JVM에서 Full GC를 강제로 실행한다.

```
RMI DGC 기본 GC 주기:
  JDK 1.4.2 ~ 5.0: 1분 (60,000ms)
  JDK 6+:          1시간 (3,600,000ms)
```

이를 제어하는 JVM 속성은 다음과 같다.

```bash
# DGC 클라이언트 측 주기 (밀리초)
-Dsun.rmi.dgc.client.gcInterval=3600000

# DGC 서버 측 주기 (밀리초)
-Dsun.rmi.dgc.server.gcInterval=3600000
```

중요한 점은 `-XX:+DisableExplicitGC`가 **RMI DGC의 Full GC는 막지 못한다**는 것이다. RMI DGC는 `System.gc()` API를 통하지 않고 직접 JVM GC를 트리거한다.

### 테스트/벤치마크 환경에서의 GC 유도

#### JMH에서의 GC 제어

JMH(Java Microbenchmark Harness) 벤치마크에서는 이전 반복(iteration)에서 할당된 객체가 다음 반복에 영향을 주는 것을 막기 위해 GC를 제어한다.

```java
@Benchmark
@OutputTimeUnit(TimeUnit.MILLISECONDS)
public void myBenchmark(Blackhole bh) {
    // 벤치마크 대상 코드
}

// 각 반복 전 GC를 유도하여 힙을 깨끗하게 정리
@Setup(Level.Iteration)
public void setup() {
    System.gc();
}
```

단, JMH의 공식 접근법은 `@Fork`를 통해 별도의 JVM 프로세스에서 각 벤치마크를 실행하는 것이다. JVM 프로세스 자체를 격리하면 이전 반복의 메모리 상태가 완전히 초기화된다.

JMH에서 `System.gc()`를 호출한 직후 즉시 메모리 사용량을 측정하면 부정확한 결과를 얻을 수 있다. Concurrent GC의 경우 호출 직후 수집이 완료되지 않을 수 있기 때문이다.

#### 메모리 누수 분석 시 GC 강제 후 Heap Dump 확보

메모리 누수를 분석할 때 Heap Dump를 뜨기 전 GC를 강제 실행하여 도달 불가능한 객체를 먼저 제거하면 실제 누수 객체를 더 명확하게 식별할 수 있다.

```bash
# GC 수행 후 Heap Dump 생성 (live 옵션이 GC 후 살아있는 객체만 포함)
jmap -dump:live,format=b,file=heap.hprof <pid>
```

`live` 옵션을 사용하면 `jmap`이 내부적으로 Full GC를 수행한 후 살아있는 객체만 덤프에 포함한다. 이 방식으로 Heap Dump 크기를 줄이고 분석을 집중시킬 수 있다.

## 핵심 정리

- `System.gc()`는 강제가 아니라 GC 요청일 뿐이며 JVM이 무시할 수 있다.
- 기본적으로 명시적 GC 호출은 Full GC + STW를 유발해 운영 서버의 응답 시간에 악영향을 준다.
- 운영 환경에서는 `-XX:+DisableExplicitGC`로 막거나, G1 GC에서는 `-XX:+ExplicitGCInvokesConcurrent`로 Concurrent 처리를 유도한다.
- `DirectByteBuffer` Off-Heap 메모리와 RMI DGC는 의도치 않은 명시적 GC의 대표적인 경로이며, 각각 별도 전략으로 관리해야 한다.

---

## 기술적 한계와 보완 전략

명시적 GC 호출 대신 취할 수 있는 대안은 다음과 같다.

- **GC 튜닝**: GC가 필요한 상황 자체를 줄이도록 힙 크기, 세대 비율, GC 알고리즘을 조정한다.
- **Off-Heap 관리 전략**: `DirectByteBuffer` 대신 `ByteBuffer.allocate()`를 사용하거나, `-XX:MaxDirectMemorySize`를 명시적으로 설정하여 JVM 내부 `System.gc()` 유발을 줄인다.
- **RMI DGC 주기 조정**: `-Dsun.rmi.dgc.client.gcInterval`을 늘려 주기적 Full GC 빈도를 낮춘다.
- **Phantom Reference / WeakReference 활용**: Off-Heap 자원을 명시적으로 참조 큐와 연계하여 GC에 의존하지 않고 직접 해제하는 패턴을 적용한다.

## 키워드

- **System.gc()**: JVM에 GC 수행을 요청하는 정적 메서드. 내부적으로 `Runtime.getRuntime().gc()`에 위임하며, 강제가 아닌 권고다. JVM이 요청을 무시할 수 있다.
- **Runtime.getRuntime().gc()**: `System.gc()`가 실제로 위임하는 런타임 메서드. native 메서드로 선언되어 HotSpot의 `JVM_GC` 함수로 연결된다.
- **VMThread**: HotSpot JVM에서 VM 오퍼레이션(GC 포함)을 전담 처리하는 내부 스레드. `System.gc()` 호출 시 VMThread의 작업 큐에 GC 오퍼레이션이 삽입된다.
- **DisableExplicitGC**: `-XX:+DisableExplicitGC` 옵션. `System.gc()` 호출을 완전히 무력화한다. 단, RMI DGC의 GC는 막지 못하며, DirectByteBuffer 내부 GC 요청도 막아 OOM을 유발할 수 있다.
- **ExplicitGCInvokesConcurrent**: `-XX:+ExplicitGCInvokesConcurrent` 옵션. `System.gc()` 호출 시 Full STW GC 대신 Concurrent GC 사이클을 시작한다. G1 GC에서 가장 효과적이다.
- **Full GC / Stop-The-World (STW)**: 명시적 GC가 기본적으로 유발하는 Young + Old 전체 힙 수집 및 애플리케이션 스레드 중단 상태. 힙 크기에 비례하여 STW 시간이 길어진다.
- **DirectByteBuffer / Cleaner**: NIO의 Off-Heap 메모리 할당 메커니즘. Off-Heap 메모리 해제가 힙 GC와 연계된 Cleaner에 의존하기 때문에, 힙 GC가 충분히 발생하지 않으면 JVM 내부적으로 `System.gc()`를 호출하는 원인이 된다.
- **RMI 분산 GC (DGC)**: RMI가 분산 환경의 원격 객체 수명 관리를 위해 주기적으로 로컬 JVM에서 Full GC를 강제 실행하는 메커니즘. `-Dsun.rmi.dgc.client.gcInterval` 속성으로 주기를 조정할 수 있다.
- **Finalization**: GC 수집 전 `finalize()` 메서드를 호출하는 메커니즘. GC 타이밍에 의존하여 자원 해제가 불확실하고, 객체가 2번의 GC 사이클을 거쳐야 완전히 해제된다. Java 9부터 deprecated, Java 18에서 종료 예정(JEP 421).
