# GC란

## 개요

JVM의 가비지 컬렉션(Garbage Collection)은 프로그래머가 명시적으로 메모리를 해제하지 않아도 더 이상 사용하지 않는 객체를 자동으로 감지하고 회수하는 자동 메모리 관리 메커니즘이다. Java가 C/C++ 대비 생산성이 높은 핵심 이유 중 하나이며, JVM이 Heap 영역을 주기적으로 스캔하여 살아있는 객체와 죽은 객체를 구분하고 메모리를 재사용 가능한 상태로 만든다.

## 상세 내용

### GC의 정의

GC는 런타임에 더 이상 참조되지 않는 객체(Garbage)를 자동으로 식별하고 해당 메모리를 회수하는 JVM 내부 프로세스다. 1959년 John McCarthy가 Lisp 언어를 위해 처음 고안했으며, Java는 이를 언어 설계의 핵심 원칙으로 채택했다.

GC가 없는 환경에서는 개발자가 직접 `malloc()`으로 할당하고 `free()`로 해제해야 한다. 이 과정에서 발생하는 메모리 누수(Memory Leak), 댕글링 포인터(Dangling Pointer), 이중 해제(Double Free) 등의 버그가 Java에서는 원천적으로 방지된다.

### 수동 메모리 관리와의 비교

| 구분 | C/C++ (수동) | Java (자동 GC) |
|------|-------------|----------------|
| 할당 | `malloc()` / `new` | `new` |
| 해제 | `free()` / `delete` | GC 자동 처리 |
| 오류 위험 | 메모리 누수, 댕글링 포인터 | 없음 |
| 성능 제어 | 세밀하게 가능 | GC 튜닝 필요 |
| 개발 생산성 | 낮음 | 높음 |

수동 관리 방식은 더 세밀한 성능 제어가 가능하지만, JVM GC는 Stop-The-World 등의 트레이드오프를 안고 있다. 대신 개발자는 메모리 관리 버그 없이 비즈니스 로직에 집중할 수 있다.

### GC의 대상: Garbage란 무엇인가

GC는 참조 카운팅(Reference Counting) 방식이 아닌 도달 가능성 분석(Reachability Analysis) 방식을 사용한다.

**GC Root(루트 셋)에서 시작해 도달할 수 없는 객체**가 Garbage로 판단된다.

GC Root의 종류:
- 현재 실행 중인 스레드의 스택 프레임에 있는 로컬 변수
- 메서드 영역의 정적(static) 변수
- JNI(Java Native Interface) 참조
- 활성 Java 스레드 자체

```
GC Root
   │
   ├── Object A (살아있음 - reachable)
   │       └── Object B (살아있음 - reachable)
   │
   └── Object C (살아있음 - reachable)

Object D (죽음 - unreachable) ← 아무도 참조하지 않음
Object E ──→ Object F (죽음) ← 순환 참조여도 GC Root에서 도달 불가
```

참조 카운팅 방식은 순환 참조(Cyclic Reference) 문제를 해결하지 못한다. E → F → E처럼 서로 참조하는 객체들의 카운트는 절대 0이 되지 않아 누수가 발생한다. Reachability 분석은 이 문제를 근본적으로 해결한다.

### GC 동작 원리

JVM GC의 핵심은 **Mark - Sweep - Compact** 3단계다.

**1단계: Mark (마킹)**

GC Root에서 시작해 객체 그래프를 재귀적으로 순회하며 살아있는(reachable) 모든 객체에 mark bit를 설정한다.

```
Before Mark:
[A*] [B ] [C*] [D ] [E*] [F ]
     ↑              ↑
  unreachable    unreachable

After Mark:
[A✓] [B ] [C✓] [D ] [E✓] [F ]
```

**2단계: Sweep (스윕)**

mark되지 않은 객체를 메모리에서 제거하고, 해당 메모리 영역을 free list에 반환한다.

```
After Sweep:
[A✓] [   ] [C✓] [   ] [E✓] [   ]
     ↑            ↑         ↑
   해제됨        해제됨     해제됨
```

**3단계: Compact (컴팩션)**

Sweep만 수행하면 메모리 단편화(Fragmentation)가 발생한다. 큰 객체 할당 시 연속된 빈 공간이 없어 OOM이 발생할 수 있기 때문에, 살아있는 객체를 메모리 앞쪽으로 이동시켜 연속된 빈 공간을 확보한다.

```
After Compact:
[A✓][C✓][E✓][         연속된 빈 공간         ]
```

단, 컴팩션은 객체를 이동시키므로 해당 객체를 가리키는 모든 포인터/참조도 업데이트해야 하는 비용이 있다.

### Heap 메모리 구조

JVM Heap은 **세대별 가설(Generational Hypothesis)**을 기반으로 설계되었다.

> "대부분의 객체는 생성 직후 죽는다. 살아남은 객체는 오랫동안 살아남는 경향이 있다."

이 가설에 따라 Heap을 세대로 분리해 각 세대에 최적화된 GC 전략을 적용한다.

```
┌─────────────────────────────────────────────────────┐
│                       HEAP                          │
│                                                     │
│  ┌────────────────────────┐  ┌────────────────────┐ │
│  │    Young Generation    │  │  Old Generation    │ │
│  │                        │  │                    │ │
│  │  ┌──────┐ ┌──┐ ┌──┐   │  │  오래 살아남은     │ │
│  │  │ Eden │ │S0│ │S1│   │  │  객체들이 Promote  │ │
│  │  └──────┘ └──┘ └──┘   │  │  되어 저장         │ │
│  │  새 객체 할당  Survivor │  │                    │ │
│  └────────────────────────┘  └────────────────────┘ │
└─────────────────────────────────────────────────────┘
```

**Young Generation**
- **Eden**: 새로 생성된 모든 객체가 할당되는 영역. Eden이 꽉 차면 Minor GC 발생
- **Survivor 0 / Survivor 1**: Eden에서 살아남은 객체가 이동. 두 영역을 번갈아 사용하며 Age가 임계치(기본 15)를 넘으면 Old Generation으로 Promotion

**Old Generation**
- Young Generation의 GC에서 여러 번 살아남아 Promote된 객체 저장
- Young에 비해 크기가 크고 GC 빈도가 낮음
- Old Generation이 꽉 차면 Full GC(Major GC) 발생

### Minor GC와 Major(Full) GC

**Minor GC**
- 발생 영역: Young Generation (Eden + Survivor)
- 발생 빈도: 잦음 (초 단위)
- 소요 시간: 짧음 (밀리초 단위)
- Stop-The-World: 발생하지만 짧아 애플리케이션 영향이 미미
- 동작: Eden의 살아있는 객체를 Survivor로 복사 또는 Old로 Promote

**Major(Full) GC**
- 발생 영역: Old Generation (전체 Heap 포함)
- 발생 빈도: 드묾 (분 단위)
- 소요 시간: 길음 (초 단위)
- Stop-The-World: 발생하며 애플리케이션에 눈에 띄는 지연 유발
- 동작: Old Generation 전체를 Mark-Sweep-Compact

Minor GC를 빠르게 유지하는 것이 GC 튜닝의 기본 전략이다. Young Generation 크기를 늘리면 Minor GC 빈도가 줄지만, 한 번의 Minor GC 시간이 길어지는 트레이드오프가 있다.

### Stop-The-World

GC 수행 중 JVM은 **모든 애플리케이션 스레드를 일시 정지**시킨다. 이를 Stop-The-World(STW) 이벤트라고 한다.

STW가 필요한 이유는 GC가 객체 그래프를 탐색하는 동안 객체 참조가 변경되면 정확한 Reachability 분석이 불가능하기 때문이다.

```
Timeline:
App Threads  ━━━━━━┓         ┃━━━━━━━━━━━
                   ┗━━━━━━━━━┛
                   ↑         ↑
                  STW 시작  STW 종료
GC Thread         ┌─────────┐
                  │ Mark    │
                  │ Sweep   │
                  │ Compact │
                  └─────────┘
```

STW 시간을 줄이는 것이 GC 알고리즘 발전의 핵심 방향이다. G1 GC, ZGC, Shenandoah GC는 GC 작업의 일부를 애플리케이션 스레드와 동시에(Concurrent) 수행해 STW를 최소화한다.

### 주요 GC 알고리즘 개요

| GC | 특징 | 적합한 환경 | STW |
|----|------|-------------|-----|
| Serial GC | 단일 스레드, 단순 | 소규모 앱, 제한된 리소스 | 있음 (전체) |
| Parallel GC | 멀티 스레드, 처리량 극대화 | 배치 처리, 처리량 우선 | 있음 (전체) |
| CMS | Old Gen 동시 수집 | 응답성 우선 앱 | 부분적 |
| G1 GC | 리전 기반, 예측 가능한 Pause | 대용량 Heap, 범용 | 부분적 |
| ZGC | 완전 동시 수집, 10ms 이하 Pause | 대용량 Heap, 초저지연 | 최소화 |

**Serial GC** (`-XX:+UseSerialGC`): GC를 단일 스레드로 처리. 멀티코어 환경에서 CPU를 낭비하지만 오버헤드가 없어 소형 애플리케이션에 적합.

**Parallel GC** (`-XX:+UseParallelGC`): Java 8 기본 GC. 여러 스레드로 GC를 병렬 처리해 처리량을 극대화하지만 STW는 여전히 존재.

**CMS (Concurrent Mark Sweep)** (`-XX:+UseConcMarkSweepGC`): Old Generation GC를 애플리케이션 스레드와 동시에 수행. Java 9에서 Deprecated, Java 14에서 제거됨.

**G1 GC** (`-XX:+UseG1GC`): Java 9 이후 기본 GC. Heap을 고정 크기 리전(Region)으로 분할해 관리. 예측 가능한 Pause 시간 목표 설정 가능 (`-XX:MaxGCPauseMillis`).

**ZGC** (`-XX:+UseZGC`): Java 15에서 정식 출시. 로드 배리어(Load Barrier)와 컬러드 포인터(Colored Pointer)를 사용해 대부분의 GC 작업을 동시에 수행. Heap 크기에 관계없이 10ms 이하 Pause 목표.

## 핵심 정리

- GC는 Reachability 분석으로 GC Root에서 도달 불가능한 객체를 Garbage로 판단한다. 참조 카운팅이 아니므로 순환 참조 문제가 없다.
- Mark-Sweep-Compact 3단계로 동작하며, Compact 단계는 메모리 단편화를 방지한다.
- Heap은 세대별 가설에 따라 Young(Eden + Survivor)과 Old Generation으로 구분되며, 객체는 Age를 쌓아 Old로 Promote된다.
- Minor GC는 Young에서 자주 짧게, Full GC는 전체 Heap에서 드물지만 길게 발생한다.
- Stop-The-World는 GC의 핵심 병목이며, 최신 GC(G1, ZGC)는 동시(Concurrent) 처리로 STW를 최소화하는 방향으로 발전했다.

## 기술적 한계와 보완 전략

**한계**

- **STW로 인한 응답 지연**: 어떤 GC도 STW를 완전히 제거하지는 못한다. ZGC조차 초기 Mark 시에는 STW가 발생한다.
- **GC 예측 불가능성**: GC 발생 시점과 소요 시간을 정확히 예측하기 어려워 실시간 시스템에서 문제가 될 수 있다.
- **메모리 오버헤드**: GC 메타데이터(mark bit, age count 등) 및 Survivor 영역 유지를 위한 추가 메모리가 필요하다.
- **Floating Garbage**: 동시(Concurrent) GC 방식에서는 GC 도중 새로 생성된 Garbage가 이번 사이클에 수집되지 않고 다음 사이클로 넘어가는 "뜨는 쓰레기"가 발생한다.

**보완 전략**

- Young Generation 크기 조정: `-Xmn` 옵션으로 Minor GC 빈도와 크기 트레이드오프 조정
- GC 알고리즘 선택: 처리량 우선이면 Parallel GC, 지연 최소화가 우선이면 ZGC 선택
- 객체 생성 줄이기: 불필요한 객체 생성을 줄여 GC 압력 자체를 낮춤 (객체 풀링, 값 타입 활용)
- GC 로그 모니터링: `-Xlog:gc*` 옵션으로 GC 로그를 수집하고 GCEasy, JVM 프로파일러로 분석

## 키워드

- **Garbage Collection**: JVM이 더 이상 참조되지 않는 객체를 자동으로 감지해 메모리를 회수하는 자동 메모리 관리 메커니즘
- **Reachability**: GC Root에서 객체 참조 그래프를 따라 도달 가능한지의 여부. 도달 불가능한 객체는 Garbage로 간주됨
- **Mark-Sweep-Compact**: GC의 기본 3단계. Mark(살아있는 객체 표시), Sweep(죽은 객체 제거), Compact(살아있는 객체를 앞으로 이동해 단편화 제거)
- **Heap Memory**: JVM이 런타임에 객체를 동적으로 할당하는 메모리 영역. GC의 주 관리 대상
- **Young/Old Generation**: 세대별 가설 기반의 Heap 분리 구조. Young은 새로 생성된 객체, Old는 오래 살아남아 Promote된 객체 저장
- **Minor GC / Full GC**: Minor GC는 Young Generation만 수집하는 빠르고 잦은 GC. Full GC는 전체 Heap을 수집하는 느리고 드문 GC
- **Stop-The-World**: GC 수행 시 모든 애플리케이션 스레드를 일시 정지시키는 현상. GC의 핵심 성능 병목
- **G1 GC**: Java 9 이후 기본 GC 알고리즘. Heap을 리전 단위로 분할해 관리하며 예측 가능한 Pause 시간을 목표로 함
- **ZGC**: Java 15에서 정식 출시된 초저지연 GC. 로드 배리어와 컬러드 포인터 기술로 10ms 이하 Pause 목표
- **Root Set (GC Root)**: GC 탐색의 시작점. 현재 스택의 로컬 변수, 정적 변수, JNI 참조, 활성 스레드 등이 해당됨
