# JVM이 종료될 때의 절차

## 개요
JVM이 시작할 때 부트스트랩 절차를 거치듯, 종료될 때에도 정해진 순서의 정리 절차를 거친다. `main` 메서드 반환, `System.exit()` 호출, 시그널 수신, OOM/크래시 등 종료를 유발하는 트리거는 다양하며, 각 트리거에 따라 정상 종료(orderly shutdown)와 강제 종료(forced/abrupt termination)의 경로가 갈린다. 이 문서에서는 JVM 종료가 어떤 단계로 진행되는지, Shutdown Hook과 Finalizer가 언제 어떻게 실행되는지, 그리고 종료 시 주의할 점을 정리한다.

## 상세 내용

### 1. JVM 종료를 유발하는 트리거

JVM의 종료는 크게 두 가지 경로로 나뉜다.

**정상 종료(Orderly Shutdown)**
- 모든 non-daemon 스레드의 종료 — 마지막 사용자 스레드의 `run()` 메서드가 반환되면 JVM은 자동으로 종료 시퀀스에 진입한다.
- `System.exit(int)` 또는 `Runtime.exit(int)` 호출 — 명시적으로 종료를 요청하며, Shutdown Hook을 포함한 전체 종료 시퀀스가 실행된다.
- 외부 시그널 수신(SIGTERM, SIGINT) — OS나 컨테이너 런타임이 보내는 종료 요청으로, JVM 기본 시그널 핸들러가 `System.exit()`에 해당하는 종료 시퀀스를 트리거한다.

**강제 종료(Abrupt Termination)**
- `Runtime.halt(int)` 호출 — Shutdown Hook과 Finalizer를 모두 건너뛰고 JVM 프로세스를 즉시 종료한다.
- SIGKILL 수신 — 운영체제 수준에서 프로세스를 강제 제거하며, JVM이 어떠한 정리 작업도 수행할 기회를 얻지 못한다.
- JVM 내부 치명적 오류 — 네이티브 크래시, 스택 오버플로우 등의 치명적 오류는 보장 없이 즉시 종료될 수 있다.

### 2. 정상 종료의 전체 흐름

정상 종료는 다음 단계로 진행된다.

```
1. 종료 트리거 감지
        │
        ▼
2. Shutdown 시퀀스 진입 (Shutdown.exit 호출)
        │
        ▼
3. 등록된 모든 Shutdown Hook을 병렬로 시작
        │
        ▼
4. 모든 Hook이 종료될 때까지 대기
        │
        ▼
5. (옵션) finalization-on-exit 활성화 시 미호출 Finalizer 실행
        │
        ▼
6. 네이티브 자원 해제 및 exit code와 함께 프로세스 종료
```

**non-daemon 스레드 vs daemon 스레드**

JVM은 실행 중인 모든 스레드를 두 종류로 구분한다.

- **non-daemon 스레드**: `main` 스레드를 포함하여 기본적으로 생성되는 사용자 스레드. 이 스레드가 하나라도 살아있으면 JVM은 종료되지 않는다.
- **daemon 스레드**: `thread.setDaemon(true)`로 지정한 스레드. GC 스레드, JIT 컴파일 스레드 등이 해당된다. daemon 스레드는 JVM 종료를 막지 못하며, non-daemon 스레드가 모두 종료되면 daemon 스레드는 강제로 중단된다.

따라서 중요한 I/O 작업이나 자원 정리 로직을 daemon 스레드에서 수행하면 완료를 보장받을 수 없다.

### 3. Shutdown Hook

Shutdown Hook은 `Runtime.getRuntime().addShutdownHook(Thread)` 메서드로 등록하는 미시작 Thread 객체다. JVM이 정상 종료 시퀀스에 진입하면 등록된 모든 Hook 스레드를 동시에 시작한다.

**등록 및 해제**

```java
Thread hook = new Thread(() -> {
    // 종료 시 수행할 정리 작업
    closeResources();
    flushBuffers();
});
Runtime.getRuntime().addShutdownHook(hook);

// 필요 시 해제 (종료 시퀀스 시작 전에만 가능)
Runtime.getRuntime().removeShutdownHook(hook);
```

**보장되는 것**

- 정상 종료 시 (orderly shutdown) 반드시 실행된다.
- Hook 스레드가 모두 종료될 때까지 JVM은 기다린다.

**보장되지 않는 것**

- 실행 순서 — Hook들은 병렬로, 순서 없이 실행된다. Hook A가 Hook B보다 먼저 완료된다는 보장이 없다.
- 실행 시간 제한 — JVM에는 Hook 타임아웃이 없다. Hook 내부에서 블로킹이 발생하면 JVM이 영원히 종료되지 못한다.
- 강제 종료 시 실행 — `Runtime.halt()`나 SIGKILL로 종료되면 Hook은 실행되지 않는다.
- JVM 크래시 시 실행 — 네이티브 수준의 치명적 오류에서는 보장되지 않는다.

**Hook 내부의 주의사항**

- Hook 내부에서 다른 Hook에 의존하거나 Lock을 획득하려 하면 데드락이 발생할 수 있다.
- Hook 실행 중 새로운 Hook을 등록하거나 `System.exit()`를 재호출하면 예외가 발생한다.
- 가능하면 단일 Hook 진입점에서 모든 정리 로직을 순차적으로 실행하는 것이 안전하다.

```java
// 권장: 단일 Hook으로 순차 정리
Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    try {
        dbConnectionPool.shutdown();
        kafkaProducer.flush();
        executorService.awaitTermination(10, TimeUnit.SECONDS);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}));
```

### 4. System.exit() vs Runtime.halt()

두 메서드는 모두 JVM을 종료하지만 동작 방식이 근본적으로 다르다.

| 항목 | `System.exit(int)` | `Runtime.halt(int)` |
|------|-------------------|---------------------|
| Shutdown Hook 실행 | O | X |
| Finalizer 실행 | 옵션에 따라 | X |
| 정상 종료 시퀀스 | 전체 수행 | 건너뜀 |
| 사용 목적 | 일반적인 프로그램 종료 | 비상 탈출 (데드락 방지 등) |

`System.exit(int)`는 내부적으로 `Runtime.exit(int)`를 호출하며, exit code 0은 정상 종료, 0 이외의 값은 비정상 종료를 의미한다. Unix 관례상 exit code는 0~255 범위를 사용한다.

`Runtime.halt()`의 주된 실용 사례는 Shutdown Hook 안에서 데드락이 발생했을 때 강제로 JVM을 빠져나오기 위한 워치독 스레드에서 호출하는 것이다.

```java
// Shutdown Hook 데드락 방지 워치독 예시
Thread watchdog = new Thread(() -> {
    try {
        Thread.sleep(30_000); // 30초 대기
    } catch (InterruptedException ignored) {}
    Runtime.getRuntime().halt(1); // 강제 종료
});
watchdog.setDaemon(true);
watchdog.start();
```

### 5. Finalizer와 종료

`finalize()` 메서드는 GC가 객체를 회수하기 전에 호출하는 콜백으로, 오랫동안 자원 해제 용도로 사용되었다.

**현황: JEP 421 (Java 18)**

JEP 421은 Java 18에서 `finalize()`를 deprecated for removal로 지정했다. 이유는 다음과 같다.

- **예측 불가능한 실행 시점**: GC가 언제 finalize를 호출할지 보장할 수 없다.
- **객체 부활(resurrection) 문제**: finalize 내부에서 `this`를 다른 참조에 할당하면 객체가 되살아날 수 있다.
- **성능 저하**: finalize를 구현한 객체는 GC 처리 비용이 추가적으로 발생한다.
- **보안 취약점**: finalize를 통한 공격 벡터가 존재한다.

Java 18부터는 `--finalization=disabled` 옵션으로 finalization을 비활성화하여 의존 여부를 테스트할 수 있다.

**권장 대안: `Cleaner` API (Java 9+)**

`java.lang.ref.Cleaner`는 Phantom Reference를 내부적으로 사용하여 객체가 GC에 의해 회수될 때 정리 액션을 실행한다.

```java
public class ResourceHolder implements AutoCloseable {

    private static final Cleaner CLEANER = Cleaner.create();

    // 정리 대상 상태를 static 내부 클래스로 분리 (outer 참조 금지)
    private static class State implements Runnable {
        private final FileDescriptor fd;

        State(FileDescriptor fd) { this.fd = fd; }

        @Override
        public void run() {
            // GC에 의해 또는 명시적 close() 호출 시 실행
            fd.release();
        }
    }

    private final Cleaner.Cleanable cleanable;

    public ResourceHolder(FileDescriptor fd) {
        this.cleanable = CLEANER.register(this, new State(fd));
    }

    @Override
    public void close() {
        cleanable.clean(); // 명시적 호출 시 즉시 정리
    }
}
```

핵심 원칙: 정리 액션은 외부 객체(this)를 참조해서는 안 된다. 참조하면 해당 객체가 phantom reachable 상태가 되지 않아 Cleaner가 동작하지 않는다.

**우선 순위**는 try-with-resources > Cleaner > finalize 순이다.

### 6. 시그널 기반 종료 (컨테이너 환경)

컨테이너 환경에서는 OS 시그널을 통한 종료가 주요 패턴이다.

**SIGTERM (signal 15)**

- JVM의 기본 시그널 핸들러가 `System.exit()`에 상당하는 종료 시퀀스를 트리거한다.
- 등록된 Shutdown Hook이 실행된다.
- 컨테이너 오케스트레이터(Kubernetes, Docker)는 Pod 종료 시 SIGTERM을 먼저 보낸다.

**SIGKILL (signal 9)**

- 운영체제가 프로세스를 강제 제거하므로 JVM이 어떠한 정리 코드도 실행하지 못한다.
- Kubernetes는 `terminationGracePeriodSeconds` 경과 후 SIGKILL을 보낸다.

**Kubernetes의 Pod 종료 흐름**

```
1. kubectl delete / 스케일링 등으로 Pod 종료 요청
        │
        ▼
2. Pod 상태를 Terminating으로 표시
        │
        ├─────────────────────────────────────────────┐
        │                                             │
        ▼                                             ▼
3. SIGTERM 전송 → JVM Shutdown Hook 실행       preStop Hook 실행 (선택)
        │
        ▼
4. terminationGracePeriodSeconds 대기 (기본 30초)
        │
        ▼
5. 대기 시간 초과 시 SIGKILL 전송
```

**Spring Boot Graceful Shutdown (2.3+)**

Spring Boot 2.3부터 graceful shutdown을 지원한다.

```yaml
# application.yml
server:
  shutdown: graceful

spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s
```

SIGTERM 수신 시 Spring은 내장 서버(Tomcat/Jetty/Undertow)를 drain 모드로 전환하여 신규 요청을 거부하고, 진행 중인 요청이 완료되거나 타임아웃이 될 때까지 대기한 후 Shutdown Hook을 통해 JVM을 종료한다.

**주의**: `terminationGracePeriodSeconds`는 Spring의 `timeout-per-shutdown-phase`보다 충분히 크게 설정해야 한다. Spring 타임아웃이 30초인데 Kubernetes grace period가 30초면, Kubernetes가 SIGKILL을 보내기 전에 Spring이 정리를 마치지 못할 수 있다.

### 7. 종료 코드와 비정상 종료

**주요 exit code 관례**

| Exit Code | 의미 |
|-----------|------|
| 0 | 정상 종료 |
| 1 | 일반 오류 (`System.exit(1)` 또는 미처리 예외) |
| 3 | `-XX:+ExitOnOutOfMemoryError` 옵션 사용 시 OOM 발생 |
| 137 | 128 + 9(SIGKILL) — 외부에서 SIGKILL로 강제 종료됨 |
| 143 | 128 + 15(SIGTERM) — SIGTERM을 받아 종료됨 (정상 종료와 다름) |

Kubernetes 환경에서 exit code 137은 grace period 초과로 SIGKILL이 도달했음을 의미한다.

**OOM 관련 JVM 옵션**

```
-XX:+ExitOnOutOfMemoryError    → OOM 발생 시 exit code 3으로 즉시 종료
-XX:+CrashOnOutOfMemoryError   → OOM 발생 시 hs_err_pid.log 크래시 로그 생성 후 종료
                                  (진단 목적에 더 적합)
-XX:OnOutOfMemoryError="..."   → OOM 발생 시 지정한 셸 명령어 실행
```

`hs_err_pid<pid>.log` 파일은 JVM 내부 크래시 시 생성되며, 스레드 상태, 힙 사용량, 네이티브 스택 등 사후 진단에 필요한 정보를 담고 있다.

### 한 눈에 보기

```
[정상 종료] non-daemon 스레드 모두 종료 / System.exit() / SIGTERM
  → Shutdown 시퀀스 진입 → Shutdown Hook 병렬 실행(무순서) → (옵션) Finalizer → 네이티브 자원 해제 → exit code와 함께 프로세스 종료

[강제 종료] Runtime.halt() / SIGKILL / 네이티브 크래시
  → Hook·Finalizer 모두 건너뜀 → 정리 없이 즉시 종료
```

> 한 줄 요약: **정상 종료는 `Shutdown Hook → (Finalizer) → 종료`의 정해진 절차를 밟지만, `halt()`·SIGKILL은 모든 정리를 건너뛰고 즉시 끝낸다.**

## 핵심 정리
- 정상 종료는 "모든 non-daemon 스레드 종료" 또는 "`System.exit()` 호출"로 시작되며, 이때만 Shutdown Hook이 실행된다.
- Shutdown Hook들은 병렬·무순서로 실행되므로 Hook 간 의존성을 가정하면 안 된다.
- `Runtime.halt()`와 SIGKILL은 Hook과 Finalizer를 건너뛰므로 자원 정리가 보장되지 않는다.
- daemon 스레드는 JVM 종료를 막지 못하며, 종료 시 갑자기 중단될 수 있어 중요한 작업에 사용하면 위험하다.
- `finalize()`는 JEP 421로 deprecated이며, 종료 시 자원 정리는 try-with-resources 또는 `Cleaner`로 대체해야 한다.

## 기술적 한계와 보완 전략
- Shutdown Hook은 실행 시간 제한이 없어, Hook 내부에서 블로킹되면 JVM이 영원히 종료되지 못한다. 타임아웃 워치독 스레드(daemon)를 두어 일정 시간 후 `Runtime.halt()`로 강제 종료를 보장한다.
- 컨테이너에서 SIGKILL이 SIGTERM보다 먼저 도달하거나 grace period가 짧으면 Hook이 실행될 시간이 부족하다. `terminationGracePeriodSeconds`를 애플리케이션 최대 정리 시간보다 여유 있게 설정한다.
- 다수의 Hook이 동일 자원에 접근하면 경쟁 상태가 발생할 수 있다. Hook 수를 최소화하고 단일 진입점에서 정리 로직을 일원화한다.
- `Cleaner` 액션이 외부 객체를 참조하면 phantom reachable 상태가 되지 않아 정리가 실행되지 않는다. 반드시 static 내부 클래스로 상태를 분리해야 한다.

## 키워드

### Shutdown Hook
JVM 정상 종료 시퀀스에서 실행되도록 `Runtime.getRuntime().addShutdownHook(Thread)`로 등록하는 미시작 Thread 객체. 커넥션 풀 종료, 버퍼 플러시, 임시 파일 삭제 등 정리 작업에 사용된다. Hook들은 병렬로 실행되며 순서가 보장되지 않는다. 종료 시퀀스가 시작된 후에는 신규 등록이 불가하며, Hook 내부에서 `System.exit()`를 재호출하면 예외가 발생한다.

### Orderly Shutdown
JVM이 정해진 절차를 따라 단계적으로 종료되는 방식. 모든 non-daemon 스레드 종료 또는 `System.exit()` 호출로 시작되며, Shutdown Hook 실행 → (옵션) Finalizer 실행 → 프로세스 종료 순으로 진행된다. Abrupt Termination과 대비되는 개념이다.

### System.exit / Runtime.halt
`System.exit(int)`는 orderly shutdown 시퀀스(Hook 포함)를 수행하고 종료한다. `Runtime.halt(int)`는 Hook과 Finalizer를 모두 건너뛰고 JVM을 즉시 강제 종료한다. `halt()`는 Hook 데드락 탈출용 워치독 등 특수 목적에만 사용해야 한다.

### Daemon Thread
`thread.setDaemon(true)`로 지정된 스레드. JVM은 non-daemon 스레드가 모두 종료되면 종료 시퀀스를 시작하며, daemon 스레드의 실행 여부는 판단 기준에 포함되지 않는다. GC 스레드, JIT 컴파일 스레드, 내부 타이머 스레드 등이 daemon으로 실행된다. 종료 시 daemon 스레드는 별도 정리 없이 강제 중단된다.

### Finalizer / Cleaner
`finalize()` 메서드는 GC 직전 객체에 대해 JVM이 호출하던 콜백이나, JEP 421(Java 18)로 deprecated for removal 되었다. 실행 시점 예측 불가, 객체 부활, 성능 저하, 보안 취약점이 주요 문제였다. 대안으로 Java 9에서 도입된 `java.lang.ref.Cleaner`는 Phantom Reference를 활용하여 객체가 GC 대상이 될 때 정리 액션(Runnable)을 실행한다. 가장 권장되는 방식은 AutoCloseable + try-with-resources다.

### SIGTERM / SIGKILL
Unix 시그널로, SIGTERM(15)은 종료를 요청하는 소프트 시그널로 JVM이 핸들러를 통해 orderly shutdown을 트리거할 수 있다. SIGKILL(9)는 운영체제가 프로세스를 강제 제거하는 하드 시그널로, JVM이 핸들링할 수 없어 어떠한 정리 코드도 실행되지 않는다. Kubernetes는 Pod 종료 시 먼저 SIGTERM을 보내고, grace period 이후 SIGKILL을 보낸다.

### Graceful Shutdown
진행 중인 작업을 모두 완료한 뒤 정상적으로 종료하는 전략. Spring Boot 2.3+에서 `server.shutdown: graceful` 설정으로 활성화하면 SIGTERM 수신 시 신규 요청 수락을 중단하고 기존 요청 처리를 완료한 후 종료한다. 컨테이너 환경에서는 Kubernetes의 `terminationGracePeriodSeconds`와 함께 설계해야 한다.

### Exit Code (137 / 143)
Unix에서 시그널로 종료된 프로세스의 exit code는 `128 + 시그널 번호`로 표현된다. exit code 137(128+9)는 SIGKILL로 강제 종료됨을 의미하며, Kubernetes에서 grace period 초과 시 나타난다. exit code 143(128+15)는 SIGTERM을 수신하여 종료됨을 의미한다. exit code 3은 `-XX:+ExitOnOutOfMemoryError` 옵션으로 OOM 발생 시 JVM이 반환하는 코드다.

### terminationGracePeriodSeconds
Kubernetes에서 Pod가 SIGTERM을 수신한 후 SIGKILL이 오기 전까지 허용되는 최대 대기 시간(초). 기본값은 30초다. 이 시간 안에 JVM의 Shutdown Hook과 Spring의 graceful shutdown이 모두 완료되어야 데이터 손실 없이 정상 종료할 수 있다. 애플리케이션의 실제 종료 소요 시간보다 충분히 크게 설정해야 한다.

### Abrupt Termination
JVM이 정해진 종료 시퀀스 없이 즉시 종료되는 방식. `Runtime.halt()`, SIGKILL, 네이티브 크래시가 해당된다. Shutdown Hook과 Finalizer가 실행되지 않으므로 데이터 손실이나 자원 누수가 발생할 수 있다. Orderly Shutdown과 대비되는 개념이다.
