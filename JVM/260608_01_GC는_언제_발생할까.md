# GC는 언제 발생할까

## 개요

JVM의 Garbage Collection이 어떤 시점·조건에서 트리거되는지 정리한다. GC는 단순히 "메모리가 부족할 때" 발생하는 것처럼 보이지만, 힙 구조와 GC 알고리즘에 따라 트리거 조건이 세밀하게 다르다.

## 상세 내용

### 1. GC의 기본 트리거 조건

GC가 발생하는 근본적인 조건은 **객체 할당 실패(Allocation Failure)** 다. JVM이 Young Generation(Eden)에 새 객체를 할당하려 할 때 여유 공간이 없으면 Minor GC가 트리거된다.

**세 가지 기본 원인**

- **Allocation Failure**: Eden 영역에 새 객체를 생성할 공간이 없을 때. Young Generation에서 여유 공간이 부족해 새 객체를 만들 수 없을 때 JVM이 Minor GC를 수행한다.
- **임계 점유율 도달**: Old Generation이나 Metaspace가 일정 비율 이상 채워졌을 때.
- **명시적 요청**: `System.gc()` 호출. 단, 이는 JVM에 대한 권고(hint)일 뿐 즉시 실행을 강제하지 않는다. `-XX:+DisableExplicitGC` 플래그로 무시하도록 설정할 수 있다.

### 2. 힙 구조와 GC 발생 영역

JVM 힙은 수명에 따라 영역이 나뉘며, 각 영역마다 GC 발생 조건이 다르다.

```
Heap
├── Young Generation
│   ├── Eden Space       ← 새 객체 생성 영역
│   ├── Survivor 0 (S0)  ← Minor GC 후 생존 객체 이동
│   └── Survivor 1 (S1)
├── Old (Tenured) Generation ← Promotion된 장수 객체
└── Metaspace (Java 8+)      ← 클래스 메타데이터 (이전: PermGen)
```

- **Young Generation**: 새로 생성된 객체의 대부분이 위치. Eden이 가득 차면 Minor GC가 발생한다.
- **Old Generation**: Minor GC를 여러 번 살아남아 Promotion된 객체가 존재. Old가 가득 차면 Major/Full GC가 발생한다.
- **Metaspace**: 클래스 메타데이터를 저장하는 네이티브 메모리 영역. Java 8 이전의 PermGen을 대체하며, 여기가 꽉 차면 Full GC가 트리거될 수 있다.

### 3. Minor GC가 발생하는 시점

Minor GC는 Young Generation만을 대상으로 하는 GC다.

**트리거 조건**
- Eden 영역이 가득 찼을 때 (Allocation Failure)

**Minor GC 동작 절차**

1. Eden의 살아있는 객체를 Survivor 영역(S0 또는 S1) 중 비어있는 쪽으로 복사한다.
2. 이미 Survivor에 있던 살아있는 객체를 반대쪽 Survivor로 이동시킨다.
3. 이동된 객체의 **age(나이)**를 1 증가시킨다.
4. age가 `-XX:MaxTenuringThreshold`(기본값 15)를 초과하면 **Old Generation으로 Promotion**한다.
5. Eden과 기존 Survivor 영역을 비운다.

**Promotion 조건**
- age가 TenuringThreshold를 초과한 경우
- Survivor 공간이 부족해 더 이상 담을 수 없는 경우 → 강제 Promotion

Minor GC는 항상 Stop-The-World(STW) 를 동반하지만, Young Generation만 대상으로 하므로 일반적으로 짧다.

### 4. Major / Full GC가 발생하는 시점

**Major GC**는 Old Generation을 정리하는 GC이고, **Full GC**는 힙 전체(Young + Old + Metaspace)를 대상으로 하는 GC다.

**트리거 조건 목록**

| 조건 | 설명 |
|------|------|
| Old Generation 점유율 초과 | Old 영역이 꽉 차서 더 이상 Promotion을 수용 불가 |
| Promotion Failure | Minor GC 중 Survivor 공간 부족으로 Old로 Promotion 시도했으나 Old도 공간 부족 |
| Concurrent Mode Failure (CMS) | CMS가 동시 정리를 완료하기 전에 Old가 가득 찬 경우, STW Full GC로 폴백 |
| Metaspace 부족 | 클래스 메타데이터 공간이 꽉 찬 경우 |
| `System.gc()` 호출 | 명시적 요청 (강제는 아님) |
| OutOfMemoryError 직전 | JVM이 OOM을 던지기 전 마지막으로 Full GC를 시도 |

**Promotion Failure 발생 흐름**

```
Minor GC 발생
    → 객체를 Survivor로 이동하려 했으나 공간 부족
    → Old Generation으로 Promotion 시도
    → Old Generation도 공간 부족 또는 단편화로 인해 실패
    → Promotion Failure → Full GC 트리거
```

Full GC는 힙 전체를 대상으로 하므로 STW 시간이 길어 애플리케이션 응답 지연의 주된 원인이 된다.

### 5. GC 알고리즘별 트리거 차이

GC 알고리즘마다 트리거 기준과 STW 범위가 다르다.

**Serial / Parallel GC**
- Eden이 가득 차면 Minor GC
- Old가 가득 차면 STW Full GC (Parallel GC는 멀티스레드로 처리)
- 단순하고 예측 가능한 트리거 구조

**CMS (Concurrent Mark Sweep)**
- Old Generation의 점유율이 `-XX:CMSInitiatingOccupancyFraction`(기본 68%) 을 초과하면 동시 마킹 시작
- 동시 처리 중 Old가 계속 차오르면 **Concurrent Mode Failure** 발생 → STW Full GC로 폴백
- 단편화 문제가 심해지면 Promotion Failure도 발생
- Java 9에서 deprecated, Java 14에서 제거됨

**G1 GC (Garbage First)**
- Young GC: Eden 영역이 꽉 차면 발생 (Minor GC와 유사)
- Mixed GC: 동시 마킹 사이클 완료 후 Young + Old 일부 리전 함께 수집
- **IHOP (Initiating Heap Occupancy Percent)**: `-XX:InitiatingHeapOccupancyPercent`(기본 45%)를 초과하면 동시 마킹 사이클 시작
- **Adaptive IHOP**: G1이 마킹 소요 시간과 Old 할당 속도를 관찰해 IHOP 임계값을 자동 조정
- Full GC: Evacuation Failure 또는 동시 마킹이 완료되기 전 Old가 가득 차면 STW Full GC 발생
- `-XX:-G1UseAdaptiveIHOP`으로 Adaptive IHOP 비활성화 가능

**ZGC**
- 힙 점유율이 특정 임계값을 넘거나 할당 속도가 빠른 경우 동시 컬렉션 트리거
- 마킹, 재배치(relocation) 모두 애플리케이션 스레드와 동시에 수행
- STW는 Root 스캔 같은 짧은 단계에만 발생 (목표: 1ms 미만)
- Java 21부터 **Generational ZGC** 도입으로 Young/Old 영역 구분 처리

**Shenandoah**
- ZGC와 유사하게 동시 수집 방식
- Brooks Pointer(전달 포인터) 방식으로 이동 중에도 객체 참조 유지
- STW 목표: 10ms 미만
- 힙 점유율과 할당 속도를 기반으로 동시 컬렉션 시작 시점 결정

### 6. Stop-The-World가 동반되는 시점

**Safepoint란**

Safepoint는 JVM이 모든 스레드의 상태를 정확히 파악할 수 있는 시점이다. GC 수행 전 JVM은 모든 애플리케이션 스레드를 Safepoint에 도달시켜야 한다.

**STW 동작 흐름**

```
GC 트리거 감지
    → JVM이 모든 스레드에 Safepoint 요청 플래그 설정
    → 각 스레드는 실행 중 특정 지점(루프 뒤, 메서드 호출 전후 등)에서 플래그 폴링
    → 모든 스레드가 Safepoint 도달 (TTSP: Time To Safepoint)
    → GC 작업 수행
    → 스레드 재개
```

**TTSP (Time To Safepoint)**: 스레드들이 Safepoint에 모두 도달하는 데 걸리는 시간. 실제 GC pause 시간과 별개로 추가 지연을 발생시킬 수 있다.

**STW를 동반하는 주요 GC 단계**

| GC 알고리즘 | STW 발생 시점 |
|------------|-------------|
| Serial/Parallel GC | Minor GC 전체, Full GC 전체 |
| CMS | Initial Mark, Remark 단계 |
| G1 GC | Young GC 전체, Initial Mark, Remark, Cleanup 단계 |
| ZGC | Root 스캔, 재배치 시작 단계 (매우 짧음) |
| Shenandoah | Root 스캔, 최종 마킹 단계 (매우 짧음) |

## 핵심 정리

- GC는 기본적으로 "메모리 할당 실패" 또는 "임계 점유율 도달" 시 발생한다.
- 영역에 따라 **Minor GC**(Young)와 **Major/Full GC**(Old + 전체)로 나뉜다.
- GC 알고리즘마다 트리거 기준과 STW 범위가 다르다. 최신 알고리즘(ZGC, Shenandoah)일수록 STW가 짧고 동시 처리 비중이 높다.
- Full GC는 STW 시간이 길어 애플리케이션 응답 지연의 주된 원인이 된다.

## 기술적 한계와 보완 전략

- `System.gc()`는 권고일 뿐 강제 실행을 보장하지 않는다 → `-XX:+DisableExplicitGC`로 명시적 GC 호출 무시
- 잦은 Full GC로 인한 성능 저하 → 힙 사이징, GC 튜닝, G1/ZGC 전환
- Promotion Failure 방지 → `-XX:MaxTenuringThreshold`와 Survivor 비율 조정으로 Promotion 속도 제어
- CMS Concurrent Mode Failure → `-XX:CMSInitiatingOccupancyFraction` 낮춰 CMS가 더 일찍 시작하도록 유도
- G1 GC IHOP 튜닝 → 할당 속도가 빠른 경우 `-XX:InitiatingHeapOccupancyPercent`를 30~35%로 낮춰 마킹을 더 일찍 시작
- TTSP 지연 문제 → 긴 루프 내 Safepoint 폴링 지점 부재 시 TTSP 증가 → JVM 플래그 또는 코드 구조 개선으로 해결

## 키워드

### Garbage Collection (가비지 컬렉션)
JVM이 더 이상 참조되지 않는 객체를 찾아 메모리를 회수하는 자동 메모리 관리 메커니즘. 개발자가 직접 메모리를 해제하지 않아도 되지만, GC 발생 시점과 방식을 이해해야 성능 문제를 진단하고 튜닝할 수 있다.

### Minor GC
Young Generation(Eden + Survivor)을 대상으로 하는 GC. Eden이 가득 차 Allocation Failure가 발생했을 때 트리거된다. STW를 동반하지만 대상 영역이 작아 일반적으로 빠르다.

### Major GC / Full GC
Major GC는 Old Generation을 정리하는 GC, Full GC는 힙 전체(Young + Old + Metaspace)를 정리하는 GC다. Old 영역이 가득 찼거나 Promotion Failure 등이 발생했을 때 트리거된다. STW 시간이 길어 성능에 큰 영향을 준다.

### Eden / Survivor / Old Generation
JVM 힙의 세대별 영역 구성. Eden은 새로 생성된 객체가 할당되는 곳, Survivor는 Minor GC를 살아남은 객체가 이동하는 곳, Old Generation은 여러 번의 GC를 살아남아 Promotion된 장수 객체들이 머무는 곳이다.

### Promotion (프로모션)
Minor GC 과정에서 Survivor 영역의 객체 age가 TenuringThreshold를 초과하거나 Survivor 공간이 부족할 때 해당 객체를 Old Generation으로 이동시키는 것. Promotion 빈도가 높을수록 Old GC 발생 가능성이 높아진다.

### Stop-The-World (STW)
GC 수행을 위해 모든 애플리케이션 스레드를 일시 정지시키는 것. GC 알고리즘이 발전할수록 STW 시간을 줄이거나 동시 처리로 대체하는 방향으로 진화하고 있다.

### Safepoint (세이프포인트)
JVM이 모든 스레드의 정확한 상태(어떤 객체가 살아있는지, 스택 프레임 위치 등)를 파악할 수 있는 실행 지점. GC 수행 전 모든 스레드를 Safepoint에 도달시켜야 하며, 이 시간(TTSP)도 GC pause의 일부다.

### G1 GC IHOP (Initiating Heap Occupancy Percent)
G1 GC가 동시 마킹 사이클을 시작하는 Old Generation 점유율 임계값. 기본값은 45%. G1은 Adaptive IHOP 기능으로 할당 속도와 마킹 소요 시간을 관찰해 이 값을 자동으로 조정한다.

### Allocation Failure (할당 실패)
JVM이 Young Generation에 새 객체를 생성하려 했으나 여유 공간이 없는 상태. Minor GC의 직접적인 트리거 원인이다. GC 로그에서 `GC (Allocation Failure)` 메시지로 확인할 수 있다.
