# PG 연동을 위한 시스템 설계 및 개발

## 개요
PG(Payment Gateway)는 가맹점과 카드사/은행 사이의 결제 처리를 중계하는 시스템이다. 가맹점은 PG사 하나와 계약하는 것만으로 카드사, 은행, 간편결제 등 다양한 결제기관과 연결할 수 있다. PG 연동 시스템을 설계할 때는 결제의 정확성, 트랜잭션 일관성, 보안, 장애 복원력 등을 동시에 고려해야 한다. 본 문서에서는 PG 연동 시스템의 아키텍처 설계와 개발 시 필수적으로 고려해야 할 요소들을 정리한다.

## 상세 내용

### 1. PG 연동의 기본 흐름

결제는 **요청 → 인증 → 승인**의 3단계로 진행된다.

#### 1.1 결제 요청
- 구매자가 결제하기 버튼을 클릭하면 클라이언트에서 PG SDK의 결제 요청 메서드를 호출하여 결제창을 띄운다.
- 이 시점에 서버는 `orderId`와 최종 결제 금액을 DB 또는 세션에 임시 저장해야 한다. 이 값이 위변조 검증의 기준이 된다.

#### 1.2 구매자 인증 (카드사 인증)
- 구매자가 카드 정보(카드번호, 만료일, CVC 등)를 입력하거나 간편결제 앱으로 불러오면, 카드사가 카드 소유자를 인증한다.
- 인증 완료 후 PG사는 고유한 `paymentKey`를 발급하고 성공 URL로 리다이렉트한다.
- 이때 URL 파라미터로 `paymentKey`, `orderId`, `amount`가 전달된다.

#### 1.3 결제 승인 (서버 사이드 처리)

```
[Client] 결제창 호출
    ↓  (PG SDK)
[PG사] 카드사 인증
    ↓  (인증 완료, paymentKey 발급)
[Client] 성공 URL로 리다이렉트 (paymentKey, orderId, amount 포함)
    ↓
[Server] 금액 위변조 검증 (DB 저장 금액 vs 파라미터 금액 비교)
    ↓  (일치하는 경우에만)
[Server] PG 승인 API 호출 (paymentKey, orderId, amount)
    ↓
[PG사] 카드사 최종 승인 → 결제 금액 차감
    ↓
[Server] 결제 완료 처리 (주문 상태 업데이트, paymentKey DB 저장)
```

인증과 승인을 분리하는 이유는 데이터 정합성 때문이다. 클라이언트에서 금액을 조작해 승인을 시도하는 공격을 서버 사이드 검증으로 차단하고, 네트워크 장애나 웹훅 미수신으로 인한 데이터 불일치를 방지한다.

### 2. 시스템 아키텍처 설계

#### 2.1 결제 도메인 분리

결제는 주문 도메인과 명확한 경계를 가져야 한다. 결제 실패가 주문 로직에 영향을 주거나, 주문 취소가 결제 취소 없이 완료되는 일이 없어야 하기 때문이다.

- Payment Service를 독립 모듈로 분리
- 주문 도메인과의 경계 설정 (Bounded Context)
- 결제 상태 머신(State Machine) 명확히 정의

**토스페이먼츠 기준 결제 상태 값:**

| 상태 | 설명 |
|---|---|
| READY | 결제 준비 중 (결제창 열림) |
| IN_PROGRESS | 결제 진행 중 |
| WAITING_FOR_DEPOSIT | 가상계좌 입금 대기 |
| DONE | 결제 완료 |
| CANCELED | 결제 취소 |
| PARTIAL_CANCELED | 부분 취소 |
| ABORTED | 카드 자동 결제 승인 실패 |
| EXPIRED | 유효 시간(30분) 초과로 거래 취소 |

상태 전이는 허용된 방향으로만 이루어지도록 State Machine을 코드 수준에서 강제해야 한다. 예를 들어 DONE 상태에서 다시 IN_PROGRESS로 전이되는 것은 불가능해야 한다.

#### 2.2 PG사 추상화 계층 (어댑터 패턴)

서비스가 성장하면 PG사를 교체하거나 여러 PG사를 동시에 운영해야 하는 상황이 생긴다. 이때 결제 로직이 특정 PG사에 강하게 결합되어 있으면 변경 비용이 매우 크다.

```
[PaymentService] (도메인 로직)
        ↓
[PaymentGateway Interface] (추상화 계층)
        ↓
[TossPaymentsAdapter] [PortOneAdapter] [KakaoPayAdapter]
```

어댑터 계층에서 담당하는 역할:
- PG사별 요청 파라미터 형식 변환
- PG사별 응답/에러 코드를 내부 표준 스펙으로 매핑
- PG 장애 시 Fallback PG로 전환

#### 2.3 비동기 처리와 Webhook

결제 완료 후처리(재고 차감, 알림 발송, 정산 데이터 적재 등)를 결제 승인 트랜잭션과 분리하기 위해 메시지 큐를 활용한다.

```
[결제 승인 완료]
    ↓
[Kafka / SQS 이벤트 발행]
    ↓
[재고 서비스] [알림 서비스] [정산 서비스] (각각 독립 소비)
```

Webhook은 PG사가 결제 상태가 변경될 때 상점 서버로 실시간 알림을 보내는 기능이다. 특히 가상계좌 결제에서는 구매자가 입금하는 시점을 서버가 알 수 없으므로 Webhook이 필수다.

**토스페이먼츠 Webhook 재시도 정책:**
- 서버가 10초 이내에 200 응답을 보내지 않으면 자동 재전송
- 최대 7회(3일 19시간)까지 기하급수적 간격으로 재전송
- 7회 모두 실패 시 '실패' 상태로 변경되고 이메일 통지

Webhook 수신 엔드포인트는 빠르게 200을 응답하고, 실제 처리는 비동기로 위임해야 한다.

### 3. 데이터 정합성 보장

#### 3.1 결제 위변조 방지 (금액 검증)

클라이언트에서 결제 금액을 임의로 조작해 승인 요청을 보내는 공격을 방어해야 한다.

**검증 흐름:**

```
[결제 요청 전]
→ 서버에서 orderId와 결제 금액을 DB에 임시 저장

[성공 URL 도달 시]
→ 파라미터로 받은 amount 값을
  DB에 저장된 금액과 비교

[일치하는 경우에만]
→ 승인 API 호출
```

이 검증을 통해 파라미터 위조(amount=100 → amount=1)를 통한 부정 결제를 원천 차단한다.

#### 3.2 멱등성(Idempotency) 보장

멱등성은 동일한 요청을 여러 번 실행해도 결과가 달라지지 않는 성질이다. 결제에서는 네트워크 장애로 응답을 받지 못해 요청을 재시도했을 때 이중 결제가 발생하는 것을 막는 핵심 개념이다.

**Idempotency-Key 활용 (토스페이먼츠):**

```http
POST /v1/payments/confirm
Idempotency-Key: {UUID-v4}
Authorization: Basic {secretKey}
Content-Type: application/json

{
  "paymentKey": "...",
  "orderId": "...",
  "amount": 50000
}
```

- 모든 POST 메서드 API에 `Idempotency-Key` 헤더를 추가할 수 있다.
- 동일한 키로 재요청하면 서버는 실제로 처리하지 않고 첫 번째 요청과 같은 응답을 반환한다.
- 키는 UUID v4처럼 충분히 무작위적인 고유 값으로 생성하고 최대 300자까지 허용된다.
- 첫 요청 처리 중 동일 키로 재요청하면 HTTP 409 - `IDEMPOTENT_REQUEST_PROCESSING` 에러가 반환된다.
- 유효 기간은 첫 요청부터 15일이다.

**서버 내부 멱등성 보장 전략:**
- `orderId` 또는 별도 결제 요청 ID를 유니크 키로 DB에 저장
- 동일 키로 중복 요청이 들어올 경우 DB 레벨 유니크 제약으로 중복 차단
- Redis를 활용한 분산 락으로 동시 요청 경합 방지

#### 3.3 분산 트랜잭션과 Saga 패턴

결제 승인 → 재고 차감 → 주문 확정이 모두 원자적으로 처리되어야 하지만, 각 작업이 서로 다른 서비스에 분산되어 있다면 전통적인 DB 트랜잭션을 사용할 수 없다. 이때 Saga 패턴을 적용한다.

**Choreography 방식 (이벤트 기반):**

```
결제 승인 완료 이벤트 발행
    → 재고 서비스: 재고 차감
    → 재고 차감 성공 이벤트 발행
    → 주문 서비스: 주문 확정
```

**보상 트랜잭션 (Compensation):**

```
결제 승인 완료 → 재고 차감 실패
    → 결제 취소 이벤트 발행 (보상 트랜잭션)
    → PG 환불 API 호출
```

각 단계가 실패했을 때 이전 단계를 되돌리는 보상 트랜잭션을 미리 설계해두어야 한다.

#### 3.4 결제 상태 동기화 (Reconciliation)

Webhook이 유실되거나 처리 중 장애가 발생하면 PG사의 실제 결제 상태와 내부 시스템 상태가 불일치할 수 있다.

**이중화 전략: Webhook + Polling**

```
[Webhook] 실시간 상태 업데이트
    +
[Reconciliation Job] 주기적 배치 조회
    → PG사 결제 조회 API로 상태 확인
    → 불일치 감지 시 자동 보정 또는 알람
```

미완료 상태(IN_PROGRESS)로 일정 시간(예: 30분) 이상 남아 있는 결제는 Timeout Cancel 처리해야 한다.

### 4. 보안 설계

#### 4.1 민감 정보 처리 (PCI-DSS)

PCI-DSS(Payment Card Industry Data Security Standard)는 카드사와 카드 정보를 처리하는 사업자가 반드시 준수해야 하는 보안 표준이다.

- 카드 번호, CVC 등 민감 정보를 서버에 직접 저장하지 않는다.
- PG사가 제공하는 토큰화(Tokenization) 기능을 활용하여 PG사 측에서 카드 정보를 관리하게 한다.
- 모든 API 통신은 TLS 1.2 이상의 HTTPS 연결을 사용해야 한다.
- API Secret Key는 환경 변수나 시크릿 매니저(AWS Secrets Manager 등)로 관리하고, 코드에 하드코딩하지 않는다.

#### 4.2 Webhook 위변조 방지

Webhook 엔드포인트는 외부에 공개되어 있으므로, 실제 PG사가 보낸 요청인지 검증해야 한다.

- **IP Whitelist**: PG사가 제공하는 서버 IP만 허용
- **HMAC 서명 검증**: PG사가 요청에 서명을 포함하고, 서버는 동일한 Secret Key로 서명을 재계산하여 일치 여부 확인
- **Replay Attack 방어**: 타임스탬프 기반 유효 시간 검증 (예: 5분 이내 요청만 허용)

### 5. 장애 대응 및 복원력

#### 5.1 Circuit Breaker

PG사가 응답하지 않거나 오류율이 임계치를 초과하면, 계속 요청을 보내는 것은 리소스 낭비이고 사용자 경험도 악화된다.

```
정상 상태 (Closed)
    → 오류율 임계치 초과
    → Circuit Open (요청 즉시 거절, Fast Fail)
    → 일정 시간 후 Half-Open (일부 요청 허용)
    → 성공률 회복 시 Closed 복귀
```

주 PG가 Open 상태일 때 보조 PG로 자동 전환하는 Fallback 전략을 함께 구성한다.

#### 5.2 Timeout 전략

```
Connect Timeout: 3초 (연결 수립 시간)
Read Timeout: 30초 (응답 수신 대기 시간)
```

결제 승인 응답을 받지 못한 경우 결제가 완료된 것인지 실패한 것인지 불분명하다. 이 경우 PG사 조회 API로 실제 상태를 확인한 후 후처리해야 한다.

#### 5.3 자동 환불 (보상 처리)

- 결제 승인 후 재고 차감이나 주문 처리에 실패하면 자동으로 PG 환불 API를 호출한다.
- 자동 환불도 실패하는 경우를 대비해 수동 환불 처리 도구와 알람을 제공한다.

### 6. 데이터베이스 설계

#### 6.1 Order - Payment 테이블 분리

```
Order (주문)
├── orderId (PK)
├── userId
├── totalAmount
├── status (PENDING / PAID / CANCELED)
└── createdAt

Payment (결제)
├── paymentId (PK)
├── orderId (FK)
├── paymentKey (PG사 발급, UNIQUE)
├── pgProvider (TOSS / PORTONE / KAKAOPAY)
├── method (CARD / VIRTUAL_ACCOUNT / TRANSFER)
├── amount
├── status (READY / DONE / CANCELED / ...)
├── requestedAt
└── approvedAt
```

- `paymentKey`는 PG사가 발급하는 고유 값이며, 결제 취소/조회에 필수이므로 반드시 저장해야 한다.
- 카드 번호, CVC 등 민감 정보는 저장하지 않는다.
- 주문 상태는 결제 상태 변화에 따라 업데이트하되, 이력을 남기기 위해 상태 변경을 별도 로그 테이블에 적재하는 것이 좋다.

#### 6.2 스냅샷 설계 (데이터 불변성)

주문 이후 상품 정보가 변경되어도 주문 당시 정보가 보존되어야 한다. 이를 위해 주문 생성 시점의 상품 정보를 별도 스냅샷 형태로 저장한다.

```
OrderItem (주문 상품 스냅샷)
├── orderItemId
├── orderId (FK)
├── productId
├── productName (주문 시점 스냅샷)
├── price (주문 시점 스냅샷)
└── quantity
```

### 7. 운영 및 모니터링

#### 7.1 결제 흐름 추적

- **Correlation ID**: 하나의 결제 흐름 전체를 추적할 수 있는 고유 ID를 로그에 포함
- **Distributed Tracing**: Zipkin, Jaeger 또는 Datadog APM으로 결제 단계별 지연 시간 측정
- 결제 요청 → 인증 → 승인 → 후처리 각 단계마다 구조화된 로그 수집

#### 7.2 알람 및 대시보드

- 결제 성공률이 임계치(예: 95%) 이하로 떨어지면 알람 발생
- PG사별 응답 시간 추이 모니터링
- 실패 사유별 통계 (카드 한도 초과, 비밀번호 불일치, PG 장애 등) 대시보드

### 8. 정산 및 회계 처리

PG사는 결제 금액을 즉시 가맹점에 지급하지 않고, 수수료를 제한 후 정해진 주기(D+1, D+2 등)에 정산한다. 서버 내 데이터와 PG사 명세서를 비교하는 **Reconciliation(대사)** 작업이 필요하다.

- 일/월 단위 정산 데이터 생성 배치
- PG사 명세서와 내부 결제 데이터 항목별 대사
- 불일치 건 감지 및 수동 처리 플로우 제공
- 환불 및 취소 이력 별도 관리

## 핵심 정리
- PG 연동은 결제 도메인을 독립적으로 분리하고 어댑터 패턴으로 PG사를 추상화하는 것이 핵심이다.
- 결제 승인 전 서버에서 금액 위변조를 반드시 검증해야 한다. DB에 저장한 금액과 파라미터로 전달된 금액이 일치해야만 승인 API를 호출한다.
- Idempotency-Key를 활용해 네트워크 장애로 인한 재시도 시 이중 결제를 방지한다.
- Webhook + Reconciliation Job 이중화로 PG사와의 결제 상태 동기화 신뢰성을 확보한다.
- PCI-DSS 준수 및 카드 정보 비저장 원칙을 통해 보안 리스크를 최소화한다.
- Circuit Breaker와 보상 트랜잭션(Saga 패턴)을 통해 장애 상황에서도 데이터 정합성을 유지한다.

## 기술적 한계와 보완 전략

### 한계
- PG사 API의 응답 지연 및 간헐적 장애가 결제 UX에 직접적 영향을 미친다.
- PG사별 응답 스펙과 에러 코드가 상이하여 통합 처리가 복잡하다.
- Webhook 유실 가능성으로 인해 결제 상태 불일치가 발생할 수 있다.
- 환불/취소 처리에 PG사 정책상 제약이 존재하며 부분 취소가 불가능한 결제 수단도 있다.

### 보완 전략
- Circuit Breaker와 Fallback PG 구성으로 단일 PG 장애 영향 최소화
- 어댑터 계층에서 PG사별 응답을 내부 표준 스펙으로 변환
- Webhook + Polling 이중화로 상태 동기화 신뢰성 확보
- 주기적 Reconciliation Job으로 미일치 결제 자동 보정
- 결제 상태 머신을 명확히 정의하여 비정상 상태 전이 방지

## 키워드

### Payment Gateway (PG)
가맹점과 카드사/은행 사이의 결제를 중계하는 사업자. 가맹점은 PG 하나와 계약하여 다수의 결제 기관을 이용할 수 있다. 국내 주요 PG사로는 토스페이먼츠, KG이니시스, NHN페이코 등이 있으며, PortOne(아임포트)은 여러 PG사를 하나의 API로 추상화해주는 통합 연동 솔루션이다.

### Idempotency (멱등성)
동일한 연산을 여러 번 실행해도 결과가 달라지지 않는 성질. 결제 시스템에서는 네트워크 장애로 인한 재시도 시 이중 결제를 방지하기 위해 필수적이다. `Idempotency-Key` 헤더(UUID v4)를 요청에 포함하면 서버가 중복 요청을 감지하고 첫 번째 응답을 그대로 반환한다.

### Saga Pattern
분산 시스템에서 여러 서비스에 걸친 트랜잭션을 관리하는 패턴. 각 서비스는 로컬 트랜잭션을 실행하고 결과를 이벤트로 발행한다. 중간 단계가 실패하면 이전 단계를 되돌리는 보상 트랜잭션(Compensation Transaction)을 실행한다. Choreography(이벤트 기반)와 Orchestration(중앙 조율자) 방식이 있다.

### Webhook
서버에서 특정 이벤트가 발생했을 때 미리 등록된 URL로 HTTP POST 요청을 보내는 방식. 결제 상태 변경, 가상계좌 입금 등의 이벤트를 실시간으로 수신할 수 있다. 토스페이먼츠는 200 응답이 없을 경우 최대 7회까지 재전송한다.

### Circuit Breaker
외부 시스템(PG사) 장애 시 지속적인 요청을 차단하여 장애 전파를 막는 패턴. Closed(정상), Open(차단), Half-Open(부분 허용) 3가지 상태를 오가며 자동으로 장애 감지와 복구를 처리한다.

### PCI-DSS
Payment Card Industry Data Security Standard. 카드사와 카드 데이터를 처리하는 모든 사업자가 준수해야 하는 보안 표준. 카드 번호, CVC 등 민감 정보의 저장 금지, 암호화 전송, 접근 제어 등을 요구한다.

### Reconciliation (대사)
PG사의 정산 명세서와 내부 결제 데이터를 항목별로 대조하여 불일치를 찾아내는 작업. 미집계 결제, 중복 결제, 환불 미반영 등을 탐지한다.

### Adapter Pattern (어댑터 패턴)
호환되지 않는 인터페이스를 연결해주는 구조 패턴. PG 연동에서는 각 PG사의 API 규격이 다르더라도 내부 코드가 단일 인터페이스(`PaymentGateway`)만 바라보도록 구성한다. PG사 교체나 신규 추가 시 어댑터만 추가하면 되므로 유지보수성이 높아진다.

### Distributed Transaction (분산 트랜잭션)
여러 서비스 또는 DB에 걸쳐 원자성을 보장해야 하는 트랜잭션. 결제 승인, 재고 차감, 주문 확정이 모두 성공하거나 모두 실패해야 하는 경우에 해당한다. 2PC(Two-Phase Commit) 대신 Saga 패턴을 많이 활용한다.

### State Machine (상태 머신)
시스템이 가질 수 있는 상태와 허용된 상태 전이를 명확히 정의한 모델. 결제에서는 READY → IN_PROGRESS → DONE 등의 전이만 허용하고, 불법적인 전이(DONE → IN_PROGRESS)는 코드 수준에서 차단한다.
