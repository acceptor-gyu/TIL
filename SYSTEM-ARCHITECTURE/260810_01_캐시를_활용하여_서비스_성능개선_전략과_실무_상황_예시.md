# 캐시를 활용하여 서비스 성능개선 전략과 실무 상황 예시

## 개요
- 캐시(Cache)의 정의와 성능 개선 관점에서의 역할
- 왜 캐시가 지연 시간(Latency) 단축과 처리량(Throughput) 향상에 효과적인가
- 캐시가 필요한 상황 vs 오히려 독이 되는 상황

캐시는 "다시 계산하거나 다시 가져오기에는 비용이 큰 데이터를, 더 빠르고 더 가까운 저장소에 복제해두는 기법"이다. DB 조회, 외부 API 호출, 무거운 연산 결과처럼 매번 수행하기엔 비용이 큰 작업의 결과를 메모리(로컬/분산)에 저장해두고 재사용함으로써 응답 지연을 줄이고, 동일 자원(DB 커넥션, CPU, 네트워크 대역폭)으로 더 많은 요청을 처리(처리량 향상)할 수 있게 한다.

반대로 캐시가 오히려 독이 되는 경우도 있다.
- **쓰기가 잦고 실시간 정합성이 중요한 데이터** (예: 계좌 잔액, 재고 수량의 정확한 실시간 값)는 캐시-DB 간 정합성 유지 비용이 성능 이득보다 커질 수 있다.
- **접근 패턴이 균일하게 분산되어 Hit Ratio가 낮은 데이터**는 캐시 적재/관리 비용만 발생하고 이득이 없다.
- **데이터 크기가 크고 접근 빈도가 낮은 경우** 메모리 낭비 및 Eviction으로 인한 캐시 오염(Cache Pollution)이 발생할 수 있다.

## 상세 내용

### 1. 캐시의 기본 원리

**Locality (지역성)**
- **시간적 지역성(Temporal Locality)**: 최근에 접근한 데이터는 곧 다시 접근될 가능성이 높다. (예: 인기 게시글 조회수)
- **공간적 지역성(Spatial Locality)**: 접근한 데이터 근처의 데이터도 곧 접근될 가능성이 높다. (예: 페이지네이션 시 인접 페이지)
- 이 지역성 덕분에 **파레토 법칙(80:20 법칙)** — 전체 요청의 80%가 20%의 데이터에 집중되는 현상 — 이 실무 트래픽에서 흔히 관찰되고, 이 20%만 캐싱해도 큰 성능 이득을 얻을 수 있다.

**Cache Hit / Cache Miss / Hit Ratio**
- **Cache Hit**: 요청한 데이터가 캐시에 존재하여 원본 저장소(DB 등)를 거치지 않고 바로 응답한 경우
- **Cache Miss**: 캐시에 데이터가 없어 원본 저장소까지 조회해야 하는 경우
- **Hit Ratio = Hit 수 / (Hit 수 + Miss 수)**: 캐시 효율을 나타내는 핵심 지표. 일반적으로 Hit Ratio가 높을수록 원본 저장소 부하와 평균 응답 시간이 감소한다.

**캐시 계층 구조**
```
CPU 캐시(L1/L2/L3) → 로컬(In-Process) 캐시 → 분산 캐시(Redis 등) → CDN → Origin(DB/Storage)
```
계층이 원본에 가까울수록 용량은 크지만 느리고, 사용자(요청자)에 가까울수록 빠르지만 용량이 작고 정합성 관리가 어렵다. 이를 **Multi-Level Cache(다단계 캐시)** 구조로 조합해 사용하는 것이 실무의 일반적인 패턴이다.

### 2. 캐시 배치 위치별 전략

| 위치 | 대상 데이터 | 특징 |
|---|---|---|
| 클라이언트/브라우저 캐시 | 정적 리소스, API 응답 | `Cache-Control`, `ETag`, `Last-Modified` HTTP 헤더로 제어. 네트워크 왕복(RTT) 자체를 없앨 수 있음 |
| CDN 캐시 | 이미지, JS/CSS, 정적 페이지 | Edge 서버에서 응답하여 지리적으로 가까운 곳에서 처리, Origin 부하 대폭 감소 |
| 애플리케이션 로컬 캐시 | 자주 조회되나 서버 간 공유 불필요한 데이터 | Caffeine, Guava, Ehcache. 네트워크 홉이 없어 가장 빠르지만, 서버 인스턴스마다 별도로 존재해 정합성 관리가 어려움 |
| 분산 캐시 | 여러 서버가 공유해야 하는 데이터 | Redis, Memcached. 서버를 확장(Scale-out)해도 캐시 데이터가 공유되어 일관성 유지가 쉬움, 단 네트워크 홉 발생 |
| DB 버퍼 풀 캐시 | DB 페이지(디스크 블록) | InnoDB Buffer Pool 등 DB 엔진 자체 내부 캐시로 애플리케이션이 직접 제어하지는 않음 |

실무에서는 흔히 **로컬 캐시(1차) + 분산 캐시(2차) + CDN(정적 자원)** 을 조합한 다단계 구조를 사용한다.

### 3. 캐시 읽기/쓰기 패턴

**Cache-Aside (Look-Aside)**
- 애플리케이션이 캐시를 먼저 조회하고, Miss 시 DB를 조회한 뒤 그 결과를 캐시에 채워 넣는 방식 (Lazy Loading)
- 가장 널리 쓰이는 패턴. Redis, Memcached와 함께 사용하는 대표적인 구조
```
1. Read: 캐시 조회 → Miss → DB 조회 → 캐시에 저장 → 응답
2. Write: DB에 먼저 쓰기 → 캐시는 무효화(삭제) 또는 갱신
```

**Read-Through**
- 캐시 자체가 Miss 시 원본 저장소를 조회하는 책임을 가짐. 애플리케이션은 캐시만 바라봄
- 캐시 라이브러리/미들웨어가 DB 조회 로직을 캡슐화해야 하므로 구현 복잡도가 Cache-Aside보다 높음

**Write-Through**
- 쓰기 요청 시 캐시와 DB에 동시에(동기적으로) 반영. 캐시와 DB의 정합성이 즉시 보장됨
- 쓰기 지연이 늘어남 (두 저장소 모두 성공해야 응답)

**Write-Back (Write-Behind)**
- 쓰기 요청 시 캐시에만 먼저 반영하고, 이후 비동기로 DB에 반영(배치/큐잉)
- 쓰기 성능이 매우 좋지만, 캐시 장애 시 유실될 수 있는 데이터가 존재 (내구성 리스크)

**Write-Around**
- 쓰기는 DB에만 반영하고 캐시는 갱신하지 않음. 이후 읽기 시점에 Cache-Aside처럼 채워짐
- 한 번 쓰고 잘 읽히지 않는 데이터(로그성 데이터 등)에 적합, 캐시 오염을 방지

**정합성 vs 성능 트레이드오프 요약**

| 패턴 | 정합성 | 쓰기 성능 | 구현 난이도 |
|---|---|---|---|
| Cache-Aside | 중간 (무효화 시점 갭 존재) | 좋음 | 낮음 |
| Read-Through | 중간 | - | 중간 (캐시 계층 구현 필요) |
| Write-Through | 높음 | 낮음 (동기 이중 쓰기) | 중간 |
| Write-Back | 낮음 (유실 위험) | 매우 좋음 | 높음 |
| Write-Around | 쓰기 직후 낮음 | 좋음 | 낮음 |

### 4. 캐시 만료·갱신 전략

**TTL(Time To Live) / TTI(Time To Idle)**
- **TTL**: 생성 시점 기준 일정 시간이 지나면 무조건 만료
- **TTI**: 마지막 접근 시점 기준 일정 시간 동안 접근이 없으면 만료 (Caffeine의 `expireAfterAccess`)
- 실무에서는 TTL에 약간의 지터(Jitter)를 부여해 동시 만료를 분산시키는 경우가 많다 (Cache Avalanche 예방)

**캐시 무효화(Invalidation) 전략**
- **TTL 기반 자동 만료**: 구현이 단순하지만 만료 전까지는 Stale Data를 반환할 수 있음
- **명시적 무효화(Explicit Invalidation)**: 데이터 변경(Write) 시점에 관련 캐시 키를 직접 삭제/갱신. 정합성은 좋아지지만 변경 지점마다 무효화 로직을 빠짐없이 추가해야 함
- **이벤트 기반 무효화**: DB 변경 이벤트(CDC, Binlog 등)를 구독해 캐시를 무효화. 애플리케이션 코드와 무효화 로직을 분리할 수 있음

**Eviction 정책**
용량 제한(maxmemory 등)에 도달했을 때 어떤 데이터를 먼저 내보낼지 결정하는 정책이다.
- **LRU (Least Recently Used)**: 가장 오랫동안 사용되지 않은 항목을 제거. 시간적 지역성을 활용
- **LFU (Least Frequently Used)**: 사용 빈도가 가장 낮은 항목을 제거. 일시적으로 몰린 트래픽(버스트)에 덜 민감
- **FIFO (First In First Out)**: 먼저 들어온 항목을 먼저 제거. 접근 패턴을 고려하지 않아 Hit Ratio가 낮은 편
- **Random**: 무작위 제거. 구현이 단순하지만 예측 가능성이 낮음

Redis는 `maxmemory-policy` 설정으로 `noeviction`, `allkeys-lru`, `volatile-lru`, `allkeys-lfu`, `volatile-lfu`, `allkeys-random`, `volatile-random`, `volatile-ttl` 등을 지원하며, 근사(Approximated) LRU/LFU 알고리즘(샘플링 기반)을 사용해 정확한 LRU 대비 메모리 오버헤드를 줄인다.

### 5. 실무 상황 예시

**조회수/인기글 랭킹 등 읽기 폭주 트래픽 완화**
- 게시글 조회수처럼 쓰기는 빈번하지만 실시간 정합성이 크게 중요하지 않은 값은 Redis에 카운터로 저장하고, 주기적으로 DB에 배치 반영(Write-Back 유사 패턴)
- 인기글 랭킹(Top N)은 Redis Sorted Set(ZSET)을 활용해 DB 집계 쿼리 없이 O(log N)으로 조회

**인증 토큰·세션 조회 캐싱**
- JWT 검증이 아닌 세션 기반 인증에서 세션 정보를 매 요청마다 DB에서 조회하면 병목이 됨 → Redis에 세션을 저장해 다중 서버 환경에서도 공유
- Access Token 블랙리스트(로그아웃/탈취 토큰 관리) 조회도 캐시에 저장해 조회 비용을 최소화

**반복적인 무거운 집계 쿼리 결과 캐싱**
- 대시보드/통계 화면처럼 여러 테이블을 JOIN하고 GROUP BY 하는 무거운 쿼리는 매 요청 실행 시 DB 부하가 크므로, 결과를 일정 TTL(예: 1~5분) 동안 캐싱
- 실시간성이 중요하지 않은 값은 배치로 미리 계산해 캐시에 적재(Cache Warming)

**상품 상세/카탈로그 등 변경 빈도 낮은 데이터**
- 변경 빈도가 낮고 조회가 압도적으로 많은 데이터(상품 정보, 카테고리 등)는 Cache-Aside + 긴 TTL + 명시적 무효화(수정 API 호출 시 캐시 삭제)로 처리
- 카탈로그 성격의 데이터는 CDN 캐시(정적 JSON) 조합도 고려 가능

**로컬 캐시 + 분산 캐시 2-Tier 조합 사례**
- 1차: 각 서버 인스턴스의 Caffeine 로컬 캐시 (초단위 TTL, 매우 빠름, 네트워크 홉 없음)
- 2차: Redis 분산 캐시 (로컬 캐시 Miss 시 조회, 서버 간 공유)
- 3차: DB (Redis Miss 시 조회 후 양쪽 캐시에 채움)
- 이 구조는 로컬 캐시에서 대부분의 요청을 흡수하면서도, 서버 재시작이나 스케일 아웃 시에도 Redis를 통해 일관된 데이터를 제공한다. 단, 로컬 캐시 간 정합성(무효화 전파)은 Redis Pub/Sub 등으로 추가 처리해야 한다.

```java
// Cache-Aside 패턴 예시 (Spring + Redis)
public Product getProduct(Long productId) {
    String key = "product:" + productId;
    Product cached = (Product) redisTemplate.opsForValue().get(key);
    if (cached != null) {
        return cached; // Cache Hit
    }
    Product product = productRepository.findById(productId)
        .orElseThrow(() -> new NotFoundException(productId));
    redisTemplate.opsForValue().set(key, product, Duration.ofMinutes(10));
    return product; // Cache Miss 후 채움
}

public void updateProduct(Product product) {
    productRepository.save(product);
    redisTemplate.delete("product:" + product.getId()); // 명시적 무효화
}
```

## 핵심 정리
- 캐시는 "느리고 비싼 연산 결과를 빠르고 가까운 곳에 저장"하는 것
- Hit Ratio가 성능 개선의 핵심 지표
- 읽기 많고 변경 적은 데이터일수록 캐시 효과가 크다
- 성능과 데이터 정합성은 트레이드오프 관계
- 캐시 도입 전 반드시 "이 데이터가 캐싱할 가치가 있는가(접근 빈도, 변경 빈도, 정합성 요구 수준)"를 먼저 판단해야 한다

## 기술적 한계와 보완 전략

**캐시 정합성 문제 (Stale Data)와 무효화 비용**
- 캐시와 원본 저장소 간에는 항상 갱신 시점의 갭이 존재할 수밖에 없다 (Eventual Consistency)
- 보완: 변경 시점에 캐시를 즉시 삭제/갱신(Write-Through 또는 명시적 무효화), TTL을 짧게 설정, 버전 태그(ETag)로 클라이언트 측 검증

**Cache Stampede(Thundering Herd)와 완화**
- 인기 키의 캐시가 만료되는 순간, 다수의 요청이 동시에 원본 저장소로 몰려가는 현상
- 완화 전략: **Mutex Lock**(캐시 재생성을 한 요청만 수행하고 나머지는 대기/기존 값 반환), **PER(Probabilistic Early Recomputation, 확률적 조기 재계산)**(만료 전에 확률적으로 미리 갱신), **사전 워밍업(Cache Warming)**, TTL에 랜덤 지터 부여

**Cache Penetration / Cache Avalanche / Hot Key 문제**
- **Cache Penetration(캐시 침투)**: 존재하지 않는 키에 대한 요청이 캐시를 계속 우회해 DB로 직접 몰리는 현상(악의적 요청 포함). 보완: 존재하지 않는 값도 짧은 TTL로 캐싱(Negative Caching), Bloom Filter로 사전 필터링
- **Cache Avalanche(캐시 대량 실효)**: 다수의 캐시 키가 동시에 만료되거나 캐시 노드 자체가 장애로 다운되어 트래픽이 한꺼번에 원본으로 쏠리는 현상. 보완: TTL 분산(Jitter), 캐시 클러스터 이중화/Failover, Circuit Breaker
- **Hot Key**: 특정 키에 트래픽이 극단적으로 몰려 해당 키를 담당하는 캐시 노드(샤드)에 부하가 집중되는 현상. 보완: 로컬 캐시로 1차 흡수, 키를 여러 샤드로 분산 복제(Key Sharding)

**캐시 장애 시 원본 저장소 부하 폭증 대응**
- 캐시가 죽으면 모든 트래픽이 그대로 DB로 향해 DB까지 연쇄 장애(Cascading Failure)로 이어질 수 있음
- 보완: Circuit Breaker로 임계치 초과 시 요청 일부 차단/Fallback 응답 제공, Rate Limiting, 캐시 클러스터 자체의 고가용성(Redis Sentinel/Cluster) 확보

**메모리 비용과 Eviction으로 인한 Hit Ratio 저하**
- 캐시 용량은 유한하므로 데이터가 많아지면 자연히 Eviction이 발생해 Hit Ratio가 떨어질 수 있음
- 보완: 접근 패턴에 맞는 Eviction 정책 선택(LRU vs LFU), 캐싱 대상 데이터를 압축하거나 필요한 필드만 저장, 캐시 크기와 비용을 모니터링하며 스케일링

## 키워드
- **Cache Hit Ratio**: 전체 요청 중 캐시에서 응답한 비율. `Hit / (Hit + Miss)`로 계산하며 캐시 효율성을 나타내는 가장 기본적인 지표
- **Cache-Aside (Look-Aside)**: 애플리케이션이 캐시를 먼저 조회하고, Miss 시 원본 저장소를 조회해 캐시를 채우는 가장 널리 쓰이는 캐싱 패턴
- **Write-Through / Write-Back**: Write-Through는 캐시와 원본에 동기적으로 동시 반영해 정합성을 보장하고, Write-Back(Write-Behind)은 캐시에만 먼저 반영 후 비동기로 원본에 반영해 쓰기 성능을 극대화
- **TTL / Eviction (LRU, LFU)**: TTL은 캐시 항목의 생존 시간, Eviction은 용량 초과 시 항목을 제거하는 정책으로 LRU(최근 미사용), LFU(사용 빈도 낮음) 등이 대표적
- **Cache Stampede (Thundering Herd)**: 인기 캐시 키가 만료되는 순간 다수의 요청이 동시에 원본 저장소로 몰려가는 현상
- **Cache Penetration / Avalanche**: Penetration은 존재하지 않는 키 조회가 캐시를 우회해 DB에 직접 몰리는 현상, Avalanche는 다수의 캐시가 동시에 만료되거나 캐시 노드 장애로 트래픽이 원본에 몰리는 현상
- **Hot Key**: 특정 키에 트래픽이 비정상적으로 몰려 해당 키를 담당하는 캐시 샤드/노드에 부하가 집중되는 문제
- **Redis / Memcached**: 대표적인 인메모리 분산 캐시 스토어. Redis는 다양한 자료구조(String, Hash, Sorted Set 등)와 영속성, Pub/Sub을 지원하고, Memcached는 단순 Key-Value 저장과 멀티스레드 처리에 강점
- **Local Cache (Caffeine)**: JVM 프로세스 내부 메모리에 데이터를 저장하는 자바 로컬 캐시 라이브러리로 Window TinyLFU 기반 Eviction 알고리즘을 사용해 높은 Hit Ratio를 제공
- **데이터 정합성 (Consistency)**: 캐시와 원본 저장소 간 데이터 값이 일치하는 정도. 성능(빠른 응답)과 정합성(항상 최신 값 보장)은 서로 트레이드오프 관계에 있음
