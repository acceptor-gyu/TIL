# '배포 성공!!'을 출력하지만 컨테이너는 죽어 있었다 — 헬스체크 없는 배포의 함정

## 개요
- upbrella `.github/workflows/mac-deploy-dev.yml`(Mac mini + Docker Hub 배포) 사례 분석
- 워크플로우는 `docker run -d` 이후 곧바로 `docker image prune -af` → `echo "배포 성공!!"` 로 종료
- 문제: `docker run -d`는 "컨테이너가 기동을 시작했다"만 보장할 뿐, **애플리케이션이 살아서(alive) 트래픽을 받을 준비(ready)가 됐는지는 검증하지 않는다**
- 그 결과 앱이 부팅 직후 죽어도(DB 연결 실패, 포트 충돌, 환경변수 누락 등) CI 로그에는 초록불 "배포 성공!!"이 찍힘
- 관련 확장: 헬스체크·롤백·무중단 배포(블루-그린)가 왜 하나의 세트로 묶여야 하는지

## 상세 내용

### 1. 문제의 배포 흐름 (upbrella mac-deploy-dev.yml)
- `set -e` 로 시작해 "명령이 실패하면 중단"하도록 의도
- 실행 순서
  - (1) `docker pull birdiehyun/upbrella-dev:latest`
  - (2) 기존 컨테이너 `docker stop` + `docker rm` (신버전 검증 **전에** 구버전 제거)
  - (3) `docker network create ... || true`
  - (4) `docker run -d --name upbrella-dev -p 8765:8080 --restart unless-stopped ...`
  - (5) `docker image prune -af` (사용하지 않는 이미지 전부 삭제)
  - (6) `echo "배포 성공!!"`
- 핵심 결함: (4)와 (6) 사이에 **애플리케이션 상태를 확인하는 단계가 전혀 없음**

### 2. 왜 죽은 컨테이너인데 "성공"이 찍히는가
- `docker run -d`의 종료 코드(exit 0)는 "컨테이너 생성/시작 성공"이지 "앱 정상 기동"이 아님
- `set -e`는 `docker run` 자체가 실패할 때만 반응 → 컨테이너가 뜬 뒤 앱이 죽는 건 감지 못함
- Spring Boot 기동은 수십 초가 걸리는데, 그 사이 스크립트는 이미 끝나 있음(비동기 경주)
- 즉, CI의 초록불 = "컨테이너 프로세스가 시작됨"일 뿐, 서비스 가용성과 무관

### 3. `--restart unless-stopped` 가 장애를 숨긴다
- 앱이 부팅 직후 예외로 종료돼도 Docker가 자동 재시작 → 크래시 루프(crash loop)
- `docker ps` STATUS는 "Restarting (1) N seconds ago"로 바뀌지만, 스크립트는 이미 "배포 성공!!"을 출력하고 종료한 상태
- 재시작 정책이 "복원력"처럼 보이지만, 실상은 **실패를 조용히 반복**하며 관측성을 떨어뜨림

### 4. Dockerfile 에 HEALTHCHECK 가 없다
- upbrella `Dockerfile`은 `ENTRYPOINT ["java","-jar","upbrella-server.jar"]` 만 존재, `HEALTHCHECK` 지시어 없음
- HEALTHCHECK가 없으면 `docker ps`의 STATUS에 health 상태가 표기되지 않고 무조건 "Up"으로 보임
- 오케스트레이터/스크립트가 "healthy" 판정에 사용할 신호 자체가 존재하지 않음
- 아이러니: 이 프로젝트는 `spring-boot-starter-actuator` 의존성을 이미 포함 → `/actuator/health`(liveness/readiness)를 쓸 수 있는데도 배포 검증에 활용하지 않음

### 5. `docker image prune -af` 로 롤백 경로까지 삭제
- 신 컨테이너 검증 전에 구버전 컨테이너를 이미 `rm` 했고, 이어서 이미지까지 prune
- 새 이미지가 고장 났을 때 되돌아갈 직전 정상 이미지가 사라져 **롤백 불가 + 다운타임** 발생
- "정리(cleanup)"와 "검증(verify)"의 순서가 뒤바뀐 전형적 안티패턴

### 6. 해결 전략
- **Dockerfile에 HEALTHCHECK 추가**: `HEALTHCHECK CMD curl -f http://localhost:8080/actuator/health || exit 1`
- **배포 스크립트에서 헬스 폴링**: `docker run` 이후 `docker inspect --format '{{.State.Health.Status}}'` 를 타임아웃까지 반복 확인, `healthy` 도달 시에만 다음 단계 진행
- **애플리케이션 레벨 검증**: `curl -f http://localhost:8765/actuator/health/readiness` 를 재시도 루프로 확인
- **불건강 시 실패 처리**: healthy 미도달이면 `exit 1` 로 워크플로우 실패 처리 → Slack 알림 연동
- **검증 후 정리**: 신버전이 healthy 판정된 뒤에만 구버전 컨테이너/이미지 제거(무중단·롤백 안전)
- **블루-그린/롤링**: 새 컨테이너를 다른 포트로 띄워 헬스 확인 후 리버스 프록시(Nginx) upstream 전환, 실패 시 즉시 구버전 유지
- **Spring Boot 종료 신호 정합**: liveness/readiness 프로브 분리(`management.endpoint.health.probes.enabled=true`)로 "기동 중"과 "죽음"을 구분

### 7. [예시] 헬스체크가 붙은 안전한 배포 스크립트 골격
- `docker run -d`로 신 컨테이너 기동 (구버전은 아직 유지)
- `for` 루프 + `sleep` 으로 `Health.Status == healthy` 까지 최대 N초 대기
- healthy → 리버스 프록시 전환 → 구버전 stop/rm → 이미지 prune → "배포 성공"
- unhealthy/timeout → 신 컨테이너 로그 출력 → 신 컨테이너 rm → 구버전 유지 → "배포 실패" 로 워크플로우 종료

## 핵심 정리
- `docker run -d`의 성공은 "컨테이너 시작"이지 "서비스 준비 완료"가 아니다 — 이 둘을 구분하지 않으면 죽은 컨테이너에도 "배포 성공"이 찍힌다
- HEALTHCHECK와 헬스 폴링이 없으면 CI 로그의 초록불은 가용성을 전혀 보장하지 못한다
- `--restart` 정책은 실패를 복구하는 게 아니라 **조용히 반복**시켜 문제를 은폐할 수 있다
- 검증(verify)은 정리(cleanup)보다 먼저 와야 하며, 신버전 healthy 확인 전에는 구버전/구이미지를 지우지 않아야 롤백이 가능하다
- 이미 있는 actuator `/health` 를 배포 파이프라인의 게이트로 연결하는 것만으로 대부분의 함정을 막을 수 있다

## 기술적 한계와 보완 전략
- HEALTHCHECK의 `curl` 의존 → 슬림 이미지엔 curl이 없을 수 있음(`wget`/자바 프로브/`HEALTHCHECK` 전용 바이너리로 대체)
- readiness가 통과해도 순간적 커넥션 풀 고갈 등 런타임 장애는 못 잡음 → 배포 후 모니터링(메트릭/알럿)과 병행 필요
- 헬스 폴링 타임아웃을 짧게 잡으면 느린 기동을 실패로 오판, 길게 잡으면 장애 감지가 늦어짐 → 앱 기동 시간 기반으로 튜닝
- 단일 Mac mini 단일 컨테이너 구조는 진정한 무중단이 어려움 → 최소 2인스턴스 + 프록시 전환 또는 오케스트레이터(K8s) 고려
- 자동 롤백은 "이전 정상 버전"의 식별·보관을 전제로 함 → 이미지 태그를 `latest` 단일 태그가 아닌 커밋 SHA 태그로 관리

## 키워드

**HEALTHCHECK (Docker)**
- Dockerfile의 `HEALTHCHECK` 지시어로 컨테이너 내부에서 주기적으로 상태 점검 명령을 실행하고, 그 결과를 `docker inspect`의 `State.Health.Status`(starting/healthy/unhealthy)로 노출한다
- 이 신호가 있어야 배포 스크립트나 오케스트레이터가 "앱이 실제로 살아 있는지"를 판정할 수 있다

**liveness / readiness probe**
- liveness는 "프로세스가 죽었는가"(재시작 필요), readiness는 "트래픽을 받을 준비가 됐는가"(라우팅 대상 포함)를 구분하는 헬스 신호
- Spring Boot Actuator는 `/actuator/health/liveness`, `/actuator/health/readiness` 로 두 프로브를 분리 제공

**`docker run -d` 종료 코드의 의미**
- 디태치드 실행은 컨테이너를 백그라운드로 시작하고 컨테이너 ID를 출력한 뒤 즉시 exit 0을 반환한다
- 이 성공은 "컨테이너 생성·시작"에 대한 것이며 내부 애플리케이션의 기동 성공·정상 동작을 보장하지 않는다

**restart policy (`unless-stopped`)**
- 컨테이너가 종료되면 Docker가 자동으로 재시작하는 정책. 명시적으로 stop 하기 전까지 계속 재시작
- 크래시 루프를 자동 복구처럼 보이게 만들어, 헬스체크가 없으면 반복 실패가 은폐될 수 있다

**크래시 루프(crash loop)**
- 컨테이너가 기동 → 즉시 오류 종료 → 재시작을 반복하는 상태
- `docker ps`에서 STATUS가 "Restarting"으로 표시되며, 로그에 동일한 스택트레이스가 반복적으로 남는다

**무중단 배포 / 블루-그린(Blue-Green)**
- 신버전을 별도 인스턴스로 띄워 헬스 확인 후 트래픽을 전환하고, 문제가 없을 때만 구버전을 내리는 배포 전략
- 검증 실패 시 구버전을 유지해 다운타임과 롤백 리스크를 최소화한다

**롤백 가능성(rollback readiness)**
- 새 배포가 실패했을 때 즉시 되돌아갈 수 있도록 직전 정상 버전(컨테이너/이미지)을 보존하는 것
- 검증 전에 `docker rm` + `image prune`으로 구버전을 지우면 롤백 경로가 사라진다

**헬스 폴링(health polling / wait-for)**
- 배포 후 일정 간격으로 헬스 엔드포인트나 `docker inspect` 상태를 반복 조회해, healthy 도달 시에만 다음 단계로 진행하고 타임아웃 시 실패 처리하는 검증 루프

**Spring Boot Actuator**
- 운영용 엔드포인트(`/actuator/health`, `/metrics` 등)를 제공하는 스타터. upbrella는 이미 의존성을 포함
- 배포 파이프라인의 헬스 게이트, Prometheus 메트릭 수집 등에 활용할 수 있다
