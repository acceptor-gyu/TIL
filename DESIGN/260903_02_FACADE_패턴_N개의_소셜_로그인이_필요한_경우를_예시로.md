# FACADE 패턴 - N개의 소셜 로그인이 필요한 경우를 예시로

## 개요
구조(Structural) 패턴에 속하는 파사드 패턴의 정의와 목적을 정리하고, Google/Kakao/Naver/Apple 4개의 소셜 로그인(OAuth 2.0/OIDC) 공급자를 하나의 서비스로 통합해야 하는 실무 상황에서 파사드가 어떤 복잡도를 흡수하는지 Kotlin/Spring Boot 예제 코드로 정리한다.

## 상세 내용

### 1. 파사드 패턴이란
- GoF의 정의: "서브시스템에 있는 인터페이스들의 집합에 대한 통합된 인터페이스를 제공한다. 파사드는 서브시스템을 사용하기 쉽도록 상위 수준의 인터페이스를 정의한다." (GoF, *Design Patterns*, Structural Patterns 챕터)
- 파사드가 해결하는 문제: 클라이언트가 서브시스템 내부의 여러 클래스와 호출 순서를 알아야만 기능을 사용할 수 있는 상황에서, 그 지식을 파사드 뒤로 숨겨 결합도(coupling)를 낮춘다.
- "감싸기만 하는 래퍼"와 파사드의 차이는 의도(intent)에 있다.
  - 단순 래퍼/데코레이터는 기존 인터페이스를 유지하거나 기능을 추가하는 것이 목적이다.
  - 파사드는 여러 서브시스템에 걸친 "시나리오(use case)"를 하나의 메서드로 압축하는 것이 목적이다. 즉 파사드는 새로운 기능을 만들지 않고, 이미 존재하는 서브시스템 호출들의 조합(orchestration)만 담당한다.
- 파사드는 서브시스템을 완전히 캡슐화하지 않는다. 필요하면 클라이언트가 서브시스템 클래스에 직접 접근하는 것도 허용되는 "선택적 진입점"이다.

### 2. 문제 상황 - 소셜 로그인이 N개로 늘어날 때

**Google 하나만 있을 때**는 컨트롤러가 직접 처리해도 크게 문제되지 않는다.

```kotlin
@RestController
class LoginController(
    private val googleOAuthClient: GoogleOAuthClient,
    private val memberRepository: MemberRepository,
    private val tokenProvider: TokenProvider,
) {

    @PostMapping("/login/google")
    fun loginWithGoogle(@RequestBody request: LoginRequest): LoginResponse {
        val tokenResponse = googleOAuthClient.exchangeToken(request.authCode)
        val userInfo = googleOAuthClient.fetchUserInfo(tokenResponse.accessToken)

        val member = memberRepository.findByProviderId(userInfo.sub)
            ?: memberRepository.save(Member.of(userInfo))

        return LoginResponse(
            accessToken = tokenProvider.issueAccessToken(member),
            refreshToken = tokenProvider.issueRefreshToken(member),
        )
    }
}
```

**공급자가 4개(Google, Kakao, Naver, Apple)로 늘어나면** 다음과 같은 차이가 코드에 그대로 드러나기 시작한다.

| 항목 | Google | Kakao | Naver | Apple |
|---|---|---|---|---|
| 토큰 엔드포인트 | `https://oauth2.googleapis.com/token` | `https://kauth.kakao.com/oauth/token` | `https://nid.naver.com/oauth2.0/token` | `https://appleid.apple.com/auth/token` |
| `client_secret` 형태 | 고정 문자열 | 고정 문자열(선택) | 고정 문자열 | **매 요청마다 서명하는 JWT (ES256)** |
| 사용자 정보 획득 | UserInfo 엔드포인트 호출 | UserInfo 엔드포인트 호출 | UserInfo 엔드포인트 호출 | 최초 응답의 **`id_token` 클레임 파싱**(재조회 엔드포인트 없음) |
| 응답 포맷 | 표준 JSON 필드 | `kakao_account.email` 등 중첩 구조 | `{ "resultcode": "00", "message": "success", "response": {...} }` 래핑 | JWT 클레임(`sub`, `email`, `is_private_email`) |
| 식별자 필드명 | `sub` | `id` | `response.id` | `sub` |

이 차이를 컨트롤러가 `if/switch`로 흡수하기 시작하면 다음 문제가 생긴다.
- **OCP 위반**: 공급자가 하나 늘어날 때마다 컨트롤러(또는 서비스)의 분기문을 수정해야 한다.
- **인증 로직 중복**: 회원 조회/가입, 토큰 발급 로직이 공급자별 분기 블록마다 반복된다.
- **테스트 조합 폭발**: "공급자 × 시나리오(신규 가입/기존 회원/이메일 미동의 등)" 조합이 컨트롤러 테스트에 그대로 쌓인다.

### 3. 파사드 도입 전 설계 - 무엇을 감출 것인가

서브시스템을 먼저 식별한다.
1. 인가 코드 → 토큰 교환 (공급자별 HTTP 클라이언트)
2. ID Token 검증 (Apple/Google의 경우 JWK Set 캐싱 후 서명 검증)
3. 사용자 정보 조회 (또는 ID Token 클레임 파싱)
4. 회원 조회/가입 (도메인 서비스)
5. 우리 서비스 자체 토큰(Access/Refresh) 발급
6. 리프레시 토큰 저장(Redis 등)

파사드가 노출할 유일한 시나리오 메서드는 다음과 같이 정의한다.

```kotlin
interface SocialLoginFacade {
    fun login(provider: Provider, authorizationCode: String): AuthResult
}
```

공급자 간 차이는 파사드가 아니라 **전략(Strategy) 인터페이스**로 흡수한다.

```kotlin
interface OAuthClient {
    fun supports(): Provider
    fun exchangeToken(authorizationCode: String): OAuthTokenResponse
    fun fetchUserInfo(tokenResponse: OAuthTokenResponse): OAuthUserInfo
}

enum class Provider {
    GOOGLE, KAKAO, NAVER, APPLE
}
```

파사드는 "어떤 공급자든 로그인 절차는 6단계로 동일하다"는 사실만 알면 되고, 각 단계의 세부 구현은 `OAuthClient` 구현체와 도메인 서비스에 위임한다.

### 4. 구현 - 파사드 + 전략 조합

#### 4-1. `SocialLoginFacade` - 오케스트레이션만 담당

```kotlin
@Component
class DefaultSocialLoginFacade(
    private val oAuthClients: Map<Provider, OAuthClient>,
    private val memberService: MemberService,                  // 도메인 서비스 (가입/조회 규칙 보유)
    private val tokenProvider: TokenProvider,                  // 우리 서비스 JWT 발급
    private val refreshTokenRepository: RefreshTokenRepository,
) : SocialLoginFacade {

    @Transactional
    override fun login(provider: Provider, authorizationCode: String): AuthResult {
        // Kotlin에서는 맵 조회 결과가 nullable 타입이므로 엘비스 연산자로 미지원 공급자를 걸러낸다.
        val client = oAuthClients[provider] ?: throw UnsupportedProviderException(provider)

        // 1) 토큰 교환, 2) 사용자 정보 조회 - 외부 HTTP 호출은 트랜잭션 시작 전에 끝내둔다.
        val tokenResponse = client.exchangeToken(authorizationCode)
        val userInfo = client.fetchUserInfo(tokenResponse)

        // 3) 회원 조회/가입 - 도메인 규칙은 여기(MemberService)에 위임, 파사드는 흐름만 조립
        val member = memberService.findOrCreate(provider, userInfo)

        // 4) 우리 서비스 토큰 발급 및 리프레시 토큰 저장
        val accessToken = tokenProvider.issueAccessToken(member)
        val refreshToken = tokenProvider.issueRefreshToken(member)
        refreshTokenRepository.save(member.id, refreshToken)

        return AuthResult(accessToken, refreshToken, member.isNewMember)
    }
}
```

#### 4-2. `Map<Provider, OAuthClient>` 자동 수집 - Spring의 다중 구현체 주입

Spring은 특정 인터페이스의 구현체가 여러 개일 때 `List<T>`로 전부 주입해 준다(빈 이름을 키로 하는 `Map<String, T>` 주입도 가능하다). 다만 `Provider` 열거형을 키로 바로 받을 수는 없으므로, `@Bean` 메서드에서 `EnumMap`으로 변환해 등록한다.

```kotlin
@Configuration
class OAuthClientConfig(
    private val oAuthClients: List<OAuthClient>, // Spring이 OAuthClient 구현체를 전부 주입
) {

    // associateByTo로 EnumMap에 그대로 모으고, 반환 타입을 읽기 전용 Map으로 노출한다.
    @Bean
    fun oAuthClientMap(): Map<Provider, OAuthClient> =
        oAuthClients.associateByTo(EnumMap<Provider, OAuthClient>(Provider::class.java)) { it.supports() }
}
```

이렇게 구성하면 `SocialLoginFacade`는 `Map<Provider, OAuthClient>`를 그대로 주입받아 사용할 수 있고, **신규 공급자를 추가할 때 `OAuthClient` 구현체 하나만 새로 등록하면 파사드와 컨트롤러는 한 줄도 수정하지 않는다.**

```kotlin
@RestController
class LoginController(
    private val socialLoginFacade: SocialLoginFacade,
) {

    @PostMapping("/login/{provider}")
    fun login(
        @PathVariable provider: Provider,
        @RequestBody request: LoginRequest,
    ): LoginResponse {
        val result = socialLoginFacade.login(provider, request.authorizationCode)
        return LoginResponse.from(result)
    }
}
```

#### 4-3. 공급자 구현체별 책임 경계

**Google/Kakao/Naver**는 "인가 코드 → access_token → 표준 UserInfo 엔드포인트 조회" 흐름이 유사하다. Naver만 응답이 `{ "resultcode", "message", "response": {...} }`로 한 번 더 감싸져 있어 역직렬화 시 `response` 필드를 벗겨내는 DTO가 하나 더 필요하다.

```kotlin
@Component
class NaverOAuthClient(
    private val restClient: RestClient,
    private val properties: NaverOAuthProperties,
) : OAuthClient {

    override fun supports(): Provider = Provider.NAVER

    override fun exchangeToken(authorizationCode: String): OAuthTokenResponse =
        restClient.post()
            .uri("https://nid.naver.com/oauth2.0/token")
            .body(NaverTokenRequest.of(properties, authorizationCode))
            .retrieve()
            .body(OAuthTokenResponse::class.java)
            ?: throw OAuthProviderException(Provider.NAVER, "토큰 응답 본문이 비어 있음")

    override fun fetchUserInfo(tokenResponse: OAuthTokenResponse): OAuthUserInfo {
        // Naver 고유 규칙: 결과가 response 필드로 한 번 더 래핑되어 오며,
        // resultcode != "00" 이면 실패로 간주해야 한다.
        val raw = restClient.get()
            .uri("https://openapi.naver.com/v1/nid/me")
            .headers { it.setBearerAuth(tokenResponse.accessToken) }
            .retrieve()
            .body(NaverUserInfoResponse::class.java)
            ?: throw OAuthProviderException(Provider.NAVER, "사용자 정보 응답 본문이 비어 있음")

        if (raw.resultcode != "00") {
            throw OAuthProviderException(Provider.NAVER, raw.message)
        }
        return raw.response.toOAuthUserInfo()
    }
}
```

`RestClient.body()`는 Java API이므로 Kotlin에서는 플랫폼 타입(`OAuthTokenResponse!`)으로 들어온다. 위처럼 엘비스 연산자로 빈 응답을 즉시 도메인 예외로 번역해두면, 파사드 이후 계층에서는 널 가능성을 다시 다루지 않아도 된다.

**Apple**은 절차 자체가 다르다. `client_secret`을 고정 문자열로 발급받아 쓰는 것이 아니라, **매 토큰 교환 요청마다 Apple Developer 계정의 Private Key(P-8)로 서명한 JWT를 즉석에서 생성해 `client_secret` 자리에 넣어야 한다.** 이 JWT는 다음 클레임을 갖는다.

- `iss`: Apple Developer Team ID (10자리)
- `sub`: 우리 앱의 `client_id` (Services ID, 예: `com.example.app.web`)
- `aud`: 고정값 `https://appleid.apple.com`
- `iat` / `exp`: 발급 시각과 만료 시각(만료는 발급 시각으로부터 최대 6개월(15,777,000초) 이내)
- 헤더의 `alg`: `ES256`, `kid`: Apple Developer Console에서 발급한 Key ID

```kotlin
@Component
class AppleOAuthClient(
    private val restClient: RestClient,
    private val properties: AppleOAuthProperties, // teamId, clientId, keyId, privateKey(P-8)
    private val jwkSetCache: AppleJwkSetCache,    // Apple 공개키(JWK) 캐싱
) : OAuthClient {

    override fun supports(): Provider = Provider.APPLE

    override fun exchangeToken(authorizationCode: String): OAuthTokenResponse {
        val clientSecret = generateClientSecretJwt()

        return restClient.post()
            .uri("https://appleid.apple.com/auth/token")
            .body(AppleTokenRequest.of(properties.clientId, clientSecret, authorizationCode))
            .retrieve()
            .body(OAuthTokenResponse::class.java)
            ?: throw OAuthProviderException(Provider.APPLE, "토큰 응답 본문이 비어 있음")
    }

    // Apple 고유 규칙: client_secret은 값이 아니라 매 요청마다 서명해서 만드는 JWT다.
    private fun generateClientSecretJwt(): String {
        val now = Instant.now()
        return try {
            val signer: JWSSigner = ECDSASigner(properties.privateKey) // Nimbus JOSE+JWT

            val claims = JWTClaimsSet.Builder()
                .issuer(properties.teamId)      // Apple Developer Team ID
                .subject(properties.clientId)   // Services ID
                .audience("https://appleid.apple.com")
                .issueTime(Date.from(now))
                .expirationTime(Date.from(now.plus(Duration.ofMinutes(5)))) // 요청 직전 짧게 발급
                .build()

            SignedJWT(
                JWSHeader.Builder(JWSAlgorithm.ES256).keyID(properties.keyId).build(),
                claims,
            ).apply { sign(signer) }
                .serialize()
        } catch (e: JOSEException) {
            throw AppleClientSecretGenerationException(e)
        }
    }

    override fun fetchUserInfo(tokenResponse: OAuthTokenResponse): OAuthUserInfo {
        // Apple 고유 규칙: 별도 UserInfo 엔드포인트가 없다.
        // exchangeToken 응답에 포함된 id_token(JWT)의 클레임을 검증 후 파싱해서 사용자 정보로 삼는다.
        val claims = verifyAndParseIdToken(tokenResponse.idToken)
        return OAuthUserInfo.of(
            providerId = claims.subject,                                 // sub
            email = claims.getStringClaim("email"),
            isPrivateEmail = claims.getBooleanClaim("is_private_email"), // Apple Private Relay 이메일 여부
        )
    }

    // jwkSetCache에서 Apple 공개키(JWK)를 가져와 서명 검증 (구현 생략)
    private fun verifyAndParseIdToken(idToken: String): JWTClaimsSet = jwkSetCache.verify(idToken)
}
```

#### 4-4. 공통 사용자 표현으로의 정규화

```kotlin
data class OAuthUserInfo(
    val providerId: String,
    val email: String?,
    val nickname: String?,
    val emailVerified: Boolean,
)
```

각 `OAuthClient` 구현체는 공급자 고유 응답 구조(중첩 JSON, JWT 클레임 등)를 이 데이터 클래스 하나로 정규화해서 반환한다. 공급자에 따라 이메일/닉네임이 없을 수 있다는 사실을 `String?`으로 타입에 드러내면, 이후 계층에서 널 처리를 강제할 수 있다. 파사드와 도메인 서비스는 이 표준 형태만 알면 되므로 공급자 응답 스키마 변경이 파사드까지 전파되지 않는다.

#### 4-5. 트랜잭션 경계 - 외부 HTTP 호출을 트랜잭션 밖으로

`exchangeToken`, `fetchUserInfo`는 외부 네트워크 호출이다. `@Transactional` 안에서 이 호출들을 수행하면 DB 커넥션을 쥔 채로 외부 지연 시간만큼 대기하게 되어 커넥션 풀 고갈로 이어질 수 있다. 위 `SocialLoginFacade.login()` 예시처럼 **외부 호출을 먼저 끝낸 뒤 그 결과만 가지고 트랜잭션을 여는 것**이 안전하다. 필요하다면 트랜잭션 경계를 아예 `memberService.findOrCreate()` 내부로 좁혀도 된다.

### 5. 파사드와 혼동하기 쉬운 패턴 비교

| 패턴 | 핵심 의도 | 인터페이스 관계 | 소셜 로그인 예시에 대입 |
|---|---|---|---|
| **Facade** | 여러 서브시스템 호출을 하나의 시나리오로 단순화 | 기존 인터페이스는 그대로 두고 상위에 새 진입점 추가 | `SocialLoginFacade.login()` 하나로 6단계 절차를 감춤 |
| **Adapter** | 서로 호환되지 않는 인터페이스를 변환 | 대상 인터페이스에 맞춰 기존 클래스를 감싸 "번역" | 공급자 응답 DTO를 `OAuthUserInfo`로 변환하는 부분에 가까움(구현체 내부의 역할) |
| **Mediator** | 여러 객체 간의 복잡한 양방향 상호작용을 중재자로 집중 | 참여 객체들이 서로를 몰라도 되고, 중재자를 통해 통신(양방향) | 파사드는 단방향 위임(클라이언트→파사드→서브시스템)이라 다름 |
| **Proxy** | 실제 객체에 대한 접근을 제어(지연 로딩, 캐싱, 권한 검사 등) | 원본과 **동일한 인터페이스**를 제공하며 대리 | JWK 캐싱을 위한 `AppleJwkSetCache`가 프록시 성격에 가까움 |
| **Strategy** | 알고리즘(구현)을 캡슐화해 런타임에 교체 | 동일 인터페이스의 다수 구현체를 컨텍스트가 선택 | `OAuthClient` 구현체(Google/Kakao/Naver/Apple)가 전략에 해당 |
| **Application/Facade Service (계층 관점)** | 유스케이스 단위로 도메인 로직을 조립하는 애플리케이션 계층의 진입점 | Layered/Hexagonal에서 컨트롤러와 도메인 사이에 위치 | `SocialLoginFacade`는 GoF Facade이자 애플리케이션 서비스 역할을 동시에 수행 |

핵심 구분 기준: **Adapter는 "인터페이스가 다르다"는 문제**를 풀고, **Facade는 "인터페이스가 너무 많고 복잡하다"는 문제**를 푼다. **Mediator는 양방향/그룹 조율**이고 **Facade는 단방향 위임**이다. **Proxy는 원본과 동일한 인터페이스로 접근을 통제**하지만 **Facade는 새로운(더 단순한) 인터페이스를 제공**한다.

### 6. 파사드가 실무에서 만드는 이점
- 신규 공급자 추가 시 변경 지점 최소화: `OAuthClient` 구현체 하나 추가 + `Provider` enum 값 추가만으로 끝난다. 컨트롤러와 파사드는 무수정.
- 테스트 전략 분리
  - 파사드 단위 테스트: `Map<Provider, OAuthClient>`에 페이크(Fake)/모킹된 `OAuthClient`를 주입해 오케스트레이션 로직(회원 신규/기존 분기, 토큰 발급 순서)만 검증
  - 공급자별 통합 테스트: 각 `OAuthClient` 구현체가 실제(또는 WireMock 등으로 흉내낸) 엔드포인트와 올바르게 통신하는지 별도 검증
- 관측성/에러 처리를 파사드에 집중: 공급자별 예외(HTTP 4xx/5xx, JWT 검증 실패 등)를 `OAuthProviderException` 같은 도메인 예외로 번역하고, 재시도/타임아웃/서킷브레이커를 배치할 지점을 파사드 또는 `OAuthClient` 경계로 명확히 한다.

### 7. 안티패턴
- **God Facade**: 로그인뿐 아니라 계정 연동, 회원 탈퇴, 알림 발송까지 시나리오가 계속 붙어 파사드 하나가 수천 줄이 되는 현상. 유스케이스 단위로 파사드를 쪼개야 한다.
- **도메인 규칙 유입(빈약한 도메인 모델)**: "이메일이 이미 존재하면 자동 연동한다" 같은 정책 판단이 `SocialLoginFacade` 안에 if문으로 직접 들어가는 경우. 이 판단은 `MemberService`(도메인 서비스) 책임이어야 한다.
- **파사드 우회(leaky facade)**: 성능 때문에 혹은 급하게 컨트롤러가 `OAuthClient`를 직접 주입받아 호출하기 시작하면, 파사드가 강제하던 절차(트랜잭션 경계, 예외 번역)가 깨진다.
- **공급자 고유 규칙의 하드코딩**: 동일 이메일 중복 가입 정책, 계정 연동(Account Linking) 규칙을 파사드에 직접 작성하면 공급자가 늘어날수록 분기가 다시 파사드 안에서 폭발한다.

## 핵심 정리
- 파사드는 "기능 추가"가 아니라 "복잡도 은닉"을 위한 패턴이며, 클라이언트가 알아야 할 지식을 줄이는 것이 본질이다.
- 소셜 로그인처럼 절차는 동일하고 세부 규약만 다른 문제는 파사드(시나리오 통합) + 전략(공급자 차이 흡수) 조합이 자연스럽다.
- `Map<Provider, OAuthClient>`를 `List<OAuthClient>` 자동 주입 + `EnumMap` 변환으로 구성하면, 신규 공급자 추가가 구현체 등록만으로 끝나 OCP를 만족한다.
- 파사드는 오케스트레이션만 담당해야 하며, 비즈니스 규칙(회원 연동 정책 등)을 품는 순간 God Object로 전락한다.
- Apple처럼 매 요청마다 서명된 JWT를 `client_secret`으로 만들어야 하는 공급자 고유 규칙도, `OAuthClient` 구현체 내부로 격리하면 파사드와 컨트롤러에는 아무 영향을 주지 않는다.

## 기술적 한계와 보완 전략
- 한계: 간접 계층 추가로 호출 경로 추적이 어려워짐 → 보완: 파사드에 분산 트레이싱 span과 구조적 로깅 필드(provider, providerId) 부여
- 한계: 파사드 인터페이스가 최소 공통분모로 수렴해 공급자 고유 기능 사용이 어려움(예: Apple의 `is_private_email`) → 보완: 확장 인터페이스 분리(ISP) 또는 capability 조회 방식 제공
- 한계: 시나리오가 늘어나면 파사드가 비대해짐 → 보완: 유스케이스 단위 파사드 분할(로그인/연동/탈퇴)
- 한계: 여러 외부 호출을 조립하므로 부분 실패 시 정합성 문제 발생 → 보완: 멱등 키 기반 재시도, 보상 트랜잭션, 외부 호출과 DB 트랜잭션 분리
- 한계: 파사드 뒤에 숨은 동기 HTTP 호출이 지연을 누적 → 보완: 타임아웃/서킷브레이커, JWK·공개키 캐싱, Apple `client_secret` JWT는 만료 시간을 짧게 잡되 재생성 비용을 줄이기 위해 캐싱 후 만료 직전 갱신

## 키워드
- **Facade Pattern**: 서브시스템의 여러 인터페이스를 하나의 상위 인터페이스로 통합해 클라이언트의 사용 복잡도를 낮추는 GoF 구조 패턴
- **Structural Pattern (GoF)**: 클래스/객체를 조합해 더 큰 구조를 만드는 방법을 다루는 GoF 패턴 카테고리(Facade, Adapter, Proxy, Decorator, Composite 등)
- **Strategy Pattern**: 동일 인터페이스 뒤에 여러 알고리즘(구현)을 캡슐화하고, 런타임에 컨텍스트가 필요한 구현을 선택하도록 하는 행위 패턴. 예제의 `OAuthClient` 구현체들이 해당
- **OAuth 2.0 / OIDC**: OAuth 2.0은 인가(Authorization) 위임 프로토콜, OIDC(OpenID Connect)는 그 위에서 신원(Authentication) 확인을 위해 `id_token`(JWT)을 추가한 표준
- **Social Login (Google, Kakao, Naver, Apple)**: 각 공급자가 OAuth 2.0/OIDC를 구현하지만 토큰 엔드포인트, `client_secret` 형태, 사용자 정보 조회 방식 등 세부 규약이 다름
- **Open-Closed Principle (OCP)**: 확장에는 열려있고 변경에는 닫혀있어야 한다는 원칙. `OAuthClient` 구현체 추가만으로 신규 공급자를 지원하는 구조가 이를 만족시킴
- **Coupling / Cohesion**: 결합도(모듈 간 의존 정도)와 응집도(모듈 내부 요소들의 관련성). 파사드는 결합도를 낮추는 데 초점
- **Orchestration vs Business Logic**: 오케스트레이션(절차 조립)과 비즈니스 규칙(도메인 판단)의 책임 분리. 파사드는 전자만, 도메인 서비스는 후자를 담당해야 함
- **Adapter / Mediator / Proxy 비교**: Adapter는 인터페이스 변환, Mediator는 양방향 조율, Proxy는 동일 인터페이스로 접근 제어라는 점에서 Facade(단방향 단순화)와 구분됨
- **God Object 안티패턴**: 하나의 클래스(여기서는 파사드)가 지나치게 많은 책임을 떠안아 비대해지고 유지보수가 어려워지는 설계 결함
