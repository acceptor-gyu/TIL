# DC/OS (Datacenter Operating System)

## 개요
DC/OS(Datacenter Operating System)는 Mesosphere(現 D2iQ)가 Apache Mesos를 커널로 삼아 만든 분산 시스템 플랫폼이다. 개별 서버를 하나하나 관리하는 대신 데이터센터 전체를 "하나의 거대한 컴퓨터"처럼 추상화해서, CPU/메모리/디스크/포트 같은 물리 자원을 풀(pool)로 묶고 그 위에서 여러 애플리케이션(배치 잡, 장기 실행 서비스, 컨테이너 등)을 동시에 스케줄링·운영할 수 있게 해준다. 대규모 클러스터에서 서버별로 애플리케이션을 수동 배치하면 자원 활용률이 떨어지고 운영 부담이 커지는 문제를 해결하기 위해 등장했으며, Kubernetes 이전 시기에 대규모 컨테이너/빅데이터 워크로드(Spark, Kafka, Cassandra 등)를 한 클러스터에서 함께 운영하기 위한 대표적인 솔루션이었다.

## 상세 내용

### DC/OS란 무엇인가
- DC/OS는 스스로를 "분산 시스템이자, 클러스터 매니저이자, 컨테이너 플랫폼이자, 운영체제"라고 정의한다. 리눅스가 한 대의 머신에서 프로세스·메모리·파일 시스템을 추상화하듯, DC/OS는 여러 대의 머신(에이전트 노드)에 흩어진 자원을 추상화해서 하나의 논리적 자원 풀로 다룬다.
- 단, DC/OS는 호스트 OS가 아니다. 각 노드는 여전히 자체 커널(리눅스)을 가지고 있고, DC/OS는 그 위에서 동작하는 분산 커널 계층으로 볼 수 있다.
- 등장 배경은 대규모 데이터센터에서 서버를 서비스별로 고정 할당(static partitioning)하면서 발생하는 낮은 자원 활용률과, 서비스가 늘어날수록 커지는 수동 운영 부담을 해결하려는 데 있다. Twitter, Airbnb 등에서 Mesos를 대규모로 운영하며 검증된 자원 공유 모델을 상용 패키지로 만든 것이 DC/OS다.

### 아키텍처 구성
- **Apache Mesos 기반 커널**: DC/OS의 핵심 클러스터 관리 기능은 Apache Mesos가 담당한다. Mesos는 분산 시스템 커널로서 자원 격리(cgroups, 컨테이너)와 자원 분배를 책임진다.
- **Master / Agent 노드 구조**: Master 노드는 클러스터 상태 관리, 스케줄링 의사결정, 리더 선출을 담당하고, Agent 노드는 실제 태스크(컨테이너/프로세스)가 실행되는 워커 역할을 한다. 운영 환경에서는 보통 홀수 개(3, 5, 7대)의 Master를 구성해 쿼럼(quorum)을 유지한다.
- **ZooKeeper를 통한 상태 관리와 리더 선출**: Mesos Master들은 Apache ZooKeeper를 이용해 리더를 선출하고, 클러스터 상태에 대한 합의를 유지한다. DC/OS는 ZooKeeper의 운영을 쉽게 하기 위해 Exhibitor 같은 컴포넌트를 함께 활용한다. 리더 Master가 죽으면 ZooKeeper 기반으로 새 리더가 빠르게 선출되어 가용성을 확보한다.
- **Admin Router, Mesos DNS 등 시스템 컴포넌트**: Admin Router는 DC/OS UI, CLI, API 요청을 받아 각 내부 컴포넌트(Mesos, Marathon, Metronome 등)로 라우팅하는 nginx 기반 게이트웨이다. Mesos DNS는 실행 중인 태스크에 `<task>.<framework>.mesos` 형태의 DNS 이름을 부여해 서비스를 찾을 수 있게 한다.

### 핵심 개념
- **자원 추상화**: CPU 코어, 메모리, 디스크, 포트 등 클러스터 내 모든 물리 자원을 하나의 논리적 풀로 묶어 관리한다. 개별 서버 단위가 아니라 클러스터 전체를 기준으로 자원을 배분하기 때문에 활용률이 크게 높아진다.
- **Two-Level Scheduling (Mesos 자원 제안 모델)**: Mesos는 스케줄링을 두 단계로 나눈다. 1단계에서 Mesos Master(Allocation 모듈, 기본적으로 Dominant Resource Fairness(DRF) 알고리즘 사용)가 Agent들이 가진 여유 자원을 모아 "Resource Offer"라는 형태로 각 프레임워크에게 제안한다. 2단계에서 프레임워크(예: Marathon)의 스케줄러가 그 오퍼를 받아들일지, 어떤 태스크를 그 자원에 배치할지 스스로 결정한다. 이 방식 덕분에 Mesos 자체는 중앙에서 모든 스케줄링 로직을 알 필요 없이 확장성 있게 동작할 수 있다.
- **Framework와 Scheduler의 관계**: Mesos에서 "프레임워크"는 스케줄러와 실행기(Executor)의 쌍으로 구성된다. 스케줄러는 오퍼를 수락/거절하고 태스크를 오퍼된 자원에 매핑하며, 실행기는 Agent에서 실제로 태스크를 구동하고 생명주기를 관리한다. Marathon, Metronome, Spark, Kafka 등이 각각 독립적인 프레임워크로 Mesos 위에서 동작한다.

### 워크로드 실행
- **Marathon**: 장기 실행(long-lived) 서비스를 오케스트레이션하는 DC/OS의 기본 컨테이너 오케스트레이터다. 헬스체크, 장애 시 재시작, 롤링 업데이트, 앱/포드(pod) 배포 등을 담당하며 Mesos 프레임워크로 동작한다.
- **Metronome**: 배치(batch) 작업이나 cron 형태의 스케줄 작업을 실행하는 프레임워크다. Marathon이 계속 떠 있어야 하는 서비스를 다루는 반면, Metronome은 짧게 실행되고 끝나는 잡을 다룬다(DC/OS Jobs로도 불린다).
- **컨테이너 런타임 지원**: DC/OS는 Docker 컨테이너 런타임과, Mesos 자체 Universal Container Runtime(UCR, 과거 Mesos Containerizer) 두 가지를 모두 지원해서 Docker 이미지든 네이티브 실행 파일이든 컨테이너화해서 실행할 수 있다.

### 서비스 디스커버리와 네트워킹
- **Mesos DNS, VIP, 오버레이 네트워크**: Mesos DNS로 태스크를 DNS 이름 기반으로 찾을 수 있고, VIP(Virtual IP)를 통해 여러 인스턴스에 대한 고정된 가상 주소/포트로 접근할 수 있다. DC/OS 오버레이 네트워크는 컨테이너별로 별도의 IP를 부여해 포트 충돌 없이 여러 인스턴스를 같은 Agent에 배치할 수 있게 한다.
- **로드밸런싱(Marathon-LB, Edge-LB)**: Marathon-LB는 HAProxy 기반으로 Marathon 앱 앞단에서 L4/L7 로드밸런싱과 외부 트래픽 진입을 처리한다. Edge-LB는 이를 대체/보완하는 좀 더 유연한 엣지 로드밸런서로, 클러스터 외부에서 들어오는 트래픽을 내부 서비스로 라우팅한다.

### 패키지 관리
- **Universe 카탈로그와 서비스 설치**: Universe는 DC/OS의 공식 패키지 저장소로, Kafka, Cassandra, Spark, Jenkins 같은 서비스를 CLI(`dcos package install`)나 UI 한 번의 클릭으로 설치할 수 있게 해준다. 각 패키지는 Marathon 앱 정의, 설정 스키마, 업그레이드 절차 등을 포함하고 있어 복잡한 분산 시스템도 표준화된 방식으로 배포할 수 있다.

## 핵심 정리
- 핵심 포인트 1: DC/OS는 데이터센터의 CPU/메모리/디스크/포트를 하나의 자원 풀로 추상화해 클러스터 전체를 한 대의 컴퓨터처럼 다룬다.
- 핵심 포인트 2: Mesos의 Two-Level Scheduling(자원 제안 → 프레임워크의 태스크 배치)이 확장성과 다양한 워크로드 혼재 운영의 핵심 메커니즘이다.
- 핵심 포인트 3: Marathon(장기 실행 서비스)과 Metronome(배치 작업)이라는 두 오케스트레이터, 그리고 Universe 패키지 카탈로그로 다양한 분산 서비스를 표준화된 방식으로 배포·운영한다.

## 기술적 한계와 보완 전략
- Kubernetes가 사실상 컨테이너 오케스트레이션의 표준으로 자리 잡으면서 DC/OS/Mesos 생태계와 커뮤니티, 서드파티 지원이 크게 축소되었다. D2iQ는 이후 Kubernetes 기반 플랫폼(Konvoy 등)으로 전략을 전환했다.
- ZooKeeper, Mesos Master/Agent, Marathon, Admin Router 등 다층 컴포넌트로 구성되어 있어 운영 복잡도와 학습 곡선이 높은 편이다. 장애 지점(리더 선출, ZooKeeper 쿼럼 등)에 대한 이해 없이 운영하기 어렵다.
- 현재는 Mesos 위에서 Kubernetes를 얹어 쓰는 하이브리드 접근(예: DC/OS Kubernetes 서비스)이나, 순수 Kubernetes로의 완전 전환이 실무에서 더 일반적인 대안으로 자리 잡았다. 새로운 프로젝트에서 DC/OS를 신규 도입하는 경우는 드물고, 레거시 운영 관점에서 이해해 둘 가치가 있는 기술로 남아 있다.

## 키워드
- **Apache Mesos**: DC/OS의 핵심 분산 시스템 커널. 클러스터의 CPU/메모리/디스크 등 자원을 추상화하고, Master-Agent 구조로 자원을 분배·격리하는 역할을 한다.
- **Marathon**: Mesos 위에서 동작하는 장기 실행 서비스 오케스트레이터. 헬스체크, 자동 재시작, 롤링 업데이트 등 컨테이너 서비스의 생명주기를 관리한다.
- **Two-Level Scheduling**: Mesos의 스케줄링 모델. 1단계에서 Master가 자원을 오퍼로 제안하고, 2단계에서 각 프레임워크의 스케줄러가 태스크를 실제로 배치하는 방식으로, 중앙 집중형 스케줄러보다 확장성이 높다.
- **ZooKeeper**: Mesos Master들의 리더 선출과 클러스터 메타데이터(상태) 합의를 담당하는 코디네이션 서비스. DC/OS는 이를 안정적으로 운영하기 위해 Exhibitor 등을 함께 사용한다.
- **Resource Offer**: Mesos Master가 Agent의 여유 자원을 묶어서 프레임워크에게 제안하는 단위. 프레임워크는 이 오퍼를 수락하거나 거절해서 태스크를 배치할지 결정한다.
- **Container Orchestration**: 여러 컨테이너의 배포, 스케줄링, 스케일링, 장애 복구를 자동화하는 것. DC/OS에서는 Marathon(서비스)과 Metronome(배치)이 이 역할을 나눠 맡는다.
- **Mesos Framework**: 스케줄러와 실행기(Executor)의 쌍으로 구성된 Mesos 위의 애플리케이션 단위. Marathon, Metronome, Spark, Kafka 등이 각각 독립적인 프레임워크로 동작한다.
- **Service Discovery**: 동적으로 배치되는 태스크의 위치(IP/포트)를 다른 서비스가 찾을 수 있게 하는 메커니즘. DC/OS에서는 Mesos DNS와 VIP(Virtual IP)를 통해 구현된다.
- **Universe Package**: DC/OS의 공식 패키지 카탈로그. Kafka, Cassandra, Spark 등 복잡한 분산 서비스를 표준화된 정의(Marathon 앱 스펙 포함)로 손쉽게 설치·업그레이드할 수 있게 한다.
- **Kubernetes 비교**: DC/OS/Mesos는 다양한 워크로드(빅데이터, 배치, 장기 서비스)를 하나의 클러스터에서 혼재 운영하는 데 강점이 있었으나, 현재는 생태계와 커뮤니티 규모에서 Kubernetes가 사실상 표준으로 자리 잡아 DC/OS의 실무 채택은 크게 줄어들었다.
