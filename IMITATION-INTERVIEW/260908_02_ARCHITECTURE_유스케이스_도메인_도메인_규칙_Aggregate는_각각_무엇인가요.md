# [ARCHITECTURE] 유스케이스, 도메인, 도메인 규칙, 애그리거트(Aggregate)는 각각 무엇이고 어떻게 구분하나요?

> DDD 핵심 용어의 정의와 경계

## 개요
- 전제 정리: **층위가 다르**다. 이 넷은 병렬 개념이 아니라 **하나가 다음을 낳는 순서**를 갖는다.

```
[도메인]        우리가 다루는 현실의 업무 영역
    │
    │  그 영역에서 "항상 참이어야 하는 것"을 찾아내면
    ▼
[도메인 규칙]   어겨지면 업무가 망가지는 제약
    │
    │  그 규칙을 "누가 책임지고 지킬 것인가"를 정하면
    ▼
[애그리거트]    규칙을 함께 지켜야 하는 객체 묶음 = 일관성 단위
    │
    │  그 애그리거트를 "어떤 시나리오에서 쓸 것인가"를 정하면
    ▼
[유스케이스]    액터가 목표를 달성하는 한 번의 흐름
```

- 한 문장 정의와 각 용어가 답하는 질문:

| 용어 | 한 문장 정의 | 답하는 질문 | 배달앱 예시 |
| --- | --- | --- | --- |
| 도메인 | 소프트웨어가 다루는 **현실의 업무 영역** | "우리는 무슨 일을 하는 회사인가?" | 음식 주문과 배달 |
| 도메인 규칙 | 그 영역에서 **항상 참이어야 하는 제약** | "무엇이 절대 어겨지면 안 되는가?" | 조리 시작 후에는 취소 불가 |
| 애그리거트 | 그 규칙을 함께 지켜야 하는 **객체 묶음(일관성 단위)** | "그 규칙을 누가 책임지는가?" | 주문(Order) |
| 유스케이스 | 액터가 목표를 달성하는 **한 번의 시나리오** | "사용자가 무엇을 하러 오는가?" | 주문 취소하기 |

- 답변의 축: **도메인은 발견하는 것, 규칙은 도메인에서 찾아내는 것, 애그리거트는 규칙이 정해 주는 것, 유스케이스는 그 위에서 조립하는 것.** 이 방향이 반대로 뒤집히면(테이블 먼저 → 화면 먼저 → 규칙은 서비스에) 전형적인 절차지향 코드가 된다.
- 관련 정리: [헥사고날 아키텍처](../ARCHITECTURE/260615_01_헥사고날_아키텍처.md) · [Hexagonal Architecture에서 port와 adapter는 각각 어떤 책임을 가지나요?](./260908_01_ARCHITECTURE_Hexagonal_Architecture에서_port와_adapter는_각각_어떤_책임을_가지나요.md) — 이 네 용어가 실제로 어느 패키지에 놓이는지는 그쪽에서 다룬다.

## 상세 내용

### 0. 먼저 하나의 비유로 네 용어를 묶기

**은행 창구**를 떠올리면 네 용어가 한 장면 안에 전부 들어온다.

| 창구 풍경 | 대응하는 용어 | 설명 |
| --- | --- | --- |
| 은행이 하는 일 = 돈을 맡고 빌려주는 업(業) | **도메인** | 시스템이 아니라 **업무 영역** 자체 |
| "잔액보다 많이 뺄 수 없다" | **도메인 규칙** | 전산이 없던 시절에도 성립하던 제약 |
| 통장 한 권 (잔액 + 거래내역이 한 묶음) | **애그리거트** | 잔액과 거래내역은 **따로 고칠 수 없다**. 통장 단위로 꺼내 고치고 통장 단위로 정리한다 |
| 창구 뒤 업무 안내판 ("입금 / 출금 / 이체 / 신규 개설 / 해지") | **유스케이스** | 고객이 은행에 와서 **할 수 있는 일의 목록** |

여기서 바로 읽히는 성질이 몇 개 있다.
- **규칙은 창구 직원이 만들지 않는다.** 은행업이 원래 갖고 있던 것을 직원이 집행할 뿐이다 → 규칙은 유스케이스가 아니라 도메인이 소유한다.
- **통장을 반쪽만 꺼낼 수 없다.** 거래내역만 고치고 잔액을 안 고치면 통장이 깨진다 → 애그리거트는 통째로 로드/검증/저장한다.
- **안내판에는 "고객정보 업데이트"라고 안 적혀 있다.** "주소 변경 신고", "예금 해지"처럼 목적이 적혀 있다 → 유스케이스 이름은 CRUD가 아니라 목적이다.

### 1. 도메인(Domain)

#### 1-1. 정의
**소프트웨어가 해결하려는 현실의 문제 영역(problem space) 그 자체.** 코드가 아니라 업무와 지식의 영역이다.

- 배달앱의 도메인 = 음식 주문과 배달
- 병원 시스템의 도메인 = 진료와 처방
- 항공사의 도메인 = 운항 스케줄과 좌석 판매
- 물류사의 도메인 = 집화·간선·배송

#### 1-2. 현실에서 도메인을 알아보는 법
**그 회사가 신입에게 가장 먼저 가르치는 용어 목록이 곧 도메인이다.**

| 업계 | 신입이 첫 주에 배우는 말 |
| --- | --- |
| 배달앱 | 단건배차, 묶음배차, 피크 할증, 쿠폰 중복, 라이더 콜 |
| 병원 | 초진/재진, 수가, 삭감, 처방전 반려 |
| 이커머스 | 부분 취소, 반품 회수, 옵션 재고, 정산 마감 |
| 은행 | 여신/수신, 지급정지, 영업일 기준 |

이 단어들이 **회의에서도 코드에서도 똑같이 쓰이는 상태**가 유비쿼터스 언어(Ubiquitous Language)다. 회의에서는 "배차", 코드에서는 `assign`, DB에서는 `matching_tb`라면 번역 비용이 영원히 발생하고, 그 번역 과정에서 규칙이 소실된다.

#### 1-3. 서브도메인 분류 — 전부 똑같이 정성 들일 필요는 없다
도메인은 하나가 아니라 여러 서브도메인으로 나뉘고, **셋의 투자 수준이 달라야 한다.**

| 구분 | 의미 | 배달앱 예시 | 설계 투자 |
| --- | --- | --- | --- |
| 코어(Core) | 경쟁력의 원천. 여기서 돈을 번다 | 주문, 배차 알고리즘, 정산 | 도메인 모델 엄격 적용 |
| 지원(Supporting) | 우리 사업에 필요하지만 차별점은 아님 | 리뷰, 쿠폰, 고객센터 문의 | 적당히. 규칙만 도메인에 |
| 일반(Generic) | 어디나 똑같음. 사면 된다 | 로그인, 알림 발송, 지도 | 라이브러리/SaaS 사용, CRUD로 충분 |

면접에서 "DDD를 전부 적용했나요?"라는 질문이 오면 이 표가 답이 된다 — **코어에만 적용하고 일반 서브도메인은 CRUD로 두는 것이 정상이다.**

#### 1-4. 자주 하는 오해 3가지

| 오해 | 실제 |
| --- | --- |
| "`domain` 패키지에 있는 코드 = 도메인" | 도메인은 **현실**이고, 패키지는 그 현실을 담은 모델이 놓이는 자리일 뿐이다 |
| "도메인 = 도메인 모델" | 모델은 도메인을 **목적에 맞게 추린 것**이다. 지도는 땅이 아니다. 같은 '회원'도 마케팅 관점과 정산 관점에서 다른 모델이 된다 |
| "JPA `@Entity`가 도메인 모델" | `@Entity`는 **DB 행에 대응하는 객체**다. 규칙이 하나도 없는 `@Entity`는 도메인 모델이 아니라 데이터 홀더다 |

### 2. 도메인 규칙(Domain Rule / Business Rule)

#### 2-1. 정의
**그 도메인에서 항상 참이어야 하는 사실, 또는 반드시 지켜져야 하는 제약.** 결정적인 특징은 이것이다 — **시스템이 없어도 존재한다.**

"잔액보다 많이 출금할 수 없다"는 전산화 이전의 은행에도 있었다. 개발자가 **만드는 것이 아니라 업무에서 발견하는 것**이다.

#### 2-2. 네 가지 유형

| 유형 | 설명 | 배달앱 예시 | 검사 시점 |
| --- | --- | --- | --- |
| **불변식(Invariant)** | 객체가 **어느 순간에나** 만족해야 하는 상태 조건 | 주문 총액 = 항목 금액 합계 − 할인 + 배달비 | 상태가 바뀔 때마다 |
| **상태 전이 규칙** | 어떤 상태에서 어떤 상태로 갈 수 있는가 | `COOKING` → `CANCELED` 불가, `PENDING` → `CANCELED` 가능 | 전이를 시도할 때 |
| **정책(Policy)** | 비즈니스 판단. **자주 바뀐다** | 최소 주문금액 12,000원, 5만원 이상 배달비 무료 | 해당 계산 시점 |
| **계산 규칙** | 값을 도출하는 방식 | 배달비 = 기본료 + 거리 할증 + 피크 할증 | 값을 요청할 때 |

**불변식과 정책을 구분하는 것이 실무에서 중요하다.** 불변식은 코드에 박아도 되지만, 정책은 자주 바뀌므로 값을 외부(설정·DB·정책 테이블)로 빼고 **규칙의 형태만 도메인에 남긴다.**

```java
// 정책 값을 코드에 박으면 배포 없이 못 바꾼다
if (totalAmount < 12_000) throw new BelowMinimumOrderAmountException();

// 규칙의 형태는 도메인에, 값은 밖에서 주입
public class Shop {
    private final Money minimumOrderAmount;   // 가게마다 다르고 자주 바뀐다
    public void validateOrderable(Money orderAmount) {
        if (orderAmount.isLessThan(minimumOrderAmount)) {
            throw new BelowMinimumOrderAmountException(id, minimumOrderAmount);
        }
    }
}
```

#### 2-3. 이건 도메인 규칙인가? — 구분 훈련
면접에서 가장 잘 갈리는 지점이다.

| 규칙 | 분류 | 이유 |
| --- | --- | --- |
| 잔액보다 많이 출금할 수 없다 | **도메인 규칙** | 은행업 자체의 제약. 종이 장부로 해도 필요하다 |
| 이체는 1일 5천만원 한도 | **도메인 규칙** | 금융 규제/상품 약관 = 업무 규칙 |
| 조리 시작 후에는 취소 불가 | **도메인 규칙** | 가게와의 약속. 어기면 현업이 손해를 본다 |
| 비밀번호는 8자 이상 | 애플리케이션/보안 정책 | 도메인(여수신·주문)과 무관 |
| 한 번에 100건까지만 조회 | 인프라 제약 | 성능 보호용. 업무가 요구한 적 없다 |
| 주문번호는 UUID로 생성 | 기술 결정 | 업무는 "고유하면 된다"만 요구한다 |
| 이메일 형식이 맞아야 한다 | 형식 검증 | 입력 어댑터의 관심사 |
| 이메일은 중복될 수 없다 | **도메인 규칙** | "계정 = 사람 하나"라는 업무 전제 |

두 가지 판정 질문이면 대부분 갈린다.
1. **"이 규칙을 어겼을 때 화내는 사람이 개발자인가, 현업인가?"** — 현업이면 도메인 규칙이다.
2. **"종이와 펜으로 이 업무를 운영해도 이 규칙이 필요한가?"** — 필요하면 도메인 규칙이다.

#### 2-4. 규칙이 새어 나간 코드 vs 규칙을 가진 코드
가장 흔한 실패는 규칙이 **유스케이스(서비스)로 새어 나가는 것**이다.

```java
// ❌ 규칙이 서비스에 흩어진 코드
@Transactional
public void cancelOrder(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    if (order.getStatus() == OrderStatus.DELIVERING || order.getStatus() == OrderStatus.DELIVERED) {
        throw new IllegalStateException("배달이 시작된 주문은 취소할 수 없습니다.");
    }
    if (order.getStatus() == OrderStatus.COOKING) {
        throw new IllegalStateException("조리가 시작되어 취소할 수 없습니다.");
    }
    order.setStatus(OrderStatus.CANCELED);
    order.setCanceledAt(LocalDateTime.now());
    orderRepository.save(order);
}
```

무엇이 문제인가. **같은 규칙이 다른 곳에도 필요하다는 것**이다. 고객 취소, 가게 사장 취소, 결제 실패에 의한 자동 취소, 미수락 30분 경과 배치 취소 — 취소 경로는 최소 4개다. 위 코드는 그 4곳에 복사되고, **한 곳만 고치는 순간 규칙이 갈라진다.** 그리고 `setStatus`가 열려 있으므로 규칙을 통과하지 않고 상태를 바꾸는 코드가 언젠가 반드시 생긴다.

```java
// ✅ 규칙을 애그리거트가 갖는 코드
public class Order {
    private OrderStatus status;
    private LocalDateTime canceledAt;

    public void cancel(LocalDateTime now) {
        if (!status.cancelable()) {                       // 상태 전이 규칙은 여기 한 곳에만
            throw new OrderNotCancelableException(id, status);
        }
        this.status = OrderStatus.CANCELED;
        this.canceledAt = now;
    }
}

public enum OrderStatus {
    PENDING(true), ACCEPTED(true), COOKING(false), DELIVERING(false), DELIVERED(false), CANCELED(false);
    private final boolean cancelable;
    public boolean cancelable() { return cancelable; }
}
```

이제 취소 경로가 4개든 10개든 규칙은 한 곳에 있다. **`setStatus`를 없애는 것이 절반**이다. setter가 열려 있으면 규칙을 아무리 잘 써도 우회로가 남는다.

### 3. 애그리거트(Aggregate)

#### 3-1. 정의
**함께 변경되어야 하고, 함께 규칙이 검사되어야 하는 객체들의 묶음.** 그리고 그 묶음을 대표하며 일관성을 책임지는 객체를 **애그리거트 루트(Aggregate Root)**라고 한다.

#### 3-2. 왜 필요한가 — 객체 그래프에 선을 긋는 일
객체를 연관으로 잇기 시작하면 그래프가 무한히 이어진다.

```
주문 → 회원 → 그 회원의 다른 주문들 → 각 주문의 가게 → 가게의 전체 메뉴 → ...
```

여기서 답해야 하는 질문이 세 개 생긴다.
- 주문 하나를 고치려면 **어디까지 메모리에 올려야 하는가?**
- 저장할 때 **어디까지 한 트랜잭션으로 묶어야 하는가?**
- 규칙을 검사할 때 **어디까지가 검사 범위인가?**

애그리거트는 이 세 질문에 대해 **같은 답**을 주는 선이다. 그래서 애그리거트는 "묶음"이 아니라 **경계**라고 이해하는 편이 정확하다.

#### 3-3. 현실 비유 — 전표 한 장
**애그리거트는 서류철에 철해 둔 전표 한 장이다.**

| 전표의 성질 | 애그리거트의 성질 |
| --- | --- |
| 항목만 따로 떼어 고칠 수 없다. 전표를 통째로 꺼내 고친다 | 애그리거트는 루트를 통해 통째로 로드한다 |
| 고친 뒤 "합계가 항목 합과 맞는지" 확인하고 철한다 | 저장 전에 불변식을 검사한다 |
| 두 사람이 같은 전표를 동시에 고치면 사고가 난다 | 애그리거트 = 동시성 제어 단위 |
| 다른 전표를 참조할 땐 **전표번호만** 적는다 | 다른 애그리거트는 **ID로만** 참조한다 |

#### 3-4. 구성 요소
```java
public class Order {                      // 애그리거트 루트
    private final OrderId id;
    private final MemberId memberId;      // ✅ 다른 애그리거트는 ID로 참조
    private final ShopId shopId;          // ✅
    // private final Shop shop;           // ❌ 객체로 물면 경계가 무너진다
    private final List<OrderLine> lines;  // ✅ 내부 엔티티는 객체로 소유
    private final Address deliveryAddress;// ✅ 값 객체
    private Money totalAmount;
    private OrderStatus status;

    public void changeQuantity(MenuId menuId, int quantity) {
        findLine(menuId).changeQuantity(quantity);
        this.totalAmount = recalculateTotal();   // 불변식을 루트가 다시 맞춘다
    }

    public List<OrderLine> lines() {
        return List.copyOf(lines);   // 내부 컬렉션을 그대로 반환하지 않는다
    }
}
```

| 구성 요소 | 역할 | 예 |
| --- | --- | --- |
| 애그리거트 루트 | 외부의 유일한 진입점. 불변식을 최종 책임 | `Order` |
| 내부 엔티티 | 루트 안에서만 식별되는 객체 | `OrderLine` |
| 값 객체(VO) | 식별자 없이 값으로 동등한 객체 | `Money`, `Address`, `PhoneNumber` |

#### 3-5. 지켜야 하는 4가지 규칙

**(1) 외부는 루트를 통해서만 접근한다**
현실 비유로는 **부서 대표번호**다. 팀원 직통번호를 외부에 뿌리면 결재선을 건너뛴 요청이 들어온다.
```java
order.lines().get(0).changeQuantity(5);   // ❌ 총액 불변식이 깨진 채로 남는다
order.changeQuantity(menuId, 5);          // ✅ 루트가 총액을 다시 맞춘다
```
`getLines()`가 수정 가능한 리스트를 반환하면 이 규칙은 문서에만 존재하게 된다.

**(2) 한 트랜잭션에서는 한 애그리거트만 수정한다**
여러 애그리거트를 한 트랜잭션에 묶으면 락 범위가 커지고 데드락 확률이 올라간다. 이 원칙을 지킬 수 없을 때의 처리는 꼬리질문 ③에서 다룬다.

**(3) 다른 애그리거트는 ID로 참조한다**
`Order`가 `Shop` 객체를 물면, 주문을 로드할 때 가게가 딸려 오고 실수로 가게를 수정할 여지가 생긴다. `ShopId`만 들고 있으면 경계가 코드로 강제된다.

**(4) 애그리거트 밖의 일관성은 결국 일치(eventual consistency)로 맞춘다**
"주문이 완료되면 회원 등급을 재계산한다"가 **밀리초 단위로 정확할 필요는 없다.** 도메인 이벤트로 넘긴다.

#### 3-6. 경계는 무엇이 정하는가 — **불변식이 정한다**
가장 중요한 문장이다. **테이블 구조나 FK가 아니라, "동시에 깨지면 안 되는 규칙"이 애그리거트 경계를 정한다.**

**영화관 좌석 예매**로 후보를 비교해 보면 명확해진다. 지켜야 할 불변식은 "**한 좌석은 한 명만 예매할 수 있다**"이다.

| 후보 | 경계 | 결과 |
| --- | --- | --- |
| A. 상영관(Theater) 전체 | 상영관 = 애그리거트 | 불변식은 지켜지지만 **상영관 하나에서 동시 예매가 1건씩만** 처리된다. 실패 |
| B. **상영회차(Screening)** | 회차 + 그 회차의 좌석들 | 같은 회차 예매만 직렬화된다. 불변식도 지켜진다. **현실적인 답** |
| C. 좌석(Seat) 하나 | 좌석 = 애그리거트 | 동시성은 최고지만 "연석 4개를 한 번에" 같은 규칙을 보장할 수 없다 |

```java
public class Screening {                          // 애그리거트 루트 = 상영회차
    private final ScreeningId id;
    private final Map<SeatNo, Seat> seats;        // 내부 엔티티

    public Reservation reserve(MemberId memberId, List<SeatNo> seatNos) {
        for (SeatNo no : seatNos) {
            Seat seat = seats.get(no);
            if (seat == null) throw new SeatNotFoundException(no);
            if (seat.isTaken()) throw new SeatAlreadyTakenException(no);  // 불변식 검사
        }
        seatNos.forEach(no -> seats.get(no).occupy(memberId));
        return Reservation.of(id, memberId, seatNos);
    }
}
```

여기서 얻는 결론이 답변의 핵심이다.
- **애그리거트를 크게 잡으면 불변식은 쉽게 지켜지지만 동시성이 죽는다.**
- **작게 잡으면 동시성은 좋지만 규칙을 보장할 범위가 줄어든다.**
- 그래서 경계 설계는 **"이 불변식이 정말로 즉시 일관성이어야 하는가"**를 묻는 일이다.

애그리거트만으로 부족할 때는 DB 유니크 인덱스 같은 최후 방어선을 함께 둔다. → [따닥 방지 전략과 적절한 케이스 사례](../SYSTEM-ARCHITECTURE/260502_01_따닥_방지_전략과_적절한_케이스_사례.md) · [수강신청 시스템 동시성 처리](../SYSTEM-ARCHITECTURE/260306_02_수강신청_시스템_동시성_처리_Transactional_isolation_read_committed.md)

#### 3-7. 하지 말아야 할 경계 설정
- **FK를 따라 묶기** — DB 관계는 저장 구조이지 일관성 요구가 아니다.
- **화면에 같이 보이니까 묶기** — 조회 요구는 애그리거트가 아니라 조회 전용 모델(projection)로 푼다.
- **컬렉션이 무한히 자라는 묶음** — `Order` 안에 `deliveryHistory` 1,000건이 딸려 오면 로드할 때마다 전부 읽는다. **무한 증가 컬렉션은 별도 애그리거트로 분리**한다.

### 4. 유스케이스(Use Case)

#### 4-1. 정의
**액터(사용자·외부 시스템·스케줄러)가 시스템을 통해 하나의 목표를 달성하는 시나리오.** 즉 "이 시스템으로 할 수 있는 일"의 목록이다.

- 창구 업무 안내판: "입금 / 출금 / 이체 / 신규 개설 / 해지"
- 키오스크 첫 화면: "매장 식사 / 포장 / 주문 내역 확인"
- 주민센터 신청서 함: "전입 신고 / 등본 발급 / 인감 등록"

#### 4-2. 유스케이스의 책임 5가지
```java
@Transactional                                              // ④ 트랜잭션 경계
public void cancel(CancelOrderCommand command) {
    Order order = loadOrderPort.load(command.orderId());    // ① 애그리거트 로드
    order.cancel(clock.now());                              // ② 규칙 실행은 도메인에 위임
    saveOrderPort.save(order);                              // ③ 저장
    events.publish(new OrderCanceled(order.id()));          // ⑤ 후속 통보는 이벤트로
}
```

1. 필요한 애그리거트를 불러온다
2. **도메인 메서드를 호출한다** — 판단하지 않고 위임한다
3. 결과를 저장한다
4. 트랜잭션·권한 경계를 정한다
5. 외부 통보(환불 요청, 알림, 이벤트)를 트리거한다

#### 4-3. 유스케이스가 **하지 말아야** 할 것: 규칙 판단
2-4에서 본 대비가 그대로 적용된다. **유스케이스에 `if`가 늘어나면 규칙이 도메인 밖으로 새고 있다는 신호다.**

허용되는 `if`와 아닌 `if`는 이렇게 갈린다.

| 코드 | 판정 |
| --- | --- |
| `if (order == null) throw new OrderNotFoundException();` | ✅ 조회 실패 처리 = 흐름 제어 |
| `if (!currentUser.canManage(order)) throw new AccessDeniedException();` | ✅ 인가 = 애플리케이션 관심사 |
| `if (order.getStatus() == COOKING) throw ...` | ❌ 상태 전이 규칙 = 도메인 |
| `if (order.getTotalAmount() < shop.getMinimum()) throw ...` | ❌ 정책 = 도메인 |

#### 4-4. 이름 짓기 — CRUD는 유스케이스가 아니다
창구에서 "고객정보 업데이트요"라고 말하는 사람은 없다.

| 나쁜 이름 | 좋은 이름 | 왜 |
| --- | --- | --- |
| `updateOrder` | `cancelOrder`, `changeDeliveryAddress` | 규칙과 허용 조건이 서로 완전히 다르다 |
| `updateUser` | `withdrawMembership`, `changeAddress`, `agreeToMarketing` | 권한도, 감사 로그 요구도, 알림도 다르다 |
| `processPayment` | `payForOrder`, `refundCanceledOrder` | "처리"는 아무 정보도 주지 않는다 |

**"이름에 '및'이나 'and'를 넣고 싶어지면 유스케이스를 쪼갤 때다."**

#### 4-5. 유스케이스는 도메인 규칙을 만들지 않는다 — 하지만 순서는 소유한다
헷갈리기 쉬운 부분을 정리하면 이렇다.

| 질문 | 소유자 |
| --- | --- |
| "배달 시작된 주문은 취소할 수 있는가?" | **도메인** (Order) |
| "취소하면 환불을 먼저 하는가, 상태 변경을 먼저 하는가?" | **유스케이스** |
| "취소 알림을 가게와 고객 중 누구에게 보내는가?" | **유스케이스** (또는 도메인 이벤트 구독자) |
| "환불 금액은 얼마인가?" | **도메인** (취소 시점에 따른 환불 정책) |

즉 **"무엇이 허용되는가"는 도메인, "어떤 순서로 진행되는가"는 유스케이스**다.

### 5. 네 용어를 한 사건으로 관통하기

배달앱에서 **고객이 주문을 취소하는 사건** 하나에 네 용어가 전부 등장한다.

| 단계 | 내용 | 어느 용어인가 |
| --- | --- | --- |
| 우리가 다루는 영역은 음식 주문과 배달이다 | 문제 영역 | **도메인** |
| "조리 시작 후에는 취소할 수 없다", "취소 시 결제 전액 환불" | 항상 참이어야 하는 제약 | **도메인 규칙** |
| 주문 상태와 주문 항목은 함께 바뀌어야 하므로 `Order`가 한 묶음 | 규칙을 책임지는 일관성 단위 | **애그리거트** |
| 고객이 앱에서 "주문 취소"를 눌러 환불까지 완료되는 흐름 | 목표 달성 시나리오 | **유스케이스** |

코드로는 이렇게 배치된다.

```java
// [도메인 규칙 + 애그리거트] 무엇이 허용되는지는 Order가 안다
public class Order {
    public Refund cancelBy(Canceller canceller, LocalDateTime now) {
        if (!status.cancelable()) throw new OrderNotCancelableException(id, status);
        if (canceller.isCustomer() && status == ACCEPTED && acceptedMoreThan(5, MINUTES, now)) {
            throw new CancelWindowExpiredException(id);
        }
        this.status = CANCELED;
        this.canceledAt = now;
        return Refund.full(paymentId, totalAmount);   // 환불 금액 계산도 도메인 규칙
    }
}

// [유스케이스] 어떤 순서로 진행되는지는 서비스가 안다
@Transactional
public void cancel(CancelOrderCommand command) {
    Order order = loadOrderPort.load(command.orderId());
    Refund refund = order.cancelBy(command.canceller(), clock.now());
    saveOrderPort.save(order);
    events.publish(new OrderCanceled(order.id(), refund));   // 환불·알림은 커밋 후에
}
```

`cancelBy`에는 도메인 규칙만, `cancel`에는 순서만 있다. **이 분리가 유지되는지가 네 용어를 제대로 이해했는지의 실질적인 척도다.**

### 6. 꼬리질문 ①: 도메인 모델과 JPA Entity, DTO는 어떻게 다른가요?

셋은 **존재 이유가 다르다.**

| 구분 | 존재 이유 | 바뀌는 이유 | 비유 |
| --- | --- | --- | --- |
| 도메인 모델 | 규칙을 보유하고 집행한다 | 비즈니스 규칙이 바뀔 때 | 계약의 **내용** |
| JPA Entity | DB 행과 객체를 매핑한다 | 스키마가 바뀔 때 | 서류함에 보관하는 **양식** |
| DTO | 경계를 넘어 데이터를 나른다 | API 스펙이 바뀔 때 | 상대에게 보내는 **사본** |

합쳤을 때 생기는 실제 문제:
- **Entity = 도메인 모델**로 두면 → 기본 생성자와 setter가 강제되고, 지연 로딩 프록시가 규칙 실행 중에 튀어나오며, **컬럼 하나 추가가 도메인 변경으로 취급된다.**
- **도메인 모델 = DTO**로 두면 → 내부 모델 필드명을 바꾸는 순간 API 응답 스키마가 깨진다. 내부 리팩터링이 외부 계약 변경이 된다.

현실적인 절충: **소규모 프로젝트에서는 Entity와 도메인 모델을 합쳐도 된다. 단, 합치더라도 setter를 없애고 의미 있는 메서드로 규칙을 넣는다.** 분리보다 중요한 것은 **빈혈 모델(Anemic Domain Model)로 두지 않는 것**이다.

### 7. 꼬리질문 ②: 도메인 규칙은 엔티티, 도메인 서비스, 유스케이스 중 어디에 두나요?

**이 순서로 판단한다. 위에서 걸리면 아래로 내려가지 않는다.**

**1순위 — 애그리거트(엔티티/값 객체) 안**
애그리거트 하나의 상태만으로 판단할 수 있으면 여기가 기본값이다.
```java
order.cancel(now);            // 주문 상태만 보면 됨
money.plus(other);            // 값 객체의 계산 규칙
```

**2순위 — 도메인 서비스**
여러 애그리거트가 필요하거나, 어느 한쪽에 두면 어색한 규칙일 때만.
```java
// 이체: 어느 계좌에 두어도 한쪽에 치우친다 → 도메인 서비스
public class TransferService {
    public void transfer(Account from, Account to, Money amount) {
        from.withdraw(amount);   // "잔액보다 많이 못 뺀다"는 from이 안다
        to.deposit(amount);      // "정지 계좌엔 입금 불가"는 to가 안다
    }
}
```
대표 사례: 계좌 이체, 이메일 중복 검사(전체 회원 대상), 최적 배차(라이더 여럿 비교).

**주의**: 도메인 서비스는 **남발하면 빈혈 모델로 가는 지름길**이다. `OrderService`, `MemberService`처럼 애그리거트 이름 + Service로 만든 도메인 서비스는 십중팔구 규칙이 갈 곳을 못 찾은 결과다. **"정말 한 애그리거트로 안 되는가"를 두 번 묻는다.**

**3순위 — 유스케이스**
규칙이 아니라 **순서·트랜잭션·권한·통보**일 때만. 여기에 비즈니스 판단이 들어가면 1순위로 되돌린다.

### 8. 꼬리질문 ③: 하나의 유스케이스에서 여러 애그리거트를 수정해야 하면 어떻게 하나요?

원칙은 "한 트랜잭션 = 한 애그리거트"이지만, 현실에서는 자주 부딪힌다. **세 단계로 판단한다.**

**1단계: 정말로 즉시 일관성이 필요한지 되묻는다**
대부분은 아니다. "주문 완료 시 회원 등급 재계산", "리뷰 작성 시 가게 평점 갱신"은 몇 초 늦어도 아무 문제가 없다. 이런 것은 **도메인 이벤트로 넘긴다.**

**2단계: 즉시 일관성이 필요하다면 애그리거트 경계를 의심한다**
"항상 함께 바뀌고, 절대 어긋나면 안 된다"면 애초에 **한 애그리거트여야 했을 가능성**이 높다. 경계를 다시 긋는 것이 정답일 수 있다.

**3단계: 그래도 나눠야 하면 결과적 일관성 + 보상 처리**
```java
@Transactional
public void complete(CompleteOrderCommand command) {
    Order order = loadOrderPort.load(command.orderId());
    order.complete(clock.now());
    saveOrderPort.save(order);
    events.publish(new OrderCompleted(order.id(), order.memberId(), order.totalAmount()));
}

// 별도 트랜잭션에서 처리 — 실패해도 주문 완료는 되돌리지 않는다
@TransactionalEventListener(phase = AFTER_COMMIT)
public void on(OrderCompleted event) {
    rewardPointUseCase.grant(event.memberId(), event.totalAmount());
}
```

여기서 두 가지를 함께 말하면 좋다.
- **이벤트 발행 자체의 신뢰성**은 별도 문제다. 커밋 후 발행하다 실패하면 이벤트가 유실된다 → Outbox 패턴. [Outbox table에 event가 많이 쌓이면 polling과 발행 지연을 어떻게 줄일 수 있나요?](./260904_02_Outbox_table에_event가_많이_쌓이면_polling과_발행_지연을_어떻게_줄일_수_있나요.md)
- **트랜잭션 안에서 외부 호출을 하면 안 된다.** 락을 잡은 채 네트워크를 기다리면 동시성 대책이 무너진다. [비관적 락으로 막은 동시성이 @Transactional 안의 Slack 호출로 되살아났다](../SYSTEM-ARCHITECTURE/260730_01_비관적_락으로_막은_동시성이_Transactional_안의_Slack_호출로_되살아났다.md)

### 9. 꼬리질문 ④: 애그리거트가 커지거나 유스케이스가 커지면 어떤 문제가 생기나요?

**큰 애그리거트의 증상과 원인**

| 증상 | 원인 |
| --- | --- |
| 저장 시 락 경합, 낙관적 락 충돌이 잦다 | 서로 무관한 데이터가 한 버전 필드를 공유한다 |
| 조회 한 번에 수천 건이 딸려 온다 | 무한 증가 컬렉션(이력, 로그, 댓글)을 내부에 뒀다 |
| 트랜잭션이 길어져 커넥션이 마른다 | 경계가 넓어 로드/검증 시간이 길다 |

판정 질문: **"이 둘이 서로 다른 시각에 따로 바뀔 수 있는가?"** → Yes면 분리 후보다. 상품과 상품 리뷰, 주문과 배송 이력이 대표적이다.

**큰 유스케이스의 증상**
- 메서드 하나가 200줄이고 애그리거트를 5개 로드한다
- 이름에 '및', 'and'가 들어간다 (`createOrderAndSendNotification`)
- 파라미터에 `boolean` 플래그가 있다 (`cancel(orderId, boolean byAdmin)` → 서로 다른 유스케이스다)

해법은 같다. **유스케이스를 목적 단위로 쪼개고, 후속 처리는 이벤트로 떼어낸다.**

### 10. 면접 답변 시나리오 (요약 흐름)
> 네 용어를 나란히 비교하지 말고 **"하나가 다음을 낳는 순서"**로 말한다. 이 순서 자체가 이해도를 보여준다.

1. **층위부터 정리한다** — "도메인은 문제 영역, 도메인 규칙은 그 영역에서 항상 참이어야 하는 것, 애그리거트는 그 규칙을 지킬 책임 단위, 유스케이스는 그것을 사용하는 시나리오입니다. 병렬 개념이 아니라 순서가 있습니다."
2. **도메인은 발견하는 것임을 강조** — "도메인은 코드가 아니라 업무 영역입니다. 그래서 신입에게 가장 먼저 가르치는 용어 목록이 곧 도메인이고, 그 용어를 코드에서도 그대로 쓰는 게 유비쿼터스 언어입니다."
3. **규칙 판정 기준을 제시** — "'이걸 어기면 화내는 사람이 개발자인가 현업인가', '종이와 펜으로 운영해도 필요한 규칙인가'로 구분합니다. 비밀번호 8자 제한은 도메인 규칙이 아니고, 이체 한도는 도메인 규칙입니다."
4. **애그리거트는 불변식이 정한다고 말한다** — "테이블이나 FK가 아니라 '동시에 깨지면 안 되는 규칙'이 경계를 정합니다. 영화관 예매에서 좌석 중복 방지가 불변식이면 상영회차가 애그리거트가 되고, 상영관 전체로 잡으면 동시성이 죽습니다."
5. **유스케이스는 판단하지 않고 조율한다** — "'무엇이 허용되는가'는 도메인, '어떤 순서로 진행되는가'는 유스케이스입니다. 유스케이스에 `if`가 늘면 규칙이 새고 있다는 신호로 봅니다."
6. **한 사건으로 관통해 보인다** — 주문 취소 예시로 네 용어를 한 번에 배치한다.
7. **적용 범위를 스스로 제한한다** — "전 영역에 적용하지 않습니다. 코어 서브도메인에만 엄격하게 적용하고, 알림·인증 같은 일반 서브도메인은 CRUD로 둡니다."

## 핵심 정리
- 핵심 포인트 1: **네 용어는 병렬 개념이 아니라 순서다.** 도메인(문제 영역) → 도메인 규칙(그 영역의 제약) → 애그리거트(규칙을 지킬 책임 단위) → 유스케이스(그것을 쓰는 시나리오). 이 방향이 뒤집혀 테이블·화면에서 출발하면 규칙이 서비스로 흩어진 절차지향 코드가 된다.
- 핵심 포인트 2: **도메인 규칙은 만드는 것이 아니라 발견하는 것이다.** "어겼을 때 화내는 사람이 현업인가", "종이와 펜으로 운영해도 필요한가"로 판정한다. 이 기준으로 도메인 규칙 / 애플리케이션 정책 / 인프라 제약 / 기술 결정이 갈린다.
- 핵심 포인트 3: **애그리거트 경계는 테이블이나 FK가 아니라 불변식이 정한다.** 크게 잡으면 불변식은 쉽게 지켜지지만 동시성이 죽고, 작게 잡으면 반대가 된다. 그래서 경계 설계의 실질은 "이 불변식이 정말 즉시 일관성이어야 하는가"를 묻는 일이다.
- 핵심 포인트 4: **"무엇이 허용되는가"는 도메인, "어떤 순서로 진행되는가"는 유스케이스다.** 유스케이스에 비즈니스 조건문이 늘어나면 규칙이 도메인 밖으로 새고 있다는 신호이고, 그 규칙은 취소 경로가 늘어날 때마다 복사되어 갈라진다.
- 핵심 포인트 5: **한 문장 비유 — 도메인은 은행업, 도메인 규칙은 "잔액보다 많이 못 뺀다", 애그리거트는 통장 한 권, 유스케이스는 창구 뒤 업무 안내판이다.** 규칙은 창구 직원이 만들지 않고, 통장은 반쪽만 꺼낼 수 없으며, 안내판에는 "고객정보 업데이트"가 아니라 목적이 적혀 있다.

## 기술적 한계와 보완 전략

**한계 1: 조회 요구가 애그리거트 설계를 망가뜨린다**
목록 화면 하나 때문에 애그리거트를 크게 잡거나, 리포지토리에 조인 쿼리를 밀어넣게 된다.
→ 보완: 쓰기 모델(애그리거트)과 읽기 모델(projection DTO)을 분리한다. 조회는 애그리거트를 복원하지 않고 필요한 컬럼만 뽑는 전용 쿼리로 처리한다(CQRS의 읽기 분리).

**한계 2: 애그리거트 경계는 처음부터 맞히기 어렵다**
도메인 이해가 얕은 초기에 그은 경계는 대개 틀린다.
→ 보완: 처음에는 **작게** 잡는다. 나중에 합치는 것이 쪼개는 것보다 훨씬 싸다. 그리고 경계를 바꿀 여지를 남기기 위해 애그리거트 간 참조를 반드시 ID로 유지한다.

**한계 3: 도메인 규칙과 정책의 경계가 시간에 따라 이동한다**
처음엔 불변식이던 것이 나중에 "가게마다 다른 정책"이 된다(예: 최소 주문금액).
→ 보완: 값을 코드에 박지 말고 규칙의 **형태**만 도메인에 남기고 값은 외부에서 주입한다. 변경 빈도가 높은 정책은 정책 객체(Policy)로 분리해 교체 가능하게 만든다.

**한계 4: 결과적 일관성의 실패 처리가 실제로 어렵다**
이벤트 기반으로 넘긴 후속 처리가 실패하면 데이터가 어긋난 채 남는다.
→ 보완: 발행 신뢰성은 Outbox로, 처리 실패는 재시도 + DLQ로, 어긋남은 정합성 배치로 검출한다. **"이벤트로 넘겼다"가 "책임을 넘겼다"가 되지 않게 보정 수단을 함께 설계한다.**

**한계 5: 팀이 용어를 다르게 쓰면 구조가 갈라진다**
누구는 서비스에 규칙을 넣고 누구는 엔티티에 넣으면, DDD 용어를 쓰는 절차지향 코드가 된다.
→ 보완: 판단 규칙을 문서가 아니라 **레퍼런스 슬라이스(모범 유스케이스 1개)**로 고정하고, "엔티티에 setter 금지", "유스케이스는 도메인 예외를 던지지 않는다" 같은 검증 가능한 규칙만 ArchUnit/린트로 강제한다.

## 키워드
- **도메인(Domain)**: 소프트웨어가 다루는 현실의 업무 영역. 코드가 아니라 문제 영역 자체이며, 그 영역의 용어 목록이 곧 도메인의 윤곽이다
- **서브도메인(Core / Supporting / Generic)**: 도메인을 경쟁력 기여도에 따라 나눈 구분. 코어에만 엄격한 도메인 모델링을 적용하고 일반 서브도메인은 CRUD로 두는 것이 정상적인 판단이다
- **유비쿼터스 언어(Ubiquitous Language)**: 도메인 전문가와 개발자가 회의·문서·코드에서 동일한 단어를 쓰는 상태. 번역이 발생하는 지점에서 규칙이 소실된다
- **도메인 모델(Domain Model)**: 도메인을 목적에 맞게 추려 규칙을 담아 표현한 객체 모델. 도메인 그 자체도, JPA 엔티티도 아니다
- **빈혈 도메인 모델(Anemic Domain Model)**: 필드와 getter/setter만 있고 규칙이 없는 모델. 규칙이 서비스로 흩어져 같은 규칙이 여러 곳에 복사되는 원인
- **도메인 규칙(Domain Rule)**: 도메인에서 항상 참이어야 하는 제약. 시스템이 없어도 존재하며, 개발자가 만드는 것이 아니라 업무에서 발견하는 것
- **불변식(Invariant)**: 객체가 어느 순간에나 만족해야 하는 상태 조건. 애그리거트 경계를 결정하는 실질적 기준
- **정책(Policy)**: 비즈니스 판단에 따라 자주 바뀌는 규칙. 값은 외부로 빼고 규칙의 형태만 도메인에 남긴다
- **애그리거트(Aggregate)**: 함께 변경되고 함께 검사되어야 하는 객체 묶음. 로드·검증·저장·동시성 제어의 단위
- **애그리거트 루트(Aggregate Root)**: 애그리거트의 유일한 외부 진입점이자 불변식의 최종 책임자. 내부 컬렉션을 수정 가능한 형태로 노출하면 이 책임이 무너진다
- **ID 참조(Reference by Identity)**: 다른 애그리거트를 객체가 아닌 식별자로 참조하는 규칙. 경계를 코드로 강제하고 로딩·트랜잭션 범위를 제한한다
- **결과적 일관성(Eventual Consistency)**: 애그리거트 경계 밖의 일관성을 즉시가 아니라 도메인 이벤트로 맞추는 방식. 발행 신뢰성은 Outbox 같은 별도 수단이 필요하다
- **유스케이스(Use Case)**: 액터가 시스템으로 하나의 목표를 달성하는 시나리오. 규칙을 판단하지 않고 애그리거트 로드·위임·저장·트랜잭션·통보를 조율한다
- **도메인 서비스(Domain Service)**: 여러 애그리거트가 필요하거나 어느 한쪽에 두면 어색한 규칙을 담는 무상태 객체. 남발하면 빈혈 모델로 가는 지름길
