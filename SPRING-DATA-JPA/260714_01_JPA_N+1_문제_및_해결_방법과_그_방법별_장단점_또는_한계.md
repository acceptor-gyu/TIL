# JPA N+1 문제 및 해결 방법과 그 방법별 장단점 또는 한계

## 개요
JPA를 사용할 때 가장 빈번하게 마주치는 성능 이슈인 N+1 문제의 정의와, 이를 해결하는 대표적인 전략들, 그리고 각 전략이 가진 장단점과 한계를 정리한다.

## 상세 내용

### 1. N+1 문제란

부모 엔티티를 조회하는 쿼리 1번과, 그 결과로 얻은 N개의 부모 각각에 대해 연관 엔티티를 조회하는 쿼리 N번이 추가로 발생해 총 **N+1번**의 쿼리가 실행되는 현상이다.

```java
@Entity
public class Team {
    @Id @GeneratedValue
    private Long id;
    private String name;

    @OneToMany(mappedBy = "team", fetch = FetchType.LAZY)
    private List<Member> members = new ArrayList<>();
}

@Entity
public class Member {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "team_id")
    private Team team;
}
```

```java
List<Team> teams = teamRepository.findAll();   // 1번: SELECT * FROM team

for (Team team : teams) {
    team.getMembers().size();                  // N번: 팀마다 SELECT * FROM member WHERE team_id = ?
}
```

팀이 100개면 총 101번의 쿼리가 실행된다. 이는 단순히 쿼리 수가 많다는 문제를 넘어, 매 쿼리마다 발생하는 **네트워크 왕복(round trip) 비용**과 **DB 커넥션 점유 시간 증가**로 이어져 트래픽이 몰릴수록 커넥션 풀 고갈, 응답 지연이 심화되는 근본 원인이 된다.

### 2. N+1이 발생하는 근본 원인

- **프록시와 지연 로딩(LAZY)**: `FetchType.LAZY`로 매핑된 연관 필드는 실제 접근 시점(`getMembers().size()` 등)에 프록시가 초기화되며 별도 쿼리를 실행한다. 컬렉션 하나하나가 개별적으로 초기화되므로 N번의 쿼리가 발생한다.
- **즉시 로딩(EAGER)에서도 발생**: `FetchType.EAGER`로 바꾸면 문제가 해결될 것 같지만 그렇지 않다. `findAll()`처럼 JPQL 기반 조회는 Hibernate가 **JPQL을 SQL로 먼저 번역**한 뒤, 반환된 각 엔티티의 EAGER 연관관계를 별도의 SELECT로 즉시 로딩하기 때문에 로딩 시점만 앞당겨질 뿐 쿼리 수는 동일하다. 즉, EAGER는 글로벌 페치 전략을 지정하는 매핑 정보일 뿐, JPQL 실행 시점의 조인 전략을 강제하지 않는다.
- **1차 캐시가 막아주지 못하는 경우**: 영속성 컨텍스트의 1차 캐시는 **동일한 식별자(PK)**로 이미 조회한 엔티티만 재사용한다. `team.getMembers()`처럼 컬렉션 연관관계를 최초로 초기화하는 시점은 캐시에 없는 새로운 쿼리이므로 캐시가 N+1을 막지 못한다.
- **연관관계 타입별 발생 양상**
  - `@ManyToOne` / `@OneToOne`: 프록시 객체 1건 초기화 → 상대적으로 가볍지만 리스트가 길면 여전히 N번 발생
  - `@OneToMany`: 컬렉션 전체를 초기화하는 쿼리가 N번 발생, 데이터 양이 많아 영향이 크다
  - `@ManyToMany`: 중간 조인 테이블까지 거치므로 쿼리 복잡도와 카티션 곱 위험이 가장 크다 (실무에서는 `@ManyToMany`를 지양하고 중간 엔티티로 풀어내는 것이 권장된다)

### 3. 해결 방법별 상세와 장단점

#### 3-1. Fetch Join (JPQL / QueryDSL)

`JOIN FETCH`로 연관 엔티티를 한 번의 쿼리로 함께 조회한다.

```java
@Query("SELECT t FROM Team t JOIN FETCH t.members")
List<Team> findAllWithMembers();
```

```sql
SELECT t.*, m.*
FROM team t
INNER JOIN member m ON t.id = m.team_id;
```

**장점**
- 쿼리 1번으로 해결되어 가장 직관적이고 빠르다.

**한계**
- 컬렉션 페치 조인 + 페이징 동시 사용 불가: `firstResult`/`maxResults`를 지정하면 Hibernate가 SQL 레벨에서 페이징을 적용하지 못하고 **전체 결과를 메모리로 로딩한 뒤 애플리케이션에서 페이징**한다 (`HHH000104`, Hibernate 6에서는 `HHH90003004` 경고). 데이터가 많으면 OOM 위험이 있다.
- 컬렉션 페치 조인은 동시에 2개 이상 불가: `List`(Bag) 타입 컬렉션 2개를 동시에 페치하면 `MultipleBagFetchException`이 발생한다. `Set`으로 바꾸면 예외는 피할 수 있지만 카티션 곱 문제는 남는다.
- 카티션 곱(Cartesian Product): 조인으로 인해 부모 로우가 중복 반환된다. Hibernate 5는 SQL/애플리케이션 레벨의 `DISTINCT`로 직접 제거해야 했지만, **Hibernate 6부터는 JPQL에 `DISTINCT`가 없어도 애플리케이션(Java) 레벨에서 부모 엔티티 중복을 자동 제거**한다 (단, SQL 레벨 중복 로우 자체가 사라지는 것은 아니므로 네트워크 전송량 문제는 여전하다).
- 글로벌 페치 전략이 아니므로 조회 화면/쿼리마다 매번 명시해야 하는 번거로움이 있다.

#### 3-2. @EntityGraph

리포지토리 메서드 단위로 선언적으로 페치 조인을 적용한다.

```java
@EntityGraph(attributePaths = {"members"})
@Query("SELECT t FROM Team t")
List<Team> findAllWithMembers();
```

내부적으로 `jakarta.persistence.loadgraph`(기본) 또는 `jakarta.persistence.fetchgraph` 힌트를 통해 Hibernate가 **LEFT OUTER JOIN** SQL로 변환한다.

| 타입 | 힌트 | 지정된 속성 | 지정되지 않은 속성 |
|---|---|---|---|
| `LOAD` (기본) | `loadgraph` | EAGER | 매핑된 FetchType 그대로 유지 |
| `FETCH` | `fetchgraph` | EAGER | 모두 LAZY로 강제 (매핑 무시) |

**장점**
- Spring Data JPA 메서드 이름 쿼리와 조합 가능하며, 어노테이션 추가만으로 페치 전략을 적용할 수 있다.
- `@NamedEntityGraph`로 정의하면 여러 리포지토리 메서드에서 재사용 가능하다.

**한계**
- 내부적으로 항상 **LEFT OUTER JOIN**으로 고정되어 INNER JOIN을 강제할 수 없다.
- 페치 조인과 동일한 페이징 메모리 로딩 한계, `MultipleBagFetchException` 한계를 그대로 승계한다.
- `@NamedEntityGraph`를 엔티티에 직접 선언하면 조회 전략 관련 메타 정보가 도메인 엔티티에 섞여 응집도가 떨어질 수 있다.

#### 3-3. Batch Size (`@BatchSize` / `hibernate.default_batch_fetch_size`)

지연 로딩 시점에 개별 조회 대신 **IN 절**로 묶어서 조회해 N번을 1+(N/batch_size)번으로 줄인다.

```java
@BatchSize(size = 100)
@OneToMany(mappedBy = "team", fetch = FetchType.LAZY)
private List<Member> members = new ArrayList<>();
```

```yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
```

```sql
SELECT * FROM team;
SELECT * FROM member WHERE team_id IN (1,2,...,100);
```

**장점**
- 페이징과 함께 사용 가능 (컬렉션 페치 조인의 실질적 대안)
- 카티션 곱이 없어 조인 방식보다 데이터 전송량이 적다.
- 글로벌 설정(`default_batch_fetch_size`) 하나로 애플리케이션 전체에 일괄 적용 가능

**한계**
- 쿼리 수가 완전히 1개가 되지는 않는다 (1 + N/batch_size).
- IN 절 파라미터 개수가 매번 달라지면 DB 실행 계획 캐시 미스가 늘어날 수 있다. `hibernate.query.in_clause_parameter_padding=true`로 파라미터 개수를 2의 거듭제곱 단위로 패딩하면 캐시 히트율을 개선할 수 있다.
- 적정 batch size 튜닝이 필요하다 (일반적으로 100~1000 사이에서 데이터 크기와 DB IN 절 파라미터 제한을 고려해 결정).

#### 3-4. DTO 직접 조회 (Projection, QueryDSL, JPQL `new` 연산자)

```java
public interface TeamSummary {
    String getName();
    int getMemberCount();
}

@Query("SELECT t.name AS name, SIZE(t.members) AS memberCount FROM Team t")
List<TeamSummary> findTeamSummaries();
```

**장점**
- 필요한 컬럼만 SELECT하므로 엔티티 로딩 오버헤드가 없고, 영속성 컨텍스트 관리 부담이 줄어든다.

**한계**
- 엔티티가 아니므로 변경 감지(Dirty Checking)를 통한 업데이트가 불가능하다 (조회 전용).
- API 스펙이 바뀔 때마다 DTO와 쿼리를 함께 수정해야 해서 재사용성이 낮다.
- 컬렉션을 포함한 DTO(예: 팀-멤버 목록)는 결국 컬렉션 데이터를 별도 쿼리로 조회한 뒤 애플리케이션 메모리에서 `Map` 기반으로 조립해야 한다.

#### 3-5. 컬렉션 조회 최적화 패턴 (루트 1번 + 컬렉션 IN 절 1번)

루트 엔티티를 먼저 조회하고, 얻은 ID 목록으로 자식 컬렉션을 IN 절로 한 번에 조회한 뒤 `Map<ID, List<ChildDto>>`로 메모리에서 조립하는 방식이다.

```java
List<Team> teams = teamRepository.findAll();
List<Long> teamIds = teams.stream().map(Team::getId).toList();

List<Member> members = memberRepository.findByTeamIdIn(teamIds);
Map<Long, List<Member>> membersByTeamId = members.stream()
    .collect(Collectors.groupingBy(m -> m.getTeam().getId()));
```

**장점**: 쿼리 수가 2번으로 고정되고, 페이징도 문제없이 가능하다.
**한계**: 코드 복잡도가 올라가고, 연관관계 계층이 깊어질수록(팀-멤버-장비 등) 조립해야 할 쿼리 수가 늘어난다.

#### 3-6. 2차 캐시 / 쿼리 캐시

Hibernate Second Level Cache(예: Ehcache, Redis 연동)로 동일 연관 데이터의 반복 조회 자체를 회피하는 방식이다.
**한계**: 캐시와 DB 간 정합성 관리 비용이 크고, 분산 서버 환경에서는 캐시 무효화(invalidation) 전파가 까다롭다.

#### 3-7. 기본 전략 정리

모든 연관관계는 `fetch = FetchType.LAZY`로 매핑하는 것을 원칙으로 하고, 실제로 필요한 화면/API에서만 Fetch Join, `@EntityGraph`, Batch Size 등을 선택적으로 적용한다. `FetchType.EAGER`를 기본값으로 사용하는 것은 N+1을 해결하는 것이 아니라 문제를 숨기고 통제 불가능하게 만드는 안티패턴이다.

### 4. 상황별 선택 가이드

| 상황 | 권장 전략 |
|---|---|
| 단건 조회 + 연관 엔티티 필요 | Fetch Join / `@EntityGraph` |
| 페이징 + 컬렉션 연관관계 | `default_batch_fetch_size` 또는 DTO 조립 패턴 |
| 조회 전용 API + 성능 극한 최적화 | DTO 직접 조회 / 네이티브 쿼리 |
| ToOne(`@ManyToOne`, `@OneToOne`) 관계 | Fetch Join으로 한 번에 |
| ToMany(`@OneToMany`, `@ManyToMany`) 관계 | Batch Size 조합 |

실무에서는 **ToOne은 Fetch Join, ToMany는 Batch Size**를 함께 조합하는 것이 가장 널리 쓰이는 기본 공식이다.

### 5. 탐지와 검증

- `spring.jpa.properties.hibernate.show_sql=true` 또는 `p6spy`, `datasource-proxy` 같은 라이브러리로 실제 실행되는 쿼리 로그를 확인한다.
- 테스트 코드에서 `Statistics`를 활성화(`hibernate.generate_statistics=true`)하고 `session.getSessionFactory().getStatistics().getQueryExecutionCount()`로 특정 로직 실행 전후 쿼리 실행 횟수를 단언(assert)해 회귀를 방지한다.
- `spring.jpa.open-in-view` 설정과의 관계: 기본값 `true`(OSIV 켜짐)에서는 뷰 렌더링 시점까지 영속성 컨텍스트가 열려 있어 N+1이 컨트롤러/뷰 계층에서 조용히 발생할 수 있다. `open-in-view=false`로 끄면 트랜잭션 종료 시 영속성 컨텍스트도 닫히므로, 트랜잭션 밖에서 지연 로딩을 시도할 때 `LazyInitializationException`이 즉시 발생해 N+1 문제를 개발 초기 단계에서 조기에 발견하게 해준다.

## 핵심 정리
- N+1은 지연 로딩 프록시가 각 엔티티마다 개별적으로 초기화되며 발생하는 문제이며, `FetchType.EAGER`로 바꾸는 것은 해결책이 아니라 문제를 숨기는 것이다.
- Fetch Join은 쿼리 1번이라는 강력한 장점이 있으나, 컬렉션 페이징과 다중 컬렉션 동시 페치에서 명확한 한계(`MultipleBagFetchException`, 메모리 페이징)를 가진다.
- `@EntityGraph`는 Fetch Join을 선언적으로 사용할 수 있게 해주지만 내부 동작(LEFT OUTER JOIN)과 한계는 Fetch Join과 사실상 동일하다.
- `hibernate.default_batch_fetch_size`는 페이징과 공존 가능한 가장 실용적인 범용 해법으로, 실무 기본값으로 많이 채택된다.
- 조회 전용 화면은 엔티티를 거치지 않고 DTO로 직접 조회하는 것이 가장 빠르고 메모리 효율적이다.
- 은탄환은 없으며, ToOne은 Fetch Join, ToMany는 Batch Size라는 조합이 실무의 기본 공식이다.

## 기술적 한계와 보완 전략
- 컬렉션 페치 조인 + 페이징: Hibernate가 전체 결과를 메모리에 로딩 → OOM 위험. `@BatchSize` 또는 `default_batch_fetch_size`로 대체.
- `MultipleBagFetchException`: `List`(Bag) 타입 컬렉션 두 개 이상 동시 페치 불가 → `Set`으로 변경하거나, 하나만 Fetch Join하고 나머지는 Batch Size로 분리.
- 카티션 곱으로 인한 데이터 증폭: `DISTINCT` 사용(Hibernate 6부터는 엔티티 쿼리에서 부모 엔티티 중복을 애플리케이션 레벨에서 자동 제거) 또는 Batch Size로 쿼리를 분리해 근본적으로 회피.
- DTO 직접 조회의 재사용성 저하: 조회 전용 리포지토리를 커맨드용 리포지토리와 분리(CQRS 지향)해 책임을 나눈다.
- Batch Size의 IN 절 파라미터 가변성: `hibernate.query.in_clause_parameter_padding=true`로 파라미터 개수를 2의 거듭제곱으로 패딩해 DB 실행 계획 캐시 히트율을 개선한다.
- 근본적으로 해결이 어려운 복잡한 집계/통계 쿼리: 네이티브 쿼리, 읽기 전용 레플리카, 조회 전용 비정규화 테이블(또는 Elasticsearch)로 별도 최적화한다.

## 키워드
- **N+1 Problem**: 부모 엔티티 조회 1회 + 연관된 자식 엔티티를 개별 조회하는 N회가 추가로 발생해 총 N+1번의 쿼리가 실행되는 ORM 성능 이슈.
- **Fetch Join**: JPQL의 `JOIN FETCH` 구문으로 연관 엔티티를 조인해 한 번의 쿼리로 즉시 로딩하는 명시적 페치 전략.
- **@EntityGraph**: JPA 2.1에서 도입된 애노테이션으로, 리포지토리 메서드 단위 또는 `@NamedEntityGraph`를 통해 선언적으로 페치할 연관 엔티티를 지정하는 기능.
- **@BatchSize / hibernate.default_batch_fetch_size**: 지연 로딩 시 IN 절로 여러 건을 묶어 조회함으로써 쿼리 수를 1+(N/batch_size)로 줄이는 Hibernate 최적화 기능.
- **Lazy Loading & Proxy**: 연관 엔티티를 실제 접근하는 시점까지 로딩을 지연하고, 그 자리에 프록시 객체를 넣어두는 JPA의 기본 전략.
- **MultipleBagFetchException**: 두 개 이상의 `List`(Bag) 타입 컬렉션에 Fetch Join을 동시에 적용할 때 발생하는 Hibernate 예외.
- **Cartesian Product**: 조인 연산으로 인해 부모 로우가 자식 로우 수만큼 중복되어 반환되는 현상. `DISTINCT`나 컬렉션 조회 분리로 완화한다.
- **DTO Projection**: 엔티티 전체가 아니라 필요한 컬럼만 선택해 DTO로 직접 조회하는 방식으로, N+1 자체를 원천 차단한다.
- **OSIV (Open Session In View)**: 영속성 컨텍스트(및 DB 커넥션)를 뷰 렌더링이 끝날 때까지 열어두는 설정(`spring.jpa.open-in-view`). 끄면 지연 로딩 미스가 `LazyInitializationException`으로 즉시 드러난다.
- **Second Level Cache**: 여러 트랜잭션(영속성 컨텍스트)에 걸쳐 공유되는 Hibernate의 2차 캐시로, 반복 조회를 줄여 N+1의 영향을 완화할 수 있다.
