# Redis의 근사 LRU 알고리즘이란

## 개요
Redis는 메모리 한계(`maxmemory`)에 도달하면 설정된 정책에 따라 키를 제거(eviction)한다. 이때 LRU(Least Recently Used) 정책을 선택하더라도 Redis는 교과서적인 "정확한 LRU"를 구현하지 않고, 무작위 샘플링과 후보 풀(eviction pool)을 이용한 **근사(Approximated) LRU** 알고리즘을 사용한다. 이는 메모리 효율성과 성능을 위한 트레이드오프이며, 실제 접근 패턴(파레토 법칙)에서는 정확한 LRU와 거의 동일한 효과를 낸다.

## 상세 내용

### 1. 배경: Redis의 메모리 관리와 maxmemory
- `maxmemory` 설정으로 캐시가 사용할 최대 메모리를 지정한다. 기본값 0은 무제한을 의미하며(64비트 기준), 이 값을 초과하면 Redis는 지정한 eviction 정책에 따라 메모리 사용량이 다시 한계 아래로 내려갈 때까지 키를 제거한다.
- 새로운 데이터를 추가하는 명령이 들어올 때마다 Redis는 메모리 사용량을 점검하며, 한 번에 큰 데이터가 추가되는 경우(`SINTERSTORE` 등) 일시적으로 `maxmemory`를 초과할 수 있다.
- replication/AOF를 사용하는 경우 복제 버퍼에 사용되는 메모리는 `maxmemory` 비교 대상에서 제외되므로, 실제 운영 시에는 `maxmemory`를 조금 여유 있게 잡는 것이 권장된다(`INFO memory`의 `mem_not_counted_for_evict` 값 참고).
- eviction이 필요한 이유: 캐시에 저장된 데이터는 원본(DB 등)의 사본이므로, 메모리가 부족할 때 오래되거나 덜 쓰이는 데이터를 지워도 안전하게 다시 캐싱할 수 있기 때문이다.

### 2. maxmemory-policy 종류
`maxmemory-policy` 디렉티브로 정책을 선택한다.

| 정책 | 설명 |
|---|---|
| `noeviction` | 키를 제거하지 않고, 쓰기 명령에 에러를 반환(읽기는 정상 동작) |
| `allkeys-lru` | 전체 키 중 LRU 기준으로 제거 |
| `volatile-lru` | TTL이 설정된 키 중 LRU 기준으로 제거 |
| `allkeys-lfu` | 전체 키 중 LFU(사용 빈도) 기준으로 제거 |
| `volatile-lfu` | TTL이 설정된 키 중 LFU 기준으로 제거 |
| `allkeys-random` | 전체 키 중 무작위로 제거 |
| `volatile-random` | TTL이 설정된 키 중 무작위로 제거 |
| `volatile-ttl` | TTL이 짧게 남은 키부터 제거 |
| `allkeys-lrm` / `volatile-lrm` | (Redis 8.6+) 읽기가 아닌 "쓰기" 시각 기준으로 가장 오래 수정되지 않은 키를 제거 (Least Recently Modified) |

- `volatile-*` 계열 정책은 TTL이 설정된 키가 하나도 없으면 `noeviction`처럼 동작한다.
- 접근 패턴에 따라 선택 기준이 다르다. 일부 키에 접근이 집중되는 파레토 법칙을 따르는 서비스라면 `allkeys-lru`가 기본적으로 좋은 선택이고, 접근 빈도가 균등하다면 `allkeys-random`, 캐시와 영구 데이터를 한 인스턴스에서 함께 쓴다면 `volatile-*` 계열을 고려할 수 있다(다만 가능하면 캐시용/영구 저장용 인스턴스를 분리하는 것을 권장).
- `expire`가 설정된 키는 메모리를 추가로 사용하므로, `allkeys-lru`가 `volatile-lru`보다 메모리 효율이 좋다.

### 3. 정확한 LRU의 비용
- 전통적인 LRU는 이중 연결 리스트(모든 항목을 접근 순서로 유지) + 해시맵(O(1) 조회)으로 구현한다. 키에 접근할 때마다 리스트에서 해당 노드를 맨 앞(혹은 맨 뒤)으로 옮기는 연산이 필요하다.
- Redis의 모든 키에 대해 이런 구조를 유지하려면 키마다 별도의 포인터(prev/next)를 저장해야 하고, 모든 GET/SET 연산마다 리스트 재정렬 비용이 발생한다. 데이터셋이 커질수록 이 오버헤드가 누적되어 메모리 사용량과 CPU 비용이 크게 늘어난다.
- Redis는 이 비용을 줄이기 위해 정확한 순서 추적 대신 근사치를 사용하는 방식을 택했다.

#### 정확한 LRU를 구현하면 드는 비용 (근사 LRU가 회피하는 것)
근사 LRU의 "메모리/CPU 절약"은, **정확한 LRU를 구현했다면 치렀어야 할 비용을 아예 발생시키지 않는다**는 뜻이다. 두 축으로 나뉜다.

- **메모리 — 순서 유지용 자료구조를 만들지 않아서**: 정확한 LRU는 모든 키를 접근 순서대로 정렬된 이중 연결 리스트로 묶어야 하므로 키마다 `prev`/`next` 포인터(64비트 기준 각 8바이트, 합 16바이트)가 추가로 든다. 키가 1억 개면 순서 유지용 포인터에만 약 1.6GB가 순수 오버헤드로 나간다. 근사 LRU는 이 리스트를 아예 만들지 않고, 오브젝트가 원래 가진 24비트 `lru` 필드(3바이트)에 "마지막 접근 시각"만 기록하므로 그만큼을 절약한다.
- **CPU — 매 접근마다 재정렬을 하지 않아서**: 정확한 LRU는 `GET`/`SET`이 일어날 때마다 해당 노드를 리스트 맨 앞으로 옮기는 재정렬(포인터 조작)을 해야 한다. 초당 수십만 건이 들어오는 Redis에서는 이 비용이 모든 명령에 상시 부과된다. 근사 LRU가 접근 시 하는 일은 `lru` 필드에 현재 클럭값을 덮어쓰는 단순 대입뿐이며, 재정렬이 없다. 대신 후보 선정 비용을 "모든 접근"이 아니라 "실제로 제거가 필요한 순간"으로 몰아넣고, 그마저도 전체 순회가 아닌 소수 샘플만 검사한다.

| 구분 | 정확한 LRU | 근사 LRU |
|---|---|---|
| 순서 유지 자료구조 | 이중 연결 리스트 (키당 +16B) | 없음 (기존 24bit 필드 재활용) |
| 접근(GET/SET) 시 비용 | 매번 리스트 재정렬 | 필드에 값 대입만 |
| 제거(eviction) 시 비용 | 상시 정렬 유지 비용이 이미 지불됨 | 필요할 때 소수 샘플만 검사 |

정리하면, "모든 키의 정확한 순서를 항상 알고 있어야 한다"는 제약을 포기함으로써 그 순서를 유지하는 데 드는 메모리(자료구조)와 CPU(상시 재정렬)를 통째로 없앤 것이다. 그 대가로 "진짜 가장 오래된 키"가 아닌 키가 뽑힐 수 있지만, 파레토 분포 워크로드에서는 그 손실이 미미하다(→ 5번 참고).

### 4. Redis의 근사 LRU 동작 원리
- Redis 오브젝트(`robj`)는 24비트짜리 `lru` 필드를 가지고 있으며, 여기에 마지막으로 접근된 시각(정확히는 전역 클럭 `server.lruclock`의 하위 24비트)을 기록한다. 24비트로도 약 194일까지 표현 가능하며, 오버플로우 처리를 통해 클럭 랩어라운드를 다룬다.
- 정확한 LRU처럼 전체 키의 순서를 유지하는 대신, eviction이 필요할 때마다 무작위로 소수의 키를 샘플링하고, 그중 idle time(마지막 접근 이후 경과 시간)이 가장 긴 키를 제거 후보로 선택한다.
- `maxmemory-samples` 설정으로 매 eviction 시 검사할 샘플 개수를 조정할 수 있다(기본값 5). 값을 높일수록(예: 10) 정확한 LRU에 더 가까워지지만 CPU 비용이 늘어난다. `CONFIG SET maxmemory-samples <count>`로 런타임에도 조정 가능하다.
- Redis 3.0부터는 매번 새로 샘플링하는 대신 "eviction pool"이라는 후보 풀(크기 16의 정렬된 리스트)을 활용한다. 새로 샘플링된 키들을 기존 풀과 비교해 idle time이 더 긴 키로 풀을 갱신하며, 제거 시에는 풀에서 가장 idle time이 긴 키를 뽑는다. 이 개선으로 근사 LRU가 진짜 LRU에 훨씬 가깝게 동작하게 되었다(Redis 2.8 대비 Redis 3.0의 정확도가 크게 향상됨).

#### 오해 주의: eviction pool로 "상시 관리"하는 것이 아니다
근사 LRU를 "pool로 순위를 관리하는 방식"으로 오해하기 쉽지만, 실제 구조는 다르다. **recency의 원천(source of truth)은 pool이 아니라 각 오브젝트의 24비트 `lru` 필드**이며, 평상시에는 어떤 순위 자료구조도 관리하지 않는다.

- **키에 접근할 때**: 그 키의 `lru` 필드에 현재 시각을 덮어쓰는 것이 전부다. 이 시점에 pool도, 리스트도 건드리지 않는다. 즉 "어떤 키가 가장 오래됐는가"는 어디에도 미리 계산되어 있지 않고, 필요할 때 그때그때 추정한다.
- **제거가 필요할 때만**: (1) 무작위로 `maxmemory-samples`개를 뽑아 → (2) 각 키의 `lru` 필드로 idle time을 계산하고 → (3) 그 결과를 pool과 비교해 갱신한 뒤 → (4) pool에서 가장 idle한 키를 제거한다.

여기서 pool의 역할은 "매번 뽑은 샘플을 그냥 버리지 않고, 지금까지 본 것 중 가장 오래된 후보들을 누적해서 기억"하는 임시 작업 버퍼다. 그래서 사이클이 반복될수록 진짜 오래된 키를 뽑을 확률이 올라간다. pool이 없어도 근사 LRU는 동작하며(Redis 2.8까지는 pool 없이 매번 샘플링만 했다), pool은 3.0에서 정확도를 끌어올리기 위해 추가된 보조 장치일 뿐이다.

| 구성요소 | 역할 | 관리 시점 |
|---|---|---|
| 오브젝트의 24bit `lru` 필드 | recency의 원천 데이터 | 키에 접근할 때마다 갱신 |
| 랜덤 샘플링 | 전체 순회 없이 후보 추출 | 제거가 필요할 때만 |
| eviction pool (16칸) | 샘플 결과를 누적해 후보 정확도 향상 | 제거가 필요할 때만 |

#### 소수 샘플은 어떤 기준으로 뽑는가
"무작위로 몇 개를 뽑는다"는 실제로 세 단계를 거친다. "어디서 → 어떻게 → 무엇을 고르는가"로 나눠 보면 명확하다.

- **① 어디서 뽑는가 — 정책이 대상 딕셔너리를 결정한다**: 샘플은 "전체 키"가 아니라 정책에 따라 다른 딕셔너리에서 뽑는다. `allkeys-*`는 메인 키스페이스 딕셔너리(`db->dict`)에서, `volatile-*`는 TTL이 설정된 키만 모인 별도 딕셔너리(`db->expires`)에서 샘플링한다. 그래서 `volatile-lru`는 만료 대상 키들 사이에서만 후보를 고르며, TTL 없는 키는 샘플 후보에 들어오지도 않는다.
- **② 어떻게 뽑는가 — 완전한 균등 무작위는 아니다**: `dictGetSomeKeys()`는 해시 테이블에서 무작위 시작 버킷을 하나 잡고, 거기서부터 연속된 버킷을 훑으며 필요한 개수만큼 엔트리를 주워 담는다. 키가 버킷에 고르게 흩어져 있으므로 결과는 "대체로 무작위"에 가깝지만, 같은 버킷 체인의 엔트리가 함께 뽑히는 등 엄밀한 균등 분포는 아니다. 이렇게 설계한 이유는 속도다 — 전체를 순회하지 않고 값싸게 소수 후보를 확보하는 것이 목적이다.
- **③ 무엇을 고르는가 — idle time(LRU)·빈도(LFU) 기준**: 뽑힌 샘플마다 LRU 모드에서는 `idle time = 현재 클럭 − lru 필드`가 가장 긴(가장 오래 안 쓰인) 키를, LFU 모드에서는 빈도 카운터가 가장 낮은 키를 선호한다. 이 후보들을 eviction pool에 누적한 뒤 최종적으로 가장 idle한(혹은 가장 덜 쓰인) 키를 제거한다.

| 단계 | 기준 / 전략 |
|---|---|
| 대상 선정 | `allkeys-*`→메인 dict / `volatile-*`→expires dict |
| 샘플 추출 | `dictGetSomeKeys()`로 무작위 버킷부터 연속 수집 (균등 X, 속도 우선) |
| 샘플 개수 | `maxmemory-samples` (기본 5, 높일수록 정확도↑·CPU↑) |
| 후보 선정 | idle time(LRU)·빈도(LFU) 기준, eviction pool에 누적 후 최댓값 제거 |

핵심 전략은 "정확도를 위해 전수 조사하지 않고, 정책이 좁혀준 대상 안에서 값싸게 흩뿌려 뽑은 소수 표본을 pool로 누적 정제한다"이다. `maxmemory-samples`가 이 표본 크기이자 정확도-비용을 조절하는 유일한 튜닝 손잡이다.

### 5. 근사 LRU vs 정확한 LRU 비교
- 샘플 수가 많을수록 정확도는 올라가지만 CPU 사용량이 늘어난다. 공식 문서의 실험에 따르면 Redis 3.0 + 샘플 5개만으로도 Redis 2.8보다 훨씬 이론적 LRU에 가까워졌고, 샘플 10개를 사용하면 이론적 LRU 성능과 거의 동일한 수준까지 근접한다.
- 실제 서비스의 접근 패턴이 파레토 법칙(멱법칙, power law)을 따르는 경우—즉 일부 "핫" 데이터에 접근이 몰리는 경우—근사 LRU와 정확한 LRU의 차이는 시뮬레이션상 거의 없거나 미미했다.
- 결론적으로 메모리/CPU 절약이라는 이득에 비해 캐시 히트율 손실은 매우 작으며, 필요하면 `maxmemory-samples`를 조정해 정확도-비용 트레이드오프를 튜닝할 수 있다.

### 6. LFU와의 비교
- LRU는 "최근성(recency)"만 고려하므로, 과거에 아주 자주 접근됐더라도 최근에 딱 한 번만 접근이 없었으면 제거 후보가 될 수 있다. 반면 LFU(Least Frequently Used)는 "접근 빈도(frequency)"를 기준으로 삼아, 드물게 쓰이는 키를 우선 제거한다. Redis 4.0부터 `allkeys-lfu`, `volatile-lfu` 정책으로 지원된다.
- LFU도 LRU와 마찬가지로 근사 방식이며, 오브젝트당 몇 비트만으로 접근 빈도를 추정하기 위해 Morris counter(확률적 카운팅 알고리즘)를 사용한다. 접근 시 카운터를 1씩 증가시키는 대신 `1 / (1 + counter * lfu-log-factor)` 확률로 증가시켜, 카운터 값이 커질수록 증가 확률이 낮아지도록 설계했다(0~255 범위로 포화).
- LRU에서 24비트로 쓰던 필드를 LFU 모드에서는 재활용해, 16비트는 마지막 접근 시각(분 단위, decay 계산용), 8비트는 로그 스케일 빈도 카운터(`LOG_C`)로 분할해서 사용한다.
- `lfu-log-factor`(기본 10): 카운터가 포화(255)되기까지 필요한 접근 횟수를 조절한다. 값이 클수록 카운터가 낮은 접근 횟수 구간에서 해상도가 높아지고(자주 접근되는 키들 사이의 미세한 차이를 잘 구분), 값이 작을수록 적은 접근만으로도 빨리 포화된다.
- `lfu-decay-time`(기본 1, 단위: 분): 특정 시간(분) 이상 접근이 없던 키를 샘플링할 때 카운터를 감소(decay)시켜, 예전에 인기 있었지만 최근엔 안 쓰이는 키가 계속 높은 우선순위를 유지하지 않도록 한다. 0으로 설정하면 카운터가 절대 decay되지 않는다.
- 요약하면 LRU는 "언제 마지막으로 썼는가", LFU는 "얼마나 자주 썼는가 + 최근에도 여전히 자주 쓰이는가(decay 반영)"를 기준으로 제거 후보를 정한다.

## 핵심 정리
- Redis는 정확한 LRU 대신, 무작위 샘플링(`maxmemory-samples`)과 eviction pool(Redis 3.0+)을 조합한 근사 LRU를 사용해 메모리/CPU 오버헤드를 크게 줄이면서도 실사용 패턴(파레토 법칙)에서는 정확한 LRU와 거의 동등한 성능을 낸다.
- 각 오브젝트는 24비트의 `lru` 필드에 마지막 접근 클럭을 저장하며, LFU 모드에서는 같은 24비트를 16비트(시각)+8비트(Morris counter 기반 빈도)로 재활용한다.
- 최근성만으로 부족한 워크로드(예: 오래됐지만 여전히 자주 조회되는 데이터)에는 LFU(`allkeys-lfu`/`volatile-lfu`)가 더 적합할 수 있으며, `lfu-log-factor`/`lfu-decay-time`으로 세밀하게 튜닝 가능하다.

## 기술적 한계와 보완 전략
- **정확도 한계**: 샘플링 기반이기 때문에 이론적으로는 "가장 오래 사용되지 않은 키"가 아닌 다른 키가 제거될 수 있다. 이를 보완하려면 `maxmemory-samples` 값을 올리되(기본 5 → 10 등), CPU 사용량 증가와의 트레이드오프를 모니터링해야 한다.
- **접근 패턴 편향 시 성능 저하**: 접근이 균일하게 분산된(파레토 법칙을 따르지 않는) 워크로드에서는 근사 LRU의 이점이 줄어들 수 있다. 이 경우 `allkeys-random`이나 애플리케이션 레벨의 TTL 설계(`volatile-ttl`)를 함께 고려한다.
- **모니터링 기반 튜닝**: `INFO stats`의 `keyspace_hits`, `keyspace_misses`, `evicted_keys`, `expired_keys` 지표를 통해 히트율과 eviction 빈도를 지속적으로 관찰하고, 기대 히트율과 실제 값의 괴리가 크면 정책이나 샘플 수를 재조정한다.
- **LFU 도입 시 워밍업 이슈**: LFU는 신규 키가 처음엔 낮은 카운터 값을 가지므로, 캐시 워밍업 직후에는 새로 들어온(아직 카운터가 낮은) 유효한 핫 데이터가 오히려 먼저 제거될 수 있다. `lfu-log-factor`/`lfu-decay-time` 조정이나 초기 캐시 예열 전략으로 완화할 수 있다.
- **Redis 8.6+의 LRM 정책**: 읽기 위주 워크로드에서 "자주 읽히지만 오래 수정되지 않은" 데이터를 구분하고 싶다면 `allkeys-lrm`/`volatile-lrm`(Least Recently Modified) 정책을 고려할 수 있다. LRU와 달리 쓰기 시에만 타임스탬프를 갱신한다.

## 키워드
- **근사 LRU (Approximated LRU)**: Redis가 정확한 LRU 대신 무작위 샘플링과 eviction pool을 이용해 구현한 LRU 근사 알고리즘. 메모리/CPU 오버헤드를 줄이면서도 실제 접근 패턴에서는 정확한 LRU와 유사한 효과를 낸다.
- **maxmemory-policy**: 메모리 한계 도달 시 어떤 키를 제거할지 결정하는 Redis 설정 디렉티브(`noeviction`, `allkeys-lru`, `volatile-lru`, `allkeys-lfu`, `volatile-lfu`, `allkeys-random`, `volatile-random`, `volatile-ttl` 등).
- **eviction (키 축출)**: `maxmemory`를 초과했을 때 설정된 정책에 따라 캐시에서 키를 강제로 제거하는 동작.
- **maxmemory-samples**: 근사 LRU/LFU에서 eviction 후보를 고를 때 매번 검사할 무작위 샘플의 개수를 지정하는 설정(기본값 5). 값이 클수록 정확도는 올라가지만 CPU 비용이 증가한다.
- **LRU clock (24bit)**: Redis 오브젝트마다 저장되는 24비트 필드로, 마지막 접근 시각(전역 `server.lruclock`의 하위 24비트)을 기록해 idle time을 계산하는 데 사용된다.
- **eviction pool**: Redis 3.0부터 도입된, 크기 16의 정렬된 후보 리스트. 매 eviction마다 새로 샘플링한 키들을 기존 풀과 비교해 idle time이 가장 긴 후보들을 유지함으로써 근사 LRU의 정확도를 크게 향상시켰다.
- **LFU (Least Frequently Used)**: 접근 빈도를 기준으로 제거 후보를 선정하는 eviction 방식. Redis 4.0부터 `allkeys-lfu`/`volatile-lfu` 정책으로 지원되며, LRU와 마찬가지로 근사 방식으로 구현된다.
- **Morris counter**: 적은 비트 수만으로 큰 값을 근사적으로 카운팅할 수 있는 확률적 카운팅 알고리즘. Redis LFU는 이를 이용해 8비트만으로 접근 빈도를 0~255 범위로 근사 추적한다.
- **랜덤 샘플링**: 전체 키를 순회하지 않고 일부 키만 무작위로 뽑아 검사함으로써 계산 비용을 낮추는 기법. 근사 LRU/LFU의 핵심 동작 방식이다.
- **캐시 교체 정책 (Cache Replacement Policy)**: 캐시가 가득 찼을 때 어떤 데이터를 내보낼지 결정하는 전략의 총칭(LRU, LFU, FIFO, Random, TTL 기반 등).
