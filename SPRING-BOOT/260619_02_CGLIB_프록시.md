# CGLIB 프록시

## 개요

Spring AOP에서 인터페이스가 없는 구체 클래스를 대상으로 프록시를 생성할 때 사용하는 CGLIB 방식의 동작 원리와 JDK 동적 프록시와의 차이를 정리한다.

## 상세 내용

### 1. 프록시가 필요한 이유

Spring은 `@Transactional`, `@Cacheable`, `@Async`, `@Aspect` 같은 부가 기능을 원본 비즈니스 코드에 손대지 않고 적용하기 위해 **프록시 패턴**을 사용한다.

```
클라이언트 → 프록시 객체 → (부가 기능 실행) → 실제 객체(타겟)
```

Spring 컨테이너는 빈을 등록할 때, 부가 기능이 필요한 클래스라면 실제 객체 대신 **프록시 객체**를 빈으로 등록한다. 클라이언트가 해당 빈을 주입받아 메서드를 호출하면 프록시가 먼저 실행되면서 트랜잭션 시작, 캐시 확인, 로깅 등 부가 기능을 수행한 뒤 실제 메서드로 위임한다.

### 2. JDK 동적 프록시 vs CGLIB 프록시

| 구분 | JDK 동적 프록시 | CGLIB 프록시 |
|------|----------------|-------------|
| 기반 | 인터페이스 | 구체 클래스 (서브클래싱) |
| 핵심 클래스 | `java.lang.reflect.Proxy` | `net.sf.cglib.proxy.Enhancer` |
| 핸들러 | `InvocationHandler` | `MethodInterceptor` |
| 인터페이스 필요 여부 | 필수 | 불필요 |
| 프록시 방식 | 인터페이스를 구현한 클래스 동적 생성 | 대상 클래스를 상속한 서브클래스 동적 생성 |
| 성능 | 리플렉션 기반 (상대적으로 느림) | 바이트코드 생성 기반 (빠름) |

#### Spring Boot 기본 전략

- **Spring Framework**: 인터페이스가 있으면 JDK 동적 프록시, 없으면 CGLIB
- **Spring Boot 2.x 이후**: `proxyTargetClass=true`가 기본값으로 설정되어 **인터페이스 유무와 관계없이 CGLIB이 기본**으로 사용됨

Spring Boot 2.x에서 CGLIB을 기본으로 바꾼 이유는, 인터페이스가 있는 클래스라도 구체 타입으로 주입받으려 할 때 JDK 동적 프록시는 구체 타입 캐스팅이 불가능하여 런타임 오류가 발생하는 문제를 방지하기 위해서다.

### 3. CGLIB 동작 원리

CGLIB(Code Generation Library)은 런타임에 바이트코드를 조작하여 대상 클래스를 **상속**한 서브클래스를 동적으로 생성한다.

#### 핵심 컴포넌트

**Enhancer**

JDK의 `Proxy`에 해당하는 클래스다. 프록시 클래스를 생성하고 인스턴스를 반환한다.

```java
Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(SampleService.class); // 상속할 대상 클래스 지정
enhancer.setCallback(new SampleMethodInterceptor()); // 인터셉터 등록
SampleService proxy = (SampleService) enhancer.create(); // 서브클래스 인스턴스 생성
```

**MethodInterceptor**

JDK의 `InvocationHandler`에 해당한다. 프록시 메서드가 호출될 때 `intercept()` 메서드가 실행된다.

```java
public class SampleMethodInterceptor implements MethodInterceptor {
    @Override
    public Object intercept(Object obj, Method method, Object[] args, MethodProxy proxy) throws Throwable {
        System.out.println("Before method: " + method.getName());
        Object result = proxy.invokeSuper(obj, args); // 실제 메서드 호출
        System.out.println("After method: " + method.getName());
        return result;
    }
}
```

`MethodProxy.invokeSuper()`는 리플렉션 대신 바이트코드로 직접 부모 메서드를 호출하므로 성능이 더 빠르다.

**FastClass**

CGLIB 내부에서 사용하는 클래스로, JNI 기반 리플렉션 대신 JVM 바이트코드로 메서드를 직접 디스패치하여 성능을 높인다. 단, 최신 JVM은 자주 호출되는 리플렉션을 자동으로 바이트코드로 변환하는 "inflation" 기능을 가지고 있어, 실제 성능 차이는 예전보다 줄어들었다.

#### 프록시 생성 흐름

```
1. Enhancer가 대상 클래스를 분석
2. 대상 클래스를 상속한 서브클래스 바이트코드 생성
3. 오버라이드된 각 메서드에 MethodInterceptor 호출 코드 삽입
4. Objenesis를 통해 생성자 호출 없이 인스턴스 생성
5. 생성된 프록시 인스턴스를 Spring 빈으로 등록
```

### 4. CGLIB 프록시의 제약

#### final 클래스 / final 메서드 프록시 불가

CGLIB은 상속으로 프록시를 만들기 때문에, `final`이 붙은 클래스나 메서드는 오버라이드할 수 없어 프록시를 생성할 수 없다.

```java
@Service
public final class OrderService { // 프록시 생성 불가
    @Transactional
    public void order() { ... }
}
```

#### private 메서드 미적용

`private` 메서드는 서브클래스에서 오버라이드할 수 없으므로 AOP 어드바이스가 적용되지 않는다.

#### Self-Invocation (내부 호출) 문제

같은 클래스 내에서 `this`로 다른 메서드를 호출하면 프록시를 거치지 않아 AOP가 동작하지 않는다.

```java
@Service
public class OrderService {

    public void processOrder() {
        // this.pay()를 호출 → 프록시를 거치지 않으므로 @Transactional 미적용
        this.pay();
    }

    @Transactional
    public void pay() {
        // ...
    }
}
```

`processOrder()`를 호출할 때는 프록시를 통하지만, 그 안에서 `this.pay()`를 호출하면 프록시가 아닌 실제 객체의 `pay()`가 직접 호출되어 트랜잭션이 시작되지 않는다.

#### 생성자 이중 호출 문제 (Spring 4.0 이전)

CGLIB은 서브클래스를 생성하기 위해 부모 클래스의 생성자를 호출해야 했다. Spring 4.0 이전에는 프록시 생성 과정에서 생성자가 두 번 호출되는 문제가 있었다.

Spring 4.0부터 **Objenesis** 라이브러리를 통해 생성자를 우회하여 인스턴스를 만들기 때문에 이 문제는 해결되었다.

### 5. Spring에서의 적용

#### proxyTargetClass 설정

```java
// AOP 설정 - 강제로 CGLIB 사용
@EnableAspectJAutoProxy(proxyTargetClass = true)

// 트랜잭션 설정 - 강제로 CGLIB 사용
@EnableTransactionManagement(proxyTargetClass = true)
```

`application.properties`로도 제어 가능하다:

```properties
spring.aop.proxy-target-class=true  # 기본값 (Spring Boot 2.x 이후)
```

#### Spring Boot에서 빈 등록과 프록시 생성 시점

```
애플리케이션 구동
  → 컴포넌트 스캔으로 후보 클래스 탐색
  → BeanDefinition 등록
  → BeanPostProcessor 동작 (AnnotationAwareAspectJAutoProxyCreator 등)
  → AOP 대상 여부 판단
  → CGLIB Enhancer로 프록시 클래스 생성
  → ApplicationContext에 프록시 빈 등록
```

#### Spring 7.0 이후 @Proxyable (참고)

Spring 7.0부터는 빈 단위로 프록시 방식을 지정할 수 있는 `@Proxyable` 어노테이션이 도입되었다:

```java
@Proxyable(TARGET_CLASS) // CGLIB 사용
@Bean
public MyService myService() { ... }
```

## 핵심 정리

- CGLIB은 대상 클래스를 **상속**한 서브클래스를 바이트코드로 생성하여 프록시를 만든다.
- Spring Boot 2.x 이후 `proxyTargetClass=true`가 기본이므로 **인터페이스가 없어도 프록시 생성**이 가능하다.
- `final` 클래스/메서드, `private` 메서드, **self-invocation**은 CGLIB 프록시의 AOP가 적용되지 않는다.
- Spring 4.0 이후 **Objenesis** 덕분에 생성자 이중 호출 문제는 해결되었다.
- `MethodInterceptor.intercept()`에서 `MethodProxy.invokeSuper()`를 사용하면 리플렉션 없이 부모 메서드를 빠르게 호출할 수 있다.

## 기술적 한계와 보완 전략

| 한계 | 보완 전략 |
|------|----------|
| Self-Invocation 미적용 | 별도 빈으로 분리 / `@Autowired MyService self` 자기 주입 / `AopContext.currentProxy()` (비권장) |
| final 클래스 프록시 불가 | `final` 키워드 제거 / AspectJ 컴파일타임·로드타임 위빙 적용 |
| private 메서드 미적용 | 접근 제어자를 `package-private` 이상으로 변경 / 설계 재고 |
| PermGen / Metaspace 증가 | 프록시 대상 최소화, 프로파일링으로 클래스 수 모니터링 |
| 상속 기반 → 단일 상속 제약 | 인터페이스 도입으로 JDK 동적 프록시 전환 고려 |

## 키워드

- **CGLIB (Code Generation Library)**: 바이트코드를 동적으로 생성하여 런타임에 클래스의 서브클래스를 만들어내는 라이브러리. Spring AOP에서 인터페이스 없는 클래스의 프록시를 만들 때 사용한다.

- **JDK Dynamic Proxy**: `java.lang.reflect.Proxy`를 이용해 인터페이스 기반으로 동적 프록시를 생성하는 JDK 내장 방식. 대상 클래스가 반드시 인터페이스를 구현해야 한다.

- **Spring AOP**: Spring에서 제공하는 AOP 구현체. 프록시 기반으로 동작하며, 런타임에 `@Aspect`, `@Transactional` 등의 어드바이스를 적용한다. 컴파일타임 위빙을 사용하는 AspectJ와 달리 프록시를 통해 부가 기능을 끼워 넣는다.

- **Enhancer**: CGLIB의 핵심 클래스. 대상 클래스를 상속한 프록시 클래스를 동적으로 생성하고 인스턴스를 반환한다. JDK의 `Proxy`와 같은 역할을 한다.

- **MethodInterceptor**: CGLIB에서 메서드 호출을 가로채는 콜백 인터페이스. `intercept()` 메서드에 부가 기능 로직을 구현하며, JDK의 `InvocationHandler`에 대응한다.

- **proxyTargetClass**: Spring AOP에서 CGLIB 강제 사용 여부를 결정하는 설정 값. `true`면 인터페이스 유무와 무관하게 항상 CGLIB을 사용한다. Spring Boot 2.x 이후 기본값은 `true`.

- **Self-Invocation**: 같은 객체 내에서 `this`를 통해 메서드를 호출하는 것. 프록시를 거치지 않고 실제 객체를 직접 호출하므로 AOP 어드바이스가 적용되지 않는다.

- **Bytecode Generation**: 소스 코드 컴파일 없이 런타임에 JVM 바이트코드(.class)를 직접 생성하는 기법. CGLIB은 이를 통해 서브클래스 프록시를 만든다.

- **Subclass Proxy**: CGLIB이 채택하는 프록시 방식. 대상 클래스를 상속받은 서브클래스를 동적으로 만들어 메서드를 오버라이드함으로써 부가 기능을 끼워 넣는다.
