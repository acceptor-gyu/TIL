# 헥사고날 아키텍처

## 개요

헥사고날 아키텍처(Hexagonal Architecture)는 Alistair Cockburn이 2005년 제안한 소프트웨어 설계 패턴으로, 공식 명칭은 **Ports and Adapters**다. 핵심 아이디어는 단순하다. 비즈니스 로직(도메인)을 DB, UI, 메시지 브로커 같은 외부 기술로부터 완전히 격리하고, 포트(Port)라는 인터페이스를 통해서만 외부와 소통하게 만드는 것이다.

이름이 "헥사고날(육각형)"인 이유는 기술적인 의미가 있어서가 아니라, 그림으로 표현할 때 육각형이 각 면에 포트를 배치하기 편리하기 때문이다. 실제로 포트 수가 6개일 필요는 없다.

---

## 상세 내용

### 1. 등장 배경과 문제 의식

전통적인 레이어드 아키텍처(Layered Architecture)에서는 계층이 위에서 아래로 흐른다.

```
Presentation Layer  →  Application Layer  →  Domain Layer  →  Infrastructure Layer
```

이 구조의 문제는 **기술 의존성이 도메인으로 침투**한다는 것이다.

- 도메인 서비스에 `@Transactional`, `@Repository` 같은 스프링 어노테이션이 붙기 시작한다.
- DB 스키마가 바뀌면 도메인 로직도 수정해야 하는 일이 생긴다.
- 테스트를 위해 DB나 외부 시스템을 반드시 띄워야 한다.
- UI가 바뀌면 비즈니스 로직 코드를 함께 수정해야 한다.

Cockburn은 이 문제를 "사용자와 테스트 케이스가 대칭적으로 동일하게 애플리케이션을 구동할 수 있어야 한다"는 목표로 정리했다. 즉, DB 없이도, UI 없이도 비즈니스 로직을 실행하고 테스트할 수 있어야 한다는 것이다.

### 2. 핵심 구성 요소

헥사고날 아키텍처는 세 가지 핵심 요소로 구성된다.

#### 도메인 코어 (Application Core)

비즈니스 규칙과 도메인 로직이 담기는 영역이다. 여기서는 어떠한 외부 기술 의존성도 가져서는 안 된다. 스프링 어노테이션, JPA 어노테이션, HTTP 관련 코드가 없어야 한다.

```java
// 외부 기술 의존 없음 - 순수 비즈니스 로직
public class Order {
    private final String orderId;
    private final List<OrderItem> items;
    private OrderStatus status;

    public void confirm() {
        if (items.isEmpty()) {
            throw new IllegalStateException("주문 항목이 없습니다.");
        }
        this.status = OrderStatus.CONFIRMED;
    }
}
```

#### 포트 (Port)

도메인 코어가 외부 세계와 소통하기 위한 인터페이스다. 포트는 도메인이 정의하고, 도메인 언어로 작성된다. 포트에는 두 종류가 있다.

**인바운드 포트 (Inbound Port / Driving Port)**
- 외부에서 도메인을 호출하기 위한 인터페이스
- 유스케이스 인터페이스라고도 부른다
- 예: `CreateOrderUseCase`, `GetOrderUseCase`

```java
// 인바운드 포트 - 도메인이 정의
public interface CreateOrderUseCase {
    OrderId createOrder(CreateOrderCommand command);
}
```

**아웃바운드 포트 (Outbound Port / Driven Port)**
- 도메인이 외부 시스템(DB, 외부 API 등)을 사용하기 위한 인터페이스
- 저장소 포트(Repository Port)가 대표적이다
- 예: `OrderRepository`, `PaymentGateway`

```java
// 아웃바운드 포트 - 도메인이 정의
public interface OrderRepository {
    void save(Order order);
    Optional<Order> findById(OrderId id);
}
```

#### 어댑터 (Adapter)

포트의 실제 구현체다. 어댑터는 외부 세계와 포트 사이의 번역을 담당한다. 어댑터도 두 종류가 있다.

**드라이빙 어댑터 (Driving Adapter)**
- 인바운드 포트를 호출하는 어댑터
- 외부 요청을 도메인이 이해할 수 있는 형태로 변환하고 유스케이스를 호출한다
- REST 컨트롤러, 스케줄러, 메시지 컨슈머 등

```java
// 드라이빙 어댑터 - 인바운드 포트를 사용
@RestController
@RequestMapping("/orders")
public class OrderRestAdapter {
    private final CreateOrderUseCase createOrderUseCase;

    @PostMapping
    public ResponseEntity<String> createOrder(@RequestBody CreateOrderRequest request) {
        CreateOrderCommand command = new CreateOrderCommand(request.getItems());
        OrderId orderId = createOrderUseCase.createOrder(command);
        return ResponseEntity.ok(orderId.getValue());
    }
}
```

**드리븐 어댑터 (Driven Adapter)**
- 아웃바운드 포트를 구현하는 어댑터
- 도메인의 요청을 특정 기술(JPA, Redis, 외부 API)로 번역한다
- JPA 레포지토리 어댑터, HTTP 클라이언트 어댑터 등

```java
// 드리븐 어댑터 - 아웃바운드 포트를 구현
@Repository
public class OrderJpaAdapter implements OrderRepository {
    private final SpringDataOrderRepository jpaRepository;

    @Override
    public void save(Order order) {
        OrderEntity entity = OrderMapper.toEntity(order);
        jpaRepository.save(entity);
    }

    @Override
    public Optional<Order> findById(OrderId id) {
        return jpaRepository.findById(id.getValue())
            .map(OrderMapper::toDomain);
    }
}
```

### 3. 의존성 방향과 의존성 역전 원칙(DIP)

헥사고날 아키텍처의 가장 중요한 규칙은 **모든 의존성이 도메인 코어를 향한다**는 것이다.

```
드라이빙 어댑터  →  인바운드 포트(인터페이스)  ←  도메인 코어
도메인 코어  →  아웃바운드 포트(인터페이스)  ←  드리븐 어댑터
```

아웃바운드 포트 쪽에서 DIP가 적용되는 방식을 주목해야 한다.

- 도메인은 `OrderRepository` 인터페이스(아웃바운드 포트)에만 의존한다.
- `OrderJpaAdapter`가 `OrderRepository`를 구현한다.
- 결과적으로 도메인은 JPA를 전혀 모르고, JPA 어댑터가 도메인에 의존하게 된다.

이것이 의존성 역전이다. 일반적으로 도메인이 인프라에 의존하지만, DIP를 통해 인프라가 도메인에 의존하도록 방향을 뒤집는다.

### 4. 동작 흐름 예시

주문 생성 요청의 전체 흐름을 따라가 보자.

**인바운드 흐름 (HTTP 요청 → 도메인)**
```
1. HTTP POST /orders 요청 도착
2. OrderRestAdapter (드라이빙 어댑터)
   - HTTP 요청 파싱
   - CreateOrderCommand 객체 생성
3. CreateOrderUseCase (인바운드 포트) 호출
4. OrderService (도메인) 비즈니스 로직 실행
   - Order 엔티티 생성
   - 도메인 규칙 검증
```

**아웃바운드 흐름 (도메인 → DB)**
```
5. OrderService가 OrderRepository (아웃바운드 포트) 호출
6. OrderJpaAdapter (드리븐 어댑터)
   - Order 도메인 객체를 OrderEntity로 변환
   - JPA를 통해 DB 저장
7. 결과를 도메인 언어로 변환하여 반환
8. OrderRestAdapter가 HTTP 응답으로 변환하여 반환
```

### 5. Layered / Clean / Onion Architecture와의 비교

세 아키텍처는 모두 DIP를 기반으로 하며 사실상 동일한 목표를 추구한다. 등장 순서와 표현 방식에 차이가 있다.

| 구분 | 레이어드 아키텍처 | 헥사고날 아키텍처 | 클린 아키텍처 | 어니언 아키텍처 |
|---|---|---|---|---|
| 제안자/시기 | - | Cockburn, 2005 | Uncle Bob, 2012 | Jeffrey Palermo, 2008 |
| 핵심 표현 | 계층(Layer) | 포트와 어댑터 | 레이어 + 유스케이스 | 양파 레이어 |
| DIP 적용 | 선택적 | 명시적 | 명시적 | 명시적 |
| 외부 격리 | 약함 | 강함 (포트 계약) | 강함 | 강함 |
| 복잡도 | 낮음 | 중간~높음 | 높음 | 중간~높음 |

**언제 헥사고날을 선택하는가?**

- 여러 외부 시스템(DB, 외부 API, 메시지 브로커)과 연동이 많아 교체 가능성이 있을 때
- 비즈니스 로직 단위 테스트가 핵심 요구사항일 때
- 동일한 도메인 로직을 여러 클라이언트(REST, gRPC, 배치)에서 재사용해야 할 때
- 마이크로서비스에서 서비스 경계와 책임을 명확히 해야 할 때

### 6. 실무 적용 시 패키지 구조 예시

Spring Boot 기반의 전형적인 헥사고날 패키지 구조다.

```
src/main/java/com/example/order/
├─ domain/
│  ├─ model/
│  │  ├─ Order.java              # 도메인 엔티티
│  │  ├─ OrderItem.java
│  │  └─ OrderStatus.java
│  └─ service/
│     └─ OrderDomainService.java  # 복잡한 도메인 로직
│
├─ application/
│  ├─ port/
│  │  ├─ in/
│  │  │  ├─ CreateOrderUseCase.java   # 인바운드 포트
│  │  │  └─ GetOrderUseCase.java
│  │  └─ out/
│  │     ├─ OrderRepository.java      # 아웃바운드 포트
│  │     └─ PaymentGateway.java
│  └─ service/
│     └─ OrderService.java            # 유스케이스 구현체 (도메인 오케스트레이션)
│
└─ adapter/
   ├─ in/
   │  └─ web/
   │     ├─ OrderRestAdapter.java     # 드라이빙 어댑터 (REST)
   │     └─ dto/
   │        ├─ CreateOrderRequest.java
   │        └─ OrderResponse.java
   └─ out/
      ├─ persistence/
      │  ├─ OrderJpaAdapter.java      # 드리븐 어댑터 (JPA)
      │  ├─ entity/
      │  │  └─ OrderEntity.java
      │  └─ repository/
      │     └─ SpringDataOrderRepository.java
      └─ payment/
         └─ PaymentHttpAdapter.java   # 드리븐 어댑터 (외부 결제 API)
```

**중요한 점은 `application`과 `domain` 패키지에는 Spring 어노테이션이 들어가지 않는다는 것이다.** `OrderService`는 `@Service` 없이 POJO로 작성하고, 스프링 빈 등록은 별도 Config 클래스에서 처리하는 방식이 이상적이다. 단, 팀의 현실적인 생산성을 고려해서 `application/service`에는 `@Service`를 허용하는 절충안을 쓰는 경우도 많다.

## 핵심 정리

- 핵심 포인트 1: 비즈니스 로직(도메인)을 외부 기술(DB, UI, 메시징)로부터 완전히 격리한다. 도메인 코어는 외부 기술을 몰라야 한다.
- 핵심 포인트 2: 포트는 도메인이 정의한 계약(인터페이스)이다. 어댑터는 그 계약을 특정 기술로 구현한 구현체다. 포트는 도메인 언어로, 어댑터는 기술 언어로 작성된다.
- 핵심 포인트 3: 모든 의존성은 도메인 코어를 향한다. DIP에 의해 인프라 어댑터가 도메인에 의존하게 되므로, 외부 기술 교체가 도메인에 영향을 주지 않는다.

## 기술적 한계와 보완 전략

**과도한 추상화와 보일러플레이트**

소규모 프로젝트나 CRUD 위주 서비스에서는 포트 인터페이스 → 유스케이스 구현 → 어댑터 구현의 3단계 구조가 코드량을 크게 늘린다. 클래스 수가 3~4배 증가하는 것이 일반적이다. 비즈니스 복잡도가 낮으면 레이어드 아키텍처로 충분하다.

**DTO/도메인 모델 변환 비용**

어댑터에서 도메인 모델로, 도메인 모델에서 영속성 엔티티로 두 번의 변환이 필요하다. 매핑 클래스(Mapper)를 별도로 관리해야 하며, 이 비용을 줄이기 위해 MapStruct 같은 코드 생성 라이브러리를 활용하는 것이 일반적이다.

**학습 곡선**

포트와 어댑터, 인바운드/아웃바운드, 드라이빙/드리븐의 개념 구분이 처음에는 직관적이지 않다. 팀 전체가 동일하게 이해하지 못하면 구조가 제각각이 되어 오히려 복잡도가 높아진다.

**보완 전략**

- 도메인 복잡도가 낮은 서비스에서는 포트를 생략하고 어댑터에서 직접 도메인 서비스를 호출하는 경량화 버전을 적용한다.
- 공통 매핑 전략을 팀 컨벤션으로 확립하고, MapStruct를 활용해 매핑 코드를 자동 생성한다.
- `application/service`에 `@Service`를 허용하는 실용적 타협을 팀에 맞게 선택한다.

## 키워드

- **Ports and Adapters**: 헥사고날 아키텍처의 공식 명칭. 포트(인터페이스)와 어댑터(구현체)로 내부와 외부를 분리하는 패턴
- **의존성 역전 원칙(DIP)**: 고수준 모듈(도메인)이 저수준 모듈(인프라)에 의존하지 않고, 둘 다 추상화(포트)에 의존하도록 만드는 SOLID 원칙
- **Inbound/Outbound Port**: 인바운드 포트는 외부에서 도메인을 호출하는 인터페이스(유스케이스), 아웃바운드 포트는 도메인이 외부를 사용하기 위한 인터페이스(레포지토리 등)
- **Driving/Driven Adapter**: 드라이빙 어댑터는 인바운드 포트를 호출하는 쪽(REST 컨트롤러 등), 드리븐 어댑터는 아웃바운드 포트를 구현하는 쪽(JPA 레포지토리 등)
- **도메인 격리(Domain Isolation)**: 도메인 코어가 외부 기술(DB, 프레임워크, UI)을 전혀 알지 못하도록 격리하는 설계 목표
- **Clean Architecture**: Uncle Bob이 2012년 제안한 아키텍처로 헥사고날과 같은 DIP 기반이며 유스케이스 계층을 명시적으로 강조
- **Onion Architecture**: Jeffrey Palermo가 2008년 제안한 양파 레이어 구조. 마찬가지로 DIP 기반이며 도메인 코어를 중심에 둔다
- **테스트 용이성(Testability)**: 포트를 Mock으로 교체할 수 있어 DB나 외부 API 없이 도메인 로직을 단위 테스트할 수 있는 특성
- **어댑터 교체(Pluggability)**: 아웃바운드 포트 구현체(어댑터)를 교체해도 도메인 코어에 영향이 없는 특성. MySQL → MongoDB 교체가 도메인 코드 수정 없이 가능
