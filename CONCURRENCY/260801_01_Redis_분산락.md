# Redis 분산락

## 개요
분산 환경에서 여러 프로세스/서버가 공유 자원에 동시 접근할 때 발생하는 경쟁 상태(Race Condition)를 방지하기 위한 Redis 기반 분산락(Distributed Lock)에 대해 학습한다.

## 상세 내용

### 1. 분산락이 필요한 이유
- 단일 프로세스 내 `synchronized`, `ReentrantLock`은 JVM 내부 메모리(모니터 락) 기준으로만 동작하기 때문에, 인스턴스가 여러 대로 스케일 아웃되면 서로 다른 JVM의 스레드끼리는 락을 공유할 수 없다.
- 다중 인스턴스(Scale-out) 환경에서는 재고 차감, 쿠폰 발급, 선착순 이벤트 등 공유 자원에 대한 동시 접근을 제어할 별도의 외부 저장소 기반 락이 필요하다.
- DB 락(비관적/낙관적 락)과 비교하면
  - 비관적 락(`SELECT ... FOR UPDATE`)은 트랜잭션이 끝날 때까지 락을 유지하므로 안정적이지만 DB 커넥션/트랜잭션에 부하가 집중되고 데드락 가능성이 있다.
  - 낙관적 락(버전 컬럼)은 충돌이 잦으면 재시도 비용이 커진다.
  - Redis는 인메모리 기반으로 응답 속도가 빠르고, DB 트랜잭션과 분리되어 락 획득/해제를 짧게 가져갈 수 있어 고빈도 동시성 제어에 유리하다.

### 2. Redis를 활용한 락 구현 방식
- `SETNX key value` (SET if Not eXists): 키가 존재하지 않을 때만 값을 설정하는 원자적 명령. 락 획득 여부를 하나의 명령으로 판단할 수 있다.
- 초기에는 `SETNX` + `EXPIRE`를 별도로 호출했으나, 두 명령 사이에 프로세스가 죽으면 TTL이 설정되지 않아 락이 영구히 풀리지 않는 문제가 있었다.
- 이를 해결하기 위해 Redis 2.6.12부터 `SET key value NX PX milliseconds` 옵션으로 "락 획득 + TTL 설정"을 하나의 원자적 명령으로 처리할 수 있게 되었다.
  - `NX`: 키가 없을 때만 설정 (락 획득)
  - `PX milliseconds`: 밀리초 단위 만료 시간 설정 (락 자동 해제)
- 락 소유자를 식별하기 위해 value에 요청자별 고유 값(UUID, 스레드 ID 등)을 저장한다. 이를 통해 "내가 건 락만 내가 해제"하는 것을 보장할 수 있다.

### 3. 락 해제의 안전성
- 단순히 `DEL key`로 락을 해제하면, 다음과 같은 문제가 발생할 수 있다.
  1. A가 락을 획득한다.
  2. A의 작업이 TTL보다 오래 걸려 락이 만료되어 B가 락을 획득한다.
  3. A의 작업이 끝나고 뒤늦게 `DEL`을 호출하면 B가 획득한 락을 A가 지워버린다.
- 이를 막기 위해 "내가 저장한 value와 현재 Redis에 저장된 value가 같을 때만 삭제"하는 GET + DEL의 원자적 처리가 필요하다.
- Redis는 여러 명령을 원자적으로 묶어 실행하기 위한 Lua 스크립트(`EVAL`)를 지원하며, 락 해제는 아래와 같은 패턴으로 구현한다.

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

- Lua 스크립트는 Redis 내에서 싱글 스레드로 원자적으로 실행되므로, GET과 DEL 사이에 다른 클라이언트가 끼어들 여지가 없다.

### 4. Spin Lock vs Pub/Sub 기반 대기
- Spin Lock 방식: 락 획득에 실패하면 일정 간격(polling interval)으로 재시도한다. 구현이 단순하지만
  - 대기 클라이언트가 많을수록 Redis에 반복적으로 요청이 몰려 부하가 커진다.
  - 재시도 간격을 짧게 하면 부하가 커지고, 길게 하면 락 해제 후 획득까지 지연 시간이 늘어난다.
- Redisson은 Pub/Sub 기반 대기를 제공한다.
  - 락 획득 실패 시 클라이언트는 해당 락에 대한 채널을 구독(subscribe)하고 대기 상태로 진입한다.
  - 락을 보유한 클라이언트가 락을 해제(`unlock`)하면 해당 채널로 메시지를 발행(publish)한다.
  - 대기 중인 클라이언트는 메시지를 받는 즉시 다시 락 획득을 시도한다.
  - 불필요한 폴링 없이 이벤트 기반으로 동작하기 때문에 Redis 부하가 적고 락 획득까지의 지연 시간도 짧다.
- 락 획득 실패 시 재시도 전략으로는 `tryLock`의 `waitTime`을 설정해 일정 시간 동안만 대기 후 포기하거나, 지수 백오프(Exponential Backoff)를 조합해 재시도 간격을 늘려가는 방식도 고려할 수 있다.

### 5. Redisson을 활용한 구현
- Redisson은 Redis 클라이언트 위에 분산 객체/서비스 API를 제공하는 라이브러리로, `RLock` 인터페이스를 통해 분산락을 손쉽게 사용할 수 있다.

```java
RLock lock = redissonClient.getLock("lockKey");
try {
    // waitTime: 락 획득을 시도할 최대 대기 시간
    // leaseTime: 락을 획득한 뒤 자동 해제될 시간
    boolean available = lock.tryLock(5, 3, TimeUnit.SECONDS);
    if (!available) {
        // 락 획득 실패 처리
        return;
    }
    // 비즈니스 로직 수행
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

- Watchdog(락 자동 연장): `leaseTime`을 명시하지 않고 `lock()` 또는 `tryLock()`을 호출하면, Redisson 내부의 Watchdog 스레드가 기본 30초(`lockWatchdogTimeout`) 주기의 1/3 간격(기본 10초)마다 락의 TTL을 갱신한다. 락을 획득한 클라이언트가 살아있는 한 락이 만료되지 않으며, 클라이언트가 다운되면 갱신이 중단되어 TTL이 지나면 자동으로 해제된다.
  - 단, `leaseTime`을 명시적으로 지정하면(`tryLock(waitTime, leaseTime, unit)`) Watchdog은 동작하지 않고 지정된 시간이 지나면 무조건 락이 해제된다.
- 재진입(Reentrant) 락: 동일한 스레드가 이미 보유 중인 락을 다시 `lock()`/`tryLock()`으로 요청하면, 내부적으로 hold count를 증가시켜 재획득을 허용한다. `unlock()`을 호출한 횟수만큼 hold count가 감소하며, 0이 되어야 실제로 락이 해제된다.

### 6. Redlock 알고리즘
- 단일 Redis 노드로 락을 운영하면, 해당 노드가 다운되거나 Master-Replica 구조에서 비동기 복제 중 Failover가 발생할 경우 락의 안전성이 깨질 수 있다. (Master에 락을 건 직후 장애가 발생해 복제가 반영되기 전에 Replica가 새로운 Master로 승격되면, 락이 사라진 것처럼 보여 다른 클라이언트가 동시에 락을 획득할 수 있다.)
- Redlock 알고리즘은 이를 보완하기 위해 서로 독립적인 N개(권장 5개)의 Redis 마스터 노드에 대해 순차적으로 락 획득을 시도하고, 과반수(N/2 + 1) 이상의 노드에서 락 획득에 성공하고 전체 소요 시간이 락의 유효 시간보다 짧을 때만 락 획득에 성공한 것으로 간주한다.
- Redlock에 대한 논쟁: Martin Kleppmann은 2016년 "How to do distributed locking" 글에서 Redlock이 네트워크 지연, GC Pause, 클록 드리프트(clock drift) 등의 상황에서 상호 배제(mutual exclusion)를 완벽히 보장하지 못한다고 비판했다. Redis 창시자 antirez(Salvatore Sanfilippo)는 이에 대한 반박 글을 남겼으며, 현재도 공식 문서에서 두 글을 모두 참고하도록 안내하고 있다.
- 실무적으로는 "락이 100% 완벽해야 하는 상황(예: 자금 이체처럼 정합성이 절대적으로 중요한 경우)"이라면 Redis 기반 락보다 Zookeeper(Chubby 스타일의 순번 기반 락)나 fencing token을 결합한 방식을 고려하고, 단순 성능 최적화/중복 실행 방지 목적이라면 Redis 분산락으로 충분한 경우가 많다.

### 7. 실무 예시: 숙박 ARI(Availability, Rates, Inventory) 관리 시스템
숙박 예약 도메인은 하나의 재고(특정 호텔, 특정 객실 타입, 특정 날짜의 잔여 객실 수)에 대해 **여러 채널(OTA, 자사 웹/앱, 프론트 데스크)이 동시에 접근**하는 대표적인 고동시성 환경이다. ARI는 그중에서도 재고(Availability/Inventory)와 요금(Rates)을 실시간으로 정합성 있게 관리해야 하므로 분산락이 특히 유용하다.

**상황 1) 마지막 1실 오버부킹(Overbooking) 방지**
- 8월 3일, 디럭스룸 잔여 재고가 1실 남은 상태에서 Booking.com·Expedia·자사 앱이 거의 동시에 예약 요청을 보낸다.
- 락이 없다면 세 요청 모두 "잔여 1실"을 읽고 각각 차감을 시도해, 재고가 `-2`가 되는 오버부킹이 발생한다. (오버부킹은 고객 응대 비용과 브랜드 신뢰 하락으로 직결되는 실무상 치명적 사고다.)
- 락 키를 **재고의 최소 단위(호텔+객실타입+날짜)** 로 잡으면, 서로 다른 날짜/객실타입 예약은 병렬로 처리하면서 동일 재고에 대한 요청만 직렬화할 수 있다.

```java
// 락 키를 "호텔-객실타입-날짜" 단위로 세분화해 락 경합 범위를 최소화
String lockKey = "lock:ari:inventory:" + hotelId + ":" + roomTypeId + ":" + stayDate;
RLock lock = redissonClient.getLock(lockKey);
try {
    // 예약 트래픽 폭주(선착순 특가 등)를 고려해 짧은 waitTime + leaseTime
    if (!lock.tryLock(3, 5, TimeUnit.SECONDS)) {
        throw new BookingException("잠시 후 다시 시도해 주세요."); // 폴백/사용자 안내
    }
    int remaining = inventoryRepository.findRemaining(hotelId, roomTypeId, stayDate);
    if (remaining < requestedRooms) {
        throw new SoldOutException("잔여 객실이 부족합니다.");
    }
    inventoryRepository.decrease(hotelId, roomTypeId, stayDate, requestedRooms);
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

- 다박(multi-night) 예약이라면 8/3, 8/4, 8/5처럼 **여러 날짜의 재고를 동시에 확보**해야 하는데, 이때 여러 락을 잡는 순서를 요청마다 다르게 하면 데드락이 발생할 수 있다. → 락 키를 **항상 날짜 오름차순 등 일관된 순서로 정렬해 획득**하여 순환 대기(circular wait)를 예방한다.

**상황 2) 채널 매니저의 요금(Rates) 동시 갱신 정합성**
- 채널 매니저가 특정 객실타입의 요금을 일괄 인상하는 배치와, 레비뉴 매니저가 프로모션가로 수동 조정하는 요청이 동시에 들어오면 "나중에 쓴 값이 이긴다(last-write-wins)"로 인해 의도치 않은 요금이 노출될 수 있다.
- 요금 갱신 구간을 분산락으로 직렬화하면, 읽기→검증(예: 최저가 하한선 체크)→쓰기가 원자적으로 처리되어 잘못된 저가 노출(요금 유출)로 인한 매출 손실을 막을 수 있다.

**상황 3) OTA로의 재고/요금 동기화(Push) 중복 방지**
- 재고·요금이 바뀔 때마다 각 OTA API로 업데이트를 push하는데, 스케줄러가 여러 인스턴스에서 동시에 도는 경우 동일 대상에 대해 push가 중복 실행될 수 있다.
- `leaseTime`을 지정하지 않고 락을 걸어 **Watchdog으로 자동 연장**하면, OTA API 응답이 느려 작업이 길어지더라도 락이 중간에 풀려 다른 인스턴스가 중복 push하는 것을 방지할 수 있다.

**ARI 도메인에서의 설계 포인트**
- 락 범위를 넓게(호텔 전체) 잡으면 정합성은 쉽지만 처리량이 급감한다. → **재고의 최소 단위로 키를 쪼개** 경합 범위를 좁히는 것이 핵심이다.
- 재고 차감처럼 금전·오버부킹과 직결되는 로직은 Redis 락만 믿기보다, **DB의 재고 컬럼에 `remaining >= 0` 제약이나 조건부 UPDATE(`WHERE remaining >= ?`)를 최종 방어선**으로 함께 두어 이중으로 보호하는 것이 안전하다.

## 핵심 정리
- 분산락은 다중 인스턴스 환경에서 공유 자원의 동시 접근을 제어하기 위한 수단이다.
- `SET NX PX`와 Lua 스크립트를 통해 락 획득/해제의 원자성을 보장해야 한다.
- Redisson의 Pub/Sub + Watchdog 방식이 Spin Lock 대비 효율적이다.
- `leaseTime`을 명시하면 Watchdog이 비활성화되므로, 자동 연장이 필요한 로직인지 여부에 따라 적절히 선택해야 한다.

## 기술적 한계와 보완 전략
- TTL 만료 후 작업이 끝나지 않은 경우 락이 중복 획득될 수 있음 → Watchdog 자동 연장
- 단일 Redis 노드 장애 시 락 신뢰성 저하 → Redlock 또는 고가용성(Sentinel/Cluster) 구성 고려
- 네트워크 지연/GC Pause로 인한 락 유효성 문제 → Fencing Token(락 획득 시 단조 증가하는 토큰을 함께 발급해, 자원 접근 시 최신 토큰인지 검증) 등 추가 검증 필요
- Redis 자체가 SPOF(단일 장애점)가 될 수 있으므로, 락이 실패했을 때의 폴백 전략(재시도, Circuit Breaker, DB 락으로 전환)도 함께 설계해야 한다.

## 키워드
- **Redis**: 인메모리 기반의 Key-Value 저장소로, 빠른 읽기/쓰기 성능과 다양한 자료구조, 원자적 명령을 제공해 캐시뿐 아니라 분산락, 메시지 브로커 등으로도 활용된다.
- **분산락(Distributed Lock)**: 여러 프로세스/서버가 물리적으로 분리된 환경에서 하나의 공유 자원에 대해 동시에 접근하지 못하도록 외부 저장소(Redis, Zookeeper 등)를 통해 제어하는 락 메커니즘.
- **Distributed Lock**: 분산락의 영문 표기. 단일 프로세스 내 락(Local Lock)과 달리 네트워크를 통해 여러 노드 간 상호 배제를 보장해야 하는 어려움이 있다.
- **SETNX**: `SET key value NX`의 축약형 명령으로, 키가 존재하지 않을 때만 값을 설정하는 원자적 연산. 분산락 구현의 가장 기본적인 빌딩 블록이다.
- **Redisson**: Redis를 자바 애플리케이션에서 손쉽게 사용할 수 있도록 분산 객체(Map, Queue 등)와 분산 서비스(Lock, Semaphore 등) API를 제공하는 오픈소스 클라이언트 라이브러리.
- **Lua Script**: Redis가 내장 지원하는 스크립팅 언어로, `EVAL` 명령을 통해 여러 Redis 명령을 하나의 원자적 단위로 실행할 수 있게 해준다. 분산락 해제 시 GET+DEL의 원자성을 보장하는 데 사용된다.
- **Redlock**: 단일 Redis 노드의 장애에 대비해 여러 독립적인 Redis 마스터 노드에 대해 과반수 합의를 통해 락을 획득하는 알고리즘. Redis 공식 문서에서 제안되었으나 안전성에 대한 논쟁이 있다.
- **Watchdog**: Redisson이 제공하는 락 자동 연장 메커니즘. `leaseTime`을 지정하지 않고 락을 획득하면, 락을 보유한 클라이언트가 살아있는 동안 백그라운드 스레드가 주기적으로 TTL을 갱신해 준다.
- **Race Condition(경쟁 상태)**: 둘 이상의 프로세스/스레드가 공유 자원에 동시에 접근하여 실행 순서에 따라 결과가 달라지는 상황. 동시성 제어(락, 트랜잭션 등)를 통해 방지해야 한다.
- **TTL(Time To Live)**: 키가 유효하게 유지되는 시간. 분산락에서는 락을 획득한 클라이언트가 비정상 종료되더라도 일정 시간 후 자동으로 락이 해제되도록 하여 데드락을 방지하는 안전장치 역할을 한다.
