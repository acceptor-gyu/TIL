# Spring Batch 사용을 고려하는 경우

## 개요
Spring Batch는 대용량 데이터를 안정적으로 일괄 처리하기 위한 스프링 생태계의 배치 처리 프레임워크다. 단순히 `@Scheduled`로 반복 실행되는 코드를 작성하는 것과 달리, 재시작(Restart), 재시도(Retry), 건너뛰기(Skip) 같은 내결함성(Fault Tolerance) 기능과 표준화된 실행 메타데이터 관리를 제공한다. "언제 도입을 고려해야 하는가"는 처리 데이터의 규모, 실패 복구 요구 수준, 운영 오버헤드를 얻는 이점과 비교해서 판단해야 한다.

## 상세 내용

### 배치 처리란 무엇인가
- 배치(Batch) 처리는 사용자의 즉각적인 응답을 요구하지 않는 대량의 데이터를 정해진 시점 또는 주기에 한 번에 처리하는 방식이다.
- 온라인(실시간) 처리가 요청 하나에 대해 즉시 응답을 반환해야 하는 것과 달리, 배치 처리는 비동기적으로 장시간 실행되며 처리량(Throughput)과 안정성이 응답 속도보다 우선된다.
- 대표적으로 대용량 데이터 집계, 파일 기반 데이터 이관, 정기 정산/리포트 생성 등이 있으며, 사람이 개입하지 않는 비대화형(non-interactive) 작업이라는 특성을 가진다.

### Spring Batch를 고려하게 되는 대표 상황
- **대용량 데이터의 일괄 처리(ETL, 통계 집계, 정산)**: 수백만 건 이상의 레코드를 읽고, 가공하고, 저장해야 하는 경우 메모리에 전체 데이터를 올리지 않고 스트리밍 방식으로 처리할 수 있다.
- **정기적으로 반복 실행되는 스케줄 기반 작업**: 일 배치, 월 정산처럼 주기적으로 실행되며 실행 이력 관리가 필요한 작업.
- **외부 시스템 연동(파일/DB 간 마이그레이션, 데이터 이관)**: CSV/XML 등 다양한 포맷의 `ItemReader`/`ItemWriter`를 기본 제공하여 이기종 시스템 간 데이터 이동을 표준화할 수 있다.
- **장시간 실행되는 작업의 안정적 수행 요구**: 실행 도중 실패하더라도 처음부터 다시 실행하지 않고, 실패 지점부터 재개할 수 있어야 하는 경우.

### Spring Batch가 제공하는 핵심 가치
- **Chunk 지향 처리(ItemReader / ItemProcessor / ItemWriter)**: 아이템을 한 건씩 읽어(`ItemReader`) 누적하다가, 지정된 커밋 간격(commit-interval)에 도달하면 가공(`ItemProcessor`, 선택)된 아이템들을 묶어 한 번에 기록(`ItemWriter`)하고 트랜잭션을 커밋한다. 전체 데이터를 메모리에 올리지 않고도 대량 처리가 가능한 이유가 여기에 있다.
- **트랜잭션 경계와 커밋 인터벌 관리**: 청크 단위로 트랜잭션이 구성되므로, 청크 내 처리는 전부 성공하거나 전부 롤백된다. 커밋 인터벌 값 조정으로 처리량과 트랜잭션 오버헤드 사이의 균형을 맞출 수 있다.
- **재시작(Restart), 재시도(Retry), 건너뛰기(Skip) 등 내결함성**: 일시적 오류는 재시도로 극복하고, 무시 가능한 데이터 오류는 스킵 정책(`SkipPolicy`)으로 건너뛰며, 잡 자체가 실패하면 마지막으로 완료된 지점부터 재시작할 수 있다.
- **JobRepository를 통한 실행 메타데이터 관리 및 이력 추적**: `Job`/`Step` 실행 상태, 파라미터, 통계(읽은 건수, 쓴 건수, 스킵 건수 등)를 DB에 영속화하여 실행 이력 조회와 재시작 판단의 근거로 사용한다.

### 직접 구현(단순 스케줄러/스크립트) 대비 장점
- **실패 지점부터 재실행 가능한 상태 관리**: `@Scheduled` 메서드나 단순 배치 스크립트는 실패 시 처음부터 다시 실행해야 하는 경우가 많지만, Spring Batch는 `JobRepository`에 저장된 `StepExecution` 상태를 기반으로 이어서 실행할 수 있다.
- **대량 처리 시 메모리 효율(스트리밍 방식)과 성능**: 전체 리스트를 한 번에 메모리에 올리는 방식이 아니라, 청크 단위로 읽고 쓰기 때문에 데이터 규모가 커져도 메모리 사용량이 일정하게 유지된다.
- **표준화된 구조로 유지보수성 및 모니터링 용이**: Job/Step 단위로 구조화되어 있어 팀 간 컨벤션이 통일되고, Micrometer 기반 메트릭이나 Java Flight Recorder 연동 등 관측성 기능도 프레임워크 차원에서 지원한다.

### 도입을 재고해야 하는 경우
- **처리량이 적고 단순한 일회성 작업**: 수십~수백 건 수준의 데이터를 한 번 처리하는 스크립트라면 Job/Step 설정, 메타데이터 테이블(`BATCH_JOB_INSTANCE` 등) 구성 자체가 과도한 비용일 수 있다.
- **실시간 응답이 필요한 요청/응답 성격의 작업**: Spring Batch는 비동기·비대화형 처리를 전제로 설계되어 있어, 사용자 요청에 즉시 응답해야 하는 API 로직에는 적합하지 않다.
- **도입/운영 오버헤드가 얻는 이점보다 큰 경우**: 메타데이터 스키마 관리, 러닝 커브, 잡 파라미터/재시작 정책 설계 등 초기 설정 비용을 고려했을 때 단순 반복 작업 대비 실익이 낮다면 굳이 도입할 필요는 없다.

### 대안 기술과의 비교
- **@Scheduled 단독 사용**: 단순 주기 실행에는 적합하지만, 실행 이력 관리·재시작·스킵/재시도 같은 기능이 없어 직접 구현해야 한다. 소규모, 단순 로직에는 오히려 가볍고 적합할 수 있다.
- **Quartz 스케줄러와의 관계**: Quartz는 "언제 실행할지"를 다루는 스케줄링 전문 라이브러리이고, Spring Batch는 "어떻게 안정적으로 처리할지"를 다루는 배치 처리 프레임워크다. 실무에서는 Quartz(또는 Spring `@Scheduled`, k8s CronJob)로 Job 실행 시점을 트리거하고, 실제 처리 로직은 Spring Batch Job으로 구현하는 조합이 흔하다.
- **메시지 큐 기반 처리, 스트림 처리(Kafka Streams 등)와의 경계**: 메시지 큐/스트림 처리는 이벤트가 발생하는 즉시(또는 짧은 지연으로) 건 단위/스트림 단위로 처리하는 데 적합하고, Spring Batch는 정해진 시점에 대량의 정적 데이터 집합을 일괄 처리하는 데 적합하다. 데이터가 이미 쌓여 있는 상태에서 일괄 마이그레이션/집계가 필요하면 Batch, 실시간에 가깝게 이벤트를 소비해야 한다면 메시징/스트리밍이 더 알맞다.

## 핵심 정리
- Spring Batch는 대용량·정기적·장시간 실행되는 데이터 처리 작업에서 재시작/재시도/스킵 같은 내결함성과 표준화된 실행 이력 관리가 필요할 때 도입을 고려한다.
- 처리량이 적거나 실시간 응답이 필요한 경우, 혹은 도입 오버헤드가 이점보다 크다면 `@Scheduled`나 단순 스크립트로 충분할 수 있다.
- Quartz(스케줄링)와 Spring Batch(처리)는 경쟁 관계가 아니라 상호 보완적으로 함께 사용되는 경우가 많다.

## 기술적 한계와 보완 전략
- **메타데이터 스키마 의존성**: Spring Batch는 `JobRepository`가 사용할 메타데이터 테이블(`BATCH_JOB_INSTANCE`, `BATCH_STEP_EXECUTION` 등)을 요구한다. 스키마 초기화 및 운영 DB 부하를 고려해야 하며, 별도의 스키마/DataSource로 분리하는 것이 일반적인 보완 전략이다.
- **청크 크기(commit-interval) 튜닝의 어려움**: 커밋 인터벌이 너무 작으면 트랜잭션 오버헤드가 커지고, 너무 크면 메모리 사용량과 재시작 시 재처리 범위가 늘어난다. 데이터 특성과 처리 시간을 기반으로 경험적으로 튜닝해야 한다.
- **분산 환경에서의 확장성 한계**: 단일 JVM 내에서의 멀티스레드 Step만으로는 처리량 확장에 한계가 있을 수 있다. Partitioning(파티셔닝)이나 Remote Chunking을 활용해 여러 워커로 작업을 분산시키는 전략으로 보완할 수 있다.
- **실패 원인 분석의 복잡성**: 스킵/재시도 정책이 과도하게 관대하면 실제 데이터 문제를 놓칠 수 있다. `SkipListener`, `ItemProcessListener` 등을 활용해 스킵/재시도 발생 시점을 로깅하고 모니터링하는 보완이 필요하다.

## 키워드
- **Spring Batch**: 대용량 배치 처리를 위한 스프링 기반 프레임워크로, Job/Step 구조와 재시작·재시도·스킵 등 내결함성 기능을 표준화해서 제공한다.
- **Batch Processing(배치 처리)**: 실시간 응답 없이 대량의 데이터를 정해진 시점/주기에 일괄로 처리하는 방식.
- **Chunk 지향 처리**: 아이템을 한 건씩 읽어 지정된 개수(청크)만큼 누적한 뒤, 처리 및 기록을 하나의 트랜잭션으로 묶어 수행하는 Spring Batch의 대표 처리 스타일.
- **ItemReader / ItemProcessor / ItemWriter**: 각각 데이터 읽기, (선택적) 가공, 쓰기를 담당하는 Chunk 지향 처리의 3대 구성 요소.
- **JobRepository**: Job/Step의 실행 상태와 메타데이터를 영속화하여 재시작 및 이력 추적을 가능하게 하는 저장소.
- **Restart / Retry / Skip**: 각각 실패 지점부터 잡을 재실행, 일시적 오류에 대한 재처리, 특정 예외 발생 시 해당 아이템을 건너뛰고 계속 진행하는 내결함성 메커니즘.
- **Step / Job**: Job은 배치 처리 전체를 나타내는 최상위 단위이며, 하나 이상의 Step(개별 처리 단계)으로 구성된다.
- **스케줄링(Quartz, @Scheduled)**: Job이 "언제" 실행될지를 트리거하는 역할을 하며, Spring Batch의 "어떻게 처리할지"와는 별개의 관심사로 함께 조합해서 사용한다.
- **ETL(Extract, Transform, Load)**: 데이터를 추출하고 변환한 뒤 적재하는 작업 패턴으로, Spring Batch의 대표적인 적용 사례 중 하나다.
- **대용량 데이터 처리**: 메모리에 전체 데이터를 올리지 않고 스트리밍 방식으로 처리하여 데이터 규모가 커져도 안정적인 리소스 사용을 유지하는 처리 방식.
