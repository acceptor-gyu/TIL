# 리프레시 토큰 회전 설계 — 클러스터가 필요한가, 토큰에 무엇을 담을까

[온보딩에서 찾은 인증 문제 두 가지](./260901_02_온보딩에서_찾은_인증_문제_두_가지.md)에서 문제 2(멀티키 Lua와 해시 슬롯)를 "현재 구성에서는 발생하지 않는다"까지 확인했지만, 클러스터 모드를 켰을 때를 가정하고 해결 방법을 찾고 싶었다.

안전 조건을 정확히 하고, **애초에 클러스터가 필요한지**를 숫자로 따지고, 고친다면 어떤 키 설계를 고를지, 그리고 그 설계가 요구하는 **토큰 형식 변경이 보안상 괜찮은지**까지 찾아봤다.

> 사내 저장소 기준이라 프로젝트명·계정 ID·도메인 같은 식별자는 일반화해서 적는다.

---

## 안전 조건을 정확히 하면

"인스턴스가 한 대니까 안전하다"는 부정확하다. Redis는 멀티키 명령에서 키들의 슬롯이 다르면, 그 슬롯을 전부 같은 노드가 갖고 있든 말든 거부한다. **소유권을 보는 게 아니라 슬롯 동일성을 본다.**

```
프라이머리 1대 + 리드 레플리카 N대, cluster mode disabled  → 안전
샤드 1개, cluster mode enabled                            → CROSSSLOT 발생
```

관리형 Redis에서 "나중에 샤드를 늘릴 계획으로 cluster mode만 미리 켜두고 샤드는 1개로 시작"하는 구성이 흔하다. 그러면 노드 수는 그대로인데 토큰 갱신이 깨진다. 정확한 안전 조건은 **인스턴스가 한 대라는 것이 아니라 cluster mode가 꺼져 있다는 것**이다. 플랜에 따라 clustering이 기본으로 켜지는 관리형 서비스도 있어서, 인스턴스 타입을 바꾸는 작업만으로도 밟을 수 있다.

## 그런데 클러스터 모드가 필요한가

결론부터: **토큰 저장소 자체가 클러스터를 필요로 할 일은 사실상 없다.** 그리고 이건 "지금은 작으니까"가 아니라 **구조적 상한** 때문이다.

### 처리량 상한이 액세스 토큰 수명에 묶여 있다

리프레시 토큰 저장소의 부하는 사용자 활동량에 비례하지 않는다. **액세스 토큰이 만료될 때만** 회전이 일어난다.

```
회전 QPS = 활성 세션 수 / 액세스 토큰 수명(3600초)
```

| 활성 세션 | 회전 QPS | 대략 메모리 |
|---|---|---|
| 10만 | ~28 | ~20 MB |
| 100만 | ~280 | ~200 MB |
| 1,000만 | ~2,800 | ~2 GB |

메모리는 키 하나당 170~200바이트로 잡은 추정치다. 키 문자열이 86바이트(`refresh-token:{u:123}:` + sha256 hex 64자)이고, 거기에 `dictEntry`·`sds`·`robj` 오버헤드와 `expires` 딕셔너리 엔트리가 붙는다. 값이 userId 숫자 문자열이라 Redis가 `OBJ_ENCODING_INT`로 저장해 값 쪽은 거의 공짜다.

숫자를 보면 **단일 노드가 여유롭다.** 1,000만 활성 세션도 4GB 인스턴스에 들어가고, 2,800 QPS는 Redis 단일 스레드 처리량(수만~십만 ops/sec)의 몇 퍼센트다. 게다가 TTL 30일이 데이터 상한을 강제하므로 **무한히 증가하지 않는다.** 캐시나 이벤트 스트림과 달리 토큰 저장소는 샤딩이 필요하지 않다.

### 그런데도 켜지는 세 가지 경로

토큰 저장소가 클러스터를 만나는 건 필요해서가 아니라 **끌려들어가서**다.

**1. HA와 혼동.** 가장 흔하다. 고가용성은 **복제 + 자동 페일오버**에서 나오고, 클러스터 모드와 별개다. 관리형 Redis는 `cluster mode disabled`에서도 프라이머리 + 레플리카 + 자동 페일오버를 제공한다(자체 운영이면 Sentinel). 위 표에서 "안전"으로 표시한 구성이고, **토큰 저장소가 원하는 것이다.**

**2. 인스턴스 공유.** 이게 현실적인 경로다. 캐시·레이트 리밋·세션·큐를 한 Redis에 얹고, 그중 **캐시가 커져서** 샤딩이 필요해지면 토큰 저장소가 같이 클러스터로 넘어간다. 토큰 쪽은 여전히 200MB인데.

**3. 플랫폼 기본값.** 위에 적은 관리형 함정 그대로다. 여기에 하나 더 — **일부 관리형 서버리스 티어는 클러스터 모드가 항상 켜져 있어 선택지가 없다.** 인스턴스 타입을 고르는 것만으로 밟는다.

### 켜면 잃는 것

| 잃는 것 | 영향 |
|---|---|
| 멀티키 Lua | 이 문제 전체 |
| 크로스 슬롯 `MGET`/`MULTI` | 운영·배치 정리 스크립트가 복잡해짐 |
| `SCAN` 한 번으로 전체 순회 | 노드별로 돌려야 함 → 디버깅 비용 |
| 비용 | 관리형은 보통 최소 3샤드 × 레플리카. 프라이머리+레플리카 2노드 대비 3배 이상 |
| 운영 표면 | 리샤딩, Lettuce 토폴로지 리프레시 튜닝(`adaptive refresh`). 잘못 잡으면 페일오버 중 스테일 토폴로지로 에러 |

얻는 건 필요 없는 수평 확장뿐이다.

### 클러스터보다 훨씬 중요한 결정 두 개

이 질문을 공부하다 알게 된 것은, 토큰 저장소에서 **클러스터 모드보다 사고를 크게 내는 설정**이 따로 있다는 것이다.

**`maxmemory-policy`를 `noeviction`으로.** 캐시와 같은 인스턴스를 쓰면서 정책이 `allkeys-lru`면, 메모리 압박 시 **리프레시 토큰이 evict되어 무작위 사용자가 로그아웃된다.** `volatile-lru`도 안전하지 않다 — 리프레시 토큰은 TTL이 있으니 후보에 들어간다. 그리고 이 정책은 **인스턴스 단위**라서 `SELECT`로 논리 DB를 나눠도 회피되지 않는다. 결국 **캐시와 물리 인스턴스를 분리**하는 게 답이다. `noeviction`이면 메모리가 차도 기존 세션은 살아 있고 **신규 로그인만 실패한다** — 올바른 실패 모드지만 메모리 알림이 필수다.

**영속성과 페일오버 시 유실.** 토큰 저장소는 "캐시 같지만 유실이 사용자에게 보이는" 드문 경우다. 데이터가 날아가면 전원 재로그인이고, 비동기 복제라 페일오버 시 최근 몇 초 쓰기가 유실되어 **그 시점에 회전 중이던 사용자만 재로그인**한다. 클러스터 모드는 여기에 전혀 도움이 안 된다. 감당할 수 있는 범위인지만 정하고, 아니면 AOF `everysec`를 켜는 문제다.

### 그래서 결정을 두 개로 쪼갠다

| 결정 | 답 | 근거 |
|---|---|---|
| 클러스터 모드를 켤 것인가 | **아니오** | 처리량 상한이 구조적으로 낮고, 잃는 게 더 많다 |
| 키를 클러스터 안전하게 설계할 것인가 | **예** | 뒤에 나올 역방향 인덱스가 키 이름을 밖에서 받아야 하고, `{...}` 추가는 문자열 리터럴 한 조각으로 **공짜** |

해시 태그는 standalone에서 완전히 무의미한 문자열이다(슬롯 개념 자체가 없다). 즉 **지금 켤 계획이 없어도 비용이 0이고**, 반대 방향으로는 비대칭이 있다 — 나중에 붙이려면 전원 재로그인이나 이중 조회 전환 기간이 필요하다. 키 형식은 코드가 아니라 저장된 데이터다.

## 옵션 A. Lua를 버리고 `GETDEL` — 가장 싸다

```kotlin
override fun rotate(refreshToken: String): RefreshTokenRotationOutput {
    val userId = redisTemplate.opsForValue().getAndDelete(keyOf(refreshToken))
        ?.toLongOrNull() ?: throw SecurityException(INVALID_REFRESH_TOKEN_MESSAGE)
    val newToken = UUID.randomUUID().toString()
    redisTemplate.opsForValue().set(
        keyOf(newToken),
        userId.toString(),
        Duration.ofSeconds(properties.refreshTokenExpirationSeconds),
    )
    ...
}
```

회전에서 지켜야 할 핵심은 **"옛 토큰이 정확히 한 번만 소비된다"** 이다. `GETDEL`(Redis 6.2+) 한 명령이 그걸 원자적으로 보장한다. 동시 요청 두 건 중 하나만 값을 받으므로 세션 복제가 막힌다. 명령이 둘로 나뉘어 각자 라우팅되니 `CROSSSLOT`도 없다.

대가는 두 명령 사이에서 죽으면 세션이 소실된다는 것이다(→ 재로그인). 다만 이미 `reissue()`가 액세스 토큰 발급 실패 시 새 리프레시 토큰까지 폐기하는 보상 처리를 하고 있어서, 성격이 같은 실패 모드가 하나 늘어나는 정도다.

**한계**: 뒤에 나올 역방향 인덱스로 가는 길이 막힌다. 인덱스까지 원자적으로 갱신하려면 결국 멀티키 스크립트가 필요하기 때문이다.

## 옵션 B. 사용자 단위 해시 태그

```
refresh-token:{u:123}:<sha256>      ← 한 사용자의 옛/새 토큰이 항상 같은 슬롯
```

Redis 클러스터는 키 이름에 `{...}`가 있으면 **중괄호 안의 문자열만으로 슬롯을 계산한다.** 그래서 같은 사용자의 토큰끼리는 항상 같은 노드에 모이고, 사용자끼리는 정상적으로 흩어진다. Lua를 그대로 유지하면서 샤딩도 살릴 수 있다.

```
❌ {refresh-token}:<hash>   → 전 사용자 토큰이 한 슬롯. 샤딩이 무의미해지고 핫스팟이 된다
✅ refresh-token:{u:123}:<hash>   → 사용자 단위로 분산되면서 회전은 단일 슬롯
```

대신 **회전 시점에 토큰 문자열만 보고 userId를 알아야** 키를 만들 수 있다. 지금 토큰은 순수 UUID라 불가능하므로 형식을 바꿔야 한다.

```kotlin
// 토큰: "123.<uuid>"
private fun keyOf(token: String): String {
    val userId = token.substringBefore('.')          // 라우팅 계산에만 쓴다
    return "refresh-token:{u:$userId}:${hash(token)}"
}
```

여기서 반드시 지켜야 할 것 하나. **토큰에서 파싱한 userId를 신원으로 신뢰하면 안 된다.** 그건 클라이언트가 보낸 문자열이다. 진실은 어디까지나 Redis가 `GET`으로 돌려준 값이고, 파싱값은 슬롯 계산 용도로만 쓴다. 둘이 다르면 거부한다.

```kotlin
val storedUserId = /* Lua가 반환한 값 */
require(storedUserId == parsedUserId) { INVALID_REFRESH_TOKEN_MESSAGE }
```

## 두 문제가 만나는 지점

앞 글에서 문제 1의 3층으로 남겨둔 "이미 발급된 리프레시 토큰을 즉시 폐기"와, 여기서 다루는 슬롯 설계는 **같은 변경 하나로 해결된다.** 역방향 인덱스가 옵션 B의 해시 태그를 전제로 하기 때문이다.

지금은 키가 토큰 해시라서 `userId`로 세션을 되찾을 방법이 아예 없다. 그래서 사용자 → 토큰 인덱스를 추가한다.

```
user-sessions:{u:123}   ZSET   member = 토큰 해시, score = 만료 epoch
```

`{u:123}`이 같으므로 토큰 키와 같은 슬롯이고, 덕분에 회전 스크립트가 둘을 한 원자 단위로 갱신할 수 있다.

```lua
local userId = redis.call('GET', KEYS[1])
if not userId then return nil end
redis.call('SET', KEYS[2], userId, 'EX', ARGV[1])
redis.call('DEL', KEYS[1])
redis.call('ZREM', KEYS[3], ARGV[2])                      -- 옛 해시 제거
redis.call('ZADD', KEYS[3], ARGV[3], ARGV[4])             -- 새 해시 등록
redis.call('ZREMRANGEBYSCORE', KEYS[3], '-inf', ARGV[5])  -- 만료분 정리
redis.call('EXPIRE', KEYS[3], ARGV[1])
return userId
```

**Set이 아니라 ZSET을 쓴 이유**가 있다. 토큰 키는 TTL로 알아서 사라지지만 인덱스 멤버는 남아 고아가 된다. score에 만료 시각을 넣어두면 `ZREMRANGEBYSCORE` 한 줄로 정리된다. 시각은 스크립트 안에서 `TIME`을 부르지 않고 밖에서 `ARGV`로 넘긴다(효과 복제라 결정론 제약은 없지만, 키 이름과 마찬가지로 입력은 밖에서 주는 편이 안전하다).

이 인덱스가 생기면 한 번에 열리는 것들이 있다.

| 기능 | 구현 |
|---|---|
| 정지 즉시 세션 종료 | `ZRANGE` → 토큰 키 일괄 `DEL` (문제 1의 나머지 절반) |
| 전체 기기 로그아웃 | 같은 연산 |
| 토큰 재사용 탐지 | 옛 키를 지우는 대신 무효 표식으로 남기고, 재제출되면 그 사용자의 토큰 계열 전체 폐기 |

세 번째는 OAuth 2.0 Security BCP의 권고다. 지금 구조에서는 탈취된 토큰을 공격자가 먼저 쓰면 정상 사용자가 401을 받고 조용히 재로그인하는 동안 공격자가 계속 회전한다. 계열 폐기가 있으면 그 순간 둘 다 끊긴다.

**`SCAN`으로 전체를 훑어 값(userId)을 비교하는 방법은 답이 아니다.** `KEYS`는 O(N) 전수 스캔이라 단일 스레드를 점유하고, `SCAN`도 커서로 쪼갤 뿐 전수 순회인 건 같다. 세션 수가 늘어나면 그대로 장애가 된다.

## 옵션 B의 전제 — 토큰에 userId를 넣어도 되는가

역방향 인덱스가 옵션 B를 요구하고, 옵션 B가 토큰 형식 변경을 요구한다. 그러면 **userId를 토큰에 노출하는 게 보안상 괜찮은가**를 따져야 한다.

처음에는 "액세스 토큰의 `sub` 클레임에도 이미 들어 있으니 새로 생기는 노출은 없다"고 정리했다. 다시 보니 그 근거는 절반만 맞고, **실제 안전 근거는 다른 데 있고 실제 위험도 다른 데 있었다.**

### 왜 위조가 불가능한가 — 해시가 프리픽스를 묶는다

"파싱값을 신원으로 신뢰하지 말라"는 원칙보다 강한 보장이 이미 있다. **해시가 프리픽스를 포함**하기 때문이다.

```
key = refresh-token:{u:$parsedUserId}:${hash(token)}   // hash는 프리픽스까지 포함
```

공격자가 456번 사용자의 토큰 `456.abc`를 `123.abc`로 바꿔 제출하면:

- `parsedUserId = 123`, `hash("123.abc") ≠ hash("456.abc")`
- 조회 키가 존재하지 않음 → 거부

즉 **키를 여는 토큰은 발급된 그 문자열 하나뿐**이라, `storedUserId == parsedUserId`는 구조적으로 항상 참이다. `require`는 도달 불가능한 방어선이지만 공짜이고 위 불변식이 깨지는 순간 잡아주므로 그대로 둔다. 대신 **"왜 항상 참인지"를 주석으로 남겨야 한다.** 없으면 나중에 죽은 코드로 지워진다.

### 1. 진짜 위험은 지금 코드가 아니라 드리프트다

위 안전성은 전부 "Redis 조회가 성공한 뒤에만 userId를 쓴다"에 의존한다. **조회 이전에 `parsedUserId`를 쓰는 경로가 하나라도 생기면 그때 뚫린다.**

| 생기기 쉬운 경로 | 공격 |
|---|---|
| 갱신 엔드포인트 rate limit을 userId로 키잉 | `<victimId>.aaa`를 반복 전송해 **피해자의 갱신 쿼터만 소진** → 사실상 표적 로그아웃 |
| 메트릭/로그 라벨에 parsedUserId | 임의값 무한 주입 → 라벨 카디널리티 폭발 |
| 해시 태그 자체 | 클라이언트가 **조회가 어느 슬롯으로 갈지 결정한다.** 실패할 조회를 한 슬롯에 집중시켜 특정 샤드 핫스팟 |

셋 다 인증 우회는 아니지만 **미인증 입력이 서버 내부 키 공간·라우팅·집계 키를 정한다**는 같은 성질에서 나온다. 처방도 문제 1과 같다 — 개별 `if`가 아니라 타입을 분리해 오용을 어렵게 만든다.

```kotlin
/** 슬롯 계산 전용. 신원으로 쓰지 말 것. */
@JvmInline value class RoutingHint(val raw: Long)
```

`Long`으로 들고 다니면 `AccessTokenPrincipal(userId, ...)`에 그대로 들어가는 사고가 언제든 난다. `findActiveById` 이름을 정직화한 것과 정확히 같은 처방이다.

### 2. 프리픽스 검증이 빠져 있다

`token.substringBefore('.')`는 **점이 없으면 문자열 전체를 반환한다.**

- 구형 UUID 토큰(`abc-def`) 제출 → 키가 `refresh-token:{u:abc-def}:...` → 마이그레이션 기간에 조용히 오작동
- 10MB 문자열 제출 → 그대로 Redis 키 이름에 편입

키 주입은 안 된다(단일 키 명령이라 파싱이 없다). 하지만 파싱 단계에서 끊는 게 맞다.

```kotlin
val userId = token.substringBefore('.', missingDelimiterValue = "")
    .toLongOrNull()?.takeIf { it > 0 }
    ?: throw SecurityException(INVALID_REFRESH_TOKEN_MESSAGE)
```

### 3. `sub`에 있다 ≠ 노출이 같다

두 토큰의 **수명과 보관 위치가 다르다.**

| | 액세스 토큰 | 리프레시 토큰 |
|---|---|---|
| 수명 | 1시간 | 30일 |
| 전송 | 매 요청 | 갱신 시에만 |
| 보관 | 보통 메모리 | httpOnly 쿠키 / localStorage / 모바일 키체인·**백업 포함** |

`sub`는 1시간마다 사라지지만 리프레시 토큰은 **30일 동안 클라이언트 저장소에 남는다.** 여기에 userId가 들어가면 서버 액세스 로그(POST 본문), 모바일 OS 백업, 에러 트래커 스냅샷에 사용자 식별자가 durable하게 남는다. 인증 우회는 아니지만 로그를 PII로 취급해야 하는 범위가 넓어지는 건 사실이다. 순차 정수 userId를 쓰면 가입 순서·총 사용자 수도 함께 드러난다.

### 4. 유출 토큰의 주인을 오프라인에 식별할 수 있게 된다

기존 순수 UUID는 **불투명했다.** 로그에서 토큰을 긁은 공격자는 그게 누구 것인지 알려면 실제로 써봐야 했고, 쓰는 순간 회전되어 소비되고 탐지 대상이 된다. 프리픽스가 붙으면 **쓰지 않고 분류·선별**이 가능해진다 — 어드민 userId만 골라 쓰는 식으로. 위에서 본 재사용 탐지가 노리는 시나리오를 공격자 쪽에서 조금 쉽게 만든다.

여기 딸린 필수 조건 하나. **UUIDv4를 유지해야 한다.** v4는 122비트 CSPRNG라 프리픽스가 붙어도 표적 추측이 불가능하다. 그런데 요즘 유행하는 **UUIDv7로 바꾸면 위험하다** — 상위 48비트가 타임스탬프라 랜덤이 74비트로 줄고, `발급 시각(≈추정 가능) + userId(알려짐)`가 붙으면 남는 미지 영역이 실질적으로 더 좁아진다. 토큰 생성기에 "v7로 바꾸지 말 것" 주석을 남겨두는 게 좋다.

## 더 나은 대안 — 세션 패밀리 ID

위 네 가지를 정리하다 알게 된 게 있다. "해시 태그를 쓰려면 userId를 넣어야 한다"고 생각했는데, **제3의 값을 넣는 선택지가 빠져 있었다.**

```
토큰            <familyId>.<uuid>              familyId = 랜덤 16바이트 (userId 아님)
토큰 키         refresh-token:{f:<familyId>}:<hash>
소유자          session-owner:{f:<familyId>}   → userId
사용자 인덱스   user-sessions:{u:123}  ZSET  member = familyId  ← 회전 시 안 바뀜
```

핵심은 **`familyId`가 회전에 걸쳐 불변**이라는 점이다. 그래서 회전 스크립트는 `{f:...}` 아래 키들만 만지고 — 단일 슬롯, `CROSSSLOT` 없음 — `user-sessions`는 **아예 건드리지 않는다.** 위에서 `ZREM`/`ZADD`로 인덱스를 갱신하던 두 줄이 사라지고, 고아 멤버 문제도 줄어든다(멤버가 토큰마다가 아니라 세션마다 하나).

| | 옵션 B (userId 프리픽스) | 패밀리 ID |
|---|---|---|
| 토큰에 드러나는 것 | userId | 무의미한 난수 |
| 회전 원자성 | 단일 슬롯 ✅ | 단일 슬롯 ✅ |
| 회전이 인덱스를 건드리나 | 예 (`ZREM`+`ZADD`) | **아니오** |
| 정지 시 전체 세션 종료 | `ZRANGE` → 토큰 키 `DEL` | `ZRANGE` → 패밀리별 `DEL` (클라이언트에서 멀티 슬롯, Lua 아님 → 문제없음) |
| 재사용 탐지 폐기 단위 | 사용자 전체 | **세션 계열** — 탈취된 세션만 끊고 나머지 기기는 살린다 |
| 로그/백업 PII | userId 포함 | 없음 |

마지막 두 행이 크다. 계열 폐기를 userId 단위로 하면 **토큰 하나가 재사용될 때 정상 사용자의 모든 기기가 로그아웃된다.** 패밀리 단위면 탈취된 계열만 끊는다. OAuth 2.0 Security BCP가 말하는 "token family"도 원래 이 단위다.

비용은 `session-owner:{f:...}` 키 하나 추가 — 회전 스크립트 안에서 같은 슬롯이므로 조회가 공짜다.

## 우선순위

| | 작업 | 비용 | 지금 해야 하나 |
|---|---|---|---|
| 1 | `issue()`에 정지 검사 추가 | 3줄 | **예.** 실제 구멍이고 즉시 막힌다 |
| 2 | `findActiveById` 이름 정직화 + 공통 게이트 | 반나절 | **예.** 호출부가 여섯 곳뿐인 지금이 가장 싸다 |
| 3 | `maxmemory-policy` 확인 + 캐시와 인스턴스 분리 | 설정 | **예.** 잘못돼 있으면 무작위 로그아웃이 이미 나고 있다 |
| 4 | 토큰에 패밀리 ID 포함 + 해시 태그 키 설계 | 하루 | **5번을 할 거라면 예.** 이유는 아래 |
| 5 | ZSET 역방향 인덱스 | 1~2일 | 어드민(정지) 에픽과 함께 |
| 6 | deny-list / 재사용 탐지 | — | 요구사항이 생기면 |

3번을 새로 넣었다. 클러스터를 파다가 나온 건데 **클러스터보다 먼저이고 더 싸다.**

4번이 판단이 갈리는 지점이다. 이걸 "클러스터 대비"로만 정당화하면 근거가 약하다. 클러스터로 갈 계획이 없으면 안 해도 되는 일이 되기 때문이다. **실제 근거는 5번(역방향 인덱스)의 전제라는 쪽이다.**

standalone에서도 제약이 남는다. 회전 스크립트가 인덱스 키를 갱신하려면 그 키 이름을 **호출 전에** 알아야 하는데, userId는 스크립트 안에서 `GET`을 한 뒤에야 나온다.

```lua
local userId = redis.call('GET', KEYS[1])
redis.call('ZADD', 'user-sessions:'..userId, ...)   -- 키 이름을 안에서 조립
```

이건 standalone에서는 **동작한다.** 다만 Redis 문서가 명시적으로 금지하는 패턴이다.

> Scripts **should never** access keys with programmatically-generated names or based on the contents of data structures stored in the database.

그래서 선택은 이렇게 된다.

| | 키 이름을 얻는 방법 | standalone | 클러스터 | 비고 |
|---|---|---|---|---|
| ① | Lua 안에서 조립 | 동작 | 깨짐 | 문서가 금지하는 패턴 |
| ② | 토큰에 식별자를 넣어 밖에서 전달 | 동작 | 동작 | 토큰 형식 변경 필요 |

**클러스터 여부와 무관하게, 규칙을 지키면서 역방향 인덱스를 만들려면 ②가 필요하다.** 클러스터 안전성은 부수 효과다. 여기에 **키 형식은 코드가 아니라 저장된 데이터**라는 점이 겹친다. 나중에 바꾸려면 기존 키를 전부 버리거나(= 전원 재로그인) 두 형식을 동시에 조회하는 전환 기간을 둬야 한다. 지금은 저장된 토큰이 며칠치밖에 없어서 사실상 공짜다.

**역으로 5번을 안 할 거라면 4번도 필요 없다.** 그 경우 답은 옵션 A(`GETDEL`)다. 키 형식을 안 건드리고 클러스터 안전성만 얻고 끝난다.

```
어드민(정지) 에픽으로 세션 종료·전체 로그아웃이 필요한가?
├─ 예   → 패밀리 ID + 해시 태그 + 역방향 인덱스   (토큰 형식을 지금 바꾼다)
└─ 아니오 → 옵션 A만                              (Lua 제거, 키 형식 유지)
```

어드민 에픽이 로드맵에 있으므로 나는 패밀리 ID를 택할 것 같다. **클러스터 모드는 켜지 않으면서 키만 클러스터 안전하게** 가는 조합이다.

**대안 하나.** 토큰 형식 변경이 부담이면, 갱신 요청에 만료된 액세스 토큰을 함께 받아 `sub`에서 userId를 꺼내는 방법도 있다(서명은 검증하고 `exp`만 무시). 서버 저장 형식을 안 건드리는 장점이 있지만, 클라이언트가 만료 토큰을 보관·전송해야 하고 `exp`를 의도적으로 무시하는 코드가 인증 경로에 생긴다. 나는 이게 더 불편해 보인다.

## 느낀 점

**"고칠 수 있는 문제"와 "지금 고쳐야 싼 문제"는 다르다.** 문제 1은 언제 고쳐도 비용이 비슷하다. 코드 몇 줄이다. 반면 이 문제는 저장된 데이터의 형식 문제라서 **시간이 갈수록 비싸진다.** 지금은 토큰 몇 개지만, 사용자가 늘고 나면 같은 변경이 마이그레이션 계획과 공지가 필요한 일이 된다. 문제의 심각도만 보고 우선순위를 정하면 이런 걸 놓친다.

**"확장성 대비"와 "되돌리기 힘든 형식 정하기"를 구분하게 됐다.** 클러스터가 필요한지 숫자로 따져보니 답이 명확히 "아니오"였다. 그런데 그게 "해시 태그도 필요 없다"로 이어지지 않는다는 게 이번의 핵심이었다. **필요 없는 인프라는 안 켜면 되고, 되돌리기 힘든 형식은 미리 정해두는 게 싸다.** 둘을 하나의 "오버엔지니어링" 판단으로 묶으면 잘못된 쪽을 고른다.

**용량 산정을 해보면 논쟁이 끝난다.** "클러스터 필요할까요"는 취향 논쟁이 되기 쉬운데, 회전 QPS가 `활성 세션 / 액세스 토큰 수명`으로 상한이 걸린다는 걸 계산해보니 1,000만 세션에서도 2,800 QPS였다. **부하가 사용자 수가 아니라 토큰 수명에 묶여 있다**는 구조를 본 게 답보다 유용했다.

**정작 위험한 건 내가 안 보던 설정이었다.** 클러스터 모드를 며칠 파는 동안, `maxmemory-policy`가 `allkeys-lru`면 무작위 로그아웃이 이미 나고 있다는 건 생각도 못 했다. **가능성 있는 미래 장애를 파기 전에 지금 켜져 있는 설정을 먼저 읽어야 한다.**

**프리픽스에 굳이 의미를 담을 이유가 없었다.** "해시 태그가 필요하다 → 회전 시점에 userId를 알아야 한다 → 토큰에 userId를 넣자"까지 한 번에 갔는데, 실제 요구는 "**같은 세션의 옛/새 토큰이 같은 슬롯**"이었을 뿐이다. userId는 그걸 만족하는 여러 값 중 하나이고, 하필 의미를 가진 값이었다. **요구사항을 한 단계 추상적으로 다시 읽으면 노출을 0으로 만드는 선택지가 나온다.**

**보안 검토는 "지금 뚫리나"가 아니라 "언제 뚫리게 되나"로 물어야 했다.** 해시가 프리픽스를 묶어서 지금은 위조 불가인데, 그 안전성이 "Redis 조회 뒤에만 userId를 쓴다"는 **관행**에 의존하고 있었다. 6개월 뒤 누군가 rate limit을 추가하면 깨진다. 결국 여기서도 답이 검사 추가가 아니라 타입 분리였다.

## 정리

- 클러스터에서 멀티키 Lua는 해시 태그로 슬롯을 묶어야 한다. `{}` 안을 **세션/사용자 단위**로 잡아야 샤딩이 살아남는다
- **토큰 저장소는 클러스터가 필요해지지 않는다.** 회전 QPS가 `활성 세션 / 액세스 토큰 수명`으로 상한이 걸리고, TTL이 데이터 상한을 강제한다
- 고가용성은 **복제 + 자동 페일오버**에서 온다. 클러스터 모드와 다른 축이다
- **`maxmemory-policy`가 클러스터보다 중요하다.** `allkeys-lru`/`volatile-lru`는 리프레시 토큰을 evict한다. 정책은 인스턴스 단위이므로 캐시와 물리 분리가 답이다
- 그래도 **키는 클러스터 안전하게** 설계한다. 해시 태그는 standalone에서 공짜이고, 나중에 붙이려면 전원 재로그인이다
- 키 이름을 Lua 안에서 조립하면 standalone에서는 되지만 문서가 금지하는 패턴이다. **역방향 인덱스를 규칙대로 만들려면 키 이름 재료를 밖에서 넘겨야 한다**
- 토큰에서 파싱한 값은 **라우팅에만** 쓰고, 신원의 진실은 저장소가 돌려준 값으로 삼는다. 해시가 프리픽스를 포함하면 이 불변식이 구조적으로 보장되지만, **조회 이전에 파싱값을 쓰는 경로가 생기면 깨진다**
- 프리픽스는 **userId가 아니라 무의미한 패밀리 ID**로. 노출이 0이 되고, 회전이 인덱스를 건드리지 않고, 계열 폐기 단위가 세션이 된다
- 역방향 인덱스는 ZSET으로. score에 만료 시각을 넣어 고아 멤버를 스스로 정리하게 한다
- **키 형식은 코드가 아니라 데이터다.** 바꿀 거면 데이터가 적을 때 바꾼다
