# 온보딩에서 찾은 인증 문제 두 가지 — 정지 계정과 Redis 클러스터 함정

[새로 합류한 프로젝트 - 셀프 온보딩](./260901_01_새로_합류한_프로젝트_셀프_온보딩.md)하면서 문제 두 건을 찾았다. 찾은 것까지는 좋은데 "그래서 어떻게 고칠 건데"가 남았다. 이 글은 그 후속으로, 문제 1의 해결책과 문제 2의 발생 조건을 정리한 기록이다.

**문제 1은 `if` 한 줄로 끝날 줄 알았는데 구조 문제였고, 문제 2는 지금 당장은 터지지 않는 문제였다.**

> 사내 저장소 기준이라 프로젝트명·계정 ID·도메인 같은 식별자는 일반화해서 적는다.

---

## 문제를 다시 정리하면

**문제 1.** 계정을 정지시켜도 이미 로그인한 사용자는 계속 API를 쓸 수 있다. 정지 검사가 소셜 로그인 경로에만 있고, 토큰 갱신 경로에는 없다. 30일짜리 리프레시 토큰을 무한히 회전시키면 정지가 사실상 "새 로그인 차단"에 그친다.

**문제 2.** 리프레시 토큰 회전이 Lua 스크립트로 옛 키와 새 키 두 개를 만진다. Redis 클러스터에서 Lua가 선언한 키는 전부 같은 해시 슬롯에 있어야 하는데, 두 토큰 해시는 다른 슬롯으로 흩어진다. **cluster mode를 켜는 순간(샤드가 1개여도)** 토큰 갱신 전체가 `CROSSSLOT`으로 실패한다.

---

## 먼저: 문제 1의 범위가 생각보다 넓었다

해결책을 짜기 전에 `isSuspended()`가 호출되는 곳을 모두 찾아봤다.


```
SocialAuthenticationService   ← 검사함 (소셜 로그인)
UserAccessTokenService        ← 검사 안 함 (토큰 갱신)
ProfileImageService           ← 검사 안 함 (프로필 이미지 발급·확정·교체)
AccountWithdrawalService      ← 검사 안 함 (탈퇴 — 허용해도 문제 없음)
```

**`isSuspended()`를 부르는 곳이 전체에서 한 군데였다.** 정지된 사용자가 토큰만 갱신하는 게 아니라 프로필 이미지도 바꿀 수 있다는 뜻이다.

이 결과가 해결책의 방향을 바꿨다. 처음에는 "갱신 경로에 `if` 한 줄 추가"로 끝날 줄 알았는데, 호출부가 여섯 곳인데 검사가 하나면 이건 **빠뜨린 사고가 아니라 빠뜨리기 쉬운 구조**다. 같은 방식으로 `if`를 다섯 개 더 추가하면 일곱 번째 호출부에서 또 빠진다.

# 문제 1 해결 전략

### 1층. 지금 바로 막기 (3줄)

```kotlin
override fun issue(userId: Long): AccessTokenOutput {
    val user = userReader.findActiveById(userId)
        ?: throw IllegalArgumentException(USER_NOT_FOUND_MESSAGE)
    if (user.isSuspended()) throw AccountSuspendedException()   // 추가
    return accessTokenIssuer.issue(AccessTokenPrincipal(userId, user.systemRole))
}
```

`AccountSuspendedException`과 전역 예외 핸들러 매핑이 이미 있어서 추가로 만들 게 없다. 이 세 줄로 **노출 창이 무기한에서 최대 1시간(액세스 토큰 잔여 수명)으로 줄어든다.** 투입 대비 효과가 가장 큰 변경이다.

### 2층. 구조로 막기 — 이름이 거짓말을 하고 있었다

근본 원인은 메서드 이름이다.

```kotlin
fun findActiveById(id: Long): User? = userRepository.findByIdAndDeletedAtIsNull(id)
```

이름은 `Active`인데 실제로는 `deletedAt IS NULL`만 본다. `status`는 안 본다. 호출하는 쪽에서는 "active를 가져왔으니 쓸 수 있는 사용자겠지"라고 읽게 된다. **이름이 보장하지 않는 것을 보장하는 것처럼 읽히면, 검사를 빠뜨리는 게 기본값이 된다.**

그래서 이름을 정직하게 바꾸고, 인증 경로가 쓸 진입점을 따로 만든다.

```kotlin
// UserReader
fun findNotDeletedById(id: Long): User? =            // 하는 일을 그대로 이름에
    userRepository.findByIdAndDeletedAtIsNull(id)

/** 인증된 요청이 사용하는 유일한 진입점. 삭제와 정지를 함께 본다. */
fun requireUsableById(id: Long): User =
    findNotDeletedById(id)?.also { if (it.isSuspended()) throw AccountSuspendedException() }
        ?: throw IllegalArgumentException(USER_NOT_FOUND_MESSAGE)
```

인증 경로는 전부 `requireUsableById`만 쓰고, 어드민처럼 정지 계정 자체를 다뤄야 하는 곳만 `findNotDeletedById`를 쓴다. 그러면 **검사를 건너뛰는 것이 실수가 아니라 명시적인 선택**이 된다. 새로 합류한 사람이 여덟 번째 호출부를 추가할 때도 자연스럽게 안전한 쪽을 고르게 된다.

이건 이 프로젝트가 이미 여러 곳에서 쓰고 있는 "잘못된 상태로 뜨느니 안 뜬다" 철학과 같은 결이다. 설정 자리표시자가 해석되지 않으면 기동을 막는 것과 똑같이, **위험한 경로를 아예 부르기 어렵게 만든다.**

### 3층. 1시간마저 없애야 한다면

정지 즉시 차단이 요구사항이 되면 무상태를 일부 포기해야 한다. 요청마다 DB를 보는 건 비싸니 Redis deny-list가 현실적이다.

```
정지 시   SET suspended-user:<userId> 1 EX 3600   (= 액세스 토큰 최대 수명)
요청 시   GET suspended-user:<sub>  → 있으면 403
```

TTL을 액세스 토큰 수명과 같게 두는 것이다. 그 시간이 지나면 키가 알아서 사라지고, 그 뒤로는 2층의 갱신 차단이 막아준다. **정지 상태를 영구 저장할 필요가 없다** — 영구 상태는 DB의 `status`가 들고 있고, Redis는 "아직 살아 있는 액세스 토큰을 무효화하는 창"만 담당한다.

다만 정지 기능(어드민 에픽) 자체가 아직 구현 범위에 없다. 지금 필요한 건 1~2층이다.

# 문제 2 — 발생 조건 확인

### 지금 설정은 standalone이다

해결 전략을 고르기 전에 이 문제가 실제로 언제 터지는지부터 확정해야 한다. 지금 설정은 이렇다.

```yaml
spring:
  data:
    redis:
      host: ${REDIS_HOST:localhost}
      port: ${REDIS_PORT:6379}
```

`cluster.nodes`가 없으므로 Lettuce가 standalone으로 붙는다. 해시 슬롯은 **클러스터 모드에만 존재하는 개념**이라, standalone은 단일 키스페이스여서 멀티키 Lua든 `MULTI/EXEC`든 키가 어디로 흩어지든 상관없다. **즉 현재 구성에서는 이 문제가 발생하지 않는다.**

지금 구성에서는 터지지 않는다는 것까지가 이 글의 범위다. 다만 이 안전은 조건부이고, **정확한 안전 조건과 "그럼 클러스터를 쓸 것인가"부터 시작하는 해결 전략은 분량이 커져서 후속 글로 분리했다.**

## 느낀 점

**이름이 틀리면 검사가 빠진다.** `findActiveById`가 `deleted_at`만 보는 걸 알아챈 뒤로, 나는 이름을 "보장"으로 읽는 습관이 있다는 걸 알았다. `Active`라고 쓰여 있으면 그 뒤를 안 의심한다. 그래서 이번 해결책의 절반은 로직 추가가 아니라 **이름을 정직하게 바꾸는 것**이 됐다. 검사를 추가하는 것보다 검사를 빠뜨리기 어렵게 만드는 게 오래 간다.

**전수 조사를 먼저 한 게 결정적이었다.** 처음엔 갱신 경로 한 곳만 고치면 되는 줄 알았다. `grep` 한 번으로 호출부 여섯 곳 중 한 곳만 검사한다는 걸 보고 나서야 "개별 수정"이 아니라 "구조 변경"이 답이라는 판단이 섰다. **문제를 발견했을 때 바로 고치지 말고 같은 종류가 몇 개인지 먼저 세어보는 것**, 이번에 얻은 습관이다.

**당장 안 터지는 문제를 어떻게 다룰지가 남았다.** 문제 2는 현재 구성에서 발생하지 않는다. 그래서 "안 고쳐도 된다"로 끝낼 수도 있었다. 그런데 리프레시 토큰 키 형식은 **코드가 아니라 저장된 데이터**라서, 나중에 바꾸는 비용이 지금과 같지 않다. **발생 조건을 확인하는 것과 대응 여부를 정하는 것은 별개의 판단**이라는 걸 알았고, 그래서 후속 글이 필요해졌다.

---

## 정리

- 정지 검사 누락은 3줄로 막히지만, 근본은 **`findActiveById`라는 이름이 보장하지 않는 걸 보장하는 것처럼 읽히는 것**이다
- 검사를 추가하는 대신 **위험한 경로를 명시적으로 골라야만 부를 수 있게** 만든다
- 정지 상태를 Redis에 영구 저장할 필요는 없다. 영구 상태는 DB의 `status`가 들고, Redis는 **살아 있는 액세스 토큰을 무효화하는 창**만 담당한다
- 문제를 발견하면 고치기 전에 **같은 종류가 몇 개인지 먼저 센다.** 개수가 해결책의 층위를 결정한다
- 멀티키 Lua가 깨지는 조건은 **인스턴스 개수가 아니라 cluster mode**다. 현재는 standalone이라 발생하지 않는다
- 발생하지 않는 문제라도 **키 형식처럼 되돌리기 비싼 것**이면 지금 판단해야 한다
