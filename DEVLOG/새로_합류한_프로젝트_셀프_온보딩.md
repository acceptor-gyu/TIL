# 새로 합류한 프로젝트 - 셀프 온보딩

새 팀에 합류했다. Kotlin + Spring Boot로 된 백엔드 서버고, 막 개발을 시작한 시점이라 인증/인가 로직 정도만, 그마저도 미완성인 상태로 구현되어있다. 그런데 작은 저장소가 읽기 쉬운 건 아니다. 오히려 작으면 "왜 이렇게 되어 있는지"를 알려줄 사람도, 축적된 코드도 적다.

> 사내 저장소 기준이라 프로젝트명·계정 ID·도메인·ARN 같은 식별자는 일반화해서 적는다.

---

## 셀프 온보딩의 기본 원칙 — 코드는 답이지 질문이 아니다

새 저장소를 받으면 보통 `src`부터 열지만, 이 방식은 두 가지가 나쁘다.

1. **질문 없이 읽으면 남지 않는다.** 클래스 이름과 메서드 시그니처는 눈으로 지나가지만, 왜 그 구조인지는 하나도 남지 않는다.
2. **코드는 결과만 말한다.** "무엇을 안 했는지", "무엇을 일부러 뺐는지"는 코드에 없다.

**그래서 먼저 가설을 세우고, 그 가설을 검증하는 질문을 들고 코드로 들어간다.** 가설을 만들어 주는 재료는 코드 바깥에 있다.

## 1. 빌드 파일 — 5분 만에 스택 전체의 지도를 얻는다

`build.gradle.kts` 하나로 이 서비스에서 사용하는 기술 스택들을 알 수 있다.

```kotlin
kotlin("jvm") version "2.4.10"
id("org.springframework.boot") version "4.0.7"
java { toolchain { languageVersion = JavaLanguageVersion.of(25) } }

implementation("org.springframework.boot:spring-boot-starter-data-jpa")
implementation("org.springframework.boot:spring-boot-starter-data-redis")
implementation("org.springframework.boot:spring-boot-starter-flyway")
implementation("org.springframework.boot:spring-boot-starter-oauth2-resource-server")
implementation("org.springframework.security:spring-security-oauth2-jose")
implementation(platform("software.amazon.awssdk:bom:2.54.7"))
implementation("software.amazon.awssdk:s3")
runtimeOnly("com.mysql:mysql-connector-j")
testImplementation("org.springframework.boot:spring-boot-testcontainers")
```

여기서 세운 가설들:

| 의존성 | 읽어낸 것 | 세운 가설 |
|---|---|---|
| MySQL + Flyway | 스키마가 마이그레이션으로 관리된다 | `db/migration`에 데이터 모델의 역사가 순서대로 있다 |
| Redis | 상태를 애플리케이션 밖에 둔다 | 세션? 캐시? 분산 락? — **찾아야 할 질문** |
| oauth2-resource-server (그런데 `oauth2-client`는 **없음**) | 토큰을 검증하는 쪽만 한다 | 남의 인가 서버에 붙는 게 아니다. 그럼 누구 토큰을 검증하지? |
| S3 | 파일을 다룬다 | 업로드 경로와 소유권 모델이 있을 것 |
| Testcontainers | 통합 테스트가 실물 컨테이너를 띄운다 | 테스트를 신뢰해도 된다 |

**`oauth2-client`가 없다는 것**처럼, *있는 것*보다 *없는 것*이 더 큰 신호일 때가 있다.

## 2. 마이그레이션 — 도메인의 역사이자 정책 문서

`db/migration`에 `V1__init.sql`, `V2__file_upload.sql` 두 개가 있었다. 이 두 파일을 읽는 게 엔티티 클래스 수십 개를 읽는 것보다 빠르다. 엔티티는 현재 상태만 보여주지만, 마이그레이션은 **변경의 순서와 이유**를 보여준다.

`V1`의 `users` 테이블에서 만난 주석:

```sql
-- 소셜 제공자마다 식별자 공간이 다르므로 (provider, social_id) 조합으로 유일성을 본다.
-- 소프트 삭제된 행도 제약 대상이라 탈퇴 계정은 같은 소셜 계정으로 재가입할 수 없다.
CONSTRAINT uk_users_provider_social_id UNIQUE (provider, social_id),

-- provider에는 CHECK를 두지 않는다. 제공자를 추가할 때 마이그레이션이 필요하지 않도록
-- 허용 값은 SocialProvider enum에서만 관리한다.
```

두 줄에서 정책이 두 개 나온다. 계정 식별 단위가 "사람"이 아니라 "소셜 계정"이라는 것, 그리고 제공자 추가는 코드 변경만으로 되게 의도했다는 것.

특히 `CHECK` 제약을 **일부러 넣지 않았다는 것**은 스키마만 봐서는 절대 알 수 없다. 주석이 없었다면 나는 이걸 "빠뜨린 것"으로 판단하고 PR을 올렸을 것이다. **신규 합류자가 만드는 가장 흔한 사고가 "의도된 부재"를 "누락"으로 오해하는 것**인데, 이 저장소는 그걸 주석으로 막고 있었다.

`V2`는 컬럼을 지우는 마이그레이션이었다.

```sql
ALTER TABLE users ADD COLUMN profile_image_file_id BIGINT NULL AFTER nickname;
-- ...
-- 업로드 엔드포인트가 없어 이 컬럼에 의미 있는 값이 쌓인 적은 없다.
ALTER TABLE users DROP COLUMN profile_image_url;
```

**"지워도 안전한 이유"가 함께 적혀 있다.** 데이터가 없다는 근거를 남긴 것이다. 덕분에 "운영 데이터 날린 거 아닌가?"를 물어볼 일이 없어졌다.

> **느낀 점.** 그동안 주석을 "코드가 안 읽히니까 어쩔 수 없이 다는 것"으로 여겼다. 좋은 코드는 주석이 필요 없다는 말도 그대로 믿었다. 그런데 여기서 본 주석들은 코드가 애초에 **말할 수 없는 것**만 적고 있었다. `CHECK`를 왜 안 넣었는지, 이 컬럼을 지워도 되는 근거가 무엇인지는 코드를 아무리 잘 써도 표현할 방법이 없다.
> 
> 이 두 파일을 읽고 나서 주석의 기준을 바꿨다. **일부러 안 한 것**은 무조건 남긴다.

## 3. `docs/` — "왜"가 어디에 적혀 있는가

`docs/features/`에 기능별 문서 세 개(소셜 로그인, 파일 업로드, 관측)가 있었다. 그런데 흔한 API 명세가 아니었다. 각 문서에 이런 섹션이 있었다.

- **왜 이렇게 만들었나** — 대안과 트레이드오프 비교
- **겪은 문제** — 실제로 터진 장애와 원인
- **아직 안 한 것** — 미구현 목록과 그 이유
- **미결사항** — 결정되지 않은 항목에 ID를 붙여 관리

특히 "겪은 문제"가 값졌다. 배포 중 인스턴스가 통째로 멎었던 장애가 이렇게 기록돼 있었다.

> 램 1GiB에 스왑이 없는 인스턴스는 설치 중 순간적으로 수백 MiB가 더 필요할 때 회수할 곳이 없어 시스템 전체가 정지한다. 진단이 까다로운 이유는 **journald가 함께 멈춰 OOM 기록이 남지 않기 때문이다.** 로그의 마지막 줄이 설치 시작 직후에서 끊겨 있으면 그게 신호다.

이건 코드를 아무리 읽어도 안 나온다. 그리고 내가 다음에 같은 증상을 만나면 30분 안에 끝낼 수 있게 해준다.

> **느낀 점.** 장애 기록을 문서로 남겨둔 게 좋았다. 나는 장애를 해결하면 안도하고 그냥 넘어갔다. 슬랙 스레드에는 남았겠지만 몇 달 뒤 검색될 리 없고, 결국 다음 사람이 같은 로그를 보며 처음부터 헤맨다. 여기서는 그 30분이 문서 한 문단으로 미리 지불돼 있었다. "기록은 나중에 나를 위한 것"이라는 말을 이번에 남의 기록으로 이득을 보면서 체감했다.

**셀프 온보딩 관점의 교훈**: 저장소를 평가할 때 나는 이제 **"왜"가 어디에 적혀 있는지**를 먼저 본다. 코드 주석이든 커밋 메시지든 `docs/`든 상관없다. 하나도 없으면 그 저장소를 이해하는 비용은 코드 줄 수와 무관하게 커진다. 7천 줄짜리인데 "왜"가 없으면, 7만 줄짜리인데 "왜"가 있는 저장소보다 느리다.

## 4. 설정 파일 — 운영 철학이 드러나는 곳

`application.yaml` 계열이 네 개(`local`/`dev`/`prod`/`test`). 여기서 패턴 하나를 발견했다.

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

`validate`다. 스키마가 엔티티와 어긋나면 **애플리케이션이 아예 뜨지 않는다.** `update`로 두면 개발은 편하지만 운영 스키마가 몰래 바뀐다.

같은 철학이 코드에도 있었다. 설정 자리표시자를 검사하는 클래스가 이런 이유를 달고 있었다.

```
CORS_ALLOWED_ORIGIN_PATTERNS가 없으면 @NotEmpty를 통과한 채
"${CORS_ALLOWED_ORIGIN_PATTERNS}" 문자열 한 건이 바인딩되어
런타임에 CORS가 조용히 막힌다. 그래서 자리표시자가 해석되지 않으면
기동 자체가 실패하게 했다.
```

Spring의 `@ConfigurationProperties`는 해석되지 않은 자리표시자를 **문자열 그대로** 바인딩한다. `@NotBlank`도 통과한다. "값이 비어서 나는 장애"가 아니라 "값이 이상해서 나는 장애"가 되고, 이건 배포 몇 시간 뒤 CORS 오류로 나타난다. 기동을 막는 쪽이 훨씬 싸다.

**여기서 이 프로젝트의 규칙 하나를 찾았다: 잘못된 상태로 뜨는 것보다 안 뜨는 것을 택한다.** 스키마 검증, 자리표시자 검증, 스토리지 설정 검증(업로드 URL 유효기간이 정리 유예보다 길면 기동 실패)이 전부 같은 결정이다.

> **느낀 점.** 뜨지 않으면 5분 만에 알아채지만, 잘못된 값으로 뜨면 사용자가 먼저 발견한다. 실패를 앞으로 당기는 게 왜 이득인지 이제 구체적인 사례로 설명할 수 있게 됐다.

셀프 온보딩에서 이런 **관통하는 규칙**을 하나 찾으면 수확이 크다. 앞으로 내가 새 설정을 추가할 때 어떻게 해야 하는지가 자동으로 정해지기 때문이다. 코드 리뷰에서 지적받을 것을 미리 없앨 수 있다.

## 5. 패키지 구조 — 이름이 아니라 의존 방향으로 검증한다

```
api/         controller · dto · facade
application/ 유스케이스 서비스
domain/      entity · service · value · repository
external/    kakao · apple · storage
security/    jwt · redis
config/
common/
```

계층 이름만 보면 그럴듯하다. 그런데 **이름은 지켜지지 않아도 붙일 수 있다.** 실제로 지켜지는지는 인터페이스가 어디에 선언돼 있는지로 확인했다.

```kotlin
// domain/user/service/SocialLoginService.kt      ← 인터페이스: domain
// external/kakao/KakaoLoginService.kt            ← 구현체: external

// domain/file/service/FileStorage.kt             ← 인터페이스: domain
// external/storage/S3FileStorage.kt              ← 구현체: external

// domain/auth/service/AccessTokenIssuer.kt       ← 인터페이스: domain
// security/jwt/JwtAccessTokenIssuer.kt           ← 구현체: security
```

전부 도메인이 인터페이스를 정의하고 바깥 계층이 구현한다. 의존이 안쪽을 향한다. 그래서 도메인 서비스는 카카오도 S3도 JWT도 모른다.

이 구조가 실제로 값을 내는 지점도 찾았다. 애플 로그인이 임시 비활성화돼 있는데, 그 방식이 `external/apple` 구현체 전체를 주석 처리한 것이었다. 그런데 `SocialProvider` enum에는 `APPLE`이 남아 있다.

```kotlin
@Component
class SocialLoginServiceRegistry(services: List<SocialLoginService>) {
    private val servicesByProvider = services.associateBy(SocialLoginService::provider)

    fun resolve(provider: SocialProvider): SocialLoginService =
        servicesByProvider[provider]
            ?: throw IllegalArgumentException(UNSUPPORTED_PROVIDER_MESSAGE)
}
```

레지스트리가 `List<SocialLoginService>`를 주입받아 구현체를 자동 수집하므로, 구현체가 없는 enum 항목은 그냥 미지원(400)이 된다. 컨트롤러·파사드·도메인 서비스·스키마를 하나도 안 건드리고 제공자 하나를 껐다 켤 수 있다. 되살릴 때는 주석만 풀면 된다.

> **느낀 점.** 한마디로 **읽기 편한 코드였다.** 그 이유를 나름대로 정리해 보면, 파일을 열기 전에 그 파일이 무엇을 알고 무엇을 모르는지 예측이 됐기 때문이다. `domain` 아래에 있으면 카카오도 S3도 모를 거라는 전제로 읽기 시작할 수 있고, 그 전제가 한 번도 깨지지 않았다. 덕분에 94개 파일 중 실제로 연 것은 절반도 안 된다.
>
> **폴더를 나누는 것과 의존 방향을 지키는 것은 완전히 다른 일**이다.

## 6. CI/CD — 이 팀이 무엇을 "성공"으로 보는가

`.github/workflows/`에 `pr-check.yml`과 `deploy.yml` 두 개.

**머지로 자동 배포하지 않는다.**

```yaml
on:
  workflow_dispatch:
    inputs:
      environment: { type: choice, options: [dev, prod] }
```

배포 시점을 사람이 고른다. 팀이 작고 인스턴스가 한 대일 때는 합리적인 선택이다. 이걸 미리 안 덕분에 "머지했는데 왜 안 올라가지?"로 시간을 쓰지 않았다.

**성공 판정 기준이 "컨테이너가 떴다"가 아니다.** 롤아웃 후 로드밸런서 타깃 그룹의 헬스 상태를 폴링해서 모든 타깃이 `healthy`가 될 때까지 기다린다.

```bash
STATES="$(aws elbv2 describe-target-health ... --output text)"
if [ -n "${STATES}" ] && ! echo "${STATES}" | grep -qvw healthy; then
  echo "모든 대상이 healthy 입니다."; exit 0
fi
```

원격 명령 실행 API는 보통 접수만 하고 즉시 반환한다. 거기서 안 기다리면 롤아웃이 실패해도 워크플로는 초록불로 끝난다. 이 파이프라인은 그걸 알고 세 군데(에이전트 설정, 롤아웃, 헬스체크)에서 각각 기다린다.

**파이프라인은 마지막이 아니라 중간에 읽는 게 맞다.** 배포를 직접 하기 전에 읽어야 첫 배포에서 당황하지 않는다.

> **느낀 점.** 기다리는 코드가 세 군데나 있는 게 인상적이었다. 나는 배포 스크립트를 짤 때 "명령을 보냈다"까지만 쓰고 초록불이 뜨면 끝난 줄 알았다. 그런데 접수만 하고 즉시 반환하는 API 뒤에서 롤아웃이 실패하면, CI는 성공인데 서비스는 죽어 있는 최악의 조합이 된다. **초록불이 무엇을 보증하는지 한 번 생각해보자**

## 7. 그리고 코드를 읽었다

여기까지 오면 코드를 열 때 손에 질문이 들려 있다.

- Redis는 결국 무엇에 쓰이나?
- 리소스 서버로 **누구의** 토큰을 검증하나?
- 가입 중에는(=사용자 행이 아직 없을 때는) 인증을 어떻게 하나?

답을 찾으러 가는 것과 훑는 것은 속도가 다르다. 그리고 세 개 다 예상과 달랐다.

| 가설 | 실제 |
|---|---|
| Redis = 캐시 또는 세션 | **리프레시 토큰 저장 하나뿐.** `@Cacheable`도 Spring Session도 분산 락도 없다 |
| 외부 인가 서버의 토큰을 검증 | **자기가 발급한 토큰을 자기가 검증한다.** HS256 대칭키 하나로 발급·검증 |
| 가입 전 요청은 인증이 없다 | 인증이 없는 게 아니라 **인증 주체가 다르다.** 시큐리티 필터가 아니라 파사드가 단기 가입 토큰을 검증한다 |

세 줄 다 "가설이 틀렸다"인데, **틀린 가설이 맞은 가설보다 온보딩에 도움이 됐다.** 왜 다른지를 따라가는 과정에서 설계 의도가 드러났기 때문이다. 예를 들어 리프레시 토큰만 JWT가 아니라 불투명 UUID인 이유는 "JWT는 폐기할 수 없어서"였고, 그 한 줄이 이 서비스의 인증 트레이드오프 전체를 설명했다.

## 셀프 온보딩의 진짜 산출물 — 신규 합류자만 찾을 수 있는 것

온보딩 첫 주의 결과물은 "이해했다"가 아니라 **"이건 이상한데요"** 두 건이었다.

### 1. 정지된 계정이 계속 API를 쓸 수 있다

계정 정지 검사가 소셜 로그인 경로에만 있었다.

```kotlin
// 로그인 경로
userReader.findActiveBySocialAccount(profile)?.let { user ->
    if (user.isSuspended()) throw AccountSuspendedException()   // ← 여기만
    return authenticated(user)
}

// 토큰 갱신 경로
val user = userReader.findActiveById(userId) ?: throw IllegalArgumentException(...)
return accessTokenIssuer.issue(AccessTokenPrincipal(userId, user.systemRole))
```

`findActiveById`를 저장소까지 따라가 보니 `deletedAt IS NULL`만 본다. **`status`는 안 본다.** 결과적으로 이미 로그인한 사용자를 정지시켜도 30일짜리 리프레시 토큰을 계속 회전시키며 무제한으로 API를 쓸 수 있다. 정지가 "새 로그인"만 막는다.

### 2. 인프라 변경 시점에 터질 폭탄

리프레시 토큰 회전을 Lua 스크립트로 원자적으로 처리하는데, 스크립트가 옛 키와 새 키 **두 개**를 만진다. Redis 공식 문서는 클러스터링이 켜진 구성에서 Lua가 선언한 키가 전부 같은 해시 슬롯에 있어야 한다고 명시한다. 두 토큰 해시는 다른 슬롯으로 흩어지므로 `CROSSSLOT` 오류가 난다.

지금은 standalone이라 문제가 없다. 문제는 **터지는 시점이 코드 변경이 아니라 인프라 변경 시점이라는 것**이다. 관리형 Redis를 클러스터 모드로 바꾸는 순간 토큰 갱신 전체가 실패하는데, 그때 원인을 애플리케이션 코드에서 찾게 된다.

---

두 건의 해결책은 따로 정리했다 → [온보딩에서 찾은 인증 문제 두 가지 해결 전략](260901_02_온보딩에서_찾은_인증_문제_두_가지.md)

두 건 모두 **기능 단위로 보면 안 보이고 코드 경로를 따라가야 보이는 문제**다. 그리고 둘 다 "이 기능이 아직 구현 범위에 없어서" 드러나지 않은 것들이었다.

여기서 셀프 온보딩의 값을 다시 정리하게 됐다. 신규 합류자는 도메인 지식이 없어서 불리하지만, 대신 **"원래 그런 것"이 하나도 없다.** 기존 멤버는 `findActiveById`를 백 번 봤기 때문에 그 이름을 의심하지 않는다. 나는 처음 봤기 때문에 저장소 구현까지 따라갔다. **이 시야는 몇 주 지나면 사라지므로, 첫 주에 발견한 위화감은 반드시 그때 기록해야 한다.**

## 첫 주를 마치고 느낀 점

정리하면서 남은 생각들이다. 기술적인 결론이라기보다 태도에 관한 것에 가깝다.

**읽기 편한 코드는 짧은 코드가 아니었다.** 처음에는 7천 줄밖에 안 돼서 금방 읽겠다고 생각했다. 그런데 실제로 속도를 만들어 준 건 분량이 아니라 **예측 가능성**이었다. 파일을 열기 전에 그 안에 무엇이 있을지 짐작이 되고, 그 짐작이 계속 맞아떨어지는 경험. 반대로 예전에 봤던 어떤 저장소는 이보다 작았는데도 훨씬 오래 걸렸다. 이름과 실제가 자꾸 어긋나서 전부 열어봐야 했기 때문이다.

**주석의 중요성을 다시 알았다.** 이번 온보딩에서 가장 크게 바뀐 생각이다. "좋은 코드는 주석이 필요 없다"는 말을 나는 "주석을 쓰지 마라"로 잘못 읽고 있었다. 실제로 값이 컸던 주석은 코드를 설명하는 주석이 아니라 **코드가 구조적으로 표현할 수 없는 것**을 적은 주석이었다. 제약을 일부러 안 넣은 이유, 컬럼을 지워도 되는 근거, 액세스 토큰이 폐기되지 않는다는 사실. 셋 다 코드만 보면 각각 "누락", "위험한 변경", "버그"로 오해하기 딱 좋은 것들이다.

**한 번도 안 물어보고 첫 주를 보냈다.** 물어볼 사람이 없어서가 아니라, 물어보려고 정리하다 보면 답이 문서나 마이그레이션에 이미 있는 경우가 많았다. 결과적으로 팀에 한 질문은 "왜 이렇게 돼 있나요"가 아니라 **"제가 이해한 게 맞나요"**와 **"이건 의도한 동작인가요"** 두 종류였다. 질문의 질이 달라지니 답변도 짧고 정확하게 돌아왔다. 온보딩 비용은 결국 신규 합류자가 아니라 **기존 멤버의 시간**으로 지불되는 거라, 이 차이가 팀 입장에서는 꽤 클 것 같다.

**남의 코드를 읽는 경험이 내 코드를 바꿨다.** 계층을 나누는 것과 의존 방향을 지키는 게 다른 일이라는 것, 배포 스크립트의 초록불이 무엇을 보증하는지 따져야 한다는 것, 기본값을 박아 넣는 게 장애를 미루는 행위라는 것. 전부 내가 쓸 때는 안 보이다가 **읽는 입장이 되니까 보인 것들**이다. 잘 쓰인 코드를 정독하는 게 왜 학습이 되는지 이번에 처음 실감했다.

**아쉬웠던 점도 있다.** 첫 주라는 이유로 위화감을 기록만 하고 팀에 바로 공유하지 않았다. "내가 아직 모르는 맥락이 있겠지"라고 미룬 건데, 정지 계정 건은 좀 더 일찍 꺼냈어도 됐다. 확신이 없으면 없는 대로 질문 형태로 던지는 게 맞았다. 신규 합류자의 시야는 유통기한이 짧으니 다음에는 미루지 않으려 한다.

---

## 다음 프로젝트에서도 쓸 순서

1. **`build.gradle.kts`(또는 `package.json`)** — 스택 파악과 가설 세우기. *있는 것*만큼 *없는 것*도 본다
2. **마이그레이션** — 도메인의 역사와 정책. 엔티티보다 먼저
3. **`docs/` 또는 그에 준하는 것** — "왜". 없으면 커밋 메시지와 PR 본문으로 대체
4. **설정 파일** — 환경 구성과 운영 철학. 관통하는 규칙 하나를 찾는다
5. **패키지 구조** — 이름이 아니라 **의존 방향**으로 검증
6. **CI/CD** — 무엇을 성공으로 보는가. 첫 배포 전에 읽는다
7. **코드** — 구체적인 질문을 들고. 가설과 다른 지점을 우선 판다
8. **위화감 기록** — 첫 주에만 보이는 것들. 확신이 없어도 적어 둔다

## 정리

- **코드를 마지막에 읽는다.** 앞의 여섯 단계는 코드를 읽을 때 쓸 질문을 만드는 과정이다
- **가설을 세우고 검증한다.** 틀린 가설이 설계 의도를 가장 빠르게 드러낸다
- **"왜"가 어디 있는지가 저장소 이해 비용을 결정한다.** 코드 줄 수보다 이게 더 큰 변수다
- **관통하는 규칙 하나를 찾으면 앞으로의 결정이 자동으로 정해진다.** 이 프로젝트에서는 "잘못된 상태로 뜨느니 안 뜬다"였다
- **신규 합류자의 위화감은 유통기한이 있다.** 첫 주에 기록하지 않으면 두 달 뒤엔 나도 "원래 그런 것"이라고 말하게 된다

그리고 내가 이 저장소를 빠르게 이해할 수 있었던 건 코드가 짧아서가 아니라 **결정의 근거가 코드와 같은 저장소에 있었기 때문이다.** 문서를 따로 쓰는 게 부담이라면 최소한 마이그레이션과 설정 파일에 "왜"를 남기자. 다음 사람의 첫 주가 며칠 줄어든다.
