# 없는 행을 잠그고 넣었더니 교착이 났다 — gap lock과 READ COMMITTED

"없으면 만들고, 있으면 고친다"를 동시성 안전하게 쓰는 가장 흔한 모양은 이것이다. 먼저 `SELECT ... FOR UPDATE`로 잠그고, 없으면 `INSERT`한다. 행이 있을 때는 잘 동작한다. 문제는 **행이 없을 때**다. MySQL의 기본 격리 수준(REPEATABLE READ)에서 없는 키를 잠그면 레코드가 아니라 **틈(gap)** 이 잠기고, 그 틈은 다른 트랜잭션도 동시에 잠글 수 있다. 둘이 같은 틈을 쥔 채 각자 INSERT하면 서로를 기다리다 교착한다.

지금 개발하는 프로젝트에는 `SELECT ... FOR UPDATE`가 세 군데 있다. 구장·날짜별 알림 발송 기준, 첫 위치 정보 동의, 채팅방 열기다. 앞의 둘은 트랜잭션을 READ COMMITTED로 열어 풀었고, 채팅은 **id만 먼저 읽고 기본 키로 잠그는** 다른 길로 풀었다. 같은 문제에 답이 둘인 이유와, 두 번째 길에 숨어 있던 JPA 함정까지 정리한다.

> 사내 저장소 기준이라 프로젝트명·도메인 같은 식별자는 일반화해서 적는다.

## 1. 잠그고, 없으면 넣는다

부킹 매니저가 티타임을 올리면, 그 구장을 찜한 회원에게 "새 티타임이 올라왔다"는 알림을 **구장·날짜별로 하루 한 번** 보낸다. 같은 날 여러 매니저가 같은 구장에 티타임을 올려도 알림은 한 건이어야 한다. 그 "오늘 이미 보냈는가"를 기록하는 표가 발송 기준(digest)이다.

```sql
CREATE TABLE golf_course_tee_time_digests (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    golf_course_id BIGINT NOT NULL,
    registration_date DATE NOT NULL,
    created_at DATETIME(6) NOT NULL,
    CONSTRAINT uk_golf_course_tee_time_digest_day UNIQUE (golf_course_id, registration_date)
);
```

등록 흐름은 이렇다.

```kotlin
fun register(input: TeeTimeRegistrationInput): TeeTime {
    val manager = accounts.findActiveByIdForUpdate(input.managerId)   // 계정 잠금
        ?: throw IllegalArgumentException(AccountFinder.USER_NOT_FOUND_MESSAGE)
    ...
    val golfCourse = golfCourses.getForUpdate(input.golfCourseId)      // 구장 잠금
    ...
    val teeTime = teeTimeRepository.save(TeeTime.register(...))
    notifications.registered(teeTime)                                  // 발송 기준
    return teeTime
}
```

```kotlin
@Transactional(propagation = Propagation.MANDATORY)
fun registered(teeTime: TeeTime) {
    val date = teeTime.createdAt.atZone(GolfCourseTeeTimeDigest.ZONE).toLocalDate()
    if (digests.findByGolfCourseIdAndRegistrationDate(teeTime.golfCourseId, date) != null) return
    val digest = digests.save(GolfCourseTeeTimeDigest.record(teeTime.golfCourseId, teeTime.createdAt))
    notifications.sendNow(...)
}
```

```kotlin
@Lock(LockModeType.PESSIMISTIC_WRITE)
fun findByGolfCourseIdAndRegistrationDate(golfCourseId: Long, registrationDate: LocalDate): GolfCourseTeeTimeDigest?
```

`PESSIMISTIC_WRITE`라 이 조회는 `SELECT ... FOR UPDATE`다. 그날 첫 등록이면 행이 없다. **없는 행을 잠근 뒤 넣는다.**

위치 정보 동의도 같은 모양이다. 동의 행은 주체 키(회원이면 회원, 비회원이면 서버가 발급한 토큰)가 기본 키이고, 첫 동의에는 행이 없다.

```kotlin
val existing = consents.lock(subject)               // FOR UPDATE, 첫 동의면 null
val consent = existing ?: LocationConsent.create(subject, version, clock.instant())
...
consents.saveAndFlush(consent)
```

## 2. 왜 교착하는가

### "없는 키를 잠근다"는 어떤 상황인가

발송 기준 표에 지금 이런 행이 있다고 가정해보면, 유니크 인덱스 `(golf_course_id, registration_date)`는 **구장 id가 먼저, 날짜가 나중**인 순서로 정렬된다.

```text
uk_golf_course_tee_time_digest_day (인덱스 순서)
─────────────────────────────────────────────
(3, 2026-09-30)
                     ← 빈자리: (3, 10-01), (5, 10-01), (6, 10-01) 이 여기에 들어갈 자리다
(8, 2026-09-29)
(8, 2026-09-30)
                     ← 빈자리: (8, 10-01) 이 여기에 들어갈 자리다
[supremum]           ← 인덱스 끝을 나타내는 가상 레코드
```

10월 1일 아침, 그동안 티타임이 올라온 적 없는 구장 5에 첫 티타임이 올라온다. 발송 기준 조회가 나간다.

```sql
SELECT * FROM golf_course_tee_time_digests
 WHERE golf_course_id = 5 AND registration_date = '2026-10-01'
   FOR UPDATE;
-- Empty set
```

결과는 비어 있다. 그런데 이 문장은 아무것도 잠그지 않은 게 아니다. 잠글 행이 없을 뿐, 잠금은 걸렸다. **"없는 키를 잠근다"는 이 상황이다.** `(5, 2026-10-01)`이라는 행은 아직 없고, 이 트랜잭션은 그 행이 생길 자리를 잠갔다. 그 자리는 `(5, 10-01)` 하나만의 자리가 아니라 `(3, 09-30)`과 `(8, 09-29)` 사이의 **틈 전체**다.

### 왜 레코드 잠금이 아니라 gap lock이 걸리나

InnoDB의 행 잠금은 **값에 걸리지 않고 인덱스 레코드에 붙는다.** 잠금 정보는 "어느 페이지의 몇 번째 레코드"를 가리키는 비트로 관리된다. 그래서 `(5, 10-01)`이라는 값 자체를 잠글 방법이 없다. 붙일 레코드가 없기 때문이다. 잠금을 걸 수 있는 대상은 **이미 인덱스에 있는 레코드**뿐이다.

`FOR UPDATE`가 실제로 하는 일을 순서대로 보면 이렇다.

| 단계 | 하는 일 | 위 예시에서 |
| --- | --- | --- |
| 1 | 인덱스에서 검색 키 이상인 첫 레코드에 커서를 놓는다 | `(5, 10-01)` 이상인 첫 레코드는 `(8, 09-29)` |
| 2 | REPEATABLE READ의 잠금 읽기는 기본으로 **next-key lock**을 건다. next-key lock은 레코드 자신 + 그 앞의 틈이다 | `(8, 09-29)` 레코드와 `((3, 09-30), (8, 09-29))` 틈 |
| 3 | 그 레코드가 검색 조건과 같지 않다. 유니크 인덱스의 등치 검색이라 이 레코드 자체는 지킬 이유가 없으므로 **레코드 부분을 빼고 틈만** 잠근다 | `(8, 09-29)` 앞의 틈에 **gap lock** (`X,GAP`) |
| 4 | 다음 레코드가 아예 없으면 인덱스 끝의 가상 레코드(supremum)를 잠근다. supremum은 실제 행이 아니라서 사실상 "마지막 레코드부터 끝까지의 틈"이다 | `(8, 10-01)`을 찾았다면 `(8, 09-30)` 뒤부터 끝까지 |

왜 굳이 무언가를 잠가야 하는가. REPEATABLE READ의 잠금 읽기는 **같은 문장을 다시 실행해도 같은 결과**를 보장해야 한다(phantom 방지). "비어 있었다"는 결과를 유지하려면, 그 키가 들어갈 수 있는 범위에 **아무도 INSERT하지 못하게** 하는 수밖에 없다. 값을 잠글 수 없으니 그 값을 품는 틈을 잠그는 것이다.

행이 있을 때와 비교하면 차이가 분명하다.

| | 행이 있을 때 | 행이 없을 때 |
| --- | --- | --- |
| 커서가 놓이는 레코드 | 찾는 바로 그 레코드 | 다음 레코드 (없으면 supremum) |
| 걸리는 잠금 | **레코드 잠금** (`X,REC_NOT_GAP`). 유니크 등치 검색이라 틈은 잠그지 않는다 | **gap lock** (`X,GAP`). 레코드는 잠그지 않는다 |
| 막는 범위 | 그 행 하나 | 이웃한 두 레코드 사이의 **모든 키** |
| 같은 코드를 부른 다른 트랜잭션 | 같은 행이면 기다린다 | 같은 틈이면 **기다리지 않고 같이 잠근다** |

같은 `findBy...ForUpdate` 한 줄이 **두 번째 등록부터는 레코드 하나를, 첫 등록에서는 남과 공유하는 틈을** 잠근다. 잠금의 성격이 데이터 상태에 따라 바뀐다는 것이 이 문제의 출발점이다. gap lock의 개념은 [MySQL Lock 종류](../RDBMS/260220_01_RDBMS_MySQL_Lock_종류.md)에 있다.

실제로 무엇이 잠겼는지는 `performance_schema.data_locks`에서 볼 수 있다. 위 조회 직후라면 대략 이런 모양이다(출력은 형태만 보인 예시다).

```text
INDEX_NAME                          LOCK_TYPE  LOCK_MODE  LOCK_DATA
──────────────────────────────────  ─────────  ─────────  ─────────────────────────────
NULL                                TABLE      IX         NULL
uk_golf_course_tee_time_digest_day  RECORD     X,GAP      (8, 2026-09-29) 레코드와 그 PK
```

`LOCK_DATA`가 찾던 `(5, 10-01)`이 아니라 **다음 레코드**를 가리키고, `LOCK_MODE`가 `X,GAP`이다. "그 레코드 앞의 틈을 잠갔다"는 뜻이다.

### 같은 틈을 둘이 잠그면

여기서 두 가지 성질이 겹친다.

| 성질 | 뜻 |
| --- | --- |
| **gap lock끼리는 충돌하지 않는다** | 두 트랜잭션이 같은 틈을 동시에 잠글 수 있다. gap lock의 목적은 "남이 넣지 못하게"이지 "나만 읽게"가 아니다 |
| **INSERT는 insert intention lock을 요구한다** | 이 잠금은 **남이 쥔 gap lock과 충돌한다.** 틈을 잠근 트랜잭션이 있으면 그 틈에 넣으려는 쪽이 기다린다 |

같은 날 아침, 구장 6에도 첫 티타임이 올라온다. `(6, 10-01)`도 `(3, 09-30)`과 `(8, 09-29)` 사이에 들어갈 키라 **같은 틈**이다.

```text
T1 (구장 5, 10/01 첫 등록)                  T2 (구장 6, 10/01 첫 등록)
──────────────────────────                 ──────────────────────────
SELECT (5, 10-01) FOR UPDATE
  → 행 없음, (8, 09-29) 앞 틈에 X,GAP
                                            SELECT (6, 10-01) FOR UPDATE
                                              → 행 없음, 같은 틈에 X,GAP (충돌 없음)
INSERT (5, 10-01)
  → insert intention 이 T2 의 gap lock 과 충돌 → 대기
                                            INSERT (6, 10-01)
                                              → insert intention 이 T1 의 gap lock 과 충돌 → 대기
                     ── 순환 대기: InnoDB 가 한쪽을 교착 희생자로 롤백 ──
```

두 세션으로 그대로 재현할 수 있다.

```sql
-- 세션 1                                      -- 세션 2
BEGIN;                                          BEGIN;
SELECT * FROM golf_course_tee_time_digests
 WHERE golf_course_id = 5
   AND registration_date = '2026-10-01'
   FOR UPDATE;            -- Empty set
                                                SELECT * FROM golf_course_tee_time_digests
                                                 WHERE golf_course_id = 6
                                                   AND registration_date = '2026-10-01'
                                                   FOR UPDATE;   -- Empty set, 바로 돌아온다
INSERT INTO golf_course_tee_time_digests
  (golf_course_id, registration_date, created_at)
VALUES (5, '2026-10-01', NOW(6));   -- 멈춘다
                                                INSERT INTO golf_course_tee_time_digests
                                                  (golf_course_id, registration_date, created_at)
                                                VALUES (6, '2026-10-01', NOW(6));
                                                -- ERROR 1213 (40001): Deadlock found ...
```

세션 2의 SELECT가 **바로 돌아온다**는 점이 핵심이다. 행 잠금이었다면 여기서 기다렸을 것이고, 기다렸다면 교착 대신 직렬화가 됐을 것이다.

### 어떤 키들이 같은 틈에 떨어지나

인덱스가 구장 id 순서라서, 두 키가 같은 틈에 떨어지는 조건은 **둘 사이에 기존 레코드가 하나도 없는 것**이다.

| 키 | 떨어지는 틈 | 함께 교착할 수 있는 키 |
| --- | --- | --- |
| `(3, 10-01)` | `(3, 09-30)` ~ `(8, 09-29)` | `(5, 10-01)`, `(6, 10-01)` — 구장 3은 이력이 있어도 같은 틈이다 |
| `(5, 10-01)`, `(6, 10-01)` | 같은 틈 | 서로 |
| `(8, 10-01)` | `(8, 09-30)` ~ supremum | 구장 8보다 id가 큰, 이력 없는 모든 구장의 첫 등록 |

그래서 위험은 고르게 퍼져 있지 않다. **발송 기준 행이 아직 없는 구장들**이 id 순으로 이웃해 있으면 한 틈을 공유한다. 새로 등록된 구장이나 티타임이 드물게 올라오는 구장이 그렇다. **id가 가장 큰 구장들**은 supremum 앞의 틈 하나를 함께 쓴다. 위치 동의는 주체 키가 무작위 토큰이라 이웃이 무작위로 정해지지만, 행이 적은 초기에는 틈 하나하나가 넓어서 서로 다른 첫 동의가 같은 틈에 떨어지기 쉽다.

### 잠금을 하나 더 잡아도 막지 못한다

등록은 이미 구장 행을 잠그고 있었다. 위치 동의는 회원이면 계정 행을 잠근다. 그런데 이 잠금들은 **같은 대상끼리만** 줄을 세운다.

| 앞단 잠금 | 줄을 세우는 범위 | 막지 못하는 것 |
| --- | --- | --- |
| 구장 행 잠금 | 같은 구장의 등록끼리 | **다른 구장**의 같은 날 첫 등록 |
| 계정 행 잠금 | 같은 회원의 동의끼리 | **다른 회원**의 첫 동의 |
| (비회원) | 아무것도 줄 세우지 않는다 | 모든 비회원의 첫 동의 |

T1과 T2는 서로 다른 구장을 잠갔으니 앞단에서 아무도 기다리지 않고 둘 다 digest 조회까지 온다. 틈은 구장 단위가 아니라 **인덱스 단위**라서, 서로 다른 구장이 같은 틈을 공유한다.

> 앞단 잠금이 지켜 주는 것은 **같은 키의 중복**이고, 교착을 만드는 것은 **다른 키의 이웃함**이다. 잠금을 더 촘촘히 걸어서 풀 문제가 아니다.

## 3. 첫 번째 답 — READ COMMITTED로 연다

READ COMMITTED에서 InnoDB는 일반 검색과 인덱스 스캔에 gap lock을 쓰지 않는다. 외래 키 검사와 중복 키 검사에만 쓴다. 없는 키를 `FOR UPDATE`로 읽으면 **아무것도 잠그지 않고** null을 돌려준다. 틈이 잠기지 않으니 위의 순환이 생길 수 없다.

```kotlin
/**
 * **READ_COMMITTED 로 연다.** 구장의 첫 등록은 없는 발송 기준 행(날짜별 알림)을 잠근 뒤 넣는데,
 * REPEATABLE READ 에서는 그 잠금이 gap lock 이 되어 다른 구장의 같은 날 첫 등록과 교착한다.
 * 계정·구장은 모두 잠금 읽기라 격리 수준을 낮춰도 판단이 달라지지 않는다.
 */
@Transactional(isolation = Isolation.READ_COMMITTED)
fun register(input: TeeTimeRegistrationInput): TeeTime
```

```kotlin
@Transactional(isolation = Isolation.READ_COMMITTED)
override fun consent(userId: Long?, guestToken: String?, request: LocationConsentRequest): LocationConsentResponse
```

예약 등록은 이미 같은 판단으로 READ COMMITTED였다. 이번에 그 판단을 같은 모양의 두 경로로 넓혔다.

```kotlin
// 빈 예약에 FOR UPDATE를 걸면 서로 다른 티타임의 INSERT도 RR gap lock으로 교착할 수 있다.
@Transactional(isolation = Isolation.READ_COMMITTED)
override fun register(actorId: Long, request: ReservationRequest): ReservationResponse
```

### 그럼 중복은 누가 막나

gap lock은 원래 "없던 행이 끼어드는 것"을 막는 장치였다. 그걸 끄면 같은 키가 두 번 들어가는 것은 무엇이 막는가. 경로마다 따로 확인했다.

| 경로 | 같은 키의 동시 첫 삽입을 막는 것 |
| --- | --- |
| 발송 기준 | **구장 행 잠금**이 같은 구장끼리 줄을 세운다. 뒤의 등록은 앞의 커밋 뒤에 digest를 읽고 이미 있는 행을 본다. 최후 방어선은 `(golf_course_id, registration_date)` 유니크 키 |
| 위치 동의 (회원) | **계정 행 잠금** + 기본 키 |
| 위치 동의 (비회원) | 첫 동의마다 **새로 발급하는 무작위 토큰**이 주체 키다. 같은 키로 동시에 첫 동의가 들어올 일이 없다. 그리고 기본 키 |

앞단 잠금이 한 일이 바뀌었다. 전에는 "같은 키 중복 방지"와 "교착 유발" 둘 다에 관여하는 것처럼 보였는데, 사실 처음부터 중복 방지만 하고 있었다. 격리 수준을 낮춰도 그 역할은 그대로다.

### 격리 수준을 낮춰도 판단이 그대로인가

READ COMMITTED의 대가는 **잠그지 않는 읽기가 문장마다 새 스냅샷을 본다**는 것이다. 한 트랜잭션 안에서 같은 행을 두 번 읽으면 값이 다를 수 있다. 그래서 각 경로의 판단이 무엇에 기대는지 확인했다.

- 티타임 등록: 판단 재료(매니저 자격, 구장 선택 가능 여부, 발송 기준 유무)가 **모두 잠금 읽기**다. 잠금 읽기는 격리 수준과 상관없이 언제나 최신 커밋을 읽는다
- 위치 동의: 판단은 **잠근 동의 행**과 **한 번 읽은 약관 버전**으로만 한다. 두 번 읽어 비교하는 곳이 없다

이 확인 없이 격리 수준만 내리면, 교착은 사라지고 정합성 버그가 대신 들어올 수 있다.

### 격리 수준은 트랜잭션을 여는 쪽이 정한다

함정이 하나 더 있었다. Spring에서 `isolation`은 **새 트랜잭션을 시작하는 메서드에서만** 적용된다. 이미 열린 트랜잭션에 참여하는 메서드의 값은 무시된다.

티타임 등록에는 입구가 둘이다. 어드민 등록은 `TeeTimeRegistrationService.register`가 트랜잭션을 열지만, 매니저 등록은 `ManagedTeeTimeService.register`가 먼저 열고 그 안에서 같은 메서드를 부른다. 안쪽에만 READ COMMITTED를 달면 매니저 경로는 여전히 REPEATABLE READ다.

```kotlin
/** 없는 발송 기준 행의 gap lock 교착을 피하려고 READ_COMMITTED 로 연다([TeeTimeRegistrationService.register]). */
@Transactional(isolation = Isolation.READ_COMMITTED)
override fun register(actorId: Long, request: ManagerTeeTimeRequest): TeeTimeResponse {
    policy.requireManager(users.findActiveByIdForUpdate(actorId))
    return TeeTimeResponse.from(registration.register(...))
}
```

그래서 **트랜잭션을 여는 모든 입구**에 같은 수준을 달았다. 발송 기준을 쓰는 쪽(`registered`)은 `MANDATORY`라 직접 트랜잭션을 열지 않는다. 대신 "호출 트랜잭션은 READ_COMMITTED여야 한다"를 KDoc에 적었다.

> `Propagation.MANDATORY`는 **이미 열린 트랜잭션 안에서만 실행되게 하는** 전파 옵션이다. 진행 중인 트랜잭션이 있으면 거기에 참여하고, 없으면 새로 열지 않고 `IllegalTransactionStateException`을 던진다. 기본값인 `REQUIRED`는 트랜잭션이 없으면 새로 연다. 그래서 `MANDATORY` 메서드는 격리 수준을 스스로 정하지 못하고, 부른 쪽의 트랜잭션을 그대로 따른다.

## 4. 두 번째 답 — id만 먼저 읽고 기본 키로 잠근다

채팅방 열기도 "있으면 그 방, 없으면 새 방"이다. 부킹 문의 방은 `(매니저, 문의한 사람)` 한 쌍에 하나이고, 고객센터 방은 회원마다 하나다. 둘 다 유니크 키가 있다.

```sql
ADD CONSTRAINT uk_chat_rooms_booking_pair UNIQUE (booking_manager_id, booking_inquirer_id);
CONSTRAINT uk_chat_rooms_support_user UNIQUE (support_user_id)
```

리뷰에서 나온 원래 결함은 교착이 아니라 **있던 방을 잠그지 않고 고친 것**이었다. 다시 문의하면 방에 안내 메시지를 남기고 방의 마지막 메시지를 옮기는데, `ChatRoom`은 버전 컬럼 없이 모든 컬럼을 덮어쓴다. 잠그지 않고 읽은 방을 저장하면 그 사이 매니저가 보낸 답이 옮겨 둔 `lastMessageId`가 안내로 되돌아간다. 고객센터 방에 두 기기가 동시에 다시 들어오면 둘 다 "나가 있음"을 보고 입장 안내를 두 번 남겼다.

그러니 잠가야 한다. 그런데 가장 자연스러운 방법인 **유니크 키로 바로 잠그는 것**은 위에서 같은 상황이 발생할 수 있다. 처음 여는 두 요청에게는 방이 없고, REPEATABLE READ에서 없는 유니크 키를 잠그면 gap lock이다.

특히, 채팅방 열기에는 **이미 중복 키 재시도 경로**가 있었다.

```kotlin
override fun open(userId: Long): ChatRoomResponse =
    ChatRoomResponse.from(
        try {
            supportChatRoomService.open(userId)
        } catch (exception: DataIntegrityViolationException) {
            // 두 번 눌렀거나 두 기기에서 동시에 눌렀다. 먼저 만들어진 방을 그대로 준다
            supportChatRoomService.get(userId)
        },
        ...
    )
```

동시에 처음 열면 하나는 유니크 제약에 걸리고, 트랜잭션 밖에서 먼저 만들어진 방을 다시 읽어 돌려준다. 사용자에게는 실패가 아니다. gap lock 교착이 생기면 이 경로가 무력해진다. 진 쪽이 받는 것은 **중복 키 오류가 아니라 교착 오류**라서, `DataIntegrityViolationException`을 잡는 재시도에 걸리지 않는다. "같은 방으로 들어간다"가 되어야 할 결과가 500으로 바뀐다.

그래서 채팅은 격리 수준이 아니라 **잠그는 대상을 바꿨다.**

```kotlin
@Query("select room.id from ChatRoom room where room.supportUserId = :supportUserId and room.deletedAt is null")
fun findIdBySupportUserId(@Param("supportUserId") supportUserId: Long): Long?
```

```kotlin
@Transactional(propagation = Propagation.MANDATORY)
fun findSupportRoomOfForUpdate(userId: Long): ChatRoom? =
    openedRoomForUpdate(chatRoomRepository.findIdBySupportUserId(userId))

/**
 * 이미 있는 방을 기본 키로 잠근다.
 * id 를 읽은 뒤 방이 지워졌으면 null 이다. 여는 쪽은 새로 만들려다 유니크 제약에 걸리고,
 * 그것은 지금까지와 같은 결과다.
 */
private fun openedRoomForUpdate(id: Long?): ChatRoom? =
    id?.let(chatRoomRepository::findByIdAndDeletedAtIsNullForUpdate)
```

```text
방이 있을 때                               방이 없을 때
──────────────                            ──────────────
id 조회 (잠그지 않음) → 42                 id 조회 (잠그지 않음) → null
PK 42 FOR UPDATE → 레코드 잠금             잠그지 않는다. gap lock 없음
재입장·안내·마지막 메시지 갱신              INSERT → 동시 요청이면 유니크 제약 위반
                                             → 트랜잭션 밖에서 되읽기 (기존 경로 그대로)
```

**있는 방만 잠근다.** 없을 때의 경쟁은 원래 설계대로 유니크 제약이 처리한다. 존재하는 기본 키를 잠그는 것은 레코드 잠금 하나라 틈을 건드리지 않는다.

### 두 답의 차이

| | 발송 기준·위치 동의 | 채팅방 |
| --- | --- | --- |
| 없을 때 동시 삽입을 막는 것 | 앞단 잠금(구장·계정) | 유니크 제약 + 트랜잭션 밖 재시도 |
| 교착을 없앤 방법 | READ COMMITTED로 gap lock 자체를 끈다 | 없는 키를 잠그지 않는다 |
| 트랜잭션 격리 수준 | 바꿨다 | 그대로(REPEATABLE READ) |

채팅 쪽에서 격리 수준을 바꾸지 않은 이유는 문의 트랜잭션에는 잠그지 않는 읽기가 섞여 있고, 그 읽기의 **시점**이 결과를 바꾼다(6장).

## 5. 엔티티를 먼저 읽으면 잠가도 옛 값이다

"id만 먼저"에는 이유가 하나 더 있다. 이게 더 찾기 어렵다.


```kotlin
val room = chatRoomRepository.findBySupportUserIdAndDeletedAtIsNull(userId)    // 엔티티로 읽고
    ?.let { chatRoomRepository.findByIdAndDeletedAtIsNullForUpdate(it.id!!) }  // 그 id 로 잠근다
```

두 번째 조회는 실제로 `SELECT ... FOR UPDATE`를 DB에 보내고, 잠금도 정말 잡힌다. 하지만 결과 행이 **이미 영속성 컨텍스트에 있는 엔티티**와 같은 id면, Hibernate는 그 행으로 엔티티를 새로 채우지 않는다. 처음 읽어 둔 **그 인스턴스를 그대로** 돌려준다. 1차 캐시가 같은 id에는 같은 객체를 보장하기 때문이다.

```text
T1                                         T2 (매니저의 답장)
──                                         ──────────────────
SELECT room (잠금 없음) → 인스턴스 r
  r.lastMessageId = 100
                                           PK 잠금 → lastMessageId = 101 → 커밋
SELECT room FOR UPDATE  (T2 커밋 뒤 획득)
  → DB 행은 101, 그러나 반환된 것은 r (여전히 100)
r 의 옛 값을 보고 판단하고 고친다
→ 버전 없는 전체 컬럼 UPDATE 가 T2 의 변경을 덮어쓸 수 있다
```

**코드는 잠근 모양이고, DB에서도 잠금이 잡혔는데, 들고 있는 값은 잠금 전의 것이다.** 잠금의 목적은 "최신 값을 보고 판단한다"인데 그 절반만 일어난다. 버전 컬럼이 없어서 충돌로 드러나지도 않는다.

id는 스칼라 값이라 영속성 컨텍스트에 아무것도 남기지 않는다. 그래서 첫 엔티티 로드가 잠금 조회가 된다. 같은 원칙이 예약 확정 쪽 주석에도 있다.

```kotlin
/**
 * **계정·티타임을 잠그기 전에 엔티티를 읽지 않는다.** 미리 읽은 계정·티타임은 영속성 컨텍스트에 남아, ...
 */
```

> 잠금 조회를 **그 트랜잭션에서 그 엔티티를 처음 읽는 조회**로 만들어야 한다. 앞에 잠그지 않은 읽기가 있으면, 잠금은 잡혀도 값이 오래된 것일 수 있다.

### 잠금 조회는 `MANDATORY`

같은 커밋에서 채팅의 잠금 조회(`getForUpdate`, `findByJoinPostIdForUpdate`, 멤버 `*ForUpdate`)를 모두 `Propagation.MANDATORY`로 바꿨다. 기본값(`REQUIRED`)이면 트랜잭션 없이 불려도 그 조회만의 트랜잭션을 열었다 닫고, 잠금도 그 순간 풀린다. 겉보기에는 잠근 코드라 리뷰에서 놓친다. 고아 파일 정리에서 쓴 것과 같은 장치다([정리 배치와 사용자 요청이 같은 행을 다툴 때](./정리_배치와_사용자_요청이_같은_행을_다툴_때.md)).

## 6. 잠그지 않는 읽기의 위치도 결과를 바꾼다

같은 커밋에서 부킹 문의가 문의한 사람의 계정을 확인하도록 고쳤다. 액세스 토큰은 탈퇴나 정지 뒤에도 만료 전까지 유효해서, 탈퇴한 계정이 매니저와의 방을 열 수 있었다. 이 확인은 **잠그지 않는** 읽기로 넣었다. 문의가 쓰는 것(방, 멤버, 안내, 문의 수)을 탈퇴나 정지 처분이 읽지 않으니, 둘이 겹쳐도 "문의 뒤 처분"이라는 직렬 순서와 결과가 같다. 지킬 불변식이 없는 곳에 계정 잠금을 더하면 같은 사람의 문의끼리만 줄을 세울 뿐이다.

문제는 그 읽기를 **어디에** 두느냐였다.

```kotlin
@Transactional
fun inquire(inquirerId: Long, teeTimeId: Long): BookingChatRoomOpened {
    val teeTime = teeTimeLookup.getForUpdate(teeTimeId)          // 1. 티타임 잠금
    val inquirer = accounts.findActiveById(inquirerId)           // 2. 잠그지 않는 확인은 그 뒤
        ?: throw IllegalArgumentException(AccountFinder.USER_NOT_FOUND_MESSAGE)
    if (inquirer.isSuspended()) throw AccountSuspendedException()
    ...
}
```

문의 트랜잭션은 REPEATABLE READ다. REPEATABLE READ의 스냅샷은 트랜잭션 시작이 아니라 **첫 번째 잠그지 않는 읽기에서** 만들어진다. 계정 확인을 티타임 잠금 앞에 두면 이렇게 된다.

```text
T1 (같은 매니저에게 첫 문의)               T2 (같은 매니저에게 동시 문의)
──────────────────────────                ──────────────────────────
                                           계정 확인 → 스냅샷 S 생성 (방 없음)
티타임 잠금 → 방 생성 → 커밋
                                           티타임 잠금 획득 (T1 커밋 뒤)
                                           방 id 조회 (잠그지 않는 읽기 → 스냅샷 S)
                                             → 방 없음  ← T1 의 방이 안 보인다
                                           INSERT → 유니크 제약 위반 → 재시도
```

재시도가 있으니 결과는 맞다. 하지만 정상 경로로 끝날 수 있는 요청이 **매번** 롤백과 재시도로 돈다. 확인을 잠금 뒤로 옮기면 스냅샷이 잠금 대기가 끝난 뒤에 만들어진다. 그러면 T2가 T1의 방을 보고 그 방으로 들어간다. 중복 키 재시도는 **마지막 방어선**으로만 남는다.

채팅 쪽에서 격리 수준을 내리지 않았는데도 동작하는 것은 이런 순서 조정 덕분이다. 이 트랜잭션에 잠그지 않는 읽기를 하나 추가할 때마다 그 위치를 다시 봐야 한다.

## 7. 테스트는 첫 트랜잭션을 커밋 직전에 붙잡는다

동시성 결함은 "두 스레드를 동시에 출발"시켜서는 잘 재현되지 않는다. 테스트 지원 코드에 첫 업무를 **쓰기까지 한 뒤 커밋하지 않고 붙잡아 두는** 도구가 있다.

```kotlin
/** **첫 업무의 실제 쓰기 잠금을 커밋까지 유지**하여 후속 요청의 대기와 최신 상태 재검사를 검증한다. */
fun <T : Any> raceWithUncommittedWrite(
    transactions: PlatformTransactionManager,
    first: () -> T,
    second: () -> T,
): Pair<T, T> {
    ...
    // first 를 트랜잭션 안에서 실행하고 written 신호 뒤 commit 신호까지 기다린다
    // second 를 출발시키고, 250ms 안에 끝나지 않는 것(=잠금에 막혀 있음)을 확인한다
    assertThatThrownBy { b.get(250, TimeUnit.MILLISECONDS) }.isInstanceOf(TimeoutException::class.java)
    commit.countDown()
    return a.get(15, TimeUnit.SECONDS) to b.get(15, TimeUnit.SECONDS)
}
```

두 번째가 **정말로 기다렸는지**를 먼저 단언하고, 그 다음에 결과를 본다. 잠금이 없으면 두 번째가 250ms 안에 끝나 첫 단언에서 실패한다. 이번에 추가된 시나리오는 두 가지다.

- 나갔던 고객센터 방에 두 기기가 동시에 다시 문의해도 **입장 안내는 하나만** 남는다
- 다시 문의하는 사이 매니저가 답해도 **방의 마지막 메시지는 그 답**이다

둘 다 "있는 방을 잠근다"를 검증한다. 방이 없을 때의 경쟁(중복 키 → 트랜잭션 밖 재시도)은 기존 테스트가 이미 보고 있었고, 그 테스트가 계속 통과하는 것이 "gap lock 교착으로 재시도가 무력해지지 않았다"는 확인이다.

## 8. 남아 있는 것

**발송 기준의 격리 수준 요구는 KDoc에만 있다.** `registered()`는 `MANDATORY`라 트랜잭션이 있는 것은 보장하지만, 그 트랜잭션이 READ COMMITTED인지는 보장하지 않는다. 새 입구가 이 메서드를 기본 `@Transactional`로 부르면 교착이 조용히 돌아온다. 현재 트랜잭션의 격리 수준은 `TransactionSynchronizationManager.getCurrentTransactionIsolationLevel()`로 읽을 수 있다. 그러니 `MANDATORY`처럼 실행 중에 확인하게 만들 수도 있다. [문서에만 있던 규칙은 지켜지지 않는다](./문서에만_있던_규칙은_지켜지지_않는다.md)에서 정리한 그대로다.

**READ COMMITTED로 연 유스케이스가 늘었다.** 예약, 티타임 등록, 위치 동의, 조인의 여러 경로가 각자의 이유로 READ COMMITTED다. 경로마다 "잠그지 않는 읽기에 판단을 기대지 않는다"를 확인했지만, 이 확인은 코드가 바뀔 때마다 다시 해야 한다. 기본 격리 수준을 전역으로 READ COMMITTED로 바꾸는 선택지도 있지만, 그러면 6장처럼 REPEATABLE READ 스냅샷 시점에 기대는 코드의 전제가 함께 바뀐다. 지금은 유스케이스 단위로 근거를 적는 쪽을 택했다.

---

## 느낀 점

**"먼저 잠그고 없으면 넣는다"는 행이 있을 때만 안전하다.** 같은 `SELECT ... FOR UPDATE`라도 행이 있으면 레코드 하나를 잠그고, 없으면 다음 레코드 앞의 틈을 잠근다. 틈 잠금은 다른 트랜잭션도 함께 잡을 수 있으므로, 같은 코드가 첫 요청과 두 번째 요청에서 서로 다른 잠금을 잡는다. 이 패턴을 쓸 때는 행이 없는 경우에 무엇이 잠기는지 따로 확인해야 한다.

**앞단 잠금이 순서를 정하는 범위와 gap lock이 걸리는 범위는 다르다.** 구장 행 잠금은 같은 구장의 요청끼리만 순서를 정한다. gap lock은 인덱스에서 이웃한 키 전체에 걸리므로, 서로 다른 구장의 요청이 같은 틈을 잠글 수 있다. 잠금을 설계할 때 "어떤 요청끼리 순서가 정해지는가"와 "어떤 요청끼리 같은 잠금 대상을 쓰는가"를 각각 적어 보면 이 차이를 확인할 수 있다.

**해결 방법이 둘로 나뉜 기준은 "행이 없을 때 중복 삽입을 무엇이 막는가"였다.** 발송 기준은 구장 행 잠금이 중복을 막으므로 gap lock이 필요 없었고, READ COMMITTED로 gap lock을 껐다. 채팅방은 유니크 제약과 재시도가 중복을 막으므로, 없는 키를 잠그지 않는 방식으로 바꿨다. 두 경우 모두 gap lock을 없애기 전에 그 역할을 다른 장치가 이미 맡고 있는지 확인했다.

**잠금을 얻은 것과 최신 값을 읽은 것은 별개다.** 같은 엔티티를 잠그기 전에 읽어 두면, 잠금 조회는 DB에 `FOR UPDATE`를 보내 잠금을 얻지만 영속성 컨텍스트에 있던 이전 인스턴스를 돌려준다. SQL 로그만으로는 이 문제가 드러나지 않는다. 잠금이 의도대로 동작하는지 확인하려면 "그 트랜잭션에서 그 엔티티를 처음 읽는 조회가 잠금 조회인가"를 봐야 한다.

**교착은 기존 예외 처리가 기대하는 예외 종류를 바꾼다.** 채팅방의 재시도는 중복 키 예외(`DataIntegrityViolationException`)를 잡도록 작성돼 있었다. gap lock 교착이 생기면 같은 경쟁 상황에서 교착 예외가 발생하고, 요청은 재시도를 거치지 않고 500으로 끝난다. 교착이 생길 수 있는 경로에서는 성능뿐 아니라 기존 예외 처리가 여전히 동작하는지도 확인해야 한다.

---

## 정리

- InnoDB의 잠금은 값이 아니라 **인덱스 레코드에 붙는다.** 없는 키는 붙일 레코드가 없어서, 그 키 다음 레코드 앞의 틈에 `X,GAP`이 걸린다(다음 레코드가 없으면 supremum). 행이 있으면 같은 문장이 레코드 잠금(`X,REC_NOT_GAP`)만 건다
- REPEATABLE READ에서 **없는 키를 `FOR UPDATE`로 읽으면 gap lock**이 걸린다. gap lock끼리는 충돌하지 않고 INSERT의 insert intention lock과 충돌하므로, 같은 틈을 쥔 두 트랜잭션이 각자 INSERT하면 교착한다
- 서로 다른 키라도 **인덱스에서 이웃한 빈자리**면 같은 틈에 떨어진다. 구장·계정 같은 앞단 잠금은 **같은 대상끼리만** 줄을 세우므로 이것을 막지 못한다
- 첫 번째 답: **READ COMMITTED**는 검색에 gap lock을 쓰지 않는다. 단, 판단이 **잠금 읽기**에만 기대는지 경로마다 확인해야 한다. 같은 키 중복은 앞단 잠금과 유니크 키가 막는다
- `isolation`은 **트랜잭션을 여는 메서드에서만** 적용된다. 참여하는 메서드의 값은 무시되므로 모든 입구에 달아야 한다
- 두 번째 답: **id만 잠그지 않고 읽은 뒤 기본 키로 잠근다.** 있는 행만 레코드 잠금으로 잠그고, 없을 때의 경쟁은 유니크 제약 + 트랜잭션 밖 재시도에 맡긴다
- 교착은 중복 키 오류가 아니라 **교착 오류**로 끝나서, `DataIntegrityViolationException`을 잡는 기존 재시도를 무력화한다
- 엔티티를 먼저 읽어 두면 잠금 조회가 **영속성 컨텍스트의 옛 인스턴스**를 돌려준다. 잠금 조회가 그 엔티티의 첫 로드가 되게 한다
- REPEATABLE READ의 스냅샷은 **첫 잠그지 않는 읽기**에서 만들어진다. 그 읽기를 잠금 대기 뒤로 옮겨야 앞선 트랜잭션의 커밋이 보인다
- 동시성 테스트는 첫 트랜잭션을 커밋 직전에 붙잡고, 두 번째가 **실제로 기다렸는지**부터 단언한다
