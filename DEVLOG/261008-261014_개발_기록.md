## 2. 기획 확정본을 따라가며

10-09 기획 개정은 23개 문서 전체였다. 바로 고치기 시작하지 않고, 먼저 **서버가 기획과 어디서 다른지를 감사 문서로 정리했다**. 항목마다 고유 ID를 붙여 두었다. 뒤따른 PR들이 커밋 메시지와 KDoc에서 그 ID를 가리킨다. 어떤 결정이 어떤 PR로 들어갔는지 ID 하나로 추적할 수 있다.

### 2-1. 배포 중에는 옛 코드가 옛 값을 다시 쓴다

연령대 선택지 "50대 이상"이 "50대"와 "60대 이상"으로 나뉘었다. 저장된 값은 V98이 "50대"로 옮긴다. 서버는 생년월일로 연령대를 계산하지 않기 때문에, 50대인지 60대인지를 알 수 없다. 출시 전이라 영향받는 회원이 직접 다시 고르면 된다.

처음 버전은 enum에서 `FIFTIES_PLUS`를 지웠다. 리뷰에서 문제가 나왔다. **롤링 배포 중에는 옛 태스크가 아직 돌면서 `FIFTIES_PLUS`를 다시 저장할 수 있다.** 새 태스크는 그 값을 enum으로 읽지 못해 회원 로딩에 실패하고, 그 회원이 포함된 목록이 전부 500이 된다.

그래서 옛 값을 **읽기 전용으로** 남겼다.

| 자리 | 처리 |
| --- | --- |
| 입력 (프로필·모집 조건) | 옛 값은 400. 선택지만 받는다 |
| 읽기 (`User.ageGroup`) | `FIFTIES_PLUS`를 `FIFTIES`로 읽는다 |
| 모집 조건 응답 | 저장된 (50, null)을 (50, 59)로 바꿔서 내린다. 앱이 모르는 값을 받지 않게 |
| 목록 필터 | 옛 앱이 보내는 `ageFrom=50`만 있는 요청도 받는다. 목록과 지도 전체가 400이 되지 않게 |

```kotlin
val LEGACY_FIFTIES_PLUS = AgeCondition(50, null)
// 응답: 저장된 옛 조건은 50대로 읽는다
AgeCondition(minAge, maxAge).let { if (it == LEGACY_FIFTIES_PLUS) FIFTIES else it }
```

옛 태스크가 모두 내려간 뒤에 V98과 같은 UPDATE를 한 번 더 돌리는 마이그레이션으로 이 처리를 걷어 낸다. 지난주의 "컬럼 제거는 두 번에 나눠 배포한다"와 같은 원리다. **값을 없앨 때도 읽는 쪽이 먼저 준비돼야 한다.**

같은 종류의 문제가 하나 더 있었다. 조인 삭제 제안의 기한이 지나면 1분 배치가 "만료" 상태로 확정하고 방에 안내를 남기게 했다. 그런데 배포 직후 첫 배치는 **며칠, 몇 주 전에 기한이 지난 제안까지** 모두 확정한다. 아직 열린 방마다 늦은 "삭제 제안이 만료되었습니다"가 찍히고, 그 방들이 채팅 목록 맨 위로 올라온다. 그 제안들은 조회할 때 이미 만료로 보이고 있었으니 참여자에게 새로 알릴 것이 없었다. 그래서 V100이 밀린 제안을 **안내 없이** 만료로 표시하고, 배치는 그 뒤에 생기는 것만 처리한다.

### 2-2. REPEATABLE_READ는 행을 고정하지만 시각은 고정하지 않는다

10-09 기획은 위치 기능 없이 출시한다. 그래도 골프장 지도는 연다. 골프장 좌표는 사용자의 위치 정보가 아니기 때문이다. 지도 핀의 건수도 고쳤다. 예전에는 최대 500개까지 불러온 카드를 세어서 핀 숫자를 만들었다. 카드가 잘리면 핀 숫자가 줄어들거나 핀이 사라졌다. 이제 골프장별 `GROUP BY`로 따로 센다.

건수 쿼리와 카드 쿼리는 같은 REPEATABLE_READ 트랜잭션에서 읽는다. 그래서 두 쿼리가 같은 행을 본다. 하지만 리뷰에서 빈틈이 하나 나왔다. **두 쿼리가 "오늘", "지금", 매니저 정지 판정에 쓸 시각을 각자 시계에서 읽고 있었다.** 자정이나 티오프 경계를 사이에 두면 둘이 다른 집합을 센다. 카드에는 있는 골프장이 건수에는 없을 수 있었다.

```kotlin
@Transactional(readOnly = true, isolation = Isolation.REPEATABLE_READ)
override fun map(...): TeeTimeMapResponse {
    val at = clock.instant()   // 기준 시각은 한 번만 읽는다
    val golfCourseCounts = teeTimeLookup.mapCountsByGolfCourse(search, favorites, at)
    val page = teeTimeLookup.searchForMap(search, favorites, at)
    ...
    // 카드가 있는 골프장은 반드시 건수에도 있다. 없으면 대체값으로 덮지 않고 실패한다
    TeeTimeMapGroup(teeTimes.first().golfCourse, itemCounts.getValue(id), teeTimes)
}
```

시각을 한 번만 읽어서 두 쿼리에 넘긴다. 같은 행과 같은 시각을 보면 카드가 있는 골프장에는 반드시 건수가 있다. 그래서 "건수가 없으면 카드 수를 쓴다"던 대체 처리도 지웠다. **버그를 가리던 안전장치는 버그를 고치면 지운다.**

### 2-3. 이미 보낸 알림 조건은 잠그지 않는다

티타임 알림은 티타임 등록 트랜잭션 안에서 맞는 조건을 찾는다. 조건 행을 번호 순으로 잠그고, (조건, KST 날짜) 유니크 행으로 하루 한 번만 보낸다.

처음 버전은 맞는 조건을 **모두** 잠갔다. 오늘 이미 보낸 것도 포함해서다. 인기 있는 날짜의 조건은 하루 종일 모든 골프장의 등록과 맞는다. 그러면 모든 등록이 그 조건 행 하나에 줄을 선다.

발송 기록은 조건과 함께만 지워지므로 "오늘 보냈다"는 사실은 그날 내내 참이다. 그래서 **잠그지 않고 읽어서 이미 보낸 것을 먼저 빼도 안전하다.** 남은 ID만 번호 순으로 잠그고, 그 사이 커밋된 기록이 있는지 한 번 더 확인한다.

리뷰에서 나온 것이 하나 더 있다. 조건 매칭 쿼리는 목록 필터를 손으로 뒤집어 옮긴 것이다. 그래서 **"목록이 이 티타임을 돌려준다 ⇔ 같은 조건이 이 티타임과 맞는다"** 를 시간대 경계(초 단위 포함), 공개 여부, 2·3·4인, 식사, 지역, 이름까지 항목마다 확인하는 테스트를 붙였다. 같은 판정을 두 곳에서 하면 두 곳이 같은지를 테스트가 지켜야 한다.

### 2-4. 유니크 키에 NULL을 넣으면 막히지 않는다

신고는 예전에 (신고자, 대상) 유니크라 전역에서 한 번만 할 수 있었다. 기획은 "같은 조인에서 같은 대상은 한 번"이다. 그래서 같은 사람의 두 번째 무단 불참을 다른 조인에서 신고할 수 없었다. 무단 불참 2회가 영구정지의 근거인데 말이다.

`join_post_id`를 유니크 키에 그냥 넣으면 안 된다. MySQL 유니크는 NULL을 서로 다른 값으로 본다. 조인 없는 신고가 몇 번이고 들어간다. 그래서 NULL이 없는 생성 열을 두었다.

```sql
ALTER TABLE reports
    ADD COLUMN context_key VARCHAR(20)
        GENERATED ALWAYS AS (CASE
            WHEN target_type = 'USER' AND join_post_id IS NOT NULL THEN CONCAT('J', join_post_id)
            ELSE '-'
        END) STORED NOT NULL;
```

회원 신고만 조인을 맥락으로 쓴다. 모집글·메시지·채팅방은 대상 자체가 맥락을 정하기 때문이다. 리뷰에서 옛 행 문제도 나왔다. 예전에는 티타임 신고도 요청에 온 조인을 저장했다. 저장된 `join_post_id`를 유형과 관계없이 키에 쓰면 옛 행은 `J<조인>`, 같은 대상의 새 신고는 `-`가 되어 중복이 통과한다. **유형별 규칙으로 키를 정해야 옛 행도 새 신고와 같은 키를 얻는다.** 애플리케이션의 `Report.contextKeyOf`와 SQL이 같은 식이어야 사전 확인(409)과 유니크가 같은 것을 막는다.

지난주에는 탈퇴자 후기의 작성자를 NULL로 비워서 **일부러** 유니크를 피했다. 이번에는 같은 성질 때문에 생성 열을 썼다. 같은 성질을 반대 방향으로 쓴 셈이다.

## 3. 기간이 끝난 기록은 지우고, 법이 남기라는 기록은 떼어 둔다

개인정보처리방침은 보관 기간을 **상한**으로 적는다. 그런데 서버는 기간이 지나도 지우지 않는 기록이 많았다. 탈퇴한 계정의 ID도 운영자와 매니저가 매일 읽는 표에 그대로 남아 있었다. 10/10에 PR 세 개로 이 둘을 정리했다.

### 3-1. 두 가지 일

| 일 | 대상 | 방식 |
| --- | --- | --- |
| **보관 기간 파기** | 탈퇴 1년 뒤 제재 원장·처분 이력, 닫힌 지 1년(고객센터는 3년) 지난 채팅, 마케팅 푸시 수신 기록 | 행을 물리 삭제 |
| **법정 보존 기록 분리** | 탈퇴 계정이 걸린 끝난 예약(5년), 처리된 신고(3년), 게시물 조치, 표시·광고 기록(6개월) | 원본 행을 AES-GCM 사본으로 봉인하고, 운영 표의 계정 칸만 비운다 |

선정은 privacy 슬라이스가 하고, 삭제와 칸 비우기는 각 표를 가진 슬라이스가 privacy.required 계약을 구현해서 한다. 예약 파기와 같은 분업이다. 탈퇴가 user → privacy로 흐르기 때문에 privacy가 다른 슬라이스의 provided를 부르면 순환이 생긴다.

### 3-2. 리뷰에서 나온 것들

이 세 PR은 리뷰를 여러 번 거쳤다. 지적들을 모아 보면 대부분 **"다른 배치나 다른 규칙과 어긋나지 않는가"** 였다.

| 지적 | 처리 |
| --- | --- |
| 분리 배치가 10분마다 예약·신고·사본 **표 전체를** 훑었다 | 아직 분리하지 않은 탈퇴 계정 목록에서 출발한다. `users.deleted_at` 인덱스로 찾고, 늦은 커밋을 고려해 하루를 겹쳐 본다. 계정마다 칸별 인덱스로 찾는다 |
| 예약 분리와 신고 분리가 한 트랜잭션에서 **예약 → 신고** 순으로 잠갔다. 보존 기간 파기는 **신고 → 예약** 순이다 | 계정·슬라이스마다 따로 커밋한다. 반대 순서 잠금이 한 트랜잭션에 같이 있지 않게 |
| 실패한 계정이 계속 맨 앞에서 재시도됐다 | 실패하면 본 시각만 별도 트랜잭션으로 기록해서 줄 뒤로 보낸다 |
| 신고자 칸을 비우면 "서로 다른 신고자 3명이면 가림" 집계에서 탈퇴자가 빠진다 | 칸을 비운 신고는 사본의 원래 신고자로 센다. 같은 사람이 두 조인에서 신고했으면 한 명이다 |
| 채팅 보관은 "신고가 걸린 방은 처리 완료부터 3년"인데, 신고 원장이 먼저 지워지면 방이 신고 없는 방으로 보여 일찍 지워졌다 | 방 보관 기산점을 신고 원장 파기와 같은 시각으로 맞췄다 |
| 게시물 조치를 신고와 함께 지우면 채팅 보관이 붙잡던 방이 일찍 풀린다 | 조치는 조치부터 3년이 지나고 이어진 신고도 없어졌을 때 지운다 |
| 처리되지 않은 티타임 신고가 걸린 티타임의 예약까지 분리했다 | 그 신고가 처리될 때까지 두고 다음 회차에 다시 본다 |
| 채팅 파기가 100개 방을 한 트랜잭션에서 넓게 잠가 신고 접수가 기다렸다 | 방마다 READ_COMMITTED 트랜잭션에서 방 → 메시지 → 신고 범위 순으로 잠근다. 모든 범위에 인덱스를 둔다 |

지난주 정리에 "여러 자격이 쓰는 정의는 한 곳에 둔다"를 적었다. 이번 주에는 **기간**이 그 대상이었다. 채팅 보관, 신고 원장 파기, 게시물 조치 파기가 서로의 존재를 근거로 삼는다. 그래서 하나의 기산점이 어긋나면 다른 하나가 일찍 풀린다.

### 3-3. 시작이 막히지 않게

출시 제휴 상품은 서버 설정의 고정 데이터다. 설정으로 넣은 상품도 표시·광고 기록을 남겨야 해서, 기동할 때 설정과 마지막 기록을 비교해서 바뀐 것만 남기게 했다. 여러 인스턴스가 한 번만 기록하도록 잠금 행으로 직렬화한다.

처음 버전은 **매번 기동할 때마다** 잠금을 잡았다. 바뀐 게 없어도 잠금 행이 없거나 잠금을 기다리면 배포가 기동에 실패할 수 있었다. 이제 잠그지 않고 먼저 비교하고, 차이가 있을 때만 잠근 뒤 다시 읽고 기록한다. 잠금 행이 지워졌으면 `insert ignore`로 다시 만든다. **기동은 차이가 있는데 기록하지 못했을 때만 실패한다.**

## 4. 상태 코드는 앱의 다음 행동이다

10/12에 dev에서 E2E QA를 돌렸고, 그 후속을 PR 하나로 고쳤다. 고친 것을 보면 **응답 코드가 앱에 잘못된 행동을 시키던** 경우가 많았다.

| 상황 | 예전 | 이제 | 이유 |
| --- | --- | --- | --- |
| 내 계정에 등록되지 않은 기기 토큰으로 열람 갱신·실시간 티켓 요청 | 401 | 409 `DEVICE_NOT_REGISTERED` | 앱은 401을 세션 만료로 읽고 토큰 갱신이나 로그아웃을 한다. 서버는 FCM이 무효라고 한 토큰을 지우므로 정상 앱도 이 상황을 만난다 |
| 출시 설정으로 꺼 둔 위치 기능 요청 | 503 | 409 `LOCATION_FEATURE_DISABLED` | 결정으로 끈 것이지 장애가 아니다. 503이면 모니터링이 서버 오류로 세고 앱은 재시도한다 |
| 필수 쿼리 파라미터·헤더 누락 | 스프링 기본 응답, 비회원은 401 | 400 `INVALID_REQUEST` | `/error`가 인증을 요구해서 비회원에게 401이 갔다 |
| 공개 GET(`/terms` 등)에 망가진 토큰 | 401 | 비회원으로 처리 | 다른 공개 GET과 같게 |
| 정지된 고객의 예약 확정 시도 | `ACCOUNT_SUSPENDED` | 409 | 앱은 그 코드를 **요청한 사람 본인**의 정지로 읽는다 |
| 모든 매니저 기능의 403 | "예약 관리 권한이 없습니다." 하나 | 매니저 제한·권한 없음·남의 티타임을 나눔 | 앱이 원인별로 다른 화면을 보여 줘야 한다 |

지난주에 "같은 거절이라도 원인이 누구에게 있는지에 따라 오류 코드를 나눈다"를 적었다. 이번 주에는 그 상태 코드를 **받은 앱이 무엇을 하는지**까지 봐야 했다. 401은 "다시 로그인하라", 503은 "잠시 뒤 다시 시도하라"는 지시다. 그 지시가 맞지 않는 상황에 그 코드를 내면 앱은 멀쩡한 세션을 버리거나 의미 없는 재시도를 한다.

QA에서 나온 나머지도 적어 둔다.

- **로그아웃이 남의 리프레시 토큰도 지웠다.** 이제 저장된 소유자를 키를 지우는 같은 Lua 호출에서 확인한다. 남의 토큰은 조용히 무시해서 토큰이 살아 있는지도 드러내지 않는다.
- **이미 푼 정지가 되살아났다.** 제재를 무효로 하면 남은 제재로 정지를 다시 계산하는데, 운영자가 정지를 푼 사실은 원장에 없었다. 그래서 30일 제재 하나를 무효로 하자 이미 풀린 영구정지가 다시 걸렸다. 이제 정지가 끝난 마지막 시각(V106)을 남기고, 그 뒤의 제재만 본다.
- **`%` 검색이 전부를 돌려줬다.** LIKE 패턴을 키워드로 바로 만들었다. 저장된 티타임 알림 키워드가 `%`이면 모든 티타임과 맞는다. 쿼리 안에서 `!`를 escape 문자로 써서 이스케이프한다. 백슬래시는 HQL 리터럴에서 MySQL 자체의 문자열 이스케이프와 겹친다.
- **자기 글을 자기가 신고할 수 있었다.** 그 신고가 "신고자 3명이면 가림"에 들어갔다.
- **지운 공지를 가리키는 배너가 홈에 남아 404로 이어졌다.** 공지·글은 운영자, 모집자, 탈퇴 등 지우는 경로가 여럿이라 그때마다 배너를 함께 내리는 것은 다 막기 어렵다. 그래서 공개 배너 목록에서 대상이 없는 배너를 뺀다. 켜진 배너는 많아야 5장이라 조회도 많아야 5번이다.

### 4-1. 정지 회원의 실시간 스트림

QA 전날(10/10) 비슷한 경우가 하나 더 있었다. 정지 회원은 고객센터 방만 읽을 수 있다. HTTP는 그것을 지키고 있었다. 그런데 고객센터 답변을 받으려고 정지 중에도 실시간 티켓은 발급하고, 채팅 실시간 발행 네 곳(메시지, 입력 중, 퇴장, 읽음)은 **방의 활성 멤버**로 수신자를 골랐다. 정지 회원도 멤버 행은 그대로라서, 열 수 없는 방의 본문과 보낸 사람이 SSE로 흘러갔다.

모든 채팅 실시간 이벤트를 `ChatRealtimeDelivery` 한 곳으로 보내고, 그 자리에서 정지·탈퇴 계정을 계정 조회 한 번으로 거른다. 방이나 멤버에 표시를 남기지 않고 **보내는 시점에** 판단하므로, 정지가 풀리면 바로 다시 받는다. ArchUnit으로 application에서 실시간 발행은 이 클래스만 하게 묶었다. 새 발행 경로가 이 규칙을 건너뛸 수 없다.

## 5. 넘칠 때 거절하고, 거절한 것을 읽을 수 있게 남긴다

### 5-1. 부하 테스트 스크립트

현재 구성이 얼마나 버티는지 알고 싶었다. API 태스크 2개·4개일 때의 TPS, 오토스케일링이 따라가는지, 게이트웨이 태스크 하나가 SSE 연결을 몇 개나 들고 있는지. dev에서 재면 QA 트래픽이 섞이고 태스크 수도 prod보다 적다. 그래서 **prod 사양의 일회성 환경을 세우고, 재고, 내리는** 스크립트를 만들었다.

| 결정 | 이유 |
| --- | --- |
| GitHub Actions가 아니라 로컬에서 돌린다 | 호스팅 러너는 미국에 있다. 서버가 아니라 태평양 왕복을 재게 된다 |
| 시드 데이터는 API로만 넣는다 | 데이터가 운영과 같은 불변식을 지킨다. 첫 어드민만 API가 없어 같은 VPC의 일회성 mysql 태스크로 UPDATE한다. DB는 계속 닫혀 있다 |
| 고정 도착률을 단계별로 올리고, **보낸 부하의 95%를 오류 1% 미만으로 처리한 마지막 단계**를 최대로 본다 | 지연 목표가 아직 없어서 지연은 단계마다 보고만 한다 |
| SSE는 작은 asyncio 클라이언트로 잰다 | k6는 열려 있는 이벤트 스트림과 시간 초과된 요청을 구분하지 못한다 |
| 태스크 정의는 배포 워크플로의 렌더러로 만든다 | 둘이 서로 어긋날 수 없다 |

한 번 돌리는 데 4~5시간이 걸린다. 노트북이 그동안 깨어 있어야 하고, 노트북 자체가 병목이 될 수도 있다. 그래서 CodeBuild에서 도는 `remote` 모드를 붙였다. 지켜보는 사람이 없으므로 측정이 실패해도 **환경은 반드시 내린다.** 결과는 내리기 전과 후에 두 번 올린다. 내리기가 멈춰도 결과를 잃지 않게 하려는 것이다.

### 5-2. 스크립트가 멈춘 이유들

처음 며칠은 서버보다 스크립트가 먼저 멈췄다. 하나하나는 작지만, 모두 **도구가 내가 생각한 뜻으로 답하지 않았던** 경우였다.

| 증상 | 원인 |
| --- | --- |
| SSE 측정이 연결을 하나도 못 열었을 것이다 (코드 검토 중 발견) | `urllib`은 body가 있으면 form content type을 붙인다. 티켓 API가 415로 답한다 |
| 두 번째 실행이 "이미 돌고 있다"며 거절됐다 | ECS는 지운 클러스터를 `INACTIVE`로 남긴다. `grep -q ACTIVE`가 그것도 잡았다 |
| 시드가 중간에 멈췄다 | 김포·양평 골프장을 시드는 경기 북부로 넣었는데, 서버는 경기 남부로 판정하고 맞지 않는 쌍을 거절한다. 한 행이 틀리면 일괄 요청 전체가 실패한다 |
| 시드가 시작 7초 만에 502를 받았다 | `services-stable`은 컨테이너가 떴는지만 본다. 로드 밸런서의 대상이 모두 healthy가 될 때까지 기다리게 했다 |
| 밤새 돌던 실행이 `ThrottlingException`으로 멈췄다 | SSM 파라미터를 연달아 쓰는데 CLI는 기본으로 두 번만 재시도한다. adaptive 모드로 최대 10번 재시도한다 |
| `down`이 태스크 정의 26개를 남겼다 | `--family-prefix`는 접두사가 아니라 정확한 이름으로 비교한다 |
| `down`이 매번 "남은 자원이 있다"고 경고했다 | 태깅 API는 지운 ECS 자원을 몇 시간 동안 계속 돌려준다. 진짜 남은 것이 경고에 묻혔다 |

모니터 쪽도 고민이 있었다. 부하 테스트는 일부러 5xx를 낸다. 처음에는 API 서비스 태그가 붙은 모니터를 모두 음소거했는데, 그러면 dev의 컨테이너·RDS 경보까지 실행 내내 꺼진다. 인프라 쪽 모니터를 환경별로 나누고, 스크립트는 시작 전에 **모든 모니터가 loadtest 환경을 보지 않는지** 확인한다. 이번 주 마지막에는 환경별 모니터를 `env IN (dev, prod)` 하나로 합치기로 해서 IN 목록도 받게 했다. **`NOT IN`은 여전히 거절한다.** 제외 목록은 나중에 만드는 일회성 환경을 모두 통과시킨다.

### 5-3. 바빴을 뿐인 태스크가 교체됐다

10/13 측정에서 처리 용량을 넘기자 모든 요청이 느려졌다. Tomcat은 끝없이 줄을 세웠고, 요청은 Hikari 기본값인 최대 30초까지 커넥션을 기다렸다. p50이 초 단위, p95가 8~32초였다. 앱이 이미 포기한 뒤에 돌아온 응답은 아무에게도 쓸모없는 일이었다.

더 나쁜 일도 있었다. 넘친 태스크가 ALB 헬스 체크에 실패했다. `/actuator/health`는 MySQL과 Redis까지 확인한다. 커넥션 풀이 바닥났고, 헬스 체크도 같은 요청 스레드 뒤에 줄을 서다 5초 제한을 넘겼다. **ECS는 바빴을 뿐인 태스크를 교체했고, 새 태스크가 뜨는 데 3분이 넘게 걸렸다.** 용량이 가장 필요한 순간에 용량이 줄었다.

10/14에 이것을 세 단계로 고쳤고, 그중 하나는 같은 날 다시 되돌렸다.

1. **DB를 기다리지 않는 생존 확인.** liveness 그룹은 앱 자신의 상태만 본다. 그것을 `/livez`로 열었다. 관리 포트(8090)로 분리해서 헬스 체크가 별도 스레드 풀을 쓰게 했다.
2. **동시 처리 상한.** Spring Security보다 앞의 필터가 태스크당 동시에 30건만 받고, 나머지는 바로 503 `SERVER_BUSY`와 `Retry-After`로 돌려보낸다. 거절된 요청은 토큰 검사와 계정 재조회도 건너뛴다. 헬스 체크는 세지 않는다. 바쁜 태스크의 헬스 체크를 거절하면 그 태스크가 교체된다. 커넥션을 3초 안에 받지 못한 요청도 같은 503이다.
3. **헬스 체크를 다시 요청 포트로.** 관리 포트로 뺀 이유는 헬스 체크가 요청 스레드 뒤에 줄 서지 않게 하는 것이었다. 상한이 스레드를 남겨 두니 그 이유가 없어졌다. 그리고 관리 포트에는 다른 문제가 있었다. **실제 트래픽이 오지 않는 포트라서, 요청 포트가 망가진 태스크도 통과시킨다.** 헬스 체크는 사용자가 오는 길로 해야 한다.

### 5-4. 거절 로그에 숫자 대신 람다 이름이 찍혔다

넘친 순간에는 거절이 초당 수백 건이 될 수 있어서, 로그는 일정 간격마다 "그 사이 몇 건 거절했다"를 한 줄로 모아 남기게 했다. 다음 측정에서 실제로 찍힌 줄은 이랬다.

```text
RequestAdmissionFilter$$Lambda/0x...@...
```

원인은 이름 가림이었다. 파일 최상단에 `private val logger = KotlinLogging.logger {}`를 두었는데, 필터는 `OncePerRequestFilter`를 상속한다. 그 부모인 `GenericFilterBean`에 **protected `logger` 필드(commons-logging)** 가 있다. 클래스 안에서 `logger`라는 이름은 파일 수준 변수보다 상속받은 멤버가 먼저 잡힌다.

```kotlin
logger.warn { "Rejected $count requests ..." }
// KotlinLogging 의 warn(() -> Any?) 가 아니라
// commons-logging 의 Log.warn(Object) 가 불렸다. 람다 객체 자체가 메시지가 됐다.
```

`Log.warn(Object)`는 무엇이든 받으므로 컴파일도 통과한다. 고친 것은 이름 하나다.

```kotlin
// `logger`라고 지으면 안 된다. 부모 GenericFilterBean 의 protected `logger`(commons-logging)가 클래스 안에서 이 이름을
// 가려, `logger.warn { }`이 Log.warn(Object)에 람다 객체를 넘기고 로그에는 람다의 이름만 남는다(2026-10-14 부하 테스트).
private val admissionLogger = KotlinLogging.logger {}
```

그리고 **운영자가 과부하 중에 실제로 읽게 될 그 줄**을 테스트로 확인하게 했다.

### 5-5. ARM64로 같은 일을 20% 싸게, 그리고 상한 다시 계산

Fargate ARM64는 같은 vCPU·메모리에서 x86보다 20% 싸다. 서울 리전 기준 vCPU 시간당 $0.03725 대 $0.04656이다. 베이스 이미지와 두 사이드카 모두 arm64를 내고, 네이티브 바이너리를 싣는 의존성도 없었다.

```dockerfile
# 빌드 단계는 러너의 아키텍처에서 돈다. jar 는 아키텍처를 타지 않으므로
# 한 번 만들어 amd64·arm64 실행 이미지에 함께 쓴다.
FROM --platform=$BUILDPLATFORM eclipse-temurin:25-jdk AS builder
```

이 줄이 없으면 arm64 이미지의 Gradle 빌드 전체가 QEMU 에뮬레이션 위에서 돌아 몇 배 느려진다. 이미지 하나에 두 아키텍처를 같은 태그로 담아 두었으므로, 되돌릴 때는 다시 빌드하지 않고 태스크 정의만 바꾸면 된다.

ARM64로 옮기자 같은 0.5 vCPU 태스크가 초당 약 65건에서 약 110건까지 처리했다. 그런데 상한 30은 x86에서 정한 값이었다. 상한은 **"받아들인 요청은 0.5초 안팎에서 끝낸다"를 지키는 값**이다. 처리량이 바뀌었는데 상한은 그대로라, 포화와 거리가 먼 초당 60건(CPU 60%)에서도 짧은 버스트에 0.1~0.4%가 거절됐다. 50 / 110 ≈ 0.45초라서 50으로 올렸다.

같은 실행에서 거절이 제 역할을 한다는 것도 확인했다.

| 조건 | p95 | 거절 |
| --- | --- | --- |
| x86, 상한 없음, 과부하 | 8~32초 | 0% (모두 줄을 섰다) |
| ARM64, 상한 50, 태스크 2개에 225 TPS | 0.36초 | 2.2% |

## 6. 사용자 수에 비례하는 것은 로그가 아니라 지표다

### 6-1. info 로그의 78%가 채팅 메시지 세 줄이었다

Datadog은 로그를 건수로 색인하고 과금한다. 부하 테스트에서 api의 info 로그를 세어 보니 채팅 메시지 하나마다 찍히는 줄이 대부분이었다.

| 로그 | 비중 | 처리 |
| --- | --- | --- |
| `Chat message sent` | 39% | **삭제.** id·방·보낸 사람은 메시지 행에 있고, 요청은 APM 트레이스에 있다 |
| `No device token to send` / `No recipient allows this notification` | 33% | **debug.** 알림을 끈 사람, 방을 보고 있는 사람, 기기가 없는 사람은 정상이다 |
| `Nothing to send for outbox` | 6% | **debug.** 그 사이 글이 지워졌거나 수신자가 모두 걸러진 경우다 |

푸시 결과 줄도 채팅 메시지마다, 캠페인이면 수신자마다 찍혔다. 5만 명 캠페인이면 5만 줄이다. 결과에 따라 레벨을 나눴다.

```kotlin
when {
    result.unreachable > 0 -> logger.error { "Push could not reach the provider: $summary" } // 우리 쪽: 자격 증명·네트워크
    result.rejected > 0    -> logger.info  { "Push dispatched with rejections: $summary" }   // "알림이 안 와요"의 단서
    else                   -> logger.debug { "Push dispatched: $summary" }                  // 정상
}
```

기준은 **"이 줄을 보고 누군가 무엇을 하는가"** 였다. 모두 전달된 발송은 누가 무엇을 받았는지가 outbox와 알림 목록에 이미 남아 있다.

### 6-2. 로그를 내리면 전체 그림도 사라진다

성공과 생략 줄을 debug로 내리자 "푸시가 전체적으로 어떻게 나가고 있는가"를 볼 방법이 없어졌다. 그 자리를 카운터로 채웠다. Datadog 지표는 이벤트 수가 아니라 **태그 조합 수**로 과금되므로, 트래픽이 열 배가 돼도 비용이 늘지 않는다.

| 지표 | 태그 | 뜻 |
| --- | --- | --- |
| `everygolf.push.dispatch` | `category`(chat·other·marketing), `outcome`(sent·no_recipient·no_device·viewing) | 발송 요청 한 번의 결말 |
| `everygolf.push.tokens` | `category`, `result`(delivered·rejected·unreachable) | FCM에 넘긴 기기 토큰의 결과 |

예전에는 "기기가 없다"와 "기기는 있는데 모두 그 방을 보고 있다"가 같은 로그 한 줄이었다. 이제 등록된 토큰 목록과 열람 중인 기기를 걸러낸 목록을 따로 들고 둘을 구분한다. `VIEWING`은 남은 기기가 하나도 없을 때만 센다. 대시보드에서는 "열람 때문에 빠진 기기 수"가 아니라 "푸시를 통째로 생략한 건수"로 읽어야 한다.

### 6-3. 지표 라이브러리도 포트 뒤에 둔다

```text
PushSendService (application.notification)
   └─▶ PushMetrics (required 포트)
          └─ MicrometerPushMetrics (adapter.integration.metrics) ─▶ MeterRegistry ─▶ DogStatsD ─▶ 사이드카
```

ArchUnit의 core 금지 목록에 `io.micrometer..`를 추가했다. 포트에는 **회원 ID나 방 ID를 받는 자리가 아예 없다.** 태그 값 하나가 곧 과금되는 시계열 하나이므로, 포트가 받지 않으면 나중에 누가 실수로 식별자를 태그에 넣을 수도 없다.

스프링이 기본으로 다는 지표(JVM·Tomcat·Hikari·URI별 HTTP 요청)도 함께 나가면 수백 개가 커스텀 지표로 과금된다. 요청과 JVM은 dd-java-agent가 이미 보낸다. 그래서 우리가 만든 이름만 내보낸다.

```kotlin
@Bean
fun exportOwnMetersOnly(): MeterFilter = MeterFilter.denyUnless { it.name.startsWith("everygolf.") }
```

## 7. 같이 바뀐 것: 기능 밖의 변경

- **dev 전용 테스트 로그인**: 서버가 인가 코드를 직접 교환하므로 dev QA도 실제 카카오·구글 계정이 있어야 했다. 여러 사람 시나리오마다 계정이 하나씩 필요했고, 영구정지된 계정은 다시 쓸 수 없었다. 인가 코드 대신 별칭을 받아 소셜 ID로 쓰는 `SocialProvider.DEVELOPMENT`를 기존 제공자 목록에 붙였다. 가입·약관·정지·탈퇴가 실제 제공자와 같은 코드로 돈다. 계정은 (제공자, 소셜 ID)로 찾으므로 별칭이 실제 계정에 닿을 수 없다. 운영 프로필은 이 스위치가 켜져 있으면 기동을 거절한다. 주말 QA와 부하 테스트 시드가 모두 이 로그인을 썼다.
- **약관 시행본**: 번들된 약관이 "(검토 중 초안)" 제목에 "[시행일]" 자리표시가 남은 10-03 초안이었다. V97이 10-14 00:00 KST 시행본을 추가한다. 어드민 API로 넣지 않은 이유가 있다. API는 번들 초안 뒤의 등록을 모두 개정으로 보고 7일 이내 시행을 거절한다. 그 규칙은 이미 시행 중인 약관의 변경으로부터 회원을 보호하는 것이고, 이번은 출시 전 첫 게시다.
- **Valkey 테스트 컨테이너**: ElastiCache가 dev에서 Redis OSS 7.1에서 Valkey 8.2로 바뀌었고 prod도 Valkey로 시작한다. api와 게이트웨이 테스트는 아직 `redis:7`이었다. Lua 스크립트와 pub/sub을 검증한 엔진이 배포된 엔진과 달랐다.

## 느낀 점

**부하 테스트에서 먼저 드러난 것은 처리량이 아니라 관측이었다.** 거절이 몇 건이었는지 로그로 알 수 없었고, 읽어야 할 경고는 채팅 로그에 묻혀 있었다. 바쁜 태스크를 죽은 태스크로 판정한 것도 헬스 체크라는 관측이었다. 넘쳤을 때 남는 기록을 읽을 수 없다면 처리량 숫자를 알아도 운영에서 할 수 있는 일이 없다. 다음 부하 테스트에서는 숫자를 재기 전에 **과부하 중에 운영자가 실제로 보게 될 줄**부터 확인한다.

**튜닝 값은 그 값을 정한 환경에 묶여 있다.** 상한 30은 "0.5초 안에 끝낸다"는 목표를 x86 처리량으로 나눈 결과였다. 아키텍처를 바꾸면서 처리량이 바뀌었는데 상한은 그대로였다. 헬스 체크 포트도 마찬가지로, 분리한 이유가 같은 날 사라졌다. 설정값에는 숫자보다 **어떻게 나온 숫자인지**를 남겨야 다음에 다시 계산할 수 있다.

**기간이 다른 기간의 근거가 되면, 기산점 하나가 어긋날 때 다른 기록이 일찍 풀린다.** 채팅은 신고를, 신고는 처리를, 조치는 신고를 근거로 남는다. 하나씩 보면 각자 맞는 규칙이었다. 하지만 신고 원장이 먼저 지워지자 채팅은 신고 없는 방이 됐다. 파기 규칙을 만들 때는 **이 기록이 없어지면 무엇이 붙잡을 근거를 잃는가**를 먼저 물어야 한다.

**상태 코드는 앱에게 보내는 지시다.** 401은 "다시 로그인하라", 503은 "다시 시도하라"다. 서버 쪽에서는 "이 요청을 받을 수 없다"로 같아 보여도, 앱은 그 코드에 따라 멀쩡한 세션을 버리거나 의미 없는 재시도를 한다. QA에서 고친 것의 절반이 이 종류였다.

**배포 중에는 두 버전이 같은 데이터를 본다.** enum 값 하나를 지운 것, 밀린 제안을 배치가 한꺼번에 처리하는 것, 둘 다 코드만 보면 맞았다. 문제는 옛 태스크와 새 태스크가 함께 도는 몇 분, 그리고 배포 직후 첫 배치 실행이었다. 지난주의 "컬럼은 읽지 않는 버전을 먼저"가 이번 주에는 enum 값과 배치로 넓어졌다.

## 정리

- 큰 기획 개정은 먼저 **차이를 감사 문서로 정리하고 항목 ID를 붙인다**. 뒤의 PR과 KDoc이 그 ID를 가리킨다
- 값을 없앨 때는 **옛 값을 읽기 전용으로 남겨** 롤링 배포 중 옛 태스크가 쓴 값을 읽을 수 있게 한다
- 새 배치를 켜기 전에 **밀린 대상**은 마이그레이션으로 조용히 정리한다. 첫 실행이 과거 전부를 처리하지 않게
- REPEATABLE_READ는 행을 고정할 뿐이다. 여러 쿼리가 같은 판단을 하려면 **시각도 한 번만 읽어서 넘긴다**
- 하루 내내 참인 사실(오늘 이미 보냄)은 **잠그지 않고 먼저 걸러** 핫 로우 대기를 없앤다
- 손으로 옮긴 같은 필터는 **"한쪽이 돌려준다 ⇔ 다른 쪽이 맞는다"** 를 테스트로 묶는다
- 유니크 키에 nullable 칸을 넣으면 NULL끼리 막히지 않는다. **NOT NULL 생성 열**로 맥락 키를 만든다
- 파기 배치는 표 전체가 아니라 **대상 계정에서 출발**하고, 실패한 대상은 줄 뒤로 보낸다
- 서로 반대 순서로 잠그는 작업은 **한 트랜잭션에 같이 두지 않는다**
- 다른 기록의 근거가 되는 기록은 **기산점을 맞춘다**
- 기동 시 작업은 **차이가 있을 때만 잠근다**. 바뀐 것이 없는데 배포가 실패하지 않게
- 상태 코드는 앱의 다음 행동이다. 세션과 무관한 거절에 401, 장애가 아닌 거절에 503을 쓰지 않는다
- 실시간 발행은 **한 클래스**로 모으고 ArchUnit으로 묶는다. 수신자 판정은 보내는 시점에 한다
- 동시 처리 상한은 **"받아들인 요청은 이 시간 안에 끝낸다"** 를 지키는 값이다. 처리량이 바뀌면 다시 계산한다
- 헬스 체크는 DB를 기다리지 않고, **사용자가 오는 포트**로 한다
- 스프링 필터를 상속한 클래스에서 파일 수준 `logger`는 **부모의 protected `logger`에 가려진다**
- 사용자 수에 비례하는 "정상" 기록은 로그가 아니라 **카운터**로 센다. 지표 포트는 식별자를 받는 자리를 두지 않는다
- 테스트 컨테이너는 **배포된 엔진과 같은 엔진**으로 돌린다
