# 장기 키 없이 클라우드 넘나들기 — GitHub OIDC, 그리고 Fargate에서 GCP Workload Identity

이 서비스는 클라우드 경계를 두 번 넘는다. GitHub Actions가 AWS에 이미지를 올리고 배포하는 경계와, AWS에서 도는 API 태스크가 GCP의 FCM으로 푸시를 보내는 경계다. 두 곳 모두 가장 쉬운 방법은 **상대 클라우드의 장기 키를 비밀값으로 넣어 두는 것**이다. 우리는 둘 다 키를 만들지 않았다. 각 쪽이 자기 신원을 증명하면 상대가 짧은 수명의 자격 증명을 내준다.

방향은 같아도 실제로 막힌 곳은 달랐다. GitHub 쪽은 **신뢰 정책이 기대한 이름과 토큰에 실린 이름이 달랐고**, GCP 쪽은 **표준 설정 파일이 Fargate라는 실행 환경을 몰랐다.** 두 문제는 실패하는 모습도 달랐다. 앞의 것은 배포 첫 단계에서 바로 실패했고, 뒤의 것은 그대로 두면 기동은 성공하고 첫 발송에서야 터지는 문제였다.

> 사내 저장소 기준이라 프로젝트명·도메인 같은 식별자는 일반화해서 적는다.

## 1. 키를 두지 않는다는 것의 모양

두 경계를 같은 그림으로 그리면 이렇다.

```text
[GitHub Actions]                         [AWS]
  OIDC 토큰 (sub = repo:...:ref:...)  ──▶ STS AssumeRoleWithWebIdentity
                                          └▶ 배포 역할의 임시 자격 증명 (ECR push, ECS 롤아웃)

[AWS ECS 태스크]                          [GCP]
  태스크 역할의 임시 자격 증명
  └▶ GetCallerIdentity 요청에 서명    ──▶ GCP STS 토큰 교환
                                          └▶ 서비스 계정 가장 → FCM 스코프 액세스 토큰
```

> **OIDC 토큰**은 GitHub Actions가 워크플로 실행마다 발급하는 서명된 JWT다. 어느 저장소의 어느 브랜치에서 실행됐는지 같은 정보를 클레임으로 담고, 수명이 짧다. AWS는 GitHub의 공개 키로 서명을 검증해 토큰이 GitHub가 발급한 것인지 확인하고, 클레임 값을 역할의 신뢰 정책 조건과 비교한다. 조건이 맞으면 STS가 임시 자격 증명을 내준다. 저장해 둘 비밀값이 없는 이유가 이것이다.

> STS(Security Token Service)는 신원 증명을 받아 짧은 수명의 자격 증명을 내주는 서비스다. 그림에는 두 클라우드의 STS가 모두 나온다.
> - **AWS STS**: 임시 자격 증명(액세스 키, 시크릿 키, 세션 토큰과 만료 시각)을 발급한다. `AssumeRoleWithWebIdentity`는 외부 OIDC 토큰을 받아 역할의 임시 자격 증명으로 바꿔 주는 호출이다. `GetCallerIdentity`는 호출자가 어느 계정의 어떤 역할인지 돌려주는 호출이다. 별도 권한 없이 부를 수 있어서, GCP가 AWS 신원을 확인하는 데 쓴다.
> - **GCP STS**: 외부 신원 증명을 받아 GCP 연동 토큰으로 바꿔 준다(토큰 교환). 이 글에서는 AWS가 서명한 `GetCallerIdentity` 요청이 그 증명이다. 받은 토큰으로 서비스 계정을 가장해 FCM용 액세스 토큰을 얻는다.

| | GitHub → AWS | AWS → GCP |
| --- | --- | --- |
| 신원을 내는 쪽 | GitHub OIDC 토큰 | ECS 태스크 역할 |
| 신뢰하는 쪽 | IAM OIDC 공급자 + 역할 신뢰 정책 | Workload Identity 풀 + 프로바이더 |
| 신뢰 조건 | `token.actions.githubusercontent.com:sub` | `attribute.aws_role` (가정된 역할 ARN) |
| 저장된 비밀값 | 없음 | 없음. Parameter Store에 FCM 자격 증명 항목이 없다 |
| 막힌 곳 | subject 표기 | 자격 증명 소스 |

> Workload Identity Federation(WIF)은 GCP 밖에서 실행되는 워크로드가 서비스 계정 키 없이 GCP에 접근하게 하는 기능이다. 구성 요소는 셋이다.
> - **풀(pool)**: 외부 신원을 묶어 두는 단위다.
> - **프로바이더(provider)**: 어떤 외부 신원을 어떤 조건으로 받을지 정한다. 여기서는 AWS 계정을 등록하고, 호출자의 역할 ARN을 `attribute.aws_role` 속성으로 꺼내 조건에 쓴다.
> - **서비스 계정 가장 권한**: 조건을 통과한 외부 신원이 특정 서비스 계정의 권한으로 동작할 수 있게 허용한다.

장기 키를 두는 방식과 비교하면 달라지는 것은 다음과 같다.

| | 장기 키 | 신원 증명 → 짧은 수명의 자격 증명 |
| --- | --- | --- |
| 저장할 비밀값 | GitHub Secrets, Parameter Store 등에 키를 둔다 | 없다. AWS → GCP에서는 AWS 자격 증명도 넘어가지 않고 서명된 요청만 넘어간다 |
| 유출 시 유효 기간 | 지우거나 교체할 때까지 | 몇 분~몇 시간 뒤 만료된다 |
| 교체 작업 | 주기적으로 새 키를 만들어 모든 저장 위치를 갱신한다 | 매번 새로 받으므로 필요 없다 |
| 사용 범위 | 키를 가진 쪽이면 어디서든 쓸 수 있다 | 신뢰 조건(저장소·브랜치, 태스크 역할)에 맞는 실행만 받는다 |
| 회수와 추적 | 키가 복사된 곳을 모두 찾아야 한다 | 신뢰 정책을 고치면 바로 막히고, 감사 로그에 역할 세션이 남는다 |

대신 비용도 생긴다. 둘 다 **"무엇을 신뢰하느냐"가 문자열 하나로 걸려 있다**는 공통점이 있다. 이 글에서 다루는 실패 두 개는 모두 그 문자열에서 시작했다.

## 2. GitHub OIDC — 신뢰 정책이 기대한 이름과 토큰의 이름이 달랐다

배포 역할의 신뢰 정책은 평범하다. `aud`는 `sts.amazonaws.com`이어야 하고, `sub`가 허용 목록 중 하나와 맞아야 한다.

> 둘 다 OIDC 토큰의 표준 클레임이다.
> - **`aud`(audience)**: 이 토큰을 받을 대상이다. AWS에 쓸 토큰은 `sts.amazonaws.com`으로 발급받는다. 다른 서비스용으로 발급된 토큰을 AWS에 그대로 가져와 쓰지 못하게 하는 조건이다.
> - **`sub`(subject)**: 토큰의 주체, 곧 어느 저장소의 어느 ref에서 실행된 워크플로인가다. `repo:<org>/<repo>:ref:refs/heads/main` 같은 형태다. 누가 이 역할을 맡을 수 있는지는 이 값으로 정한다.

```hcl
data "aws_iam_policy_document" "assume_role" {
  statement {
    actions = ["sts:AssumeRoleWithWebIdentity"]

    principals {
      type        = "Federated"
      identifiers = [var.oidc_provider_arn]
    }

    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:aud"
      values   = ["sts.amazonaws.com"]
    }

    # Without a sub condition any GitHub repository on the internet could assume this role.
    condition {
      test     = "StringLike"
      variable = "token.actions.githubusercontent.com:sub"
      values   = var.allowed_subjects
    }
  }
}
```

`sub` 조건이 빠지면 **인터넷의 어떤 GitHub 저장소든** 이 역할을 맡을 수 있다. 그래서 이 줄이 실질적인 경계다. 처음 허용 목록은 문서에서 흔히 보는 형태였다.

```hcl
github_allowed_subjects = ["repo:my-org/server:*"]
```

그런데 모든 배포가 자격 증명 단계에서 이렇게 실패했다.

```text
Not authorized to perform sts:AssumeRoleWithWebIdentity
```

토큰의 `sub`는 `repo:my-org/server:...`가 아니었다. 이 조직은 **조직과 저장소의 숫자 ID를 박아 넣은 immutable subject**를 발급하고 있었다.

```text
기대한 것:  repo:my-org/server:ref:refs/heads/main
실제 토큰:  repo:my-org@<org_id>/server@<repo_id>:ref:refs/heads/main
```

이름만 쓰는 subject는 저장소 이름을 바꾸거나, 저장소를 지웠다가 같은 이름으로 다시 만들면 다른 저장소를 같은 이름으로 가리킨다. ID를 넣으면 그 저장소가 아니게 된 순간 일치하지 않는다. 의도는 이해되지만, 신뢰 정책 입장에서는 **같은 저장소가 두 가지 철자로 올 수 있다는 뜻**이다.

### 두 철자를 모두 받는다

```hcl
# dev accepts any branch so feature branches can deploy without editing this file.
github_allowed_subjects = [
  "repo:my-org/server:*",
  "repo:my-org@<org_id>/server@<repo_id>:*",
]
```

```hcl
# prod only trusts main, so a feature branch cannot publish a production image.
github_allowed_subjects = [
  "repo:my-org/server:ref:refs/heads/main",
  "repo:my-org@<org_id>/server@<repo_id>:ref:refs/heads/main",
]
```

지금 쓰이는 쪽 하나만 넣지 않은 이유가 커밋에 적혀 있다. **토큰이 어느 철자를 싣는지는 GitHub 쪽 설정이 정하고, 그 설정은 이 저장소의 변경 없이 바뀔 수 있다.** 오늘 맞는 하나만 받으면 그 설정이 뒤집히는 날 파이프라인이 다시 깨진다. 우리 코드가 바뀌지 않았는데 배포가 깨지는 상황이다.

나중에 정적 사이트용 저장소를 새로 만들 때는 처음부터 immutable 형식 하나만 넣었다. 새로 만든 저장소는 그 형식을 쓰고, 실제 값은 API로 확인할 수 있다.

```hcl
condition {
  test     = "StringEquals"
  variable = "token.actions.githubusercontent.com:sub"
  # New GitHub repositories use immutable OIDC subjects. Verified through
  # GET /repos/<org>/<repo>/actions/oidc/customization/sub.
  values   = ["repo:my-org@<org_id>/test-web@<repo_id>:ref:refs/heads/main"]
}
```

### 경계는 subject만이 아니다

dev와 prod는 **브랜치 범위**로 갈린다. dev는 `:*`라 기능 브랜치도 배포할 수 있고, prod는 `ref:refs/heads/main`만 받아 기능 브랜치가 운영 이미지를 올릴 수 없다. 역할 자체의 권한도 환경 안에 묶었다.

| 권한 | 범위를 좁힌 방법 |
| --- | --- |
| ECR push | 그 환경의 저장소 ARN만 |
| `ecs:UpdateService` | `service/<env-cluster>/*`만. 없으면 이 역할로 운영 서비스를 재배포할 수 있다 |
| `iam:PassRole` | 그 환경의 `*-ecs-execution`·`*-ecs-task` 역할만, `iam:PassedToService = ecs-tasks.amazonaws.com` 조건 |
| `ecs:DescribeTasks`·`ListTasks` | `ecs:cluster` 조건으로 그 환경 클러스터만 |

`PassRole`이 특히 중요하다. 태스크 정의를 등록하는 것은 그 정의에 적힌 역할을 ECS에 넘기는 일이다. 범위를 좁히지 않으면 배포 역할이 **자기보다 강한 역할을 태스크에 붙여** 권한을 우회할 수 있다.

> `iam:PassRole`은 IAM 역할을 다른 AWS 서비스에 넘겨서, 그 서비스가 역할의 권한으로 동작하게 하는 권한이다. 역할을 직접 맡는 것(`AssumeRole`)과 다르다. 넘기는 쪽은 그 역할의 권한을 갖지 않아도 된다. 그래서 넘길 수 있는 역할을 제한하지 않으면, 배포 역할이 관리자 역할을 태스크에 넘기고 그 태스크를 통해 관리자 권한을 쓸 수 있다.

OIDC 공급자 자체는 계정당 하나라 환경 상태(state)에 두지 않고 `shared`로 뺐고, `prevent_destroy`를 걸었다. dev를 지우다가 prod의 배포 경로까지 끊기면 안 되기 때문이다.

> `prevent_destroy`는 Terraform 리소스의 `lifecycle` 설정이다. 이 값이 `true`이면 그 리소스를 삭제하거나, 삭제 후 재생성(교체)하는 plan이 오류로 중단된다. 지우려면 설정을 먼저 코드에서 빼야 하므로, 실수로 지우는 일을 막는다.

워크플로 쪽은 `permissions: id-token: write`를 빼먹으면 역할을 맡는 단계에서 실패하고, job마다 러너가 다르니 배포 job에서도 역할을 다시 맡는다.

## 3. AWS → GCP — 표준 경로가 Fargate에서 동작하지 않았다

FCM으로 푸시를 보내려면 태스크가 GCP 액세스 토큰을 받아야 한다. Workload Identity Federation의 표준 경로는 이렇다.

1. `gcloud iam workload-identity-pools create-cred-config`로 설정 JSON을 만든다
2. `GOOGLE_APPLICATION_CREDENTIALS`가 그 파일을 가리키게 한다
3. 라이브러리가 파일을 읽고 알아서 교환한다

**이 경로를 쓰지 않았다.** 그 파일의 `credential_source`는 EC2 인스턴스 메타데이터(`169.254.169.254`)를 가리킨다. 사용 중이던 google-auth-library 1.43.0의 AWS 자격 증명 소스가 아는 것은 **그 주소와 환경 변수(`AWS_ACCESS_KEY_ID` 등) 둘뿐**이었다. 라이브러리 jar를 열어 확인했다.

Fargate의 자격 증명은 다른 곳에서 온다.

> **Fargate**는 ECS에서 컨테이너를 실행하는 방식 중 하나로, EC2 인스턴스를 직접 두지 않고 태스크 단위로 실행한다. 호스트는 AWS가 관리하고 컨테이너는 그 호스트에 접근할 수 없다. 그래서 EC2 인스턴스 메타데이터(`169.254.169.254`)로 자격 증명을 받을 수 없다. 대신 태스크 역할의 자격 증명은 ECS가 제공하는 태스크 전용 엔드포인트(`169.254.170.2`)에서 받는다. 그 경로는 `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` 환경 변수로 컨테이너에 주입된다.
>
> EC2 대신 Fargate를 쓰는 이유는 **호스트를 관리하는 일이 없어지기 때문**이다. EC2에서는 Docker 설치, 스왑 설정, 모니터링 에이전트 설치, 인스턴스 안의 배포 스크립트를 우리가 관리했다. Fargate에서는 이 작업이 사라진다. 배포는 태스크 정의 리비전을 등록하고 서비스를 갱신하는 선언으로 바뀐다. 대신 호스트가 없으므로 인스턴스 메타데이터를 전제한 도구는 그대로 동작하지 않는다. 이 장의 문제가 그 경우다. 옮긴 과정과 근거는 [호스트를 가지지 않으니 없어진 일들](./호스트를_가지지_않으니_없어진_일들_EC2에서_Fargate로.md)에 정리했다.

| 실행 환경 | 자격 증명이 오는 곳 | google-auth-library 1.43.0이 아는가 |
| --- | --- | --- |
| EC2 | 인스턴스 메타데이터 `169.254.169.254` | ✅ |
| 환경 변수 | `AWS_ACCESS_KEY_ID` 등 | ✅ |
| ECS Fargate | `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`가 가리키는 태스크 엔드포인트 | ❌ |

그래서 그대로 배포하면 **기동은 성공하고 첫 발송에서 인증 오류가 난다.** 설정 파일은 읽히니 컨텍스트가 뜨고, 자격 증명을 실제로 꺼내는 시점은 첫 토큰 요청이기 때문이다. 알림은 outbox를 거쳐 비동기로 나가니(→ `트랜잭션이_FCM_왕복을_감싸지_않게_하기.md`) 그 오류를 사용자 요청이 아니라 발송 로그에서야 보게 된다.

### 읽기는 AWS SDK에, 교환은 Google 라이브러리에

AWS SDK의 기본 공급자 체인은 태스크 엔드포인트를 안다. 같은 애플리케이션의 S3 클라이언트가 이미 그걸로 돈다.

```kotlin
S3Client
    .builder()
    .region(Region.of(properties.region))
    .credentialsProvider(DefaultCredentialsProvider.create())
```

그래서 **자격 증명을 읽는 일만 SDK에 맡기고**, 교환은 Google 라이브러리가 하게 했다. google-auth-library는 파일 대신 공급자를 끼울 수 있는 `AwsSecurityCredentialsSupplier`를 열어 두었다.

```kotlin
class EcsTaskRoleCredentialsSupplier(
    private val awsCredentialsProvider: AwsCredentialsProvider,
    private val region: String,
) : AwsSecurityCredentialsSupplier {
    override fun getRegion(context: ExternalAccountSupplierContext): String = region

    /**
     * 부를 때마다 새로 읽는다.
     *
     * 태스크 역할의 자격 증명은 몇 시간마다 돌고, 캐시해 두면 그 시점에 발송이 조용히 실패한다.
     * SDK 공급자가 안에서 캐시와 갱신을 함께 하므로 여기서 또 감싸지 않는다.
     */
    override fun getCredentials(context: ExternalAccountSupplierContext): AwsSecurityCredentials {
        val resolved = awsCredentialsProvider.resolveCredentials()
        return AwsSecurityCredentials(
            resolved.accessKeyId(),
            resolved.secretAccessKey(),
            // 태스크 역할은 언제나 세션 자격 증명이다. 로컬에서 장기 키로 시험할 때만 null 이 된다.
            (resolved as? AwsSessionCredentials)?.sessionToken(),
        )
    }
}
```

여기서 꺼낸 것은 **AWS 자격 증명이고, 구글로 가지 않는다.** 라이브러리는 이 값으로 AWS STS `GetCallerIdentity` 요청에 서명만 하고, **그 서명된 요청을** GCP STS에 제출한다. GCP는 그 요청을 AWS에 대신 보내 "이 호출자가 누구인가"를 확인한 뒤 토큰을 내준다. 비밀값이 경계를 넘지 않는 것이 이 방식의 핵심이다.

```kotlin
private fun workloadIdentityCredentials(properties: FcmProperties): GoogleCredentials {
    val region = DefaultAwsRegionProviderChain.builder().build().region.id()
    return AwsCredentials
        .newBuilder()
        .setAudience("//iam.googleapis.com/${properties.workloadIdentityProvider}")
        .setSubjectTokenType(ExternalAccountCredentials.SubjectTokenTypes.AWS4)
        .setTokenUrl(STS_TOKEN_URL)
        .setServiceAccountImpersonationUrl(
            "https://iamcredentials.googleapis.com/v1/projects/-/serviceAccounts/" +
                "${properties.serviceAccount}:generateAccessToken",
        ).setAwsSecurityCredentialsSupplier(
            // 공급자를 하나만 만들어 넘긴다. 안에서 캐시와 갱신을 하므로 호출마다 새로
            // 만들면 태스크 메타데이터를 발송마다 다시 읽는다.
            EcsTaskRoleCredentialsSupplier(DefaultCredentialsProvider.builder().build(), region),
        )
        // 지역별 STS 주소를 명시한다. 서명 대상이 실제로 부를 주소와 달라지면 교환이
        // `InvalidIdentityToken` 으로 떨어지고, 그 메시지만으로는 원인을 찾기 어렵다.
        .setRegionalCredentialVerificationUrlOverride(
            "https://sts.$region.amazonaws.com?Action=GetCallerIdentity&Version=2011-06-15",
        ).setScopes(listOf(FCM_SCOPE))
        .build()
}
```

세 가지를 의도적으로 정했다.

| 결정 | 이유 |
| --- | --- |
| 공급자는 **한 번만** 만들어 넘긴다 | SDK 공급자가 내부에서 캐시·갱신을 한다. 호출마다 새로 만들면 발송마다 태스크 메타데이터를 다시 읽는다 |
| 우리 쪽에서 **캐시하지 않는다** | 태스크 역할 자격 증명은 몇 시간마다 돈다. 한 번 더 감싸 캐시하면 회전 시점에 발송이 조용히 실패한다 |
| 스코프는 `firebase.messaging` **하나** | `cloud-platform`은 이 토큰이 가질 이유가 없다 |
| 지역별 STS 검증 주소를 **명시** | 서명한 주소와 실제로 부르는 주소가 어긋나면 `InvalidIdentityToken`만 남고 원인이 안 보인다 |

## 4. 경로가 셋이 되면 조용한 폴백이 생긴다

이제 자격 증명 경로가 셋이다.

```kotlin
when {
    properties.usesWorkloadIdentity -> workloadIdentityCredentials(properties)
    properties.credentialsLocation.isNotBlank() -> /* 키 파일 — 장기 키 탈출구 */
    else -> GoogleCredentials.getApplicationDefault()
}
```

1. `workload-identity-provider`와 `service-account`가 **둘 다** 있으면 태스크 역할 교환
2. `credentials-location`이 있으면 그 파일
3. 아무것도 없으면 ADC (로컬의 `gcloud auth application-default login`)

> `폴백(fallback)`은 앞의 방법을 쓸 수 없을 때 다음 방법으로 넘어가는 동작이다. 위 코드는 조건을 위에서부터 확인하고, 맞는 것이 없으면 마지막 ADC(Application Default Credentials)로 넘어간다. ADC는 Google 라이브러리가 환경에서 자격 증명을 자동으로 찾는 방식이다. 이 넘어감은 오류나 로그 없이 일어나므로, 의도한 경로가 선택되지 않았다는 사실을 실행 중에 알 수 없다.

위험한 것은 첫 번째 경로의 설정을 **한쪽만 채운** 경우다. `usesWorkloadIdentity`가 거짓이 되고, 키 파일도 없으니 ADC로 떨어진다. 로컬에서는 ADC가 있어서 잘 돈다. 배포에는 ADC가 없으니 **실수가 첫 발송에서야 드러난다.** 3장에서 피하려던 실패 모양과 똑같다.

그래서 짝이 맞지 않으면 기동에서 막는다.

```kotlin
// 한쪽만 채우면 조용히 ADC 로 떨어져, 배포에서 자격 증명이 없다는 사실이 첫 발송에서야
// 드러난다. 짝이 맞지 않으면 기동에서 막는다.
require(workloadIdentityProvider.isBlank() == serviceAccount.isBlank()) {
    "external.fcm.workload-identity-provider 와 external.fcm.service-account 는 함께 채워야 합니다."
}
```

ECS 배포에서는 기동 실패가 곧 롤아웃 실패다. 새 태스크가 정상 상태에 오르지 못하면 배포가 되돌려지고 이전 리비전이 계속 돈다. **설정 실수를 사용자가 아니라 배포 파이프라인이 먼저 보게 하는 것**이 목표였다. 성공 여부는 기동 로그 한 줄로 확인한다.

```text
Firebase credentials from AWS workload identity: provider=..., sa=..., region=...
```

### 끄고 켜는 스위치는 이미지 밖에

인프라 쪽에서 더한 파라미터는 `FCM_ENABLED` 하나다. 비밀값은 아니지만 이미지에 넣지 않았다. 푸시를 켜고 끄는 데 **릴리스가 필요하지 않게** 하기 위해서다. 애플리케이션은 모든 프로필에서 기본을 꺼짐으로 두고, 파라미터가 아예 없으면 태스크가 뜨지 않는다. 그것이 원하는 실패다. FCM 자격 증명 항목은 Parameter Store에 **없다.** 저장할 키가 없기 때문이다.

## 5. GCP 자원은 Terraform이 관리하지 않는다

AWS 쪽은 전부 Terraform인데, GCP 쪽(풀·프로바이더·서비스 계정·바인딩)은 손으로 만들었다. 일관성만 보면 이상한 선택이다. 이유는 하나다.

> `google` 프로바이더를 붙이려면 Terraform이 GCP를 호출할 자격 증명이 필요하다. **그것이 바로 이 구성으로 없애려는 장기 키다.**

키 없는 구성을 만들려고 키를 하나 만드는 셈이 된다. 지금은 GCP 자원이 dev 한 벌뿐이라 손으로 관리하는 비용이 작고, 운영 프로젝트가 생겨 **같은 자원을 두 벌 만들게 되는 시점**에 다시 판단하기로 했다.

GCP 쪽에 만든 것과 그 범위는 다음과 같다.

| 자원 | 범위 |
| --- | --- |
| 서비스 계정 | 사용자 키 **발급 안 함** |
| 역할 | `roles/cloudmessaging.editor` |
| 프로바이더 조건 | `attribute.aws_role == "arn:aws:sts::<account>:assumed-role/<env>-api-ecs-task"` |
| 가장 권한 | `roles/iam.workloadIdentityUser`를 위 principalSet **하나에만** |

> `ARN(Amazon Resource Name)`은 AWS 리소스를 계정 전체에서 하나로 가리키는 식별 문자열이다. `arn:aws:<서비스>:<리전>:<계정 ID>:<리소스>` 형태다. 역할을 맡은 세션은 `arn:aws:sts::<계정 ID>:assumed-role/<역할 이름>/<세션 이름>`으로 표시된다. 위 프로바이더 조건은 이 중 역할 이름까지를 비교한다. 그래서 **역할 이름이 바뀌면 ARN 문자열이 바뀌고 조건이 맞지 않게 된다.**

`cloudmessaging.editor`는 발송에 필요한 최소 중 가장 좁은 예약 역할이다. `cloudmessaging.messages.create` 하나만 담은 사용자 정의 역할도 가능했지만, FCM이 필요 권한을 늘릴 때 **발송이 조용히 막히는 쪽이 더 나쁘다**고 봤다.

### 대가 — 이름 하나가 두 클라우드를 묶는다

이 선택에는 분명한 대가가 있다. GCP의 신뢰가 **AWS 태스크 역할 이름 문자열**로 걸려 있는데, Terraform은 그 사실을 모른다. 역할 이름은 Terraform의 `local.full_name`에서 만들어진다.

```hcl
resource "aws_iam_role" "task" {
  name = "${local.full_name}-ecs-task"
  ...
}
```

누군가 프로젝트 이름이나 컴포넌트 이름을 바꾸면 이렇게 된다.

```text
terraform apply   → 성공 (새 이름의 태스크 역할)
배포              → 초록불 (태스크는 정상 기동, 헬스 체크 통과)
푸시 발송         → GCP 프로바이더 조건 불일치로 교환 실패
```

**배포는 초록불이고 알림만 조용히 멈춘다.** 코드로 막을 방법이 없으니, 그 리소스 바로 위에 결합을 적어 두었다. 어떤 조건과 바인딩이 이 이름에 걸려 있는지, 이름을 바꾸기 전에 어디를 함께 고쳐야 하는지, 무엇으로 확인하는지(`gcloud iam workload-identity-pools providers describe ...`)까지 적었다. 애플리케이션 설정 파일의 provider 값 옆에도 같은 경고를 적었다. 이름을 바꾸려는 사람이 두 곳 중 어디를 먼저 열든 마주치게 하려는 것이다.

## 6. 로컬에서 검증할 수 없는 코드

`EcsTaskRoleCredentialsSupplier`는 **태스크 역할이 있는 곳에서만 도는 코드다.** 로컬에서는 provider를 비워 ADC로 떨어지게 두므로, 이 경로를 실제로 타는 것은 배포된 태스크뿐이다.

그래서 검증 순서를 문서로 정해 두었다. 파라미터를 켜고, 인프라를 적용해 태스크 정의에 주입을 추가하고, 배포한다. 교환이 성립하면 기동 로그가 남고, 실패하면 컨텍스트가 뜨지 않아 롤아웃이 되돌려진다. 4장의 기동 시 검증이 여기서 다시 쓰인다. **로컬에서 못 보는 코드일수록 실패가 기동 시점으로 당겨져 있어야** 배포가 곧 테스트가 된다.

남은 한계도 있다. 로그 한 줄은 "토큰 교환 설정이 만들어졌다"까지만 말한다. 실제 교환은 첫 발송에서 일어난다. 기동 시점에 토큰을 한 번 받아 보는 것까지 하면 더 확실하지만, 그러면 GCP 장애가 API 기동을 막는다. 알림은 부가 기능이라 그 결합은 받아들이지 않았다. 실제 기기 발송 검증은 앱 등록과 APNs 키가 준비되어야 할 수 있어 아직 남아 있다.

## 느낀 점

**"키가 없다"는 것은 비밀값 대신 이름을 신뢰한다는 뜻이다.** 장기 키를 없애도 위험은 남고, 위험의 종류가 바뀐다. 신뢰 조건은 GitHub 쪽은 `sub` 문자열, GCP 쪽은 역할 ARN 문자열이다. 키는 유출이 문제가 되고, 이름은 양쪽 값의 **불일치**가 문제가 된다. 이 글의 두 실패도 모두 유출이 아니라 불일치에서 나왔다.

**신뢰 조건은 상대가 바꿀 수 있는 것까지 받아야 한다.** immutable subject 형식은 우리가 정하지 않았다. GitHub 조직 설정이 정했고, 그 설정은 우리 저장소의 커밋 없이 바뀐다. 현재 토큰에 실린 철자 하나만 허용하면, 그 설정이 바뀌는 시점에 우리 코드 변경 없이 배포가 실패한다.

**표준 경로가 실행 환경을 가정하고 있을 수 있다.** `create-cred-config`는 공식 문서가 안내하는 방법인데, 그 결과물은 EC2를 가정하고 있었다. 오류 메시지로는 이를 알 수 없었고, 라이브러리가 어떤 소스를 지원하는지는 jar를 열어 확인했다. 문서대로 했는데 동작하지 않으면 **문서가 가정한 실행 환경**이 실제 환경과 같은지부터 확인한다.

**자동 폴백은 실패가 드러나는 시점을 늦춘다.** 세 경로 중 하나로 자동으로 넘어가는 구조는 로컬에서는 ADC가 있어 동작하지만, 배포 환경에서는 설정 누락이 첫 발송 때까지 드러나지 않는다. 짝이 맞지 않는 설정을 기동 시점에 거부하는 검사 한 줄로 실패 시점을 기동으로 옮겼다. 알림 같은 부가 기능은 비동기로 실행되어 실패가 늦게 드러나므로, 설정 검증을 기동 시점에 둬야 한다.

**도구의 일관성보다 목적이 먼저다.** GCP 자원을 Terraform 밖에 둔 것은 일관성을 깨는 선택이다. 그래도 키를 없애려고 키를 만드는 것보다는 낫다고 판단했다. 대신 그 결정이 만든 결합을 코드 바로 위에 적어 두었다. **Terraform이 추적하지 못하는 결합은 리소스 정의와 설정 파일처럼 변경하는 사람이 읽는 위치에 적어야 한다.**

## 정리

- 두 클라우드 경계 모두 장기 키 대신 **신원 증명 → 짧은 수명의 자격 증명** 교환을 쓴다. GitHub → AWS는 OIDC, AWS → GCP는 Workload Identity Federation
- 배포 역할의 `sub` 조건이 실질적인 경계다. 없으면 아무 GitHub 저장소나 역할을 맡는다
- 조직 설정에 따라 `sub`가 **조직·저장소 ID를 박은 immutable 형식**으로 온다. 형식이 GitHub 쪽 설정에 달려 있으니 두 철자를 모두 받는다
- prod는 `ref:refs/heads/main`만 신뢰한다. `UpdateService`·`PassRole`은 그 환경의 클러스터와 역할로 좁힌다
- WIF 표준 설정 파일의 `credential_source`는 EC2 메타데이터를 가리킨다. google-auth-library 1.43.0은 Fargate 태스크 엔드포인트를 몰라 **기동은 성공하고 첫 발송에서 실패**한다
- `AwsSecurityCredentialsSupplier`로 **읽기는 AWS SDK 기본 공급자 체인에, 교환은 Google 라이브러리에** 맡긴다. AWS 자격 증명은 서명에만 쓰이고 구글로 가지 않는다
- 공급자는 한 번만 만들고, 자격 증명을 따로 캐시하지 않고, 스코프는 FCM 하나, 지역별 STS 검증 주소는 명시한다
- 자격 증명 경로가 셋이면 조용한 ADC 폴백이 생긴다. **짝이 맞지 않는 설정은 기동에서 막아** 롤아웃 실패로 바꾼다
- GCP 자원은 Terraform이 관리하지 않는다. 관리하려면 없애려던 장기 키가 필요하다
- 그 대가로 **태스크 역할 이름이 두 클라우드를 묶는다.** 이름을 바꾸면 배포는 초록불이고 알림만 멈춘다. 결합을 리소스 바로 위와 설정 파일에 적어 둔다
